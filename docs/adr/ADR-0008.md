# ADR-0008: Status events preceding line items

Status: **Accepted** — 2026-07-25 (Prompt 1a)

## Context

Product targeting is evaluated when a targeted status event fires
(`woocommerce_order_status_changed`). But an order can reach a targeted status
**before its line items exist**:

- `wc_create_order( array( 'status' => 'completed' ) )` fires the transition
  during creation, **before** any `add_product()` call.
- REST-created, CSV-imported, and third-party-created orders frequently set the
  status first and attach items afterward.

If targeting is evaluated at that instant, the order has **zero items**, no rule
matches, and the intended email is **silently never sent** — a data-loss-shaped
bug that is invisible in normal testing (real checkout attaches items first, so
it only bites programmatic/imported orders). Confirmed empirically in Prompt 1:
`wc_create_order(['status'=>'completed'])` fires `pending>completed` with no
items attached.

## Decision

When a **targeted status event fires on an order with zero line items**:

1. **Do not evaluate targeting and do not claim** at that moment.
2. Instead, **schedule exactly ONE deferred re-evaluation** via Action Scheduler.
   The deferred job:
   - **re-loads the order** and applies targeting to the **then-current items**;
   - if a rule matches, **claims under the ORIGINAL trigger identity** — the same
     `trigger_identity` the immediate path would have used
     ([ADR-0004](ADR-0004.md)) — so the deferred path and any later immediate
     path for the same trigger **cannot double-send** (the DB unique constraint
     collapses them to one claim);
   - if **items are still absent** at re-evaluation, **skip and log the reason**
     ([ADR-0005](ADR-0005.md): `invalidated-by-order-state` / an itemless-order
     reason) — no claim, no send.
3. **Cap at a single deferral.** There is no second re-schedule; one deferred
   re-evaluation per triggering event, then the decision is final.

The immediate path is unchanged for orders that already have items when the
status event fires (the normal checkout/admin case).

## Consequences

- Programmatic, REST, imported, and third-party orders that set status before
  attaching items still get their targeted email, via the single deferred
  re-evaluation reading live items.
- Because the deferred claim uses the **original trigger identity**, it shares
  the [ADR-0004](ADR-0004.md) uniqueness key with the immediate path — the two
  can never both send; whichever claims first wins, the other is suppressed.
- The single-deferral cap bounds the work: a genuinely itemless order (e.g. an
  abandoned/blank order that never gains items) costs exactly one deferred check
  that then skips-and-logs, never a retry storm.
- This does not weaken idempotency: the deferred path is still gated by the same
  fail-closed claim ([ADR-0004](ADR-0004.md) §fail-closed claiming).
- Targeting is always evaluated against the order's **live** items at decision
  time, consistent with [ADR-0007](ADR-0007.md)'s "placeholders resolve fresh
  from the live order".
