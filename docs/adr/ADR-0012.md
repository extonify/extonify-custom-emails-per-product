# ADR-0012: Delivery orchestration, identity consumption and logging

Status: **Accepted** — 2026-07-27 (Prompt 4)

## Context

[ADR-0011](ADR-0011.md) froze a matching engine that **writes nothing**. It
answers *which rules apply to this order for this trigger, which line items they
matched, and why*, and hands back an ordered, complete account. Something has to
consume that account: turn WooCommerce events into trigger events, decide which
decisions consume a delivery identity, send the email, and record what happened.

That consumer is the **orchestrator**, and it is the first component in this
plugin that writes as a matter of course. Everything it does is irreversible in
one direction or another — a claim permanently consumes an identity, a send
reaches a customer, a log row holds personal data — so every branch is decided
here before any of it is written.

Three earlier decisions frame this one and are not reopened:

1. **[ADR-0004](ADR-0004.md)** — the delivery identity is
   `order_id | rule_id | mode | trigger_identity`, enforced by a DB UNIQUE
   constraint, claimed atomically, fail-closed.
2. **[ADR-0005](ADR-0005.md)** — actioned decisions are logged; rules that
   merely failed product targeting are **not**, and that silence is what keeps
   the log bounded.
3. **[ADR-0011 §7a](ADR-0011.md)** — the matcher makes **no freshness
   guarantee**. Supplying current rules is the caller's job. That caller is the
   orchestrator, and this ADR is where the obligation is discharged.

**Scope of this ADR.** Separate-mode sending only. Insert mode and the
render-context production class are deliberately absent — they carry every hard
problem the POC surfaced (render slots, the bind stack, preview leakage) and
must not share a decision record with claim-then-send. Placeholders,
`delay_seconds` scheduling, ADR-0007 snapshots and `consolidation` beyond one
email per rule per trigger are likewise out of scope and are **not stubbed**.

## Decision

### 1. Lifecycle

```
WooCommerce event
  -> build TriggerEvent (BOTH families for a status change)
  -> fetch active rules for that family        [freshness is the caller's job, ADR-0011 §7a]
  -> RuleMatcher::evaluate()                   [pure, writes nothing]
  -> for each decision: apply the identity-consumption policy (§2)
  -> for each actionable decision: claim -> send -> finalize
```

**The matcher is never handed a rule set captured before a delay.** The
immediate path fetches and evaluates in the same call stack. The deferred job
(§7) re-fetches at execution time. There is no third path.

The orchestrator is the **only** class in the matching-and-delivery stack that
writes. `RuleMatcher`, `ItemResolver`, `Targeting`, `Specificity` and
`PreparedRule` remain pure, and the purity test that proves it stays green.

### 2. Identity consumption — which decisions claim a tombstone

**This is the load-bearing decision of this ADR.** A claim permanently consumes
`order|rule|mode|trigger_identity`. Claiming for the wrong reasons silently
prevents legitimate future sends; not claiming where we should permits
duplicates. Both failures are invisible at the moment they happen.

| Decision | Claims? | Logged as |
|---|---|---|
| `matched` | **yes** | claim, then `sent` / `failed` detail rows |
| `excluded_by_rule` | **yes**, `skipped` | detail row `skipped`, reason recorded |
| `targeting_invalid` | **yes**, `skipped` | detail row `skipped`, reason recorded |
| `rule_disabled` | **yes**, `skipped` | detail row `skipped`, reason recorded — **but no production path reaches it; see §2a** |
| `blocked_by_stop_flag` | **NO** | recorded on the *stop rule's* detail row |
| `no_targeting_match` | **NO** | not logged at all (ADR-0005), debug tier only |

One outcome is decided after the claim rather than by the matcher:

| Outcome | Claims? | Logged as |
|---|---|---|
| `disabled_by_filter` (§5a) | **yes** — already claimed | detail row `skipped`, reason names the filter; **never** `failed` |

**Why `blocked_by_stop_flag` must not claim.** *(DECIDED HERE.)* A blocked rule
never got the chance to match — the halt happened before it was evaluated, so
nothing is known about it. Two separate failures follow from claiming it:

- **Silent permanent loss.** If it consumed its identity and the merchant later
  removed the stop flag, that rule could never fire for that order again. The
  merchant's fix would appear to do nothing, with no record explaining why.
- **Log flooding.** In a fifty-rule store a single halt would write forty-odd
  tombstones per status change — permanent rows, never purged (ADR-0004), for
  rules that did not run.

Instead the **stop rule's own detail row** records how many rules it blocked and
their ids. One row per halt, and the diagnostic question *"why didn't rule X
send"* is still answerable: the halt is visible, attributed, and countable.

**Why the other three skips do claim.** They are per-rule, rare, and
**deterministic for that identity** — an excluded rule stays excluded, an
invalid targeting document stays invalid, a disabled rule was disabled. ADR-0004
already fires once per order per rule per identity, so consuming the identity
loses nothing that would otherwise have happened. Recording them makes the
delivery log able to answer why a rule did not send, which is the entire point
of ADR-0005 carrying reason codes rather than a boolean.

Manual resend remains available: ADR-0004 provides linked attempt rows outside
the unique constraint, so a merchant can always resend deliberately.

**`skipped` is added to `DeliveryRepository::FINAL_STATUSES`.** Schema v1 is
unreleased and `final_status` is a `varchar` allowlist enforced in PHP, so this
is a constant change and **not** a migration. `DeliveryDetailRepository::STATES`
already carries `skipped`.

### 2a. `rule_disabled` is unreachable in production, by design

*(ADDED 2026-07-27, Prompt 4a, correcting the table above.)*

The table lists `rule_disabled` as claiming with `skipped`, and that is what the
code does — but **no production path can produce it**, and that is not an
oversight:

- the **immediate** path fetches with `status = 'active'` filtered in SQL, so a
  disabled rule is simply absent;
- the **deferred** job **re-fetches** at execution time (ADR-0011 §7a), so a rule
  disabled during the delay is absent there too.

**That absence is the correct outcome.** It does not send, it consumes no
identity, and re-enabling the rule leaves it able to claim normally. `rule_disabled`
is reachable **only** when a caller deliberately hands the matcher a row it has
already read and found inactive — which nothing in this plugin does today.

**What was rejected.** Persisting the candidate rule ids at deferral time and
comparing them against the re-fetch, in order to manufacture a `rule_disabled`
row, was considered and refused twice over:

1. it rebuilds the **second staleness mechanism** explicitly rejected in Prompt 3c
   and in ADR-0002's reasoning — two sources of truth for one question;
2. it would **consume an identity for a rule the merchant switched off**, so
   switching it back on could never deliver that trigger; and
3. concretely, the Action Scheduler **argument set is what the
   `as_has_scheduled_action()` pre-check matches on** (§7). A variable-length
   candidate list inside it means two firings of the same trigger produce
   different argument sets, the pre-check stops recognising the pending
   duplicate, and the one-deferral intent is lost. The diagnostic gain does not
   pay for that.

The diagnostic question stays answerable without any of it: the rule's own
`status` column says it is disabled.

### 3. Claim outcomes — fail closed

`DeliveryRepository::claim()` returns exactly one of `claimed`, `suppressed`,
`failed`.

| Result | Meaning | Orchestrator behaviour |
|---|---|---|
| `claimed` | fresh INSERT; this delivery is ours | **send** |
| `suppressed` | the identity already exists | record nothing beyond the atomic `suppressed_count` increment the claim itself performed; **do not send** |
| `failed` | query error, or any unrecognised affected-row count | write a `failed` detail row; **do not send** |

**A send that THROWS is caught.** *(AMENDED 2026-07-27, Prompt 4a.)* The send runs
inside `woocommerce_order_status_changed`, so an SMTP plugin or a `pre_wp_mail`
filter that throws would propagate out through the merchant's status change —
potentially breaking the order update — while the tombstone stayed `claimed` with
no detail row and the consumed identity blocked every retry. `\Throwable` is
caught (not `\Exception`: a `TypeError` from a badly-typed third-party filter is
just as fatal to the order update), `failed` rows are written, the tombstone is
finalised `failed`, the sanitised message goes to `wc_get_logger()`, and nothing
escapes into the event.

**Every write is verified.** *(AMENDED 2026-07-27, Prompt 4a; extended 2026-07-28,
Prompt 4b.)* The recording methods return
`{success, rows_expected, rows_written, finalized}` and log a shortfall through
`wc_get_logger()` with the delivery id. Ignoring those results meant a sent email
whose detail rows all failed to insert was finalised `sent` with **no record of
who received it** — invisible to delivery history, and to the privacy exporter
and eraser, which find rows by recipient. A finalisation failure left the
tombstone `claimed` forever while the consumed identity blocked retry. Both
failures were silent; neither is now.

`record_claim_failure()`'s defensive *"a failed claim that somehow carries a
delivery id"* branch is held to the **same** contract: it used to insert and
finalise while checking neither result. `DeliveryRepository::claim()` returns
`delivery_id = 0` on both failure paths, so nothing in the plugin reaches that
branch today — but the method takes a claim array from its caller rather than
producing one, and unverified writes are not something to leave lying in a
fail-closed path.

**The orchestrator carries the results.** *(ADDED 2026-07-28, Prompt 4b.)* Every
structured result now lands in a per-run `Delivery\RunOutcome` — the object the
public entry points return — alongside the `EvaluationResult`. The logger already
wrote its own error on a shortfall, so no email was ever mis-sent because the
results were discarded; what was missing was the orchestrator's ability to state
a **truthful aggregate outcome** for a run, which is precisely what the
delivery-history phase will ask it for. `RunOutcome` is built per run and passed
down the call chain, never held on the orchestrator — see §11.

**There is no outcome in which an unrecognised claim result produces an email.**
The orchestrator switches on the three known values and treats *anything else*
as `failed` — the same fail-closed discipline the repository applies to the
affected-row count itself. A `failed` claim carries no `delivery_id`, so its
failure is recorded through the plugin's error log rather than a detail row that
has no parent to attach to; where a `delivery_id` does exist, the detail row is
written.

### 4. Recipient resolution

`rules.recipients` is JSON of this **exact** shape:

```
{
  "to":  ["customer" | "admin" | "an@address.test", ...],
  "cc":  [...],
  "bcc": [...]
}
```

- **`customer`** resolves to the order's billing email;
  **`admin`** to the store admin address (`admin_email`).
- **Literal addresses** are validated with `is_email()`. Invalid entries are
  **dropped**, and each drop is **recorded** in the skip/attempt reason — a
  silently dropped recipient is the same silent failure ADR-0011 spent three
  passes removing from targeting.
- Every resolved address is normalised through the existing ASCII-lowercase rule
  (`Domain\Recipient::normalize()`, the same fold `DeliveryIdentity` uses, so the
  privacy eraser's `WHERE recipient = %s` can find it on any host).
- Addresses are **de-duplicated across `to`/`cc`/`bcc`, with `to` winning**, then
  `cc` over `bcc`. One person receives one copy, on the most direct channel they
  qualified for.
- **One detail row per resolved recipient**, carrying `recipient_type` — the
  storage contract locked in Prompt 2b. **Never a comma-joined list**, which the
  detail repository refuses outright because it would be invisible to the
  privacy eraser.
- **Malformed JSON, a list-shaped root, or a channel that is not an array**
  means the rule resolves **no recipients**: log `skipped` with the reason.
  Unknown keys inside a correctly-shaped document are ignored, matching
  ADR-0011 §3's treatment of targeting — shape errors and unknown keys are
  different things.

  **Recipients are NOT decoded non-associatively, unlike targeting, and that is
  a deliberate difference.** ADR-0011 §3 makes `Targeting` decode the raw column
  with objects preserved so `{"products":{"0":1}}` can be rejected — there, an
  object's *values* would be **converted into ids**, inventing targeting the
  author never wrote. Recipients carry no such risk: every entry is validated
  individually by `is_email()` and used **as-is**, so a channel written
  `{"0":"customer"}` resolves to exactly the same recipient a list would, and
  rejecting it would buy nothing. A channel that is a **scalar** or an
  **object of the wrong depth** is still a shape error, because it cannot be
  iterated as entries at all. The consequence is that this column needs no
  encoder counterpart (`Targeting::encode()` exists only because that
  distinction is load-bearing there), and `Json::encode()` remains correct for
  it.
- **Zero resolved `to` recipients** means **do not send**: log `skipped` with the
  reason. `cc`/`bcc` alone is not a delivery.

### 4a. Literal recipients are bare addresses — stated, not implied

*(DECIDED 2026-07-28, Prompt 4b.)*

Header form is **understood** — `Alice <alice@example.test>` is accepted and
resolves to `alice@example.test` — but the display name is **not** carried into
the outbound header, and `recipient_header` is **left null for automatic
deliveries**. The column keeps its meaning for the manual and imported rows that
do populate it (ADR-0009); this phase simply never writes one.

**Why not preserve it.** `wp_mail()` splits its `$to` on commas with no regard
for RFC quoting, so a display name containing a comma (`"Smith, Alice"
<a@b.test>`) is torn into two unusable recipients the moment two entries share a
channel. The address is the deliverable; the display name is cosmetic. Trading a
cosmetic loss against a delivery failure is not a close call.

**The drop is recorded.** Resolution adds a note — *"sent a `to` entry to its
bare address; the display name is not carried into the header"* — so the
delivery log answers "where did my display name go" rather than leaving it to be
discovered. A silently discarded display name would be the same class of silent
behaviour the notes exist to eliminate.

**Header-injection defence.** *(DECIDED HERE, required.)* Any CR or LF —
**raw, percent-encoded, or HTML-entity encoded** — in a resolved recipient, in a
display name, or in the subject is **stripped before use**, and the occurrence is
**recorded**. A hostile billing name (`"Alice\r\nBcc: attacker@evil.test"`) must
not be able to inject a mail header. This is defence in depth: PHPMailer also
rejects such values, but the plugin composes the CC/BCC headers itself, and a
value that reaches header composition unstripped is one library version away
from being exploitable. The stripping is applied at the point of resolution, not
at the point of send, so nothing downstream can bypass it.

### 5. The fixed email class (ADR-0002, unchanged)

Exactly **one** `Extonify\WCEP\Email\Custom_Email extends WC_Email`, registered
through `woocommerce_email_classes` **before the mailer initialises**, so it is
present in the live `WC()->mailer()->get_emails()`. Per-rule registration stays
prohibited (ADR-0002).

`init_form_fields()` exposes **only** `enabled` and `email_type`. The `enabled`
checkbox is the **global kill switch**. Subject, heading, content, recipients and
CC/BCC are **rule-owned** and never appear in WooCommerce settings.

`trigger()`:

- sets **every** runtime field explicitly on entry — recipient, cc, bcc, subject,
  heading, content, matched items, object, delivery reference — never
  conditionally on whether an argument was supplied;
- **captures the frame it found on entry and RESTORES it** in a `finally` block,
  so an exception mid-send cannot leave state behind **and** a nested delivery
  cannot destroy the delivery it interrupted;
- reads `email_type` from the **saved setting** and never overrides it per
  delivery.

> **⚠ THE SECOND CLAUSE ORIGINALLY READ "resets all of them in a `finally`
> block".** That is superseded: clearing isolates consecutive deliveries and
> **destroys nested ones**, which cost an outer delivery its entire runtime state
> and recorded a claimed identity as `no_recipient`. **§11a is the contract** —
> capture on entry, restore on exit, the empty frame at the top level making the
> two requirements one statement. Prompt 5 must build on §11a, not on this
> clause's earlier wording. The single source of truth for what is in the frame
> is `Custom_Email::RUNTIME_FIELDS`, which also carries the one inherited field
> WooCommerce mutates mid-delivery (§11c).

**The kill switch is checked BEFORE anything is claimed.** *(AMENDED 2026-07-27,
Prompt 4a.)* The first implementation claimed the identity, called `trigger()`,
got `false` back from the disabled switch, and recorded `failed` with a message
saying the mailer reported the message as unsent. Three things were wrong with
that: the mailer did not fail, the merchant switched the feature off; `failed` is
the wrong reason code for a deliberate configuration choice; and — the real
defect — **the identity was consumed while the feature was off**, so re-enabling
it and re-firing the same trigger was suppressed. The merchant's switch was a
one-way door.

Orchestration now reads the switch before the decision loop. When it is off,
**nothing is claimed, nothing is sent, nothing is recorded** beyond a log note.
Enabling it later and re-firing the trigger delivers normally, which is asserted
by actually re-firing. The same guard covers the email class being absent from
the registry.

**One shared object serves every delivery in a request.** State bleed between
consecutive sends is the intrinsic risk of this architecture — it is the reason
ADR-0002 chose a single fixed class over per-rule registration, and the risk that
choice accepted. It is therefore **tested directly against the live
`WC()->mailer()->get_emails()` object**, never against a fresh instance, and
never assumed.

### 5a. The global switch and the per-delivery filter are two different questions

*(ADDED 2026-07-28, Prompt 4b.)*

`WC_Email::is_enabled()` is **not** the global switch. It applies
`woocommerce_email_enabled_{id}`, which is handed `$this->object` — so a third
party may legitimately answer **`true` for the store and `false` for order
#123**. The orchestrator was calling it **with no order attached**, before
anything was claimed, and reading a per-order `false` as *"the merchant switched
the feature off"*.

The failure that produced: the identity **was** claimed (the second check, inside
`trigger()`, is the one with the order attached), `trigger()` returned `false`,
and the caller recorded a **mail transport failure** — wrong reason, consumed
identity, suppressed retry, and the mailer blamed for a decision it never saw.

| Question | Where it is asked | What it reads | Effect |
|---|---|---|---|
| **Global switch** — is the feature on for this store? | orchestration, **before any claim** | `Custom_Email::is_globally_enabled()`: the saved `enabled` setting **only**, no dynamic filter | nothing claimed, nothing sent, nothing recorded beyond a log note (the Prompt 4a policy, unchanged) |
| **Per-delivery filter** — may *this* delivery go out? | `Custom_Email::trigger()`, **after** every runtime field is set | `is_enabled()`, so `woocommerce_email_enabled_{id}` sees the order, rule content and recipients | **claims**, records **`skipped`** with reason `disabled_by_filter`, **never** a `failed` transport row |

**`disabled_by_filter` claims, and is recorded `skipped`.** *(DECIDED HERE.)* The
filter rejected this specific order, rule and identity **with the full context in
front of it** — that is a decision, not a failure, and it belongs with the other
deterministic claiming skips in §2. Consuming the identity loses nothing a
merchant would want back: the filter that said no will say no again, and a
manual resend remains available through ADR-0004's linked attempt rows.

`trigger()` therefore returns a **string outcome**, not a boolean: `sent`,
`not_sent`, `disabled_by_filter`, `no_recipient`. A boolean was what made two
unrelated outcomes indistinguishable in the first place.

### 5b. Headers are WooCommerce's, plus this plugin's Cc and Bcc

*(ADDED 2026-07-28, Prompt 4b, closing a defect present on **every** delivery.)*

`Custom_Email::get_headers()` reimplemented `WC_Email::get_headers()` — it
composed Content-Type, Cc and Bcc and stopped. It therefore **never emitted
Reply-To**, so every message this plugin sent **ignored the merchant's configured
reply address** and customer replies went to the From address instead of wherever
the store had directed them. Not an edge case: every delivery, surfacing as lost
customer replies.

**The parent builds the headers.** `Custom_Email::get_headers()` calls
`parent::get_headers()` and adds only what is genuinely its own, so everything
WooCommerce knows about sender identity is inherited **by construction** and
stays inherited when WooCommerce changes it:

- **Reply-To** — the enabled/disabled setting, the configured address, the
  configured name, and core's fallback to `From name <From address>` when
  reply-to is off;
- **Content-Type** — from the store's `email_type` setting;
- **Cc/Bcc** — emitted by the parent on WooCommerce versions whose
  `email_improvements` path is active, in which case this plugin adds nothing
  and `woocommerce_email_cc_recipient_{id}` keeps the last word.

**From is not a header this class writes, on any version.**
`WC_Email::send()` binds `get_from_address()` and `get_from_name()` onto
`wp_mail_from` / `wp_mail_from_name` for the duration of the send, so the store's
sender identity applies to this plugin's messages exactly as it does to core's.
Asserted against the live send, not assumed.

**The Cc/Bcc injection runs INSIDE the parent's filter**, registered at
`PHP_INT_MIN` so it is the first `woocommerce_email_headers` callback, rather
than being appended to the parent's return value. Appending afterwards would
leave the filter unable to see this plugin's Cc and Bcc — an SMTP or
deliverability plugin reading the block would be reading an incomplete one.
**`woocommerce_email_headers` is applied exactly once**, by the parent, and that
count is asserted.

**Below the WooCommerce floor the degradation is explicit.** `get_cc_recipient()`
and `get_bcc_recipient()` arrived in WC 9.8; the provisional floor is 8.2. They
are **feature-detected**, and when absent the already-validated,
already-`HeaderGuard`-stripped runtime values are written directly. The
degradation is that WooCommerce's recipient filters are unavailable to filter —
never that the Cc and Bcc are silently dropped.

### 6. Content handling in this prompt

Subject, heading and content are sent **literally**. No placeholder substitution
exists yet; `{customer_name}` in a rule is delivered as those characters. This is
stated so the absence is a decision rather than an omission.

Content is stored through `wp_kses_post` at the repository boundary and rendered
**inside WooCommerce's own email wrapper** (`emails/email-header.php` /
`emails/email-footer.php`), so the store's header, footer and branding apply
without this plugin owning a template. Plain-text output is produced when the
store's `email_type` calls for it.

### 7. ADR-0008 deferral

A trigger firing on a **zero-item order that has at least one in-phase candidate
rule** schedules **exactly one** Action Scheduler job carrying **order id,
trigger type, trigger value and the original trigger identity**.

At execution the job:

1. reloads the order;
2. **re-fetches current active rules** (ADR-0011 §7a — this is the freshness
   obligation being discharged, not a snapshot being replayed);
3. evaluates;
4. claims under the **original identity**, so the deferred path cannot double
   send against the immediate path — the DB unique constraint collapses the two
   into one claim (ADR-0004).

**Still zero items at execution:** log the reason and stop.
**One deferral only, never a chain:** the deferred job never schedules another.

### 7a. The deferral is conditional on having something to defer *for*

*(ADDED 2026-07-28, Prompt 4b.)*

ADR-0008's reasoning is unchanged and still load-bearing: a zero-item order is
**not** evidence that nothing matches, it is evidence that the question cannot be
answered yet. But that only holds while there is a question. **When the
(already phase-filtered) rule set handed to the matcher is empty, the answer is
already known and final**, and the run returns an ordinary empty, non-deferred
result.

The deferral decision used to be taken **before** the rules were consulted, so a
zero-item order scheduled a job when:

- no active rules existed at all;
- only **insert-mode** rules existed (Prompt 5's phase);
- only **delayed** rules existed (Prompt 6's phase);
- nothing targeted that trigger family.

Every one of those jobs could only re-discover the same nothing. A status change
evaluates **two** families (§8), so a bulk import queued **two useless actions
per order** and filled Action Scheduler with work that could never deliver
anything.

**A zero-item order WITH candidates still defers.** That case is untouched.

### 7b. Scheduler duplicate prevention is best-effort; the claim is the guarantee

*(CORRECTED 2026-07-28, Prompt 4b — the previous wording described behaviour the
code deliberately does not have.)*

One description, used in the ADR, the class docblocks and the inline comments
alike:

```
Deferred job : re-fetches current active rules. A rule disabled during the delay is
               absent and sends nothing. No rule_disabled tombstone is manufactured.
Scheduler    : the per-identity pending check is best-effort; concurrent duplicate jobs
               remain possible; the atomic claim prevents duplicate delivery.
```

`as_has_scheduled_action()` **does** match the argument set, so the pre-check is
per-identity — but it is a read followed by an unlocked write, so two concurrent
requests can both pass it. Duplicate **jobs** are therefore possible and
accepted; duplicate **delivery** is not, because the ADR-0004 claim is atomic.
**The argument set must stay fixed-length** for the pre-check to keep working —
see §2a for what that rules out.

**Scheduling reports four outcomes, not a boolean.** *(AMENDED 2026-07-27,
Prompt 4a.)*

| Outcome | Meaning | Logged as |
|---|---|---|
| `scheduled` | this call created the action | notice, with the action id |
| `already_pending` | an identical action is already queued | notice |
| `scheduler_unavailable` | Action Scheduler absent or not initialised | **error** |
| `schedule_failed` | the scheduler refused or the store rejected it | **error** |

The `as_schedule_single_action()` return value is **captured** — `0` means the
action was not scheduled. A `false` return previously conflated *already
scheduled*, *scheduler unavailable* and *scheduling failed*, and the logger
reported all three as "already scheduled". The last two mean **a matching order
silently never gets its email**, which has to surface as an error rather than be
filed as routine.

**⚠ `$unique = true` IS DELIBERATELY NOT PASSED — see the flagged WooCommerce
behaviour below.** Action Scheduler's uniqueness matches **hook + group only**
and ignores arguments, so it would let one pending deferral suppress every other
order's. What replaces it is stated in **§7b** and nowhere else: an args-exact
`as_has_scheduled_action()` pre-check that is **best-effort**, and the atomic
ADR-0004 claim, which is the guarantee.

**Deactivation cancels pending deferrals.** *(AMENDED 2026-07-27, Prompt 4a.)*
`Install\Deactivator` unschedules the one-off deferral hook as well as the
recurring purge. A pending deferral that survived deactivation fired whenever the
queue next ran — possibly after the merchant reactivated the plugin days later —
sending a customer an email for a status change they had long forgotten.
"Deactivated" has to mean nothing further is sent. The one-off hooks are
unscheduled with `null` arguments, meaning *any* arguments: passing `array()`
matches only actions whose args are exactly empty, which would have left every
real deferral pending.

### 8. Event wiring

Registered in `Plugin::init()` alongside the existing `woocommerce_delete_order`
registration:

| Hook | Produces |
|---|---|
| `woocommerce_order_status_changed` | **both** `status:{to}` and `transition:{from}>{to}` |
| `woocommerce_order_fully_refunded` | `refund:{refund_id}` |
| `woocommerce_order_partially_refunded` | `refund:{refund_id}` |

A status change evaluates **both families**, each with its own identity, each
claiming **independently** — ADR-0011 §1. A `stop_processing` halt in one family
does not touch the other.

`checkout-draft` as a **destination** is ignored (ADR-0011 §1);
`transition:checkout-draft>pending` fires.

**Orchestration is inert when:**

- the schema is not operational (`Migrator::is_operational()`) — no claim, no
  send, no log, matching the degraded-mode policy the rest of the plugin already
  follows;
- a **preview or customizer render** is in progress — no claim, no send, no log.
  Detection prefers WooCommerce's own `woocommerce_is_email_preview` signal with
  the ADR-0005 render-scoped marker as the fallback. **This is a coarse guard, on
  purpose:** the full render-context machinery belongs to insert mode (Prompt 5),
  and separate mode is never triggered by a render in the first place. Erring
  toward inertness here cannot drop a real delivery, because a real delivery
  arrives through an order event, not through a render.

### 9. Phase filtering — a temporary boundary, and a load-bearing one

*(ADDED 2026-07-27, Prompt 4a, closing a customer-visible defect.)*

Only rules with **`delivery_mode = 'separate'` AND `delay_seconds = 0`** enter
this phase. Everything else is left **entirely untouched**: no claim under any
mode, no send, no detail row, no tombstone.

**What went wrong without it.** `DeliveryLogger::MODE` was hardcoded to
`separate` and neither column was read anywhere, so a rule the merchant
configured as **insert** was matched, claimed under `mode = separate`, and
**sent to the customer as a standalone email** — content meant to appear inside
their normal order email arriving as a surprise separate message, under an
identity the rule never had. A rule with a seven-day delay sent immediately.

**The filter runs BEFORE evaluation, not after**, and that ordering is part of
the decision: an insert rule carrying `stop_processing` must not halt the
separate rules in this phase, because this is not the phase that rule belongs to.
A filter applied after evaluation could not undo a halt that had already changed
every later decision.

| Phase | Owns | Claims under |
|---|---|---|
| **Prompt 4 (this one)** | `separate` + `delay_seconds = 0` | `mode = 'separate'` |
| **Prompt 5** | `insert` | `mode = 'insert'` |
| **Prompt 6** | any rule with `delay_seconds > 0` | its own phase's mode, after the ADR-0007 snapshot |

**An unfiltered rule is a defect, never a default.** When Prompt 5 and Prompt 6
land, each removes its own condition from the filter; until then the boundary is
what keeps "out of scope" meaning *left alone* rather than *processed by whatever
path happens to exist*.

### 10. One rule snapshot per delivery

*(ADDED 2026-07-27, Prompt 4a; scoped to the RUN rather than the object by
§11, Prompt 4b — read the two together.)*

The rule rows are fetched **once**, phase-filtered, handed to `RuleMatcher`, and
the **same in-memory rows** are used for claiming and sending. There is no second
read.

Re-reading the rule after matching meant an admin save in between made the rule
**match on the old targeting and send the new content to the new recipients** —
and `rule_revision_sent` recorded a revision that never produced that match, so
the audit trail described a delivery that never happened. The revision recorded
is now the revision of the row that actually matched.

### 11. No per-run state on any shared delivery object

*(ADDED 2026-07-28, Prompt 4b, closing the same nested-lifecycle failure the
render-context POC spent four passes on — arriving here on a different object.)*

**The rule snapshot of §10 is per RUN, not per object.** It lived on
`Orchestrator::$snapshot`, and `Events` shares one orchestrator for the whole
request so that several events reuse the resolver's product cache. The two facts
combine badly:

1. the outer order's run snapshots rules A and B;
2. sending A runs a third-party callback — an SMTP plugin, a `woocommerce_email_sent`
   listener, a fulfilment integration — that changes **another order's** status;
3. the inner event reaches the **same** orchestrator and **overwrites** the
   snapshot;
4. the outer loop resumes at rule B and looks it up in the **inner** run's map.

Rule B then either **disappears and is silently skipped**, or **collides with an
unrelated inner rule carrying the same id** and sends that rule's subject,
content and recipients — recording a `rule_revision_sent` belonging to a
different rule entirely. Both outcomes are invisible at the moment they happen.

**The rule.** Per-run state lives in **local variables passed down the call
chain**. The snapshot, the evaluation result and the run's outcome (§3) are
built in `evaluate_and_deliver()` and reach `deliver()` and `send()` as
arguments. A nested run gets its own and cannot reach the outer one.

**Every property of the shared delivery objects is per REQUEST**, and each is
documented as such at its declaration. Two questions have to be answered for
each, not one — *is it per-run?* **and** *what happens if this object is
re-entered while it is set?* A property that is safe under the first can still
be fatal under the second, which is how both Prompt 4c defects survived the
first version of this audit:

| Class | Property | Scope | Safe under re-entry because |
|---|---|---|---|
| `Orchestrator` | `$rules` | per request | stateless gateway onto the rules table; holds nothing a nested run could change |
| `Orchestrator` | `$matcher` | per request | pure (ADR-0011 §9) apart from the resolver it holds; see `ItemResolver` below |
| `Orchestrator` | `$logger` | per request | two repository handles, no run state |
| `DeliveryLogger` | `$deliveries` | per request | repository handle |
| `DeliveryLogger` | `$details` | per request | repository handle |
| `Events` | *(none)* | — | static methods only; the one `static $orchestrator` inside `orchestrator()` is the shared per-request instance this section makes safe |
| `RuleMatcher` | `$rules` | per request | repository handle |
| `RuleMatcher` | `$items` | per request | the shared `ItemResolver`; see §11b for what it may and may not cache |
| `ItemResolver` | `$products`, `$facts` | per request | keyed by **product id**, not by order — a nested run resolving a different order neither reads nor writes another order's entry (§11b) |
| `Custom_Email` | every field in `RUNTIME_FIELDS` | **per delivery** | cannot be moved off the object (ADR-0002), so it is captured and **restored** rather than cleared — §11a |

*(The `Orchestrator::$matcher` row originally read "keyed by product id and so
correct for every order". That described `$products`; the resolver also held an
`$orders` cache keyed by order id, which was neither. Corrected 2026-07-28,
Prompt 4c — see §11b.)*

`Custom_Email` is the deliberate exception and is governed by **§11a**: it
carries per-delivery fields because ADR-0002 chose one fixed class, so the state
cannot be moved off the object and must be **restored** instead.

> **⚠ THIS SECTION ORIGINALLY CLAIMED** that a nested send leaves the outer send
> unaffected "because `WC_Email::send()`'s arguments — recipient, subject,
> content, headers, attachments — are all evaluated before the nested event can
> fire". **That is false, and §11a is the correction.** `trigger()` calls
> `is_enabled()` — which applies the third-party `woocommerce_email_enabled_{id}`
> filter — *before* any of those arguments is evaluated. Re-entry there was
> costing the outer delivery its entire runtime state.

### 11a. State that cannot be per-run must be RESTORED, never cleared

*(ADDED 2026-07-28, Prompt 4c.)*

**The general rule, which is what §11 should have said:**

> Per-run state on an object that cannot be made per-run must be saved on entry
> and **restored** — never cleared — on exit. Clearing isolates consecutive
> calls and destroys nested ones. Any cache on a shared object must
> additionally declare what invalidates it within a single request.

§11 moved the rule snapshot to a local because `Orchestrator` allows it.
`Custom_Email` does not: ADR-0002 requires exactly one registered instance, and
WooCommerce reads the delivery off `$this`. So `trigger()` now does:

```
$previous = $this->capture_runtime_state();
try   { $this->apply_runtime_state( $args ); /* evaluate and send */ }
finally { $this->restore_runtime_state( $previous ); }
```

At the top level `$previous` is the empty state, so the object still ends clean
and the Prompt 4A isolation guarantee is **preserved rather than traded away** —
the two requirements become one statement.

**What the clearing version cost.** Outer `trigger()` set every field, then
called `is_enabled()`. A filter on `woocommerce_email_enabled_{id}` changed
another order's status; the inner event re-entered this same object, sent, and
its `finally` cleared everything. Control returned to the outer call, which saw
`recipient === ''` and returned `no_recipient` — **on an identity it had already
claimed**. A valid customer email, permanently recorded as skipped and
unretryable. The same corruption reached `woocommerce_email_sent`, where a
listener on the outer send read `$email->object === null` and `delivery_id === 0`.

**Every runtime field is declared once**, in `Custom_Email::RUNTIME_FIELDS`, and
capture, apply and restore all walk it. Three hand-maintained lists is the shape
where a new field reaches two of them and leaks through the third.

**The temporary header-injection callback obeys the same rule.**
`get_headers()` registers a **fresh closure per call** rather than
`array( $this, 'inject_copy_headers' )`. WordPress keys a registration on
callback identity, and an object-method callable has one identity for every call
on a shared instance — so a nested `remove_filter()` would strip the
registration the outer frame is still relying on. Two closures are two
registrations. Both running against one header build is harmless, because the
injector skips any header line already present.

### 11b. Every cache on a shared object declares its invalidation

*(ADDED 2026-07-28, Prompt 4c, closing a defect that broke ADR-0008.)*

`ItemResolver` is shared for the whole request — one `Events` orchestrator, one
matcher, one resolver — and it cached **resolved order contents** in `$orders`,
keyed by order id, returned on a hit. So:

1. order #100 fires a status event with **zero items**; the resolution
   `item_count = 0` is cached;
2. an importer attaches the items **later in the same request**;
3. the next status event on #100 reads the cache, still sees zero items, and
   **defers again instead of matching**.

That is exactly the create-then-attach lifecycle **[ADR-0008](ADR-0008.md)
exists to support**, defeated by a cache. Items replaced or removed mid-request
were stale in the same way.

**`$orders` is removed.** Order contents are re-read on every evaluation. The
cost is near zero — `WC_Order::get_items()` is memoised on the order object, the
item meta is already in WordPress's cache, and the expensive part stays cached.

| Cache | Keyed by | Holds | Invalidated by |
|---|---|---|---|
| `ItemResolver::$products` | product id | the `WC_Product`, or `false` for a failed load | **nothing within a request — accepted**, see below |
| `ItemResolver::$facts` | `product_id:variation_id` | type slug, parent type, virtual/downloadable, category and tag ids | **nothing within a request — accepted**, same reason |
| ~~`ItemResolver::$orders`~~ | ~~order id~~ | ~~items, notes, item_count~~ | **removed — no correct invalidation exists** |

**Why the product-keyed caches are accepted rather than invalidated.** A product
edited inside the same request that later evaluates an order containing it would
be matched on its pre-edit facts. No WooCommerce path produces that: order
contents change during ordinary order creation, which is a documented lifecycle,
whereas editing a product mid-send is not. A caller that needs to force the issue
calls `ItemResolver::flush()`. This is a decision, not an omission — the previous
audit left it unexamined, which is how `$orders` survived beside it.

### 11c. Inherited `WC_Email` state is part of the frame

*(ADDED 2026-07-28, Prompt 4d.)*

§11a made `Custom_Email` capture and restore the fields **it declares**. That is
not the whole object: it extends `WC_Email`, and a parent property WooCommerce
mutates mid-delivery corrupts an outer call exactly as one of ours would. Every
`$this->` assignment in the bundled `WC_Email` (WC 10.9.4) was read; only two
happen during a delivery at all.

| Inherited property | Mutated mid-delivery? | In the frame? | Why |
|---|---|---|---|
| `sending` | **YES** — `get_content()` sets `true`; `handle_multipart()`, on `phpmailer_init`, sets `false` | **YES** | The only parent property with a genuine outer/inner conflict. With `email_type = multipart`, a nested delivery's multipart handler switches the shared flag off; the outer send then fails its own `if ( ! $this->sending ) return;` guard and **its plain-text alternative is never generated**. |
| `email_type` | Only on the block-editor path: `get_content()` promotes `plain` → `html` | **NO** — see below | Excluded, deliberately |
| `object` | only via `set_object()`, which this plugin never calls | already in the frame | It is assigned directly by `apply_runtime_state()` and covered by §11a |
| `recipient` | never by the parent; subclasses assign it | already in the frame | Same |
| `cc`, `bcc` | constructor only, from saved options | already in the frame | Same |
| `mime_boundary`, `mime_boundary_header` | **never assigned anywhere in WC 10.9.4** | **NO** | Vestigial: declared, and left over from the pre-`handle_multipart()` multipart implementation. Nothing reads or writes them. A behavioural assertion guards this rather than the declaration audit alone — see below. |
| everything else (`id`, `title`, `enabled`, `template_*`, `plain_search`, `placeholders`, feature flags, `personalizer`, …) | constructor or `init_form_fields()` only | **NO** | Per-request configuration, not delivery state |

**Why `email_type` is excluded — a decision, not an omission.** `get_content()`
contains `$this->email_type = 'plain' === $this->email_type ? 'html' : $this->email_type;`,
reachable only when `get_block_email_html_content()` returns content, which
returns `null` immediately unless WooCommerce's `block_email_editor` feature is
enabled. Three reasons to leave it out:

1. ADR-0002 and §5 make `email_type` a **store setting**, explicitly not runtime
   state — `reset_runtime_state()` is required not to touch it. Putting it in the
   per-delivery frame would contradict that in the one place a reader checks.
2. This plugin registers **no block templates**, so there is nothing for the
   block renderer to return for its email id.
3. The mutation is **idempotent and one-way** on a single object, so an outer and
   an inner delivery of the *same* object promote identically — there is no
   divergence to protect.

The residual case — block editor on, block content returned for one order and not
another, *and* nesting — is recorded in `docs/p2-backlog.md` as accepted residual
risk under this pass's stopping rule.

**A declaration audit alone would not catch a future WooCommerce that starts
using `mime_boundary`.** So the completeness guard asserts behaviourally, after a
real delivery, that both boundary properties are still untouched — and separately
that every declared property is either in `RUNTIME_FIELDS` or on an explicit
per-request allow-list, so a property WooCommerce adds later fails the suite and
gets a human decision instead of leaking.

### 11d. Temporary global registrations are state too

*(ADDED 2026-07-28, Prompt 4d.)*

A shared object can restore every field it declares and still corrupt an outer
call — or the whole request — through the **global hook registry**. Filters added
and removed around a send are per-delivery state that happens to live in
`$wp_filter` instead of on `$this`, and they get the same capture-and-restore
treatment.

**⚠ `WC_Email::send()` has no `try`/`finally`** (verified in the bundled
WC 10.9.4; see the flagged-behaviour section). It attaches `wp_mail_from`,
`wp_mail_from_name` and `wp_mail_content_type`, then applies
`woocommerce_mail_content` and invokes the mail callback, and only then removes
them. Anything that throws in between — an SMTP plugin, a `pre_wp_mail` filter, a
`woocommerce_mail_content` callback — leaves all three attached **for the rest of
the request**.

**This plugin turns a fatal into a survivable one, which is what makes the leak
reachable.** §3 catches `\Throwable` so a broken mail plugin cannot break the
merchant's order update. A core WooCommerce email would have died with the
exception; this plugin continues — and every subsequent `wp_mail()` in that
request then carries this store's From address, From name and `text/html` content
type. These are `wp_mail`-wide hooks, so that includes WordPress password resets
and other plugins' notifications.

`Custom_Email::send()` is therefore a **narrow state-preserving wrapper**: it
records whether each of the three callbacks was attached on entry, calls
`parent::send()` unchanged, and in a `finally` restores exactly that — removing
what this send leaked, and **re-attaching** what an outer send still owns. One
mechanism, both cases; the parent's body is never reimplemented, so future
WooCommerce changes to the send path are inherited.

**PHPMailer's `AltBody` is deliberately not part of this.** `WC_Email::send()`
clears it after the mail callback and skips that on a throw, but it cannot leak:
`wp_mail()` sets `Body` and `AltBody` to `''` **before** it fires
`phpmailer_init`, which is the only hook that populates `AltBody`. Verified on
this runtime rather than assumed. Replicating the clearing would be dead code.

### 11e. A send that throws never fires `woocommerce_email_sent` — a note for Prompt 5

*(ADDED 2026-07-28, Prompt 4d.)*

`do_action( 'woocommerce_email_sent', … )` is the **last** statement in
`WC_Email::send()`, after the mail callback. When the send throws, it does not
fire — and this plugin catches the throw and carries on (§3).

Separate mode does not care: the orchestrator records `failed` from the caught
exception, not from that hook. **Insert mode will care.** ADR-0005's render slot
reaches `awaiting_send`, the send throws, nothing finalises it, and the slot is
reported `unresolved` at shutdown. **That is the POC's designed behaviour and it
is correct** — an unresolved slot is exactly the right description of a render
whose send exploded. It is stated here so Prompt 5 does not build on an
assumption that the hook always fires, and does not mistake the resulting
`unresolved` slot for a defect.

## Consequences

- The delivery log can answer *"why did rule X not send for order Y"* for every
  reason except the deliberate noise floor, and the noise floor is the one case
  where the answer is "it simply did not apply".
- A halt costs **one** row rather than one per blocked rule, and removing the
  stop flag genuinely re-enables the blocked rules for future triggers — because
  their identities were never consumed.
- One status change can produce two emails from two rules in two families. That
  is intended: they express different merchant intents and carry different
  identities.
- Because `suppressed` writes no new row, a retry storm increments a counter
  instead of growing the table — ADR-0005's bounded-log promise survives contact
  with a misbehaving integration.
- Because recipient resolution is a pure function of the recipients document plus
  two order facts, it is unit-testable without WordPress, and the
  header-injection defence is provable without a mail server.
- Because the email object is shared and `trigger()` captures its frame on entry
  and **restores** it on exit (§11a), a fifty-delivery request is as safe as a
  one-delivery request, and so is a delivery that happens *inside* another one —
  but only as long as the isolation and re-entrancy tests keep running against
  the **live** object.
- Insert mode inherits a claim-then-send path that is already proven, so Prompt 5
  can concentrate entirely on render correlation.

## Flagged WooCommerce behaviour

Recorded here and in `docs/p2-backlog.md`; **re-check on version bumps.**

- **⚠ ACTION SCHEDULER'S `$unique` FLAG IGNORES THE ARGUMENT SET.** *(Found
  2026-07-27, Prompt 4a; verified against the copy bundled with WC 10.9.4.)*
  `ActionScheduler_DBStore::build_where_clause_for_insert()` builds
  `SELECT action_id FROM … WHERE status IN (pending, running) AND hook = %s AND
  group_id = %d` — **there is no `args` term.** So `$unique = true` means "one
  pending action per hook per group", not "one per argument set".

  Confirmed by experiment on this runtime: scheduling
  `extonify_wcep_deferred_evaluation` for order 111 returns a real action id;
  scheduling it for order **222**, with different arguments, returns **0**.

  The consequence, had it been used as the obvious reading suggests: while ANY
  deferral is pending, **every other order's deferral is silently refused** — one
  busy order suppressing email for the rest of the store. That is strictly worse
  than the duplicate it would prevent. `$unique` is therefore **not** passed;
  `as_has_scheduled_action()` (which *does* match arguments) provides the
  per-identity pre-check, and the atomic ADR-0004 claim provides the guarantee.
  Asserted by
  `DeferredDeliveryTest::test_scheduling_outcomes_are_distinguished()`, which
  schedules for a second order while the first is pending.

- **`as_unschedule_all_actions( $hook, array(), $group )` matches only actions
  whose arguments are exactly empty.** `as_unschedule_action()` sets the `args`
  query term only `if ( is_array( $args ) )`, so passing **`null`** means "any
  arguments" — which is what cancelling a hook actually requires. Passing
  `array()` would have left every real deferral pending at deactivation.

- **`woocommerce_order_status_changed` fires with `( $order_id, $from, $to,
  $order )`.** The `$order` argument is passed, but the orchestrator **reloads
  the order by id** rather than trusting it, because ADR-0008's motivating case
  is precisely an order whose items are attached *after* the status transition
  fires — the passed object can be mid-construction.
- **`woocommerce_order_fully_refunded` and `woocommerce_order_partially_refunded`
  both fire with `( $order_id, $refund_id )`.** They are separate hooks for one
  ADR-0004 identity family (`refund:{id}`); a full refund fires only the
  `fully` hook, so registering both is required for coverage and cannot
  double-fire for one refund.
