# ADR-0018: Delivery history — two read-only surfaces over one data model, and how an absent detail row reads honestly

Status: **Accepted** — 2026-08-12

## Context

Every delivery phase since Prompt 4 has written to `extonify_wcep_deliveries`
and `extonify_wcep_delivery_details`. **Nothing has ever read them back for a
merchant.** This ADR covers that surface, and only the reading of it: manual
send, resend and cancel are the first admin controls that mail a customer and
belong to their own decision.

Two things make this screen different from the rules admin ADR-0017 covered.

**First, the escaping surface is larger and its provenance is worse.** A rule's
name, subject and heading are merchant-authored: hostile content there requires
a hostile administrator. A delivery's `recipient`, `subject`, `reason` and
`failure_message` are not. The recipient comes from a customer-controlled
billing field; `failure_message` carries an SMTP server's response, which quotes
that address back verbatim; `reason` routinely embeds both. **Every value on
this screen is database-sourced and none of it is safe by virtue of the write
path** — which is exactly the lesson of Prompt 9A, where `TargetLabels::describe()`
rendered term and product names straight from the database with no escaping and
was caught only because a test wrote hostile data *past* the repository rather
than through it. Storage sanitisation hid an unescaped output path. Gate 31
therefore applies here with more surface than anywhere else in the plugin, and
every entry in its table is proven by a **direct write that bypasses the
repository**.

**Second, this is the first screen whose correctness includes describing data
that is not there.** ADR-0004 split a durable tombstone from a purgeable detail
row precisely so that history could be destroyed without re-arming an order.
That split is invisible everywhere else in the plugin and unavoidable here: a
merchant looking at an old delivery will see a row with nothing beneath it, and
whether they read the plugin as working or broken depends entirely on what the
screen says at that moment.

---

## Decision

### 1. Two surfaces, one data model, and no second query path

| Surface | Where | Scope |
|---|---|---|
| Delivery history | `admin.php?page=extonify-wcep-history` — WooCommerce → Product Emails → Delivery History | Every delivery in the store, filtered and paged |
| Order panel | A meta box on the WooCommerce order screen | That order's deliveries, in place |

**The history screen is a separately registered page, not an `action` on the
rules page.** ADR-0017 §1 refused a second registered page *for the editor*, and
the argument there was that the editor is reached from the list and is the same
subject matter under an `action` parameter. History is neither: it is a peer
destination with its own subject (deliveries, not rules), and a merchant
diagnosing "did this customer get their email" is not editing a rule.

⚠ **AMENDED IN PROMPT 13C PART F — §1a BELOW SUPERSEDES THE NAVIGATION HALF OF
THIS SECTION.** This paragraph used to end *"It costs one submenu row under a
menu this plugin already appears in"*, and no row is drawn for it any more. The
page is still separately registered for the reason above — parented to the rules
page, per §1a — and it is now reached by a tab.

**Both surfaces read the same two repository methods and format through the
same class.** `Admin\DeliveryPresenter` owns every string, every escape and
every honest-absence decision; `Admin\DeliveriesListTable` and
`Admin\OrderPanel` are layout over it. There is no second query path and no
second copy of the purged/anonymised wording, because two copies of that wording
is two chances for one of them to say "unknown error".

### 1a. One submenu row, two tabs — and no top-level menu (Prompt 13C Part F)

**Decision: one row under the WooCommerce menu, labelled `Product Emails`, with
native tabs for `Rules` and `Delivery History`. No top-level menu. No custom
icon. No branding anywhere in the interface.**

| Where | Label |
|---|---|
| WooCommerce submenu — one row | `Product Emails` |
| First tab | `Rules` |
| Second tab | `Delivery History` |
| Rules screen heading | `Email Rules` |
| Editor heading | `Add Email Rule` / `Edit Email Rule` |
| History heading | `Delivery History` |
| Plugins-list row action | `Settings` |

**Why, in WooCommerce's own terms.** The published extension guidance is
explicit on four points, and the previous layout was on the wrong side of three
of them:

1. **An extension extending WooCommerce belongs inside the WooCommerce nav
   structure**, not at top level.
2. **Admin screens that are not settings belong in a submenu under the
   WooCommerce menu item** — which is where both of these already were, and the
   only point the old layout satisfied.
3. **Extension names should omit "WooCommerce"** to avoid redundancy —
   Subscriptions, not WooCommerce Subscriptions. `Custom Product Emails` and
   `Custom Email History` were not redundant in that exact way, but they carried
   the same problem one level down: both rows repeated `Custom`, and neither
   said plainly what the screen was.
4. **No logos, no branding, no self-promotion in the interface.**

**Why no top-level menu, recorded so the decision survives the next person who
wants one.** A top-level slot is the most valuable real estate in wp-admin and
every store owner's menu is shared with every other extension. A branded
top-level entry for a single email-rules extension reads as a plugin that does
not know the conventions — and it is the first thing a WordPress.org reviewer
and an experienced merchant both notice. ADR-0001 already forbade it on
trademark-identity grounds; §1a adds the navigation-convention grounds, so the
prohibition does not depend on the trademark argument alone.

**Why two rows became one.** Two sibling rows spent two slots to reach two views
of one subject. One row plus native tabs is the shape WordPress core uses for
exactly this — Settings, Tools, Site Health — and it is what the guidance asks
for. The tabs are `nav-tab-wrapper`/`nav-tab` anchors, so they inherit core's
focus outline, colour scheme and high-contrast handling, and they are
keyboard-operable by being links. The current tab carries `aria-current="page"`,
**not** `aria-selected`: these navigate rather than switch panels, so `role="tab"`
would promise scripted behaviour that does not exist.

⚠ **THE ROW IS HIDDEN; THE PAGE IS NOT. THIS IS THE PART TO GET RIGHT, AND THE
FIRST ATTEMPT GOT IT WRONG.** The history page keeps its own registration, its
own `load-` handler and its own capability check. It is hidden by being
**parented to the rules page** rather than to `woocommerce`: WordPress renders a
submenu only for slugs present in the top-level `$menu`, and
`extonify-wcep-rules` is itself a submenu — so `$submenu['extonify-wcep-rules']`
is registered, resolvable, and never walked by the menu renderer.

⚠ **`remove_submenu_page()` WAS TRIED FIRST AND IS WRONG.** It deletes the row
from `$submenu`, and `$submenu` is precisely where WordPress looks a plugin
page's parent up. With the row gone, `get_admin_page_parent()` returns empty,
`get_plugin_page_hookname()` computes a name that does not match the one
`add_submenu_page()` registered, `get_plugin_page_hook()` finds no action under
it, and `wp-admin/admin.php` refuses — **403, then "Cannot load
extonify-wcep-history." — to an administrator**. Prompt 13C Part F shipped that
briefly and caught it by fetching the page over HTTP; every unit test passed
throughout, because they call `Menu::render_history()` directly and never
traverse `admin.php`. `AdminNavigationTest::test_wordpress_routing_resolves_the_hidden_history_page()`
now asserts the WordPress-side facts instead: the parent resolves, the computed
hookname is the registered one, an action exists under it, and
`user_can_access_admin_page()` permits a capable user.

⚠ **The hook suffix changed** from `woocommerce_page_extonify-wcep-history` to
`admin_page_extonify-wcep-history` as a consequence, which is why gate 32's asset
gate compares against `Menu::hooks()` — the returned value — and never against a
hard-coded string. Assets were re-verified over HTTP as loading on both plugin
screens and on neither the dashboard.

Three consequences follow and all three are asserted:

- **Both slugs are unchanged** — `extonify-wcep-rules` and
  `extonify-wcep-history` — so every saved link, bookmark and redirect target
  still resolves.
- **The `load-` handler survives**, which matters because that is where the
  capability check and the write dispatch live. Hiding the row must never
  become unregistering the page.
- **Hiding a row is a navigation decision and must never become an
  authorisation one.** An unlinked page is not a protected page.
  `load_history()` and `render_history()` both call `require_capability()`
  first, exactly as they did when the row was drawn, and gate 28 plus
  `AdminNavigationTest` assert the refusal on the hidden page specifically.

**The plugins-list action says `Settings`, not the plugin's name**, because the
row already prints the name and point 4 above forbids the second copy. It points
at the rules screen, which is what a merchant clicking "Settings" expects to
reach. **The global enable/disable control stays under WooCommerce → Settings →
Emails**: it is one checkbox in WooCommerce's own settings surface, and moving it
to justify the link's label would be the wrong way round.

**Plugin name, slug and text domain are unchanged.** This is a navigation and
labelling change only.

### 2. What a merchant sees, and what they do not

Shown, per delivery: the order (linked), the rule (linked), the trigger, the
mode, the status, when it was first claimed and last seen, and — per attempt —
the attempt number, the attempt type, the recipient with its type, the subject,
and the reason or failure message where one was recorded.

**`identity_hash` is not shown.** It is an internal correlation key, it means
nothing to a merchant, and ADR-0010 already excluded it from the privacy
exporter for the same reason. A 64-character hex digest on a support screen is
noise that invites a merchant to quote it into a forum post.

**`snapshot` is not shown either.** On a tombstone it is the store's own
unrendered template awaiting a delayed send (ADR-0015 §2) — pending work, not
history — and on a detail row it is a structured diagnostic payload for the
logs. Neither is a sentence a merchant can act on, and ADR-0017 §2's refusal of
a raw-JSON view applies unchanged.

### 3. The rule link when the rule is gone — and why it is an id, not a name

A tombstone records `rule_id` and `rule_revision_sent`. **It does not record a
rule name, and this ADR declines to add one.**

The obvious alternative is a denormalised `rule_name` column written at claim
time. It is refused for the reason ADR-0015 §2 already refused widening the same
statement: `claim()` is one atomic statement whose affected-row count is the
plugin's entire duplicate-prevention mechanism, and adding a column that is not
part of that decision puts the most load-bearing query in the plugin at risk to
save a join. A denormalised copy would also go stale the moment a merchant
renames a rule, so the screen would show one name in the list and another in
history and neither would be wrong.

So: a live rule renders its **current** name, linked to its editor. A deleted
one renders `Rule #12` with the sentence *"This rule has been deleted."* — the
recorded id, which is the only rule identity the durable row actually holds.
The rule names for a whole page are resolved in **one** query.

> **⚠ THIS IS A STATED DEVIATION FROM THE PROMPT'S WORDING,** which assumed a
> recorded name exists. It does not, in the frozen schema, and manufacturing one
> would cost more than it buys.

### 4. Purged, anonymised, and empty must read as three different things

This is the decision most worth getting right, and it exists only because of the
ADR-0004 split.

**(a) Retention removes detail rows; it never removes tombstones.** So an old
delivery legitimately exists with nothing beneath it. The screen must say the
delivery happened and its details were removed — never render a blank row, which
reads as a bug in a plugin that is working exactly as designed.

**(b) A privacy erasure nulls the personal columns and keeps the row.** The
attempt, its type, its state and its timestamps survive; recipient, subject,
reason and failure message become `NULL`. That row must render as *redacted*,
which is a different fact from *purged* — the attempt is still there and still
says what happened, it just no longer says to whom. It must never render as
"unknown error", which asserts a failure that did not occur.

**(c) No deliveries at all is a third state.** A merchant who cannot tell "this
order never triggered a custom email" from "it did, and the details aged out"
will read a working plugin as a broken one.

The rendered sentences, verbatim:

| State | How it is detected | What the screen says |
|---|---|---|
| Details purged | Tombstone exists, **zero** detail rows | *"This delivery was recorded, but its details have been removed. See the retention note below."* |
| Attempt redacted | Detail row exists, `recipient_type` **or** `reason` is `NULL` | *"The details of this attempt were removed in response to a personal-data erasure request. The delivery itself is unchanged."* |
| No deliveries, order panel | Zero tombstones for the order | *"No custom emails have been sent for this order."* |
| No deliveries, filtered | Zero tombstones matching the filters | *"No deliveries match these filters."* |
| No deliveries, ever | Zero tombstones, no filters set | *"No custom product emails have been delivered yet. Deliveries appear here as soon as a rule sends one."* |

**The redaction markers are `recipient_type` and `reason`, and the choice is not
arbitrary.** Those are the two columns the write path *always* populates —
`recipient_type` is validated against `Recipient::TYPES` and defaults to `to`,
`reason` defaults to the empty string — so neither is ever `NULL` on a row this
plugin wrote, and either being `NULL` means the eraser has been here. `recipient`,
`subject` and `failure_message` are all legitimately `NULL` on an untouched row
(no CC, no subject recorded, nothing failed), so testing *those* would report an
ordinary delivery as redacted. **Either marker, not both**, because
`Privacy\SubjectData` scopes an erasure to contact fields, content fields, or
both — a row addressed to a third party keeps the contact fields that belong to
that other person, and a partial erasure is still an erasure.

A redacted attempt keeps its number, type, state and timestamps and simply omits
the lines whose values are gone. There is no per-field *"Removed"* marker: the
attempt-level sentence already says what happened, and repeating it per cell
would be noise on the row that is hardest to read.

**(d) The retention windows are stated on the screen — accurately, which is not
the same as stating the ADR-0005 policy.** ADR-0005 specifies 90 days normal,
180 days failed, 14 days debug, purged by a daily recurring action. **That
recurring action does not exist.** `DeliveryDetailRepository::purge_older_than()`
has no production caller; `Install\Maintenance` says so in terms
("Retention joins it when the settings UI lands"), and `docs/p2-backlog.md`
records it three times. A screen that announced those windows as current
behaviour would tell every merchant something untrue about their own data.

The note therefore states the windows **and** the fact that nothing applies them
yet:

> *"Delivery details are kept for 90 days, or 180 days for a failed delivery,
> and 14 days for debug entries. Automatic clearing is not scheduled yet, so
> details are currently removed only by a personal-data erasure request. The
> record that a delivery happened is always kept."*

### 5. Filtering, ordering and paging happen in SQL

`DeliveryRepository` grows two methods sharing one WHERE-clause builder, exactly
as `RuleRepository::query()`/`count()` do — so the pager and the page can never
disagree about what they are counting:

```php
public function query( array $args = array() ): array;   // filtered, ordered, paged rows
public function count_matching( array $args = array() ): int;
```

`count()` keeps its existing no-argument meaning (total tombstones, used by the
lifecycle assertions and uninstall), so the filtered counter takes a new name
rather than an incompatible signature.

Filters: `order_id`, `rule_id`, `final_status`, `mode`, `date_from`, `date_to`.
Every one is bound; the identifier in `ORDER BY` is allowlisted and the direction
is one of two literals.

> **⚠ CORRECTED IN PROMPT 13A.** This paragraph used to end *"because `prepare()`
> binds values and not identifiers"*, and the same claim was used to accept 46
> Plugin Check `UnescapedDBParameter` warnings. **It is false at the declared
> floor.** WordPress 6.2 added the `%i` identifier placeholder to
> `$wpdb->prepare()`, and ADR-0006's WordPress floor is 6.6. Every plugin-owned
> TABLE identifier is now bound with `%i`; the `ORDER BY` column and direction
> stay allowlisted because they are not table identifiers and `%i` does not cover
> a direction keyword. The one place a table name is still interpolated is
> `Migrator::schema_statements()`, and the reason there is specific: `dbDelta()`
> parses the string itself and never calls `prepare()`, so a `%i` would be read as
> the table's literal name.

**Ordering is `first_claimed_at DESC, id DESC`.** Newest first, tie-broken on the
primary key so paging is deterministic: without the tie-break, two deliveries
claimed in the same second may swap between page 1 and page 2 and one of them is
never shown. `first_claimed_at` and not `last_seen_at` — the latter is bumped by
`claim()`'s `ON DUPLICATE KEY UPDATE` every time the same trigger fires again, so
ordering by it would shuffle old deliveries to the top of the history whenever a
merchant re-saved an order.

**Nothing is loaded that is not shown.** No `array_slice()` over a full table
read — the defect corrected in the Prompt 7C sweep.

### 6. One new index, and why only one

The existing indexes serve the filters but **not the default view**:

| Access pattern | Served by |
|---|---|
| `order_id` filter, and the order panel | `order_id` (existing) |
| `rule_id`, and `rule_id` + status | `scheduled_lookup (rule_id, final_status)` (existing) |
| `final_status` | `lease_sweep (final_status, lease_taken_at)` (existing) |
| **Unfiltered, newest first, paged** | **nothing** |
| **`first_claimed_at` range** | **nothing** |

The unfiltered newest-first listing is the screen's default view and the one
whose cost is bounded by nothing at all: it is a full scan plus a filesort of a
table whose entire design is to grow for the lifetime of the store. Schema v1 is
unreleased, so this is an in-place amendment of v1 and **not** migration 2 — the
same reasoning `insert_lookup`, `scheduled_lookup` and `lease_sweep` were added
under.

```
KEY history_recent (first_claimed_at, id)
```

**Only one, deliberately.** Every index here is paid for on `claim()`, which runs
on every delivery. `mode` is a two-value column — an index on it would not be
chosen by the planner and would cost writes forever to serve a filter the
planner will satisfy by reading `history_recent` in order and stopping at
`LIMIT`. A `(final_status, first_claimed_at)` covering index would help a filter
on a rare status and is declined for the same reason: the planner already has
two workable plans for that query and neither is unbounded.

**Residual, stated:** filtering by `mode` alone, or by a very common
`final_status`, may filesort within the filtered set on a large store. Bounded
by `LIMIT`, not by the table. Tier 3 — recorded, not fixed.

### 7. Query count per page render: a fixed five, three of them on the delivery tables

Detail rows for the visible page are fetched **for the whole page in one
statement**, not one per delivery. So is the rule-name resolution. The formula,
counting every statement against a table this plugin owns:

```
history(page) = 1  (COUNT on deliveries, for the pager)
              + 1  (the page of tombstones)
              + 1  (every detail row for those tombstone ids — ONE batch)
              + 1  (every rule name for those rule ids — ONE batch)
              + 1  (the rule filter's options)
              = 5,  constant in page size    (of which 3 touch the delivery tables)

panel(order) = 1  (the order's tombstones)
             + 1  (their detail rows — ONE batch)
             + 1  (their rule names — ONE batch)
             + 1  (COUNT, for the "showing N of M" notice)
             = 4,  independent of how many deliveries the order has
```

It is constant, not merely small: the two batches are `IN (…)` runs whose
placeholder count is generated from the id count, and the page size (20) is far
below the 200-id chunk bound the repositories already use. The rule filter's
options are one statement whatever the page holds — it describes the store, not
the page.

The gate measures both a 3-row page and a 15-row page and requires the counts to
be **equal**, because the defect it guards against — resolving details or names
inside a column callback — shows up as a difference of exactly twelve.

**The order link is built, never loaded.** `OrderUtil::get_order_admin_edit_url()`
calls `wc_get_order()` under HPOS, which would be one order load per row — the
exact N+1 shape this section exists to forbid. The URL shape is decided once per
render from the storage mode and the recorded `order_id` is substituted into it,
so the link costs zero queries and still works for an order that has since been
deleted (it 404s, which is honest; the row is not hidden).

### 8. The order panel supports both storages, by detection

HPOS and legacy post storage register the order screen under different ids, so
the meta box is registered against the id the **active** storage reports:

```php
$screen = OrderUtil::custom_orders_table_usage_is_enabled()
    ? wc_get_page_screen_id( 'shop-order' )   // 'woocommerce_page_wc-orders'
    : 'shop_order';
```

Detected, never assumed — the plugin already declares HPOS compatibility, so a
panel that worked on only one of them would be a visible contradiction of its
own header. The callback is handed a `WC_Order` under HPOS and a `WP_Post` under
legacy; it resolves an id from either shape and reads nothing else off the
argument.

### 9. Read-only means read-only, and the space for Prompt 11 is left empty

No control on either surface writes, sends, schedules, cancels or deletes.
Rendering either surface issues `SELECT` statements and nothing else, and gate 34
proves it by assertion rather than by inspection.

**Where Prompt 11 will add actions there is empty space, not a disabled
button.** ADR-0001 forbids anything resembling a locked control, and a greyed-out
"Resend" is exactly what a paid tier looks like from the merchant's side. A
control that does not exist yet is absent.

### 10. Assets, capability, and the front end

`manage_woocommerce` on every render, checked by the entry point itself and not
inferred from the menu having drawn a link — ADR-0017 §1 unchanged, extended to
two new entry points and the panel.

`Assets::is_our_screen()` becomes **strict equality against an enumerated set**
of this plugin's own registered hooks, plus the order screen for the panel's
stylesheet. It does not become a `strpos()`, which is the idiom that puts a
plugin's CSS on other plugins' pages and starts matching more screens the moment
somebody registers a similarly named one.

## Consequences

- Two new screen renders and one meta-box render join the gate-28 table, each
  with its capability check and the test that asserts it.
- Every history value joins the gate-31 table with its escaping function and its
  output context, and each is proven inert by a **direct write past the
  repository** — the `TargetLabels` lesson applied to a surface where the hostile
  value can arrive from a customer rather than from an administrator.
- The tombstone table gains one index and no columns. `claim()` is untouched.
- The purged, anonymised and empty states are three distinguishable sentences,
  asserted separately, and the retention note tells the truth about a purge that
  is not yet scheduled.
- Paging is deterministic across a shared timestamp, asserted by a test that
  writes the collision on purpose.
- The per-page statement count is fixed — five for the history screen, four for
  the panel — and asserted not to grow with the page size.

### Accepted residual risks (deliberately not fixed)

- **The mode filter and a common-status filter may filesort within their
  filtered set** (§6). Bounded by `LIMIT`. Tier 3.
- **The retention purge still has no scheduler** — pre-existing, recorded in
  `docs/p2-backlog.md` since Prompt 1a, and now *disclosed on the screen* rather
  than papered over (§4d). Tier 2; it is not this prompt's to build.
- **The order column shows the recorded `order_id`, not the WooCommerce order
  number.** They differ only when a sequential-order-number plugin is active, and
  resolving the display number is one order load per row (§7). The id is the
  value the tombstone actually holds.
- **The panel is asserted against the live storage mode of the test harness
  (HPOS) and, for the other mode, against the screen-id resolution and the
  `WP_Post` argument shape rather than a genuinely HPOS-disabled store.** The
  harness cannot flip a store-wide storage setting mid-suite without a
  synchronisation this suite has no way to perform. Stated plainly rather than
  claimed.
