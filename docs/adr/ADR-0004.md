# ADR-0004: Delivery identity and duplicate claims

Status: **Accepted** — 2026-07-25
Amended 2026-07-25 (Prompt 1a) — (a) split the identity into a durable,
never-purged tombstone vs a purgeable detail/attempt store; (b) fail-closed
atomic claiming by affected-rows, never by error-text parsing; (c) documented
transition-identity re-fire suppression.
Amended 2026-07-25 (Prompt 1b) — corrected the tombstone bound: lifetime is
bounded by ORDER lifetime (many tombstones per order), not "never outgrows the
orders table" (which is mathematically false).

## Context

Order lifecycle hooks fire more than once for the "same" logical event. A
status can be re-entered (processing → on-hold → processing), a transition can
double-fire in quick succession under load or from overlapping requests, and
delayed deliveries execute long after the trigger. Without a durable identity
per intended delivery, the plugin would send duplicate emails.

We need an identity that is:

- **Stable** across retries and delays of the *same* intended delivery.
- **Distinct** across genuinely different triggers on the same order/rule.
- **Race-safe** — the final protection against a duplicate must be the
  database, not application timing or the scheduler.

## Decision

### Automatic separate-mode uniqueness key

```
order_id | rule_id | mode | trigger_identity
```

This tuple is enforced by a **DB UNIQUE constraint** on the deliveries table.
It is the final race protection. A claim row is **inserted before any send
attempt**; if the insert violates the constraint, the delivery is a duplicate
and is suppressed.

### Trigger identity by type

- **Status trigger** → the status slug, e.g. `status:processing`. A status
  trigger therefore fires **once per order per rule even on status re-entry**
  (returning to `processing` yields the same `status:processing` identity,
  which is already claimed).
- **Transition trigger** → `"from>to"`, e.g. `transition:pending>processing`.
  A transition identity **repeats if the same transition occurs again later**
  (e.g. `pending>processing` reached a second time) and is therefore
  **suppressed** — once per order per rule is the intended semantic, identical to
  status re-entry.
- **Refund events** → `refund:{refund_id}` (the WooCommerce refund object id).
- **Delayed executions inherit the source trigger identity.** The delay is
  **never** part of the key — a delayed send of `status:completed` shares the
  identity of the trigger that scheduled it.

### What is NOT part of the key (audit columns)

`rule revision`, `recipient snapshot`, and `subject` are stored as **audit
columns** and are **never** part of the uniqueness key. In particular,
**including rule revision in the key is prohibited**: doing so would silently
re-arm already-processed orders after any rule edit (a new revision would form
a new, unclaimed identity), re-sending to customers who already received the
email.

### Durable identity (tombstone) vs purgeable detail

The uniqueness tuple lives in a **durable tombstone row** that is **NEVER purged
by retention** and **NEVER deleted by a privacy erasure**. The tombstone holds
**only identity/outcome fields**. The tombstone contains no direct contact or
message-content fields, but remains linked to an order and is retained to
prevent unintended duplicate automatic deliveries:

```
order_id, rule_id, mode, trigger_identity, first_claimed_at,
final_status, suppressed_count
```

**All personal and diagnostic detail** — recipient, subject, rendered snapshot,
failure text, debug explanation, and manual attempt records — lives in a
**separate purgeable detail/attempt store** that references the tombstone.

- **Retention** ([ADR-0005](ADR-0005.md)) and **privacy erasure** act **only on
  the detail store**. A privacy erasure **nulls the personal fields** in the
  detail store and **leaves the tombstone intact**.
- **Tombstone lifetime is bounded by order lifetime.** Multiple tombstones may
  exist per order (rules × status identities × transition identities × refund
  identities), but **all are removed when that order is permanently deleted**.
- **Rationale:** purging the identity would **silently re-arm old orders** — a
  status touch after the purge window would form an unclaimed identity and
  re-send to a customer who already received the email. The tombstone is the
  permanent memory of "this delivery already happened".

### Ordering, race protection, and fail-closed claiming

- The claim row is inserted with status `claimed`/`scheduled` **before any send
  attempt**.
- The **DB unique constraint is the final race protection.** Action Scheduler
  action uniqueness is **secondary** (a helpful early filter, never relied on
  for correctness).
- **Claiming is fail-closed and never parses error text.** Use a single atomic
  statement and discriminate purely by affected rows:

  ```sql
  INSERT ... ON DUPLICATE KEY UPDATE
    suppressed_count = suppressed_count + 1,
    last_seen_at     = VALUES(last_seen_at),
    id               = LAST_INSERT_ID(id)
  ```

  - affected rows **= 1** → **claimed** (proceed to send).
  - affected rows **= 2** → **duplicate** (suppress; **do not send**).
  - **any other outcome**, including `false`/failed query → **CLAIM FAILURE**:
    record `failed` and **DO NOT SEND**. **Fail closed, always.** The code must
    never infer success from an unrecognised error and must never inspect error
    strings. (`LAST_INSERT_ID(id)` makes the existing row's id available on the
    duplicate branch without a second query.)

### Manual sends / resends

Manual sends and resends are recorded as **linked attempt rows**
(`parent_delivery_id`, `attempt N`, `reason`) that live **outside** the
automatic uniqueness constraint. A human choosing to resend is an intentional
act and must not be blocked by the automatic idempotency key.

### Insert-mode identity

```
order_id | rule_id | native_email_id
```

Insert-mode records are an **aggregate row** carrying an attempt/send count.
**Intentional native-email resends DO include the injected content again** (if
a store owner re-sends the completed-order email, the inserted block re-appears
— that is desired). Within a **single render**, each rule inserts **at most
once**.

## Consequences

- Re-entering a status never re-sends: the identity is already claimed;
  duplicate attempts are suppressed (with a `suppressed_count` increment,
  [ADR-0005](ADR-0005.md)).
- A double-fire of the same transition in quick succession is blocked by the DB
  unique constraint on the second insert — not by timing — so it is safe under
  concurrency. Proven in POC-A.
- Editing a rule (new revision) never re-arms past orders, because revision is
  an audit column, not part of the key.
- Delaying a delivery does not change its identity, so the delayed send cannot
  duplicate the immediate one, and cancelling/rescheduling stays keyed to the
  original trigger.
- Refund-driven deliveries are keyed to the specific refund, so two partial
  refunds produce two distinct identities while a re-fired refund event for the
  same refund is suppressed.
- Manual resends are always possible because they are linked attempt rows
  outside the constraint; automatic idempotency and human intent do not
  collide.
- Insert-mode aggregation means the native email keeps one record per
  `(order, rule, native email)` while still counting repeated legitimate sends,
  and a single render never double-inserts the same rule's block.
- The identity survives retention purges and privacy erasures (tombstone), so a
  post-purge status touch is suppressed, never re-sent — while personal data is
  still fully erasable from the detail store.
- A malformed/failed claim query can never cause a duplicate send: an
  unrecognised outcome is treated as failure and nothing is sent.

- **2026-07-25 (Prompt 1a):**
  - **(a) Tombstone vs purgeable detail.** The uniqueness tuple now lives in a
    durable tombstone, holding no direct contact or message-content fields
    (`order_id, rule_id, mode, trigger_identity,
    first_claimed_at, final_status, suppressed_count`) that retention and privacy

    duplicate, anything else = failure → do not send). Why: never infer success
    from an unrecognised error; never parse error strings.
  - **(c) Transition re-fire.** Documented that a transition identity repeats and
    is suppressed if the same transition recurs — once per order per rule.
- **2026-07-25 (Prompt 1b):** Corrected the tombstone bound. "The table can never
  outgrow the orders table" is false — one order can carry many tombstones
  (rules × status × transition × refund identities). Correct statement: tombstone
  lifetime is bounded by **order** lifetime; all of an order's tombstones are
  removed when that order is permanently deleted. (Proven by POC-A's transition
  tests producing multiple distinct tombstones on one order.)
