# ADR-0006: Test-before-advertising compatibility

Status: **Accepted** — 2026-07-25
Amended 2026-07-25 (Prompt 1a) — the WooCommerce floor is PROVISIONAL until
matrix-tested; extended the "nothing stated as tested until tested" rule to
cover the version floor and third-party integrations, not just named claims.
Amended 2026-08-14 (Prompt 13) — **the version floors are SETTLED**: PHP, WordPress
and WooCommerce floors are now executed rather than asserted. See
"Settled version floors" below. The named-third-party rule is unchanged and no
integration has passed the matrix, so the interim wording still governs.

## Context

Email-customizer plugins (YayMail, VillaTheme Email Template Customizer,
Kadence Email Designer, ThemeHigh Email Customizer, and others) hook the same
WooCommerce email rendering pipeline this plugin injects into. Claiming
compatibility with a named product we have not actually tested is both a
support-cost trap and, on WordPress.org, a credibility/guideline risk: a broken
"works with X" claim generates one-star reviews and support tickets we cannot
close. Compatibility must be **earned by testing**, then advertised — never
advertised on hope.

## Decision

**No named third-party compatibility claim** appears in `readme.txt` or any
marketing **before** it passes the test matrix below.

### Compatibility test matrix

- **Default WooCommerce email templates.**
- **WooCommerce "email improvements" toggle** — tested in **both** states
  (on and off).
- **Block email editor flag** — tested **on** where available on the runtime.
- **Free tiers** of: **YayMail**, **VillaTheme Email Template Customizer**,
  **Kadence Email Designer**, **ThemeHigh Email Customizer**.

A named product may be listed as "tested/compatible" only after it passes this
matrix, and each integration is documented **individually** (per product,
per WooCommerce email mode).

### Approved interim wording

Until a named integration passes, `readme.txt` and marketing use exactly this
wording (and nothing that names an untested third party):

> Uses WooCommerce's native email system and is designed for compatibility with
> WooCommerce email customizers; tested integrations are documented
> individually.

## Settled version floors (Prompt 13, 2026-08-14)

Every number below was produced by **executing the full suite**, not by reading
source. Where a suite run is cited it is the integration suite (853 tests /
16,132 assertions) plus the unit suite (627 tests / 10,605 assertions).

### PHP — floor 8.0, tested 8.0 through 8.4

The full suite was executed on five runtimes. Docker and a CI runner were both
unavailable on the build machine (no Docker, no `gh`, no sudo, and the
distribution ships only PHP 8.3), so self-contained static PHP builds were used
for every version other than the system one.

| PHP | Unit | Integration |
| --- | --- | --- |
| 8.0.30 | 627 / 10,605 | 853 / 16,132 |
| 8.1.34 | 627 / 10,605 | 853 / 16,132 |
| 8.2.32 | 627 / 10,605 | 853 / 16,132 |
| 8.3.6 (system) | 627 / 10,605 | 853 / 16,132 |
| 8.4.23 | 627 / 10,605 | 853 / 16,132 |

Identical totals on every version. `Requires PHP: 8.0` is therefore a tested
claim, and the ADR-0001 target range (8.0–8.4) is proven rather than held by
`PHPCompatibilityWP` static analysis alone.

### WooCommerce — floor RAISED from the provisional 8.2 to **9.6**

The POC-E floor of 8.2 is **withdrawn**, and the first candidate replacement
(8.9, which would have aligned with the sibling plugin) is withdrawn with it.
Both were withdrawn because the suite was **run** at them and failed.

#### The binding constraint: `WC_Email::$placeholders` visibility

`Delivery\RulePreview::render_insert()` reads and writes `$email->placeholders`
on the live registered native `WC_Email` object — it captures the value, merges
`{order_date}` and `{order_number}` into it so the native template renders them,
and restores it in a `finally`.

**That property is `protected` in WooCommerce up to and including 9.5, and
`public` from 9.6.** Verified by reading `includes/emails/class-wc-email.php` in
the real release archives:

| WC | `$placeholders` |
| --- | --- |
| 8.2.0 | `protected` |
| 8.9.0 | `protected` |
| 9.0.0 | `protected` |
| 9.2.0 | `protected` |
| 9.4.0 | `protected` |
| 9.5.0 | `protected` |
| **9.6.0** | **`public`** |
| 11.0.1 | `public` |

Below 9.6 the access throws
`Error: Cannot access protected property WC_Email_Customer_Processing_Order::$placeholders`.
`compose()` catches every `Throwable`, so it is **not** a fatal in the merchant's
admin — the preview screen refuses with `render_failed` and the exception goes to
the WooCommerce log. Reproduced directly at WC 8.9.0, and it is what failed two
integration tests there.

**The blast radius is the preview screen only.** `->placeholders` appears in
exactly one file in the whole plugin (`RulePreview.php`, four lines). Every other
`$this->placeholders` in `src/` is this plugin's own property on its own classes
(`Render\Injector`, `Delivery\Orchestrator`). **No delivery path touches it**, so
nothing about sending, scheduling, consolidating or recording changes below 9.6 —
what breaks is previewing an insert-mode rule.

That is still a floor: a documented feature that refuses on a screen is not a
feature this plugin may claim at that version.

#### The same version, independently, for the preview signals

9.6 is also where `woocommerce_is_email_preview`, the
`woocommerce_prepare_email_for_preview` filter and the `EmailPreview` class first
appear — unsurprisingly, since making `$placeholders` public is what core needed
for its own `EmailPreview::set_email_type()`. So the two arguments converge on one
number rather than competing.

#### Alignment with the Address Book plugin is NOT possible, and that is correct

The sibling Extonify Address Book plugin declares `WC requires at least: 8.9`.
Matching it was the open recommendation from the Prompt 1a amendment, and it is
**rejected**: this plugin has a hard 9.6 dependency the Address Book plugin does
not have, and ADR-0006's own rule is that a floor may not be lowered to match.
A merchant running both is bound by the higher of the two, which is this one.

#### The preview SIGNALS, separately, degrade cleanly

The three preview *signals* are feature-detected and would have degraded fine on
their own — they are not what sets the floor; `$placeholders` is. Below 9.6 there
is no core email preview feature at all, so there is nothing to coordinate with:

- `RenderContext::core_signal_available()` is a `class_exists()` check that
  returns false, and `core_preview_signal()` short-circuits to false. The render
  context then classifies previews using **this plugin's own render-scoped
  marker**, which ADR-0013 §5 already treats as the trustworthy signal — core's
  is the one that can leak.
- `RenderEvents` registers a filter on `woocommerce_prepare_email_for_preview`.
  Registering a callback for a hook that never fires is a no-op.
- `Delivery\RulePreview::as_preview()` **adds** `woocommerce_is_email_preview`
  rather than reading it, so that third parties see a preview as a preview.
  Adding a filter nobody reads is also a no-op.

What those three would cost below 9.6 is interoperation with a core feature that
does not exist at that version — real, verified in code, and survivable. The
`$placeholders` access above is the one that is not survivable, and it is what
the floor is set by.

`woocommerce_pos_email_footer` is the clean-degradation shape too — the POS
receipt templates it backstops only exist in WooCommerce 11.x.

⚠ **The lesson for future work: "feature-detected" was checked for the classes
and hooks and not for a PROPERTY'S VISIBILITY.** Every class and function this
plugin calls was guarded or verified present. A `public`/`protected` change on a
property of a class the plugin extends is the same kind of API break and had no
guard, because nothing in the codebase's review habits looked for one. Any future
direct property access on a WooCommerce object must be version-checked the same
way a function call is.

#### Tested corners

| Corner | WordPress | WooCommerce | PHP | HPOS | `email_improvements` | Permalinks |
| --- | --- | --- | --- | --- | --- | --- |
| Current release | 7.0.4 | 11.0.1 | 8.0 / 8.1 / 8.2 / 8.3 / 8.4 | on | on | pretty |
| Floor | 6.6.2 | 9.6.0 | 8.0 | off | off | plain |

The two corners are complementary rather than merely far apart: the floor corner
runs **classic post-based order storage** with `email_improvements` **off** and
**plain permalinks**, and the current corner runs HPOS with `email_improvements`
on and pretty permalinks. Between them both order-storage modes and both states of
the `email_improvements` toggle are executed. `block_email_editor` is off in both.

A rejected corner is recorded too, because the rejection is the evidence: the
suite was run at **WordPress 6.5.5 / WooCommerce 8.9.0 / PHP 8.0** and produced
**9 failures**, including the two that exposed the `$placeholders` break. That run
is why the floor is 9.6 and not 8.9.

#### ⚠ The floor corner is NOT fully green, and that is stated rather than tuned away

Three runs, each isolating one variable:

| Run | WP | WC | HPOS | Permalinks | Failures |
| --- | --- | --- | --- | --- | --- |
| A | 6.5.5 | 8.9.0 | off | plain | **9** |
| B | 6.6.2 | 9.6.0 | off | plain | **5** |
| C | 6.6.2 | 9.6.0 | on | pretty | **3** |

A → B removed exactly the four preview failures, which is what pins them to
`$placeholders`. B → C removed exactly the two `PlaceholderTest` failures, which
pins those to **plain permalinks**: the body correctly carries `&amp;` in a URL
that only contains a query separator when permalinks are plain, and the assertion
compares against the raw form. The plugin is right there and the test is naive.

The **three that remain at run C are WooCommerce-version differences, not plugin
defects**, and each is recorded in `docs/p2-backlog.md` with its measurement:

1. a 10-item order costs 95 queries at 9.6 against a 60-query bound measured at
   11.0.1 — same plugin query pattern, cheaper WooCommerce internals in 11.x;
2. WooCommerce's variable-product delete cascade changed between 9.6 and 11.0.1,
   so a deleted variation reports itself read at 9.6 and hollow at 11.0.1 — the
   test's tripwire fired correctly;
3. refunding every item flips the order status at 9.6, so the cancellation is
   recorded as `order_state` rather than `items_refunded` — **the delivery is
   cancelled either way**, only the recorded reason differs.

So: **the suite passes in full at the current release and has three
version-sensitive assertion failures at the floor.** Making those assertions
version-aware is required work, filed in the backlog. It was deliberately not
done in this prompt, because loosening a deliberate tripwire in the same pass
that needs it green is how a real upstream change gets waved through.

### WordPress — floor RAISED from 6.5 to **6.6**, tested up to 7.1

Nothing in the plugin's own code constrains the WordPress floor above 6.5: it
registers admin screens, list tables, an AJAX endpoint, the privacy
exporter/eraser hooks and WooCommerce email hooks, all of which long predate 6.5.

**The raise is forced by the WooCommerce floor, not by this plugin.**
WooCommerce 9.6 declares `Requires at least: 6.6`. With the WooCommerce floor at
9.6, "WordPress 6.5" describes a store that cannot run a supported WooCommerce, so
declaring it would be advertising a combination that cannot exist. `Requires at
least: 6.6` is executed at the floor corner (WordPress 6.6.2). `Tested up to: 7.1`
is executed on the **development install** (WordPress 7.1), which is where gate 4's
canonical run happens; the current corner (WordPress 7.0.4) executes the full suite
too, so 7.0 and 7.1 are both covered rather than 7.1 replacing 7.0.

⚠ **The claim was raised from 7.0 to 7.1 in Prompt 13C Part D, and only because the
evidence for 7.1 already existed.** The development install auto-updated 7.0.4 → 7.1
mid-round — recorded as an environment hazard in `docs/p2-backlog.md`, not as a
convenience — and the full unfiltered suite has since run on 7.1 twice: Part C
(888 tests, one expected stale-archive failure) and Part D's canonical gate 4 run
(**888 tests, 16 687 assertions, zero failures**). Under this ADR's own
test-before-advertising rule that is what earns the number. Plugin Check reported
`outdated_tested_upto_header` as an **ERROR** while the readme still said 7.0, which
is what prompted the check — but the check is what justifies the change, not the
error.

### Still untested, and therefore still unclaimed

- **`block_email_editor` on.** Off in both tested corners. Named as a first-class
  matrix axis above; it remains unexecuted.
- **`email_improvements` off on a WooCommerce version that HAS the flag.** The
  floor corner is "off" only because 8.9 predates the flag entirely, which is not
  the same test.
- **Every named third-party email customizer.** No integration has passed the
  matrix, so the interim wording below is what `readme.txt` uses.
- **Multisite.** Network activation is refused by design and has never been
  exercised on a real multisite install.

## Consequences

- The readme may state the plugin uses WooCommerce's native email system and is
  *designed for* compatibility, but may not assert "works with YayMail/Kadence/
  etc." until each has passed the matrix.
- Each passed integration is documented on its own (which WooCommerce email mode,
  which customizer version tier), so a claim is always traceable to a test.
- The "email improvements" toggle and the block email editor are first-class
  matrix axes, because they change the rendering pipeline our injection depends
  on; a claim that holds in one mode is not assumed to hold in the other.
- This ADR gates *marketing claims*, not code: the plugin still technically
  functions with these customizers by virtue of using native hooks
  ([ADR-0002](ADR-0002.md), [ADR-0003](ADR-0003.md)); it simply does not
  *advertise* a named integration until proven.
- No paid tiers of the customizers are required to be tested (the plugin is
  free, [ADR-0001](ADR-0001.md)); the matrix targets the free tiers users
  actually install.
- ~~**The WooCommerce version floor is PROVISIONAL until matrix-tested.**~~
  **SETTLED 2026-08-14 (Prompt 13)** — see "Settled version floors" above. The
  floor is **9.6**, executed at WordPress 6.6.2 / PHP 8.0 with HPOS off. POC-E's
  8.2 is withdrawn, and so is the 8.9 that would have aligned with the sibling
  plugin: `WC_Email::$placeholders` is protected until 9.6, and the insert-mode
  preview reads it. The alignment question the Prompt 1a amendment left open is
  closed as **not possible** — the Address Book plugin's 8.9 cannot be matched
  without claiming a version this plugin's preview does not work on. The general
  rule is unchanged and is what produced this outcome: **no compatibility claim,
  version floor, or third-party integration may be stated as tested until it
  actually is.**

## Amendment history

- **2026-08-14 (Prompt 13):** Settled all three version floors by execution.
  PHP 8.0–8.4 each ran the full suite (identical totals on every version), so
  `Requires PHP: 8.0` stops being a static-analysis claim. The WooCommerce floor
  rose from the provisional 8.2 to **9.6**, and the WordPress floor from 6.5 to
  **6.6** in consequence. Why 9.6: `WC_Email::$placeholders` is `protected` up to
  9.5 and `public` from 9.6, and `RulePreview::render_insert()` accesses it
  directly, so insert-mode preview refuses on every earlier version. That was
  found by **running** the suite at WordPress 6.5.5 / WooCommerce 8.9.0, which
  failed 9 tests — not by reading source, which is exactly the point of the
  matrix. Two premises were disproved on the way: that the preview depends on the
  9.6 preview *signals* (it does not — those are cleanly feature-detected), and
  that 8.9 could be a floor at all (it cannot, so alignment with the sibling
  Address Book plugin is impossible rather than merely declined).
- **2026-07-25 (Prompt 1a):** Extended "test before advertising" to explicitly
  cover the **version floor** and **third-party integrations**, not just named
  compatibility claims. Recorded the POC-E floor (8.2) as **provisional** and
  noted the open option to align with the Address Book plugin's floor, deferred
  to the release matrix phase. Why: a floor asserted from one runtime observation
  is not a tested guarantee and must not be presented as one.
