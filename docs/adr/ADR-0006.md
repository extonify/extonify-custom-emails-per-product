# ADR-0006: Test-before-advertising compatibility

Status: **Accepted** — 2026-07-25
Amended 2026-07-25 (Prompt 1a) — the WooCommerce floor is PROVISIONAL until
matrix-tested; extended the "nothing stated as tested until tested" rule to
cover the version floor and third-party integrations, not just named claims.

## Context

Email-customizer plugins (YayMail, VillaTheme Email Template Customizer,
Kadence Email Designer, ThemeHigh Email Customizer, and others) hook the same
WooCommerce email rendering pipeline this plugin injects into. Claiming
compatibility with a named product we have not actually tested is both a
support-cost trap and, on WordPress.org, a credibility/guideline risk: a broken
"works with X" claim generates one-star reviews and support tickets we cannot
close. Compatibility must be **earned by testing**, then advertised — never
advertised on hope.

## Decision

**No named third-party compatibility claim** appears in `readme.txt` or any
marketing **before** it passes the test matrix below.

### Compatibility test matrix

- **Default WooCommerce email templates.**
- **WooCommerce "email improvements" toggle** — tested in **both** states
  (on and off).
- **Block email editor flag** — tested **on** where available on the runtime.
- **Free tiers** of: **YayMail**, **VillaTheme Email Template Customizer**,
  **Kadence Email Designer**, **ThemeHigh Email Customizer**.

A named product may be listed as "tested/compatible" only after it passes this
matrix, and each integration is documented **individually** (per product,
per WooCommerce email mode).

### Approved interim wording

Until a named integration passes, `readme.txt` and marketing use exactly this
wording (and nothing that names an untested third party):

> Uses WooCommerce's native email system and is designed for compatibility with
> WooCommerce email customizers; tested integrations are documented
> individually.

## Consequences

- The readme may state the plugin uses WooCommerce's native email system and is
  *designed for* compatibility, but may not assert "works with YayMail/Kadence/
  etc." until each has passed the matrix.
- Each passed integration is documented on its own (which WooCommerce email mode,
  which customizer version tier), so a claim is always traceable to a test.
- The "email improvements" toggle and the block email editor are first-class
  matrix axes, because they change the rendering pipeline our injection depends
  on; a claim that holds in one mode is not assumed to hold in the other.
- This ADR gates *marketing claims*, not code: the plugin still technically
  functions with these customizers by virtue of using native hooks
  ([ADR-0002](ADR-0002.md), [ADR-0003](ADR-0003.md)); it simply does not
  *advertise* a named integration until proven.
- No paid tiers of the customizers are required to be tested (the plugin is
  free, [ADR-0001](ADR-0001.md)); the matrix targets the free tiers users
  actually install.
- **The WooCommerce version floor is PROVISIONAL until matrix-tested.** POC-E's
  recommended floor (8.2) is a single-combination observation, not a tested
  guarantee. **No compatibility claim, version floor, or third-party integration
  may be stated as tested until it actually is.** There is an open recommendation
  to align the final floor with the sibling Extonify Address Book plugin's floor
  to reduce suite-wide test burden; that decision is **deferred to the release
  matrix phase**.
