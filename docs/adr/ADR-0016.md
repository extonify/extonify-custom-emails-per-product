# ADR-0016: Consolidation — one decision, N messages

Status: **Accepted** — 2026-08-06

## Context

`consolidation` is the last column carrying behaviour no phase implements. It has
existed since schema v1, has been validated by *shape* since Prompt 5B
([ADR-0009](ADR-0009.md)), and has been filtered out of every phase since Prompt
5C — so a merchant can store a value and the rule is left entirely untouched
([ADR-0012](ADR-0012.md) §9, [ADR-0013](ADR-0013.md) §8a,
[ADR-0015](ADR-0015.md) §7).

Giving it behaviour is different in kind from every prompt before it. Delay
changed *when* a message is sent. Insert mode changed *whose* message carries the
content. Consolidation changes **how many messages one delivery identity
produces** — and the delivery identity is
[ADR-0004](ADR-0004.md)'s duplicate-suppression key. Every previous feature could
be built without touching it. This one cannot be built without answering it, so
that answer comes first and everything else follows from it.

The locked v1.0 requirement is *smart mixed-cart merging*: an order containing
three products that three rules match must not produce a storm of near-identical
emails. That is what `none` already does — one message per rule per trigger, all
matched items combined. The requirement is therefore already met, and
consolidation exists to offer the **opposite** choice deliberately: a merchant
who wants one message per product, per product, can ask for it.

## Decision

### 1. The vocabulary is EXHAUSTIVE, and it has exactly two members

| Value | Meaning |
|---|---|
| `none` (default) | one message per rule per trigger, every matched item combined — the behaviour already shipped |
| `per_product` | one message per **distinct matched product identity** (§4) |

`Delivery\Consolidation::MODES` is that list, and it is **closed**. The storage
boundary moves from shape validation to this enumeration, validated on the **RAW**
value per [ADR-0009](ADR-0009.md)'s classification: `daily`, `weekly` and
`per_order` are now **invalid values, not merely unimplemented ones**, and a write
carrying one is refused entirely — `insert()` returns `0`, `update()` returns
`false`, and any existing row is left byte-identical.

That is a real strengthening rather than a relabelling. Under shape validation
`daily` was storable and the *phase filter* was the only thing preventing it from
being delivered as `none` under another name; a single missing filter turned a
merchant's digest request into an email per order. Under an enumeration the value
cannot exist, so no filter has to remember it.

The `[a-z0-9_-]+` / `MAX_CONSOLIDATION_LENGTH` shape rules stay in place as the
*first* test rather than the only one, for the reason
`is_well_formed_native_email_id()` keeps its length bound: a value that passes the
enumeration necessarily passes the shape, and keeping the shape check makes the
`varchar(20)` column's own width impossible to exceed even if the enumeration
grows carelessly.

> **`per_order` — cross-rule merging — is deliberately EXCLUDED from v1.0.**
> It is not a third value of this column; it is a different feature. It merges
> across *different delivery identities* with different subjects, recipients,
> priorities and rule revisions, which means answering: whose subject does the
> merged message carry, which tombstone owns it, what happens when one of the
> merged rules is disabled between the trigger and the send, and how a
> per-identity `final_status` is reported for a message that has no single
> identity. None of those questions has an answer in this ADR, and inventing one
> under a value in this enumeration would be designing that feature by accident.
>
> **Adding it later requires a superseding ADR**, not an extra member here.

### 1a. An unrecognised stored value makes the rule NOT DELIVERABLE

> ⚠ **THIS CLAUSE REPLACES THE ORIGINAL §1a, WHICH WAS WRONG.** The superseded text
> read:
>
> > *"It plans **one combined message** — `none`'s behaviour — and records a note
> > naming the unrecognised value. This is defence in depth, **not** a repair in
> > ADR-0009's sense … Leaving the rule inert would silently send **nothing** — and a
> > rule that is configured, active and matching but invisible is the exact failure
> > ADR-0009 cites when explaining why `insert_position` repairs."*
>
> It was wrong on two counts, and writing it down as a decision made it worse than
> leaving it undecided.
>
> **Sending is not defence in depth.** Defence in depth is an extra BARRIER behind a
> failed one. Planning a message is not a barrier — it is a delivery the merchant
> never configured, with a note attached. The merchant asked for a digest; the
> customer got a standalone email. A note explaining that does not make it correct.
>
> **And "direct SQL only" was factually untrue.** `daily`, `weekly` and `per_order`
> were **legitimately storable** under the shape validation that shipped from Prompt
> 5B to Prompt 8. Any rule created — or created by a test — while that vocabulary was
> open still holds one, in an ordinary database, with no direct SQL anywhere. So the
> case the old clause dismissed as exotic is the ordinary upgrade path.
>
> The `insert_position` analogy was also misapplied. That column repairs because
> **every value in its set puts the same content in the same email for the same
> order** — only the location differs, so there is no different-valid-target failure
> available. `consolidation` decides **how many emails a customer receives**. The two
> are not the same kind of column, and reasoning from one to the other is what
> produced this clause.

**A rule whose `consolidation` is outside `Consolidation::MODES` is NOT DELIVERABLE.**
It creates no claim, sends no mail, schedules no job, writes no delivery record, and
**does not participate in `stop_processing`**.

The last clause is the one that made this Tier 1 rather than merely wrong.
`Orchestrator::deliverable_in_this_phase()` checked mode, delay and
`behaviour_is_implemented()` — and §9 emptied that enumeration, so it returns `true`
for everything. With no vocabulary check, an invalid rule **entered `RuleMatcher`**,
and a matching invalid rule carrying `stop_processing` **halted every lower-priority
rule behind it**. The customer received an email the merchant never configured *and*
lost the one they did. Refusal therefore happens **before evaluation**, in every
separate-mode phase, which is the only position from which a rule cannot halt
another.

Enforced in four places, deliberately:

| Where | What it stops |
|---|---|
| `RuleRepository::write_is_valid()` on the **effective** value | a legacy invalid row being re-saved unchanged by an unrelated edit |
| `Orchestrator::deliverable_in_this_phase()` | delivery, and halting, in the immediate phase |
| `ScheduledPhase::owns()` | queueing a job that could only cancel itself later |
| `ScheduledDelivery` §4 re-validation | a rule that became invalid *during* a delay |

**A legacy invalid row is correctable, and only correctable.** Supplying `none` or
`per_product` explicitly is accepted; any other write leaves the row byte-identical.
That is the ADR-0009 refuse-never-repair contract applied to data that predates the
contract: the plugin will not guess which behaviour the merchant meant, and it will
not deliver until they say.

#### The distinction this ADR must keep separate

**Unimplemented behaviour** and an **invalid value** are different mechanisms with
different lifetimes, and merging them would eventually disable the second:

| | Unimplemented behaviour | Invalid value |
|---|---|---|
| Mechanism | `UNIMPLEMENTED_BEHAVIOUR_DEFAULTS` (§9) | `Consolidation::is_valid()` — the read boundary |
| Means | *nobody has built this yet* | *this data is corrupt* |
| Lifetime | shrinks to nothing as features land — **it is empty now** | **permanent**; a vocabulary always has an outside |
| Applies to | a value the column legitimately holds | a value the column must never hold |

They are checked by two separate calls at each phase filter, with the comment saying
which is which. Folding the vocabulary check into `behaviour_is_implemented()` would
have looked like tidying and would have meant that **emptying the enumeration
silently switched the corruption check off** — which is exactly how this defect got
in.

⚠ `Consolidation::plan()` stays **total** — handed an invalid value it still returns
one combined message with a recorded note. That is now genuinely defence in depth,
because there is a barrier in front of it: the phase filters. The planner is pure and
has no way to refuse, so its safest total behaviour is the one that neither guesses a
count nor returns an empty plan a caller might read as "nothing to send". It is
unreachable from the delivery path by construction, and gate 26 asserts that.

### 2. Consolidation is separate-mode only, refused at the repository boundary

`per_product` means "one email per product". **Insert mode contributes content to
an email WooCommerce is sending**, so the number of messages is not this plugin's
to choose — WooCommerce already decided it, once, before any rule was consulted.
An insert rule asking for `per_product` is asking for something that does not
exist.

It is therefore **refused at the repository boundary**, exactly as a non-zero
`delay_seconds` already is under [ADR-0013](ADR-0013.md) §2. Same precedent, same
mechanism, no new one:

- the check reads the **effective** mode and the **effective** consolidation — from
  the write when it supplies them and from the stored row otherwise — so a partial
  update that changes only one of the two is still judged against the rule's real
  state;
- converting a stored `separate` + `per_product` rule to `insert` in one
  `update()` is refused, rather than having its consolidation quietly reset. A
  merchant whose editor says "one email per product" and whose behaviour says
  otherwise is the coercion failure ADR-0009 exists to prevent;
- `sanitize()` additionally **forces** `consolidation = 'none'` on an insert-mode
  write, bypassing the partial-update key list for the same reason it already
  forces the trigger columns and the delay. That is completeness, not repair: the
  refusal above means it only ever writes the `none` that was already true.

The insert-mode fetch (`find_active_for_native_email()`) keeps `consolidation =
'none'` in its `WHERE` clause, and that literal is now **insert mode's own
requirement under this ADR** rather than a read of the unimplemented-behaviour
list — the same move `delay_seconds = 0` made in Prompt 7.

### 3. THE LOAD-BEARING DECISION: fan-out happens under ONE claim, and ADR-0004 is unchanged

> **The tombstone remains the unit of DECISION: this rule fired for this order on
> this trigger, once, ever. Consolidation fans that one decision into N MESSAGES,
> recorded as N attempt rows beneath the same tombstone. The uniqueness key
> `order_id | rule_id | mode | trigger_identity` is untouched.**

Consequences, each recorded because each is a question somebody will ask:

- **Duplicate protection is unchanged.** A re-fired trigger is suppressed by the
  same atomic claim whether the rule sends one message or five. The second claim
  increments `suppressed_count` and nothing is sent — the fan-out is not reached,
  because the fan-out lives *after* the claim.
- **No schema change, no new identity component.** The unique index is the same
  index. Nothing about the message count enters the key, and nothing may: a key
  that included it would let a rule edited from `none` to `per_product` re-send to
  every order it had already served, which is precisely why ADR-0004 prohibits
  `revision` in the key.
- **A product added to the order AFTER the trigger gets no message.** The decision
  already happened; the fan-out expands that decision, it does not re-take it.
  This is the existing once-per-order-per-rule semantics
  ([ADR-0004](ADR-0004.md)), not a new limitation, and it is written down here so
  nobody reads it as a bug. A merchant who needs the later product covered has the
  same remedy they already had for `none`: a trigger that fires after the order is
  complete.
- **The claim is still taken before anything is sent.** Fan-out changes nothing
  about ordering: claim, then plan, then send. A claim failure still sends nothing
  at all — not one message of N (ADR-0012 §3).

The rejected alternative was **one claim per message**, keyed by adding the unit to
the identity. It fails on ADR-0004's own terms: the identity would then contain a
fact about the ORDER'S CONTENTS, so an order whose items changed would form
unclaimed identities and re-send, and a rule switched between the two
consolidation values would re-send everything. Fan-out is a delivery concern and
stays entirely below the identity.

### 4. The fan-out unit: the distinct matched PRODUCT IDENTITY

Stated precisely, because variations make "product" ambiguous:

| Matched item | Unit |
|---|---|
| simple product | `product:{product_id}` |
| variation, resolved | `variation:{variation_id}` — distinct from its parent AND from its siblings |
| variation, `partially_resolved` (variation deleted, parent alive) | `product:{product_id}` — **falls back to the parent** |
| neither id present (defensive) | `item:{item_id}` — never merges two unrelated items |

Two line items of the same product produce **ONE** message. Quantity produces
**ONE** message. Both follow from [ADR-0011](ADR-0011.md) §3: quantity and
duplicate line items are irrelevant to matching, and they must stay irrelevant
here — a rule that matched once cannot become five emails because a customer
bought five.

**Why a partially resolved variation falls back to the parent.** ADR-0011 §4's
third resolution state exists because a deleted variation's *own* facts are no
longer knowable while its identity still is. A unit is a thing a message is
*about*, and a message about a variation nobody can identify has nothing to say
that distinguishes it from its parent. Two partially resolved variations of one
parent therefore collapse into one message, which is correct: neither can be told
from the other. A partially resolved variation alongside a *live* sibling produces
two units — `variation:{live}` and `product:{parent}` — which is also correct, and
is stated here because it looks asymmetric until you notice that only one of them
is identifiable.

⚠ **The resolution state is read from the matched record, never re-derived.** The
scheduled path builds its records from `WC_Order_Item_Product::get_variation_id()`,
which returns **0** for a deleted variation on WC 10.9.4 — the behaviour ADR-0011
§4 flags, where `set_props()` swallows the setter's exception while `_variation_id`
survives in item meta. That path therefore reaches the parent unit *by a different
route* than the immediate path does, and lands on the same answer. The planner
consults `resolution` when the record carries it and treats its absence as
resolved, so neither path depends on the other's quirk.

**Ordering is deterministic: line-item order.** Units appear in first-seen order
over the matched items, which are themselves in line-item order (ADR-0011 §5). The
same order therefore always produces the same sequence of messages, which is what
makes the fan-out testable and makes "message 2" a meaningful thing to say in a
log.

### 5. Each message is contained individually; the tombstone aggregates

**Containment is per message.** One message's failure must not abort the
remaining messages — the Prompt 6A containment pattern
([ADR-0014](ADR-0014.md) §10), applied per message rather than per delivery. A
`\Throwable` while resolving message 2 is caught, recorded against message 2, and
messages 1 and 3 still send. Nothing escapes into
`woocommerce_order_status_changed`.

**Every message writes its own attempt rows, with its own true outcome.** One row
per recipient per message, exactly as a single delivery already writes one row per
recipient — so a fan-out of 3 to a customer and a CC writes 6 rows. Never a joined
list: the privacy eraser finds rows with `WHERE recipient = %s`
([ADR-0009](ADR-0009.md)).

**The tombstone's `final_status` is the AGGREGATE:**

| Message outcomes | `final_status` |
|---|---|
| all `sent` | `sent` |
| **any** `failed` | `failed` |
| at least one `sent`, rest `skipped` | `sent` |
| all `skipped`, none attempted | `skipped` |

⚠ **The third and fourth rows are an EXTENSION, stated rather than assumed.** The
rule as first written was "all sent → `sent`; any failure → `failed`; none sent →
`failed`", which considers two outcomes. There is a third: a message can be
`skipped` — the per-delivery `woocommerce_email_enabled_{id}` filter declining it
(ADR-0012 §5a), or no recipient surviving header sanitisation. Folding a skip into
`failed` would report a *deliberate third-party refusal* as a transport failure,
which is the exact defect ADR-0012 §5a was written to remove, reached through a
different column. `skipped` is already a member of
`DeliveryRepository::FINAL_STATUSES`, so the honest answer is available and is
used. "None sent → `failed`" holds unchanged wherever a message was actually
attempted.

**The per-message rows are where the detail lives.** A merchant asking *which one
failed* reads the attempt rows: each carries its own `state`, its own `subject`
(which for a `{product_name}` subject differs per message), and its own
`snapshot.consolidation` naming the unit, the index and the count. The aggregate
answers *did this delivery work*; it deliberately cannot answer *which message*,
and does not pretend to.

**⚠ The fan-out axis is `snapshot.consolidation`, NOT the `attempt` column.** The
`attempt` column means "attempt N at this delivery" — ADR-0004's manual resend
chain. The N messages of a fan-out are not retries of one another; they are one
attempt at one decision, expressed as N messages. Overloading `attempt` with the
message index would put two orthogonal facts in one column, which is the failure
shape this project has now hit three times (`not_rendered` overwriting the message
outcome, ADR-0014 §10c; a boolean merging "another actor won" with "the write
failed", ADR-0015 §8.1a; a truthy filter return read as consent, ADR-0014 §6.5).
The message index gets its own axis.

**Finalisation happens ONCE, after the last message.** Not per message: a
per-message finalise would make the tombstone hold whichever outcome was written
last, so `{failed, sent}` would report `sent` and lose the failure. The attempt
rows are still written *as each message completes*, because a row is evidence of a
side effect that has already happened and suppressing it would delete the only
record of a real email (ADR-0015 §8.9). If the aggregate finalisation itself
throws, the outer containment boundary records a delivery-level failure and
finalises — an extra diagnostic row is a better outcome than a consumed identity
stranded in `claimed`.

### 6. Placeholders bind to the message's OWN product

`{product_name}` in a `per_product` message resolves to **that message's product**,
not the first matched item. This is the same axis-binding problem
[ADR-0014](ADR-0014.md) §5a solved for the per-item insert position, on a different
axis, and it reuses the same mechanism: the message's value set is opened bound to
its unit's representative line item, and `PlaceholderValues::scoped_item()` already
resolves the singular item placeholders against the bound item.

Bound to the message's unit:

`{product_name}`, `{product_sku}`, `{product_quantity}`, `{product_url}`,
`{variation_name}`, `{variation_attributes}`, `{item_custom_field:key}`

**The representative line item is the unit's FIRST matched item in line-item
order**, and all seven bind to that same item. Where a unit spans two line items
of one product, `{product_quantity}` is therefore that line's quantity, not the
sum. Summing was rejected: `{item_custom_field:key}` cannot be summed at all — a
gift note belongs to one line — so a summing `{product_quantity}` would produce a
message whose quantity described the whole product while its meta described one
line of it. Seven placeholders describing **the same line item** is coherent; six
describing one line and one describing something else is not. One binding, one
answer.

⚠ **One value set per message, never one reused across messages.** The set
memoises by `name:parameter`, so a shared set would answer message 2 with message
1's memoised `{product_name}` — the ADR-0014 §5a defect reintroduced through the
cache. This is the same rule §5a already states for the per-item position and it is
restated because it is the single most likely way to get this feature subtly wrong.

**The PLURAL forms still list ALL matched products.** `{product_names}` and
`{matched_product_list}` are unchanged in a `per_product` message: they enumerate
every product the rule matched on the order, in every message.

A merchant writing `{product_names}` asked for the whole set — that is what the
placeholder is named for and what it means in every other context. Narrowing it to
the message's own product would make it a duplicate of `{product_name}` with a
misleading name, and would leave no way at all to say "here is your care guide for
the linen shirt, and by the way your order also contained these". The set is
therefore the same in all N messages and only the singular forms move. This is
recorded either way rather than left to be discovered.

⚠ **And the cap fallback does not change that** — §7a states it explicitly. The plural
forms keep meaning the whole matched set in every section that renders the body; what
the fallback bounds is **how many times the body is rendered**, never what a placeholder
inside it means.

**Recipient placeholders are unaffected**, and this is what makes recipient
resolution a once-per-delivery cost rather than a per-message one: ADR-0014 §7
limits recipient placeholders to `{customer_email}` and `{store_email}`, neither of
which is product-scoped. Every message in a fan-out is addressed identically, so
recipients are resolved **once**, before the fan-out, and an unusable recipient
document produces **one** skip for the whole delivery rather than N.

**`Custom_Email::$matched_items` keeps the WHOLE decision's items, unchanged.** That
property describes the DECISION — one per rule per trigger — and nothing currently
renders it; giving it a per-message meaning would put two facts in one field for the
sake of something no template reads, which is the failure shape §5 already refuses
for the `attempt` column. A message's own scope is carried by the placeholder
binding, which is the one place it belongs. Recorded so it is a decision rather than
an omission.

### 7. THE FAN-OUT CAP — a customer-facing safety limit

A category-targeted `per_product` rule meeting a wholesale order with sixty
matching line items would send that customer **sixty emails**. That is
indefensible however it is configured, so it is capped.

**Cap: `Consolidation::MAX_MESSAGES = 10`.** Beyond ten messages from one order the
experience is unambiguously wrong: no inbox reads sixty near-identical emails as
helpful, most mail providers will treat the burst as abusive, and the sender
reputation cost lands on the merchant rather than on whoever configured the rule.
Ten is generous for the intended use — a handful of matched products in a mixed
cart — and small enough that the failure mode it prevents cannot occur quietly.

**When the matched-unit count EXCEEDS the cap, the delivery falls back to ONE
message whose body carries the merchant's own content rendered ONCE PER UNIT — for
at most `cap` units (§7a) — with every remaining unit still named**, each section
labelled with that unit's product name, and the fallback recorded along with the
count.

The two obvious alternatives were rejected explicitly:

- **truncating to the first N** silently loses products. The merchant asked for
  every product to be mentioned, and a rule that mentions ten of sixty is wrong in
  a way nothing in the message reveals;
- **sending N anyway** is the failure the cap exists to prevent.

#### ⚠ AND SO WAS THE FIRST ATTEMPT AT THIS CLAUSE, WHICH LOST PRODUCTS TOO

The original wording — *"falls back to `none`: one combined message containing all
matched products"* — described a mechanism that **did not contain all matched
products**. `Consolidation::combined()` bound the message with `item_id = 0`, which is
[ADR-0014](ADR-0014.md) §5's first-matched-item binding, so the natural template for a
per-product rule:

```
Subject: Care instructions for {product_name}
Body:    Here is the care guide for {product_name}.
```

fell back to **one message naming product one**. Products 2–60 appeared nowhere the
customer could see. The clause was only ever *true* of a template that happened to
carry `{product_names}` or `{matched_product_list}` as well — that is, it depended on
the merchant having anticipated a fallback nobody had told them about and
pre-emptively adding a plural placeholder to a template written for a single product.
That is not a fallback; it is a silent omission with a note in the log.

**It survived review because the test fixture proved it.** The capped test asserted
every product name appeared in the body — against a template containing
`ALL=[{product_names}]`. The products were there because the template asked for them,
not because the mechanism put them there. A fixture that carries the very placeholder
whose absence is the failure mode cannot detect the failure mode.

#### Why per-unit sections, and why a LABEL is not decoration

The requirements are: **one** message; **no matched product absent** from the
customer-visible body *whatever the template contains*; and the fallback visible to
the merchant.

Repeating the body per unit satisfies the first and preserves the merchant's
*content* rather than merely their product names — the customer receives the care
guides, not a bare list of sixty products with no care guide attached. (⚠ **How many**
of them is bounded by §7a; this paragraph originally read *"all sixty care guides"*,
and repeating the body sixty times is exactly what made the message quadratic.) That is
why an appended `{matched_product_list}` block was rejected as the primary mechanism:
it guarantees the products are *named* while dropping everything the merchant
actually wrote about products 2–60, and it puts plugin-authored prose inside a
merchant's email.

But repetition **alone** fails the second requirement for **two** ordinary templates,
not one:

| Template | Pure repetition gives | Product named? |
|---|---|---|
| `Here is the care guide for {product_name}.` | 60 correct sections | ✅ |
| *(empty body)* | 60 empty sections | ❌ |
| `Hand wash only.` — no placeholder at all | 60 identical sections | ❌ |

The third row is the decisive one: a template with no placeholder is entirely
reasonable for a single-product rule, and repetition renders it sixty times without
ever naming a product. **So each section is labelled with its unit's product name,
and the label is a correctness requirement rather than a formatting choice.**

The label is the unit's own `{product_name}` value — read through the same value set,
so it is the LINE ITEM's stored name, which survives product deletion. It is *data
the rule is already about*, not plugin prose: no sentence is invented, nothing needs
translating, and it is escaped for its destination by the same
`PlaceholderSyntax::escape()` call every placeholder value goes through.

#### Subject and heading bind to the FIRST unit

They can carry only one value. They bind to the first unit in line-item order, which
is **exactly what `none` binds to today** — so the fallback introduces no new
semantics for the header fields at all: it is `none` for the subject and the heading,
and adds per-unit completeness to the body. A count-based form (*"…and 59 other
products"*) was rejected for the reason the appended block was: a subject is the most
visible string in the message and that form is plugin-authored prose needing
translation, to fix a field whose body already answers the question completely.

⚠ **The complexity claim that stood here was WRONG, and §7a replaces it.** It read:

> *"the message body is O(units × template). It is bounded by the order's line items —
> the same bound `{matched_product_list}` already carries — but multiplied by template
> size. Capping the section count would drop products and is therefore prohibited by
> requirement 2."*

Both sentences are false. O(units × template) holds only for a template with no
**full-set plural** in it: `{product_names}` and `{matched_product_list}` each resolve
to all N matched products (§6), so repeating the body per unit resolved them N times
and the body was **O(units²)**. And capping the section count does *not* drop products,
because a capped section still carries its **label** — which is the whole reason the
label was made a correctness requirement above. The second sentence talked the first
one out of being fixed.

**The fallback is RECORDED, with the count**, in both places a merchant looks: the
attempt row's `reason` says in words that `per_product` fell back to one message
because N matched products exceeded the cap of C, **and how many units the body was
rendered for**, and `snapshot.consolidation` carries
`{requested, mode, units, cap, fallback, rendered}` so support tooling can group by it
without parsing prose. A silent fallback would be a rule that behaves differently from
its own editor with nothing to explain why.

**The cap is filterable, defaulting to the cap:**

```php
apply_filters( 'extonify_wcep_consolidation_max_messages', Consolidation::MAX_MESSAGES, $rule, $order )
```

A site that deliberately wants more can raise it. ⚠ **Only an integer decides.**
A non-integer return — including a `WP_Error`, which is what a callback returns
when it FAILED to decide — leaves the default in place, per
[ADR-0014](ADR-0014.md) §6.5's general rule: *an extension point that cannot decide
must never be read as consent*. Here the consent in question is permission to send
a customer more email than the plugin's own default allows, so reading a
`WP_Error` as "yes, sixty is fine" would be the same fail-open with a larger blast
radius. The result is floored at 1: a filter returning `0` or a negative number
would otherwise mean "send nothing", and a delivery that sends nothing because of
an arithmetic accident is a lost email.

### 7a. THE FALLBACK'S BODY IS BOUNDED: `cap` rendered sections, then labels

The mechanism §7 describes above was **quadratic in the unit count**, and this clause
is the correction.

#### The defect

A section's body is rendered against a value set holding the **whole** matched set,
because §6 says the plural forms list all matched products. So a supported template:

```
Product: {product_name}

All products in this order:
{matched_product_list}
```

rendered N sections each containing an N-line list: **N × N = N² entries**. The cap
limited the *message* count, not the *section* count, so a sixty-line wholesale order
still produced sixty sections — roughly **3,600 list entries and ~100KB** before the
merchant's own content, past the size at which mail clients clip a message and the
customer silently loses the tail. It also retained N value objects, each memoising its
own fully-resolved full-set string: **quadratic retained memory** beside the quadratic
output.

Stated precisely so it is neither over- nor under-sold: this was **quadratic, not
unbounded** — N is bounded by the order's line items. But it needed no database
failure, no third-party pathology and no unusual configuration; only a wholesale order
and a documented placeholder.

#### The decision

> **The capped fallback renders the merchant's body for the first `cap` units and
> LABELS every remaining unit. It never renders that body more times than the fan-out
> it replaced was permitted to send it.**

`Consolidation::rendered_sections( $units, $cap ) = min( $units, max( 1, $cap ) )`, and
the planner marks each section `content => true|false`. The renderer obeys; it decides
nothing. A section whose `content` is false emits its label and nothing else.

**Why the cap and not a new constant.** The fallback did not remove the repetition the
cap exists to limit — it moved it out of N messages and into one body, and Prompt 8A
moved it without moving the limit with it. "Ten near-identical blocks is as much of
this rule as one customer should be shown for one delivery" is the same judgement §7
already made about ten near-identical messages, expressed in the same number, adjusted
by the same filter. A second constant would be a second answer to one question, and the
first merchant to raise the cap would find only half of their decision honoured.

**What the merchant gives up, said plainly.** Units past the cap keep their *name* and
lose their *body*. That is a real loss, and it is what pays for requirement 3 without
giving up requirement 2: the alternative that keeps every unit's body is the quadratic
one. It is also the *smaller* loss of the two on offer — the two-level fallback below
keeps one unit's body, this keeps `cap` of them. The merchant's remedy is the control
they already have: raise the cap and the fallback renders more sections, or stop
matching sixty products with one rule.

#### Against the five requirements

| # | Requirement | How |
|---|---|---|
| 1 | one message | unchanged — the fallback is still `mode = none`, one message, one claim |
| 2 | every matched product represented, **any** template | every unit is a section, and **every section carries its label**; the label is that unit's own `{product_name}`, which is what already made an empty and a placeholder-less template safe |
| 3 | output and retained memory **linear** in units | see the bound below — `O(C·N + N)`, for a fixed configured cap |
| 4 | `none` and uncapped `per_product` byte-identical | neither has sections at all — `sections` is `array()` outside the fallback, and the sectioned renderer is unreachable from both |
| 5 | plural semantics written down, not discovered | the clause immediately below |

#### The bound

With **N** units, cap **C**, template **T** bytes, **P** full-set plural occurrences in
the template, **W** bytes per list entry, **L** bytes per label and **H** bytes of
per-section separator and markup:

```
body(N)  ≤  C × ( T + P × N × W )   +   N × ( L + H )
            └── merchant content, at most C renderings ──┘   └─ representation ─┘
```

That is **O(C·N + N)** — linear in N **for a fixed configured cap**, with coefficient
`C × P × W + L + H` and constant `C × T`. The N² term is gone because the N-sized value
is now multiplied by **C** rather than by the section count. Before the fix the same
expression read `N × ( T + P × N × W )`.

⚠ **The fixed-cap qualification is load-bearing, not pedantry.** `C` is
`Consolidation::max_messages()`, which is filterable and is handed **the order** — so a
site can return a cap derived from the order's own size, and `C = f(N)` puts the
quadratic term straight back. That is a deliberate act on a customer-facing safety
limit, not a defect, and the filter's own documentation now says so. But "linear in N"
is a claim about a cap that does not itself depend on N, and stating it unconditionally
would be describing a configuration rather than the mechanism.

**Retained memory is bounded by a constant number of O(N) objects, not by N of them.**
Each section's value set is released as its section completes: the renderer folds that
section's notes into a de-duplicated, `MAX_NOTES`-capped accumulator and drops the set,
so **at most one section's set is live at any moment** however many units there are.
The header's set is the only other one. The notes are merged by
`PlaceholderValues::fold_notes()` — one implementation, shared with the containment
boundary, so a multi-section delivery's diagnostics are held to the same bound as a
single delivery's.

#### THE UNIT LABEL: a name that IDENTIFIES, not merely names

*(ADDED 2026-08-07, Prompt 8C. The section policy above made this a Tier 1 defect: for
a unit past the bound the label is the **whole** of what the customer receives about
it.)*

The label was `{product_name}` — the order item's stored name. **An order item's name
does not distinguish sibling variations.** Verified against the bundled WC 10.9.4
`WC_Product_Variation_Data_Store_CPT::generate_product_title()`, a variation's generated
title omits its attributes when:

| # | Condition | Source |
|---|---|---|
| 1 | the variation has **3 or more** attributes | `$should_include_attributes = count( $attributes ) < 3;` |
| 2 | it has **2 or more** attributes and any attribute **key** contains `-` — what a multi-word attribute name (`Shirt Size` → `shirt-size`) produces | the `false !== strpos( $name, '-' )` loop |
| 3 | every attribute is left "Any", so `wc_get_formatted_variation()` returns nothing to append | `$title_suffix ? … : $title_base` |

(Both #1 and #2 are also overridable through
`woocommerce_product_variation_title_include_attributes`.) In each case the title is the
bare parent name, so two units this ADR §4 defines as **distinct** —
`variation:101` ≠ `variation:102` — render as two identical lines and either could be
either. That this plugin has a separate `{variation_attributes}` placeholder is itself
the evidence that the name was never expected to carry them.

> ⚠ **This is narrower than "attribute values longer than two characters", which is
> what Prompt 8C's brief described.** No such rule exists in the bundled source — a
> single-attribute variation is titled `T-Shirt - Red` whatever the value's length. The
> defect is real; its trigger is the attribute **count** and the attribute **key**, not
> the value.

**Decision: the label is `PlaceholderValues::unit_label()`** —

```
label = {product_name}  +  ( details === '' ? '' : ' – ' + details )
details = wc_get_formatted_variation( $variation, flat: true, include_names: true,
                                      skip_attributes_in_name: true )
```

Four properties, each answering one of the constraints:

- **A simple product's label is byte-identical to before.** There is no variation, so
  there are no details, so nothing is appended. No churn where there is no problem.
- **A live variation gains only what its name does not already say.** The fourth
  argument is WooCommerce's own *"do not list attributes already part of the variation
  name"*, so a one-attribute variation titled `T-Shirt - Red` keeps exactly that and
  gains nothing; appending unconditionally would render `T-Shirt - Red – Colour: Red`.
  Switching to `{variation_name}` instead was rejected outright: WooCommerce generates
  that from the same title and it inherits the same collapse.
- **A partially resolved variation keeps the parent label**, by the same guard
  `{variation_attributes}` already uses for the same reason ([ADR-0011](ADR-0011.md) §4):
  the ids survive, the variation's own facts do not, §4 collapses it onto the parent
  unit, and there is nothing left to identify. Inventing detail there would be worse
  than admitting none.
- **The label is still a value** — resolved through the unit's own value set and escaped
  per destination by the same `PlaceholderSyntax::escape()` every placeholder goes
  through, in both HTML and plain text.

**The bound survives.** `details` is bounded by the variation's own attribute count,
which has nothing to do with N, so `L` in the formula above gains a constant and the
curve does not change shape.

⚠ **What this does NOT make impossible, stated rather than discovered.** The invariant
*two distinct units never produce identical labels* holds **for units WooCommerce's own
data distinguishes**. Two collisions survive and are recorded in
`docs/p2-backlog.md` rather than fixed:

- **two different simple products with the same title** — WordPress permits duplicate
  post titles, and the only fixes (SKU, id) would change every simple product's label,
  which the constraint on this change forbids for exactly the right reason;
- **two variations of one parent whose attribute data is identical** (both left "Any").
  Nothing honest distinguishes them, because nothing in the data does.

#### What the fallback does to PLURAL placeholders — requirement 5

**Their meaning is unchanged: `{product_names}` and `{matched_product_list}` list ALL
matched products, exactly as §6 requires, in every section that renders the body.**
Nothing is narrowed, scoped, elided or moved.

What changed is **how many times the body containing them is rendered**: at most `cap`
times. So a full-set list appears at most `cap` times in the fallback message, never
once per unit. In the labelled remainder the merchant's body does not appear at all, so
neither do its placeholders — singular or plural.

**Consequently a product name occurs in the body at most `1 + s + C × p` times**, where
`s` is the singular product placeholders in the template and `p` the full-set plurals:
once as its own label, once per singular occurrence in its own section, and once per
plural occurrence in each rendered section. A declared constant, independent of N.

#### The four alternatives, and why each was rejected

- **Scope plurals to the section's own unit.** Kills the quadratic cleanly and needs no
  bound at all — but it **contradicts §6**, which says the plural forms enumerate every
  matched product *in every message*, and the fallback is one message. `{product_names}`
  would then mean "all matched" in an uncapped `per_product` message and "this one
  product" in a capped section, silently, in a field the merchant wrote deliberately —
  and `{matched_product_list}` scoped to one unit turns *"your order also contained
  these"* into a sentence that names one product. It trades a size problem for a
  correctness problem, and it weakens an ADR clause rather than adding one.
- **Resolve full-set plurals once and reuse the string across sections.** Bounds
  *memory* to one resolution and leaves the *output* quadratic — the list still appears
  N times in the body, which is the half a customer reads. Half a fix.
- **A two-level fallback: sections while a projected size bound holds, then the body
  once plus a labelled list of every product.** Bounds output for any template, which is
  strictly stronger than this clause, and was the closest rival. Rejected on three
  counts: it needs a **byte budget with no principled value**; behaviour then depends on
  **template length**, so a merchant who adds a paragraph loses fifty-nine sections at a
  cliff they cannot see; and the output becomes **non-monotonic** in N — more units can
  mean a *smaller* body — which is hard to reason about and harder to test. It also
  leaves the list repeated once per section below the budget, so the repetition
  guarantee would hold only above a size threshold rather than structurally.
- **Strip full-set plurals from the repeated block and render them once after the
  sections.** Linear and it preserves the plural's meaning, but it **reorders
  merchant-authored content** — and worse than reordering: removing the *token* leaves
  the sentence around it, so `Your order also contained: {matched_product_list}` renders
  as *"Your order also contained:"* sixty times with nothing after it, and the list
  arrives orphaned at the end. A merchant's paragraph cannot be split from its
  placeholder without breaking it.

#### Recorded, in words and in the snapshot

The attempt row's `reason` names the unit count, the cap **and how many units the body
was rendered for**; `snapshot.consolidation.rendered` carries the same number so support
tooling can answer *how much of this rule did that customer actually see* without
re-deriving it from a cap that may since have been filtered differently.

### 8. Delayed plus `per_product`: ONE job, fanning out at execution

One scheduled job per delivery, which fans out when it runs. **N jobs are
prohibited** — that would multiply the identity problem into the scheduler, where
N actions would contend for one tombstone's lease
([ADR-0015](ADR-0015.md) §8) and a partial failure would leave some of one
delivery's messages queued and others not.

The [ADR-0007](ADR-0007.md) snapshot already carries `matched_items` as line-item
ids, and `ScheduledDelivery::surviving_items()` already rebuilds matched records
from the live order, so the units are reconstructible at execution time from what
is already stored. No new snapshot content is needed for the fan-out itself.

**`consolidation` DOES join the snapshot fields, for the phase check.**
`still_in_phase()` compares the live rule against the snapshot for exactly the
facts where a mid-delay change means the queued message is no longer the one the
merchant asked for — today `delivery_mode` and `delay_seconds`. Consolidation
belongs in that set: a merchant who switched a delayed rule from one message to
one-per-product between the trigger and the send has changed what the rule *is*,
and delivering the old shape would deliver a rule that no longer exists in that
form. So:

- the snapshot stores `consolidation`;
- `still_in_phase()` requires the live value to **equal** the snapshotted one, and
  both to be members of the vocabulary. A mismatch is `rule_left_phase`, the
  reason code that already exists for exactly this class of change;
- `as_rule_row()` supplies `consolidation` from the snapshot. Because the phase
  check above has already proven the live rule agrees, the two are the same value
  and there is exactly one place the question is decided;
- `ScheduledPhase::owns()` and `ScheduledCancellation::on_rule_updated()` no longer
  exclude a non-`none` consolidation — a delayed `per_product` rule is a rule this
  phase owns. The eager cancellation stays the weaker of the two predicates, per
  ADR-0015 §5, and the execution-time equality check catches per delivery what it
  cannot see per rule.

⚠ **The snapshot format version goes to 2**, and the bump is the honest use of the
field rather than a formality: a v1 document has no `consolidation` key, and
`read()`'s presence check would refuse it as a half-written row without ever
saying the shape had changed. Bumping makes an old queued row refuse **as a
version it does not understand** — `snapshot_unreadable`, cancelled with a reason
(ADR-0015 §4) — which is fail-closed and legible. Schema v1 is unreleased, so no
merchant has a queued v1 delivery to lose.

### 9. Gate 15 becomes an EMPTY enumeration, and the test stays

With consolidation implemented, `Orchestrator::UNIMPLEMENTED_BEHAVIOUR_DEFAULTS` is
**empty**.

**The enumeration and its test are NOT deleted.** The test asserts the constant is
empty, so a future column carrying behaviour nobody has built yet **re-arms the
gate automatically** the moment somebody adds it — and adding it without adding
the filter is a failing test rather than a defect somebody has to notice. Deleting
the mechanism because it currently has nothing to hold would remove the discipline
that caught `consolidation` in the first place.

`behaviour_is_implemented()` survives with an empty list, returning `true`, so both
phase filters keep their call site and a future entry needs no new plumbing.

## Consequences

- A merchant who wants one message per matched product can have it, and one who
  does not is unaffected: `none` is the default and its behaviour, its writes and
  its query cost are unchanged.
- `daily`, `weekly` and `per_order` cannot be stored. A store that had one of them
  in a rule now has a rule that refuses to save until the value is corrected —
  which is louder and more accurate than the previous state, where the rule saved
  and then did nothing.
- Duplicate protection, delayed scheduling, cancellation, retention, the privacy
  exporter and the privacy eraser all work unchanged, because a fan-out is N
  ordinary attempt rows under one ordinary tombstone. No component had to learn
  about consolidation to keep working.
- A fan-out of N costs **no more matching or resolution work than a single
  delivery**: the matcher runs once, `ItemResolver`'s product cache is shared, the
  order's line items are indexed per message from `WC_Order::get_items()` (memoised
  on the order object), and recipients resolve once. The only per-message cost is
  the message itself.
- One message failing, one message being refused by a filter, and one message
  throwing are each contained and recorded without touching the others, and the
  tombstone tells the truth about the set.
- A wholesale order cannot produce an email storm: the cap converts the worst case
  into one combined message and says so — and that message's size and retained memory
  are **`O(C·N + N)` — linear in the matched-unit count for a fixed configured cap**
  (§7a), for every template including one that writes a full-set plural.
- Insert mode is untouched, structurally: the combination cannot be stored.

### Accepted residual risks (deliberately not fixed)

- **A fan-out is not atomic.** If the process dies between message 2 and message 3,
  messages 1 and 2 have been sent and recorded and message 3 never happens; the
  tombstone is left `claimed` and the consumed identity blocks a retry. This is
  the same exposure a single delivery already has between its send and its record,
  widened by the loop. It is not fixable without making the whole fan-out
  transactional with respect to an external mail transport, which is not
  achievable — a sent email cannot be rolled back. Recorded rather than hidden.
- **A third party's `woocommerce_email_enabled_{id}` callback that answers
  differently per message** produces a partially delivered fan-out. That is the
  callback's decision, honestly recorded per message; nothing here overrides a
  third party's per-delivery answer.
- **The cap is per delivery, not per order.** Three `per_product` rules each
  matching ten products send thirty messages, none of which exceeds the cap. A
  per-order ceiling is a different feature — it would have to arbitrate between
  rules, which is the same cross-identity problem `per_order` merging raises in §1
  — and is recorded in `docs/p2-backlog.md`.
- **A fan-out of N leaves N WooCommerce order notes.** Traced, not assumed:
  WooCommerce's own
  `Automattic\WooCommerce\Internal\Email\EmailLogger` hooks `woocommerce_email_sent`
  and calls `WC_Order::add_order_note()`, which reaches `wp_update_comment_count()`
  and `get_post( $order_id )` — a MISS under HPOS, where an order is not a post, and
  WordPress does not cache misses. So each message costs a comment insert plus a few
  uncached lookups. It is **not** this plugin's matching or resolution work (measured
  identical for N=1 and N=4 by the gate 6 test), it is what WooCommerce does for every
  email any plugin sends, and it is exactly what N separate rules would cost. Left
  alone: suppressing WooCommerce's own order note would remove a record the merchant
  is entitled to.

Each of these is in `docs/p2-backlog.md`.
