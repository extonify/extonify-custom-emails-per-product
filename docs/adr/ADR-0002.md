# ADR-0002: Single fixed, runtime-configured `WC_Email`

Status: **Accepted** — 2026-07-25
Amended 2026-07-25 (Prompt 1a) — added mandatory runtime-state isolation
(explicit set + `finally` reset on every `trigger()`) and a registration-timing
rule (filter attached before the mailer initialises).
Amended 2026-07-25 (Prompt 1b) — reset runtime state at BOTH ends (entry + finally)
and set every field unconditionally; `email_type` is a store setting only (never a
per-delivery runtime argument; reset must not force it).

## Context

WooCommerce delivers transactional email through `WC_Email` subclasses that are
registered via the `woocommerce_email_classes` filter. Each registered class
becomes a row in **WooCommerce → Settings → Emails**, owns a settings form
(`init_form_fields()`), and persists its own `subject`, `heading`, recipients,
and `email_type` in the options table.

This plugin lets a store define *many* rules that each send a custom email when
an order matches a product. A naive implementation would register one
`WC_Email` subclass per rule. That approach is structurally broken:

- **Dual source of truth.** A rule's subject/heading/content would live in the
  rule record *and* in the email's own WooCommerce settings, which drift apart.
- **Stale settings.** WooCommerce persists the email's settings independently;
  editing a rule would leave the email's stored settings pointing at old
  content until someone re-saves the settings screen.
- **Mailer bloat.** Every rule would add a row to Settings → Emails and a
  class instance to the mailer, unbounded in the number of rules.
- **Block email-editor conflicts.** The WooCommerce block/email-editor keys
  templates by email ID; dynamically-named per-rule email IDs collide with and
  confuse that system.

Separately, some deliveries are **inserted into an existing native email**
(insert mode, [ADR-0005](ADR-0005.md)); those never register a `WC_Email` at
all. This ADR governs the **separate-mode** delivery path (the plugin sends its
own email).

## Decision

There is **exactly one** `WC_Email` subclass:
`Extonify\WCEP\Email\Custom_Email`, registered once via
`woocommerce_email_classes`.

- **All** separate-mode deliveries flow through this single class via a runtime
  entry point:

  ```
  trigger( WC_Order $order, Rule $rule, array $matched_items, Delivery $delivery )
  ```

  `trigger()` sets the **recipient, subject, heading, and content at runtime**
  from the rule and delivery, then sends. Nothing about the rule is baked into
  the class definition or into WooCommerce's stored email settings.

- **Per-rule `WC_Email` registration is permanently prohibited.** The number of
  registered email classes is always exactly one, independent of how many rules
  exist. No code path may register a second `WC_Email` for a rule.

- `init_form_fields()` on `Custom_Email` is overridden to expose **only two
  fields**: the `enabled` toggle and the `email_type` selector. Subject,
  heading, content, recipients, CC/BCC, and delay are **rule-owned** and
  **never** appear in WooCommerce's email settings.

- The single visible entry in **WooCommerce → Settings → Emails** functions as
  the plugin's **global kill switch**. Its description links to the plugin's
  rules screen (where all real configuration lives). When the entry is
  disabled, no separate-mode delivery is sent.

- **Runtime state isolation (mandatory).** Because one shared object serves every
  delivery, `trigger()` sets **every** runtime field explicitly on **every**
  call — **never conditionally on whether an argument was supplied**: recipient,
  cc, bcc, subject, heading, content, matched items, order/object, and delivery
  reference. **No field may carry over between consecutive deliveries in one
  request.** Relying on the previous call's cleanup alone leaves state exposed to
  external mutation, to a partially-completed prior call, and to future code
  paths that set a property before calling `trigger()`.

  *(AMENDED 2026-07-28, Prompt 4c.)* This clause originally required
  `reset_runtime_state()` **on entry and in a `finally`**. The entry half is
  unchanged in effect — every field is still assigned unconditionally — but the
  exit half is now a **restore of the frame captured on entry**, not a clear.
  `trigger()` is re-entrant: `is_enabled()` applies the third-party
  `woocommerce_email_enabled_{id}` filter *before* the recipient, content and
  headers are evaluated, so a nested delivery can complete inside an outer one.
  A clearing `finally` handed the outer call an empty object and its claimed
  delivery was recorded as `no_recipient`. At the top level the captured frame is
  empty, so the isolation guarantee above is unchanged. See
  [ADR-0012 §11a](ADR-0012.md).

- **`email_type` has one source of truth: the WooCommerce setting.** It is one of
  the two fields on the fixed email's settings form, i.e. a **global store
  setting**, and must **not** also be a per-delivery runtime argument. Rules own
  recipient, CC, BCC, subject, heading, content, and delay — **not output
  format**. `reset_runtime_state()` must **not** force `email_type` to `'html'`;
  it leaves the store's saved setting untouched. A per-rule format override is out
  of v1.0 scope and would require a superseding ADR.

- **Registration timing.** The `woocommerce_email_classes` filter must be
  attached **before the mailer is initialised** so the class is present in the
  live `WC()->mailer()->get_emails()` collection — not merely constructible by
  the filter after the fact. If registered too late, WooCommerce never adds the
  entry to Settings → Emails and never routes through it.

## Consequences

- The rule record is the **single source of truth** for subject, heading,
  content, recipients, CC/BCC, and delay. WooCommerce email settings can never
  drift from or override a rule.
- Settings → Emails stays a constant size (one row) no matter how many rules a
  store creates; the mailer holds one extra class instance, not N.
- The block email editor sees one stable email ID for this plugin and cannot be
  confused by per-rule IDs.
- Because the class is runtime-configured, the same singleton object is reused
  across many deliveries in a single request. That reuse is safe only if no
  per-delivery state leaks between calls; the singleton-safety guarantee for
  the insert-mode registry is specified in [ADR-0005](ADR-0005.md) and proven
  in POC-D, and the shared order-item render context is stack-based
  ([ADR-0003](ADR-0003.md)).
- The global kill switch gives store owners and support a single, discoverable
  off-switch that stops all separate-mode sending without deleting rules.
- Delivery idempotency and duplicate protection are handled by the delivery
  layer ([ADR-0004](ADR-0004.md)), not by WooCommerce's per-email settings.

## Amendment history

- **2026-07-25 (Prompt 1a):** Added two mandatory rules. (1) **Runtime state
  isolation** — `trigger()` sets every runtime field explicitly and resets them
  in a `finally` block so nothing carries between consecutive deliveries on the
  shared singleton (proven by POC-B's A→B isolation test). (2) **Registration
  timing** — the `woocommerce_email_classes` filter is attached before the
  mailer initialises so the class actually appears in
  `WC()->mailer()->get_emails()`. Why: the shared-object design is only safe if
  per-delivery state cannot leak, and "constructible via the filter" is not the
  same as "registered in the live mailer collection".
- **2026-07-25 (Prompt 1b):** (a) `trigger()` resets runtime state at **both**
  entry and `finally`, setting every field unconditionally — never relying on the
  previous call's cleanup, which is exposed to external mutation and partial prior
  calls (proven by POC-B's contamination test on the live object). (b)
  **`email_type` is a store setting only**, not a per-delivery runtime argument;
  `reset_runtime_state()` must not force it. POC-B exercises HTML/plain by
  temporarily updating the saved setting and restoring it.
