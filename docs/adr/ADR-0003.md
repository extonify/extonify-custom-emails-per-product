# ADR-0003: Email-render context for shared order-item hooks

Status: **Accepted** — 2026-07-25
Amended 2026-07-25 (Prompt 1a) — replaced the single "no-op unless stack active"
rule with a two-class (shared vs email-only) gating rule requiring email-only
callbacks to validate email ID / order / audience; replaced the whole-stack
footer clear with `cleanup_matching()` for nested-render safety.
Amended 2026-07-25 (Prompt 1b) — cleanup/pop are RENDER-scoped by render token,
removing exactly one frame; matching on the email object alone is insufficient
because one shared object serves every delivery of an email type.
Amended 2026-07-25 (Prompt 1c) — pop/cleanup additionally TUPLE-validate the
frame against the supplied email object + order id; a valid token for a different
render removes nothing and records a mismatch.
Amended 2026-07-25 (Prompt 1d) — an INTERRUPTED render, preview or otherwise, must
never leave an active context frame; reconciliation at the start of every push plus
the shutdown fallback enforce this.

## Context

Insert-mode content ([ADR-0005](ADR-0005.md)) is injected through WooCommerce's
order/email hooks. Several of those hooks are **shared** between email templates
and front-end order templates. The critical one is:

- `woocommerce_order_item_meta_end` — fires **inside email templates**
  (`templates/emails/email-order-items.php`, plain-text variant) **and inside
  front-end order templates**: My Account → view-order
  (`templates/order/order-details-item.php`), the thank-you / order-received
  page, and the order-pay page (`templates/checkout/form-pay.php`).

If our injection callbacks are registered globally, they would fire on the
customer's front-end order views as well as in emails — leaking email-only
content onto storefront pages. We also cannot register/deregister callbacks
lazily around each email send, because sends can be nested, batched, and
interleaved with other output in a single request ([ADR-0005](ADR-0005.md),
POC-D), and because a hook that is added and removed around one send would
still be active during another send that overlaps it.

Two runtime facts from the WooCommerce source (verified against 10.9.4)
constrain the design:

1. `woocommerce_email_order_details` fires with **four** arguments
   `($order, $sent_to_admin, $plain_text, $email)` from the email templates,
   and is the outermost email-body action — the correct place to bracket "we
   are now rendering an email".
2. `woocommerce_order_item_meta_end` is called with **four** arguments in
   current core (`$item_id, $item, $order, $plain_text`) in both email and
   front-end templates. However, **stale theme/plugin template overrides in the
   wild still call it with three arguments** (omitting `$plain_text`). A
   callback that requires the fourth parameter would throw `ArgumentCountError`
   on those installs.

## Decision

- **All injection callbacks are permanently registered** (added once at boot,
  never added/removed per send), and fall into **two classes** with different
  gating (amended — see below):

  - **SHARED hooks** — `woocommerce_order_item_meta_end` and any hook that also
    fires on front-end order templates. These are **hard no-ops unless the
    email-render stack is active**, because they carry no `$email` argument and
    cannot otherwise tell an email render from a storefront view. The fourth
    parameter is **optional with default `false`** (stale 3-arg overrides).

  - **EMAIL-ONLY hooks** — `woocommerce_email_before_order_table`,
    `woocommerce_email_after_order_table`, `woocommerce_email_order_meta`,
    `woocommerce_email_customer_details`. These never fire on the front-end and
    **self-identify** from their own `$email` and `$plain_text` arguments. They
    **MUST validate before emitting anything**: (1) the email **ID matches the
    rule's targeted native email**, (2) the **order matches the current render**,
    and (3) the **audience matches** (`$sent_to_admin` state). **Unconditional
    emission is prohibited** — a rule targeting `customer_processing_order` must
    **never** appear in Admin New Order, Customer Completed, Refunded, or any
    unrelated email.

- The email-render context is a **stack, not a boolean.** Emails can nest and
  the same request can render several; a boolean flag would be corrupted by the
  inner render clearing the outer one. The stack is:
  - **Pushed** on `woocommerce_email_order_details` at **priority 5**, minting a
    unique **render token** and capturing a frame: `render token`, `email ID`,
    `email object`, `order ID`, `$sent_to_admin`, `$plain_text`.
  - **Popped** on `woocommerce_email_order_details` at **priority 15** (same
    action, after the body content between priorities 5 and 15 has rendered).
  - **Cleaned up render-scoped** on `woocommerce_email_footer` — a backstop that
    removes **exactly one frame: the finishing render's** (by render token),
    never the whole stack and never all frames of an email (amended — see below).

- The stack API is **render-scoped by token** (matching on the email object alone
  is insufficient, because WooCommerce serves every delivery of a given email
  type from **one shared object** — nested same-object renders produce two frames
  with the same `spl_object_id`):
  - `push( $email, $order, $plain_text, $sent_to_admin )` — push a frame, minting
    and returning its render token.
  - `pop_matching( $email, $order, $render_token )` — remove **exactly one** frame
    (this render's) by token, **tuple-validated**: the frame bearing the token
    must also belong to `$email` and (when supplied) `$order`; a valid token from
    a **different** render removes **nothing** and **records a mismatch**.
  - `cleanup_matching( $email, $order, $render_token )` — footer backstop that
    removes **exactly one** frame (the finishing render's) by token with the same
    tuple validation, leaving every other render's frame — inner or outer, same
    object or not — untouched.

- SHARED-hook callbacks read the **top frame** of the stack to decide context
  (email ID, plain vs HTML, admin vs customer). If the stack is empty, they do
  nothing. EMAIL-ONLY callbacks validate against their own arguments as above.

- **An interrupted render must never leave an active context frame.** A frame is
  pushed at priority 5 and popped at priority 15; anything that throws in between —
  a foreign injection callback, a template override, a preview renderer — unwinds
  past the pop, and the surviving frame would make "are we rendering an email?"
  answer **yes while nothing is rendering**. That is the exact invariant this ADR
  exists to guarantee, so `pop_matching`/`cleanup_matching` are **not** the only
  teardown path:

  - **Reconciliation at the start of every push.** A **preview** frame that still
    exists when the next render begins is proof that a preview was interrupted — a
    completed preview always removes its own frame at the order-details close.
    Such frames are dropped, together with their open order-details and footer
    tokens, **before** the new frame is pushed, so no render ever inherits a
    previous render's residue.
  - **The shutdown fallback**, which runs the same reconciliation, bounds the
    residue to the request even if no further render occurs.

  PHP offers no unwind hook at a call site we do not own, so teardown at the
  *instant* of interruption is not achievable; the guarantee is that the residue is
  cleared by the next push or by shutdown, whichever comes first, and is never
  observable by another render. Non-preview renders are unchanged: their frames are
  removed by the tuple-validated pop and footer backstop as before.

- Every callback that binds `woocommerce_order_item_meta_end` (and any other
  shared hook) declares the fourth parameter **optional with a default of
  `false`**:

  ```php
  public function on_order_item_meta_end( $item_id, $item, $order, $plain_text = false ) { … }
  ```

  This tolerates both the current four-argument core call and stale
  three-argument overrides without an `ArgumentCountError`.

## Consequences

- **Hard guarantee:** on any front-end order view (view-order, thank-you,
  order-pay) there is **zero injected output and zero PHP notices/warnings**,
  because no email-render context is ever active there and the callbacks
  short-circuit. This is a release gate, proven by POC-C's negative gates.
- Nested/batched email renders are safe: each render pushes and pops its own
  frame; the top frame always describes the render currently in progress.
- The plugin is resilient to outdated templates that call the shared item hook
  with three arguments — no fatal, because the fourth parameter defaults.
- The `woocommerce_email_footer` backstop uses
  `cleanup_matching($email, $order, $render_token)` to remove **exactly one**
  frame — the finishing render's. An **inner email triggered mid-render** (even
  the **same singleton object** rendering a second order) cannot destroy the
  **outer** render's context, which is the exact scenario the stack exists to
  survive (proven by POC-C's same-singleton nested test).
- Because callbacks are always registered and only gated by context, there is
  no window where a concurrent overlapping send finds the hook missing — the
  context, not hook registration, is the single decision point.
- Email-only injection can never contaminate an unrelated email: validating
  email ID, order, and audience means a rule targeting one native email is
  invisible in every other (proven by POC-C's negative isolation tests).
- An exception thrown between push and pop cannot leave the context permanently
  "inside an email": the frame and its open tokens are reconciled at the next push
  or at shutdown (proven by POC-C's interrupted-preview zero-residue test).

## Amendment history

- **2026-07-25 (Prompt 1a):** (a) **Hook classes** — split callbacks into SHARED
  (stack-gated, optional 4th param) and EMAIL-ONLY (self-identify via `$email`/
  `$plain_text`, and MUST validate email ID + order + audience before emitting;
  unconditional emission prohibited). Why: the original blanket "no-op unless
  stack active" was empirically wrong for order_meta/customer_details (they fire
  after the stack pops) and did not prevent a rule's content from leaking into an
  unrelated email. (b) **Nested-safe cleanup** — the footer backstop now removes
  only the finishing email's frames (`cleanup_matching`) instead of clearing the
  whole stack, so an inner email triggered mid-render cannot destroy the outer
  render's context. Added the explicit `push`/`pop_matching`/`cleanup_matching`
  API.
- **2026-07-25 (Prompt 1b):** Made cleanup/pop **render-scoped by render token**
  (BLOCKER fix). The 1a `cleanup_matching($email)` removed **every** frame of an
  email object; when the **same singleton** renders nested (same object, two
  frames) it destroyed the inner *and* the outer frame — the exact failure the
  stack exists to prevent. Signatures are now
  `pop_matching($email, $order, $render_token)` and
  `cleanup_matching($email, $order, $render_token)`, each removing exactly one
  frame. Recorded that object identity alone is insufficient because WooCommerce
  serves every delivery of a given email type from one shared object.
- **2026-07-25 (Prompt 1c):** `pop_matching`/`cleanup_matching` now **tuple-
  validate** — the frame bearing the token must also match the supplied email
  object and order id, else nothing is removed and the mismatch is recorded. A
  valid token from a different render can no longer remove the wrong frame (proven
  by POC-C's foreign-token rejection test).
- **2026-07-25 (Prompt 1d):** Stated explicitly that an **interrupted render,
  preview or otherwise, must never leave an active context frame**, and named the
  two mechanisms that enforce it: **reconciliation of stale preview frames at the
  start of every push** (which also purges their open order-details and footer
  tokens) and the **shutdown fallback**. Prompt 1c's teardown covered only the
  normal path, so an exception between priority 5 and priority 15 left a frame
  behind and `in_email()` kept answering yes for the rest of the request. Also
  recorded that the order-details close retires a **plain-text** render's footer
  backstop entry, since plain templates never fire `woocommerce_email_footer` and
  the entry would otherwise leak one token per plain render.
