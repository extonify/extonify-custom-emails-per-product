# ADR-0019: Manual delivery actions — identity for a send with no trigger, and one email per confirmed click

Status: **Accepted** — 2026-08-12

## Context

Every admin surface so far has been read-only or has written rule rows. **This one
sends email to real customers on a merchant's click.**

The failure mode changes accordingly, and so does what an argument has to prove. A
defect in the history screen produced a wrong log line. A defect here sends a
stranger's customer an email they never expected, or sends it five times because a
button was double-clicked, or sends nothing while reporting success. So this ADR is
organised around three questions the read-only surfaces never had to answer: **what
identity does a send with no trigger get**, **what makes a resubmission collide
instead of sending again**, and **what does the plugin refuse outright**.

One more thing is being decided here rather than inherited. `'manual'` has been a
member of `DeliveryDetailRepository::TYPES` since Prompt 2 and **has never been
written by any code path**. This prompt is its first user, so its meaning is defined
below rather than assumed.

---

## Decision

### 1. Four actions, and the two that already have a state machine

| Action | Precondition | What it does |
|---|---|---|
| **Resend** | tombstone is terminal | a new attempt row on the SAME tombstone, linked to the previous attempt |
| **Send now** | tombstone is `scheduled` | executes the queued delivery ahead of its delay |
| **Cancel** | tombstone is `scheduled` | terminalises it `cancelled`, then removes the job |
| **Send manually** | the rule has never fired for this order | creates its own tombstone and sends |

Send now and cancel are transitions on a delayed delivery, so they are **already**
governed by ADR-0015's state machine and use the **guarded** `transition()` — never
`set_final_status()`, never an unconditional write. Resend and manual send are the
immediate path's shape and use its unconditional write, because there is no lease and
no second actor.

### 2. The manual identity: `manual:<token>`, and why it cannot collide

**A manual send has no trigger, so it has no trigger identity.** ADR-0004 provides for
resends — *linked attempt rows outside the automatic constraint* — and that covers the
three actions with a parent tombstone. It does not cover a rule that has never fired.

**A manual send creates its own tombstone**, with the trigger identity

```
manual:<32 lowercase hex characters>
```

`manual` joins `DeliveryIdentity::TRIGGER_PREFIXES`. This is an **addition** to the
identity vocabulary, not a weakening of it: the uniqueness key is unchanged
(`sha256(order_id|rule_id|mode|trigger_identity)`), the `UNIQUE` index on
`identity_hash` is unchanged, and the form still satisfies
`is_valid_trigger_identity()`'s length bound and character class. What changes is only
that a fourth prefix is recognised, and the prefix is what makes a manual delivery
**recognisable as manual when read back** — by the history screen, by support, and by
anything that later needs to tell a merchant's send from the store's own.

**It cannot collide with an automatic identity** because no automatic path can ever
produce one: `TriggerEvent` emits only `status:`, `transition:` and `refund:`, and
insert mode only `native:`. The prefixes are disjoint by construction, and the
identity hash includes the prefix.

**Consequences, stated because they are real outcomes rather than defects:**

- A manual send **does not consume any automatic identity**. The rule still fires
  normally later if its trigger occurs.
- Two manual sends of the same rule for the same order are **two distinct
  identities**, which is correct: the merchant asked twice, deliberately, and
  confirmed twice.
- **Therefore a customer can receive the message twice** — once because the merchant
  sent it by hand, and again when the trigger fires. That is the price of not
  suppressing a rule's normal behaviour, and the alternative is worse: letting a
  manual send consume the automatic identity would silently disable a rule for that
  order, with nothing on any screen to say so. **The confirmation dialog says this
  out loud** (§6) rather than leaving the merchant to discover it.

### 3. A resend renders from the CURRENT rule

A resend renders from the rule **as it is now**, not as it was. The common reason a
merchant resends is that they corrected something, and a resend that faithfully
reproduced the original mistake would be useless. `rule_revision_sent` already records
which revision produced each attempt, so the history stays honest about what was
actually sent when.

Consequences:

- **Rule deleted → refuse** (§4). A completed delivery has no snapshot to fall back
  on — ADR-0015 §2 releases it at the terminal state, deliberately, because a
  retained snapshot per delivery is a resource that grows for the lifetime of the
  store. So there is genuinely nothing to render, and the refusal says so.
- **Rule disabled → allow, and say so.** The merchant is acting deliberately on one
  specific order; refusing would mean disabling a rule retroactively blocks support
  for orders it already served. The confirmation states that the rule is currently
  disabled and that this send does not re-enable it.
- **Placeholders resolve fresh against the live order** (ADR-0014 §8). A resend six
  months later shows the order as it is now, not as it was. This follows from
  rendering at send time and is not a separate decision; it is recorded because it
  surprises people.

### 4. What the plugin refuses, and why each refusal is its own sentence

Every refusal names its own reason, sends nothing, and writes nothing partial. A
generic "could not send" throws away the one thing the merchant needs.

| # | Condition | Applies to | Why |
|---|---|---|---|
| R1 | rule deleted | resend, send now | nothing to render (§3) |
| R2 | rule is **insert mode** | all four | ADR-0013 §2: insert content has no message of its own — no subject, no recipients, no envelope. There is nothing to send |
| R3 | consolidation or mode outside the vocabulary | all four | ADR-0016 §1a read boundary: the rule is not deliverable |
| R4 | delivery is **not terminal** | resend | it is still in flight; wait for it, or cancel it |
| R5 | delivery is **not `scheduled`** | send now, cancel | another actor already owns it |
| R6 | schema not operational | all four | `Migrator::is_operational()`; degraded mode no-ops rather than half-working |
| R7 | the order no longer exists | all four | nothing to resolve placeholders or recipients against |
| R9 | custom emails switched off globally | all four | ADR-0012 §5: nothing is claimed while the feature is off |

R9 and R6 are checked **before anything is claimed**, exactly as
`Orchestrator::deliver()` does, so a refused manual send leaves no tombstone behind.

Two more conditions refuse for reasons that are not in the table above because they
are facts about the request rather than about the store: a **delivery id that does
not exist**, and **a rule whose targeting matches nothing on this order** — the
second refuses rather than sending a message about no products, and claims no
identity while doing so.

> **⚠ AN EARLIER DRAFT OF THIS TABLE CARRIED AN "R8 — the rule already has a delivery
> for this order" REFUSAL FOR MANUAL SENDS. It was removed, because it contradicted
> §2.** §2 states that two manual sends of the same rule and order are two distinct
> identities *because the merchant asked twice*; a refusal on the second would have
> made §2 unreachable. The order panel's rule picker offers every rule for the same
> reason — hiding already-delivered ones would have put the same contradiction in the
> UI instead of the handler.

### 5. One click, one email

**Every action is POST with a fresh action-specific nonce.** There is no GET link that
sends anything, anywhere — gate 36 proves it by asserting that the handlers refuse a
GET and that no rendered markup contains a send URL.

**The mechanism, stated rather than asserted.** Three independent guards, each already
frozen in an ADR, plus one new one that covers the case none of them reaches:

| Action | What makes a replay collide |
|---|---|
| Manual send | **The confirmation token IS part of the trigger identity.** A replay carries the same token, hashes to the same `identity_hash`, and `claim()` returns `SUPPRESSED` off the `UNIQUE` index — the same single statement that has prevented duplicate automatic sends since ADR-0004. Permanent, and it survives the token store being wiped. |
| Send now | `transition( scheduled → executing )`. The second caller gets `LOST_RACE` and returns without sending — ADR-0015 §8.2's lease, doing exactly what it was built for. |
| Cancel | `transition( scheduled → cancelled )`. Same. |
| Resend | **A single-use confirmation token**, consumed before anything is sent. |

**The token, and why it is a `delete` rather than a `select`.** A confirmation screen
issues a random token and stores it as a non-autoloaded option. The handler consumes
it with `delete_option()`, whose return value is decided by the **affected-row count**
of one `DELETE` statement — the same idiom `claim()` and `transition()` use, and the
reason is the same: two concurrent requests both pass any *read* check, and only one
can win a single-statement write. Read-then-delete would be a race with a window
exactly as wide as a double-click.

The token is required and consumed for **all four** actions, not only for resend. The
other three have stronger guarantees already, but a single uniform gate is one thing
to prove rather than four, and the backstops remain underneath it.

**Growth is bounded.** Tokens are non-autoloaded (so they never load on a normal
request), carry an expiry, and every issue purges a bounded page of expired ones. The
live set is bounded by the confirmations a merchant opens within the TTL.

### 6. Confirmation is a step, not a checkbox

No action that sends email executes without an explicit confirmation screen showing:
the rule, the order, **the recipients that will actually receive it** (resolved, not
the rule's definition), and what the action will do. The recipient list is resolved
for display through the same `RecipientResolver` the send uses, so the merchant is
shown the addresses that will really be used rather than `{customer_email}`.

Each dialog names its own consequence:

- **Resend** — that it renders from the rule as it is now, and, when the rule is
  disabled, that it is disabled and stays disabled.
- **Send now** — that the delay is skipped and the scheduled job is removed.
- **Cancel** — that **the identity is permanently consumed** (ADR-0015 §1a), so the
  rule cannot fire again for this order and trigger. This is irreversible and the
  merchant is told before confirming, not after.
- **Send manually** — the §2 note: this does **not** replace or suppress the
  automatic delivery, so the customer may receive the email again if the rule's
  trigger later fires.

### 7. Everything else is reused, not rebuilt

A second send path is how two send paths diverge. Manual sends therefore go through
the same components as automatic ones:

| Component | Shared how |
|---|---|
| Containment boundary | `Orchestrator::send()` — the same `try`/`catch` that keeps a throw out of the caller |
| Recipient resolution | `Orchestrator::resolve_recipients()` → `RecipientResolver` |
| Placeholder resolution | `Orchestrator::compose()` → `PlaceholderResolver`, fresh against the live order |
| Consolidation | `Consolidation::plan()` with the same cap and the same capped fallback |
| Logging | `DeliveryLogger`, typed `manual` or `resend` |
| Send-now execution | `ScheduledDelivery::run()` in full — lease, re-validation, containment, terminal write |

`send_scheduled()` and the new `send_manual()` both delegate to one private
`execute_claimed()`, so there is **one** body that builds a decision and enters
`send()`. The only difference is the `transition_from` field on the claim: `executing`
for a delayed delivery whose terminal write must be conditional on its lease
(ADR-0015 §8.1), absent for a manual one, which is the immediate path's unconditional
write. Nothing else differs, and gate 39 names each component with the test that
proves the manual path goes through it.

**Send now is the strongest case of this.** It does not re-implement execution at all:
it removes the queued job and then calls `ScheduledDelivery::run()`, which takes the
lease itself. Ordering the unschedule first is safe in every case *because the lease,
not the unschedule, is the guard* — a job that survives a failed unschedule fires
later, fails to take the lease from a terminal row, and exits. The outcome reported to
the merchant is read from the tombstone afterwards rather than guessed.

One consequence, stated: **send now re-validates exactly as the scheduler would**
(ADR-0015 §4). If the merchant disabled the rule after scheduling, send now cancels
with `rule_disabled` rather than sending — which is the same answer the delay would
have produced, and diverging from it would make "send now" mean something different
from "send".

### 8. `manual` and `resend` as attempt types

- `manual` — a send the merchant initiated for a rule that had not fired.
- `resend` — a send the merchant initiated for a delivery that already had a genuine
  attempt.

  > **⚠ CORRECTED DURING IMPLEMENTATION.** This section first claimed the type was
  > derived by `DeliveryDetailRepository::record_attempt()`'s
  > `$type_by_genuine_attempt` (ADR-0013 §6b). It is not: `record_attempt()` serves
  > the INSERT-mode render path, while a separate-mode send records through
  > `DeliveryLogger::write_attempt_rows()`, which hard-coded `auto`. The type is
  > therefore **declared by the action** — `resend()` passes `resend`, `send_manual()`
  > passes `manual` — and rides on the claim array beside `transition_from`, so the
  > shared send body applies it without knowing which caller invoked it.
  > `DeliveryDetailRepository` still validates the value against `TYPES`, so an
  > unrecognised type is refused at the storage boundary rather than stored.
- A merchant's **cancellation** row is typed `manual` too — it is a merchant action,
  and typing it `auto` alongside the scheduler's own cancellations would make the two
  indistinguishable in the history exactly where the difference matters.

## Consequences

- Four handlers join the gate-28 table, each with its capability check and its own
  nonce action.
- `DeliveryIdentity::TRIGGER_PREFIXES` grows by one member; the uniqueness key, the
  hash and the `UNIQUE` index are untouched.
- `DeliveryLogger::record_scheduled_cancellation()` gains an attempt-`type` argument
  defaulting to `auto`, so a merchant cancellation is distinguishable from the
  scheduler's without a second cancellation path.
- `Orchestrator` gains one public entry point and one shared private body; the send,
  resolve, render, fan-out and logging path is unchanged and unforked.
- The delivery history screen and the order panel gain controls in the space ADR-0018
  §9 deliberately left empty. **They are still empty for anyone without
  `manage_woocommerce`** — absent, not disabled, per ADR-0001.

### Accepted residual risks (deliberately not fixed)

- **A manually sent email can be followed by the automatic one** (§2). Disclosed in
  the confirmation rather than engineered away, because the alternative silently
  suppresses a rule.
- **A resend renders the rule as it is now**, so a resend after an edit does not
  reproduce what the customer originally received (§3). `rule_revision_sent` records
  which revision produced each attempt, so the history remains honest; reproducing the
  original would require retaining every rendered body forever.
- **Confirmation tokens are rows in `wp_options`.** Non-autoloaded, expiring, and
  purged a bounded page at a time on issue. A store that opens thousands of
  confirmation screens inside the TTL and completes none of them holds thousands of
  small rows until they expire.
- **Send now does not offer to bypass re-validation** (§7). A merchant who disabled a
  rule and then clicks "send now" gets a cancellation, not an email. Correct, and
  worth stating because it will read as a bug to somebody.
