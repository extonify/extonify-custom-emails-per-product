# ADR-0020: Preview and test emails — a render that writes nothing, and a send that is recorded honestly

Status: **Accepted** — 2026-08-13

## Context

Two capabilities ship together here and they are deliberately opposites.

**Preview** answers "what would this rule produce for this order?" It renders a real
message from a real order and puts it on a screen. It **writes nothing and sends
nothing** — no tombstone, no attempt row, no ledger slot, no scheduled action, no mail.

**A test email** answers "does this actually arrive, and does it look right in a real
mail client?" It is a **real send** through `wp_mail()`, so it must be recorded as one.

Two pieces of frozen machinery get their first feature consumer here, and both exist
because of defects found earlier:

- **ADR-0013 §5's preview scoping.** WooCommerce's `EmailPreview::render_preview_email()`
  calls `clean_up_filters()` with **no `try`/`finally`**, so an interrupted preview
  leaks `woocommerce_is_email_preview = true` for the rest of the request and a later
  **real** send classifies itself as a preview and silently writes no delivery record.
  `RenderContext` prefers core's signal but **demotes it** the moment reconciliation
  proves it leaked, and a preview render gets a frame and **no slot**. Until now that
  has only ever been exercised by tests.
- **`'test'` in `DeliveryDetailRepository::TYPES`.** Present since Prompt 2, **never
  written by any code path** — exactly where `'manual'` stood before ADR-0019. Its
  meaning is defined below rather than assumed.

> ⚠ **VERIFIED AGAINST THE BUNDLED WOOCOMMERCE, WHICH IS 11.0.1, NOT THE 10.9.4 EVERY
> EARLIER ADR NAMES.** Every behaviour those ADRs flag still holds — see *Flagged
> WooCommerce behaviour* at the foot of this document. The version drift itself is
> recorded as a finding for Prompt 13's compatibility matrix; nothing in this ADR
> depends on 10.9.4 specifically.

---

## Decision

### 1. A preview writes nothing, and the reason is structural

A preview resolves placeholders against a real order and renders the message in **HTML
and plain text**. It produces **no tombstone, no attempt row, no ledger slot, no
scheduled action and no mail**.

That is not a promise kept by a conditional. It is kept by three separate structures,
and each is named here because each has to survive a refactor:

| What stops the write | Where it lives |
|---|---|
| A preview render creates a **frame and no slot**, so it can never register a rule, never reach `awaiting_send`, never bind, and can never produce a record | `RenderContext::push()` + `RenderEvents::on_render_start()` (ADR-0013 §5) |
| The preview path **never claims an identity**, so `DeliveryRepository::claim()` is not called and no tombstone can exist | `Delivery\RulePreview` — it holds no `DeliveryRepository` at all |
| The preview path **never enters `Orchestrator::send()`**, so no attempt row and no `wp_mail()` | `Delivery\RulePreview` calls the composers directly and stops before the send |

#### 1a. How the preview enters the no-slot render state: BOTH signals, deliberately

`Delivery\RulePreview` enters the preview state by doing **both** of the things
ADR-0013 §5 recognises, and the reason is that each covers the case the other cannot:

1. **`RenderContext::mark_preview_pending( $email )`** on the object whose render is
   about to begin — the native `WC_Email` for insert mode, the plugin's `Custom_Email`
   for separate mode. This is the **plugin-owned** signal. It is render-scoped,
   consumed at the next `push()` (or `refuse()`), and **cannot leak**, because the one
   render that consumes it is the one it was set for.
2. **`woocommerce_is_email_preview` asserted true for the duration**, added before the
   render and removed in a **`finally`**. This is the **world-facing** signal: third
   parties, and WooCommerce's own code, read it to decide whether they are looking at a
   preview, and a preview that did not set it would have them behaving as though a real
   message were going out.

The `finally` is the entire difference between this feature and core's. Core adds the
filter in `set_up_filters()` and removes it in `clean_up_filters()` with nothing between
them to survive a throw. This plugin's removal is in a `finally` block, so an
interrupted preview of ours leaves the signal exactly as it found it.

**What happens when core's signal has already leaked from a third party's interrupted
preview earlier in the same request.** `RenderContext::push()` reads:

```php
$core       = self::core_preview_signal();
if ( ! $core ) { $this->signal_leaked = false; }      // a false reading heals trust
$trust_core = self::core_signal_available() && ! $this->signal_leaked;
$is_preview = $trust_core ? ( $core || $marker ) : $marker;
```

So with the signal distrusted, `$is_preview` is decided **by the marker alone**:

- **Our preview still classifies as a preview**, because we set the marker. The frame
  is created, no slot is opened, nothing is written.
- **A later real send still classifies as a real send**, because it has no marker — and
  that is the ADR-0013 §5 guarantee, restated: a leaked signal must never cost a
  merchant a delivery record.

`signal_leaked` is set by `reconcile_previews()` only when a **stale preview frame** is
found *and* core's signal still reads true — i.e. only when something was interrupted
and did not clean up. Our own preview cannot produce that state, because our `finally`
clears the filter; when our preview is interrupted, the next `push()` reads the signal
as **false**, reconciles the stale frame away, and proceeds with trust intact.

#### 1b. The demote-on-leak behaviour MUST survive this feature

Stated as an obligation rather than an observation, because it is the one thing on this
prompt whose failure is silent:

> **A preview that throws must not cause the merchant's next real delivery to write no
> record.** Neither the interrupted preview's stale frame, nor a `woocommerce_is_email_preview`
> left true by somebody else, may make a subsequent real send classify itself as a
> preview.

Gate 41 asserts both halves — an interrupted preview of ours, and a leaked signal from a
third party — with a **real** delivery performed afterwards **in the same request**.

> ### ⚠ A TIER 1 DEFECT WAS FOUND HERE DURING IMPLEMENTATION, AND FIXED
>
> Writing gate 41 surfaced a **pre-existing** hole between this clause and ADR-0012 §8,
> in code neither prompt had reason to look at before.
>
> **ADR-0012 §8's coarse guard did not participate in ADR-0013 §5's demotion.**
> `Orchestrator::is_rendering_preview()` read `woocommerce_is_email_preview` **raw**:
>
> ```php
> if ( true === apply_filters( 'woocommerce_is_email_preview', false ) ) {
>     return true;                       // ← believed unconditionally
> }
> ```
>
> and `is_operational()` is built on it. So after **any** leak of that signal — core's
> own interrupted preview, or a third party's — `Orchestrator::run()` returned `null`
> for **every separate-mode delivery for the rest of the request**: no claim, no
> tombstone, no attempt row, no log line, no email. A status change fires once, so that
> delivery was **silently lost**. Measured, not theorised: the first draft of gate 41
> staged the leak, ran a real delivery, and found zero rows and zero messages.
>
> **ADR-0012 §8's own docblock asserted this could not happen** — *"erring toward
> inertness here cannot drop a real delivery"*. That reasoning was wrong, and it is
> corrected rather than quietly worked around, because it is the same failure mode
> ADR-0013 §5 built demotion to prevent for insert mode.
>
> **The fix is one line and it weakens nothing.** The coarse guard now asks the same
> question the render context asks, answered in the same place:
>
> ```php
> if ( true === apply_filters( 'woocommerce_is_email_preview', false ) ) {
>     return ! RenderEvents::context()->signal_leaked();
> }
> ```
>
> - An **unproven** signal is still believed, which is ADR-0012 §8's original posture
>   and remains the safe direction to be wrong in — a preview must never mail a customer.
> - A signal `RenderContext::reconcile_previews()` has **proven** leaked (a stale preview
>   frame with the signal still true) is no longer believed by either guard.
> - It **reads** the established verdict and does not reconcile. Calling
>   `reconcile_previews()` from the delivery path would tear down a preview frame that is
>   still *live* whenever a third party triggers an order event from inside a preview
>   render, turning a coarse read into a destructive one.
>
> **This plugin's own preview cannot produce the state in the first place** (§1a's
> `finally`), so the fix is about *other people's* leaks. Gate 41b asserts both guards
> recover, with the stale frame produced by a genuinely interrupted render rather than by
> hand.

#### 1c. The preview does NOT apply `woocommerce_mail_content`, and that is a divergence from core

Core's `EmailPreview::render_preview_email()` finishes with
`apply_filters( 'woocommerce_mail_content', $inlined )`. This plugin's preview does not,
for two reasons that are the same reason twice:

- `woocommerce_mail_content` is `WC_Email::send()`'s **first** filter. Firing it from
  something that is not a send is precisely the divergence gate 39 exists to prevent.
- `RenderEvents::on_mail_content()` is registered on it at `PHP_INT_MIN` and calls
  `RenderLedger::reserve()`, which **unconditionally appends a reservation** — a blank
  one when no candidate exists. A preview that fired it would leave ledger residue on
  the request-shared singleton, contradicting §1 in exactly the way ADR-0005's
  "recording `is_preview` on a slot was not enough" already contradicted it once.

`WC_Email::style_inline()` **is** applied to the HTML format, because it is the
transformation `send()` performs on the message and omitting it would show the merchant
an unstyled approximation of the email rather than the email. It runs inside the
preview's containment boundary, because it applies
`woocommerce_mail_style_inline_callback`, which a third party owns.

### 2. A preview renders a REAL order, chosen by the merchant

**Decision: a real order, always.** The entire value of a preview is seeing real
placeholder values. A synthetic order — the road core's `EmailPreview` takes, with its
`PreviewOrder` at id 0 and its dummy products — renders `{customer_first_name}` as
`John` and `{product_name}` as `Dummy Product`, which teaches a merchant nothing about
the rule they just wrote.

**Which order.** The merchant either types an order id, or takes the default: **the most
recent order the rule's targeting matches**.

> ⚠ **THE SEARCH FOR THAT ORDER IS BOUNDED, AND THE BOUND IS THE DECISION.** It scans
> the most recent `RulePreview::MATCH_SCAN_LIMIT` (= 20) orders and stops at the first
> match. An unbounded "find me an order this rule matches" is a full order-table scan
> plus one targeting evaluation per row, on an admin request, on a store with a million
> orders — a resource that grows without bound in normal operation, which is Tier 1.
> Twenty is enough to find a match on any store where the rule is actually firing, and
> when it does not, §2a says so plainly rather than searching harder.

**Consequences, stated:**

#### 2a. No order matches → say so, and offer to preview anyway

The screen states that no recent order matches this rule's targeting, and still offers
preview against **any order id the merchant supplies**. A preview of a non-matching order
renders with **empty matched-item placeholders** and carries a visible, non-dismissible
note saying exactly that — because a preview that silently rendered `{product_name}` as
blank would look like a broken rule rather than a non-matching order.

#### 2b. Preview respects the SAME targeting the delivery phases use

Matched items come from `ManualDelivery::matched_items()` → `RuleMatcher::match_rule_against_order()`
— the same call, on the same matcher, that the automatic path and the manual path use
(gate 39). A preview showing content for an order the rule would not match is worse than
no preview: it is a confident wrong answer.

#### 2c. The preview reads customer personal data into an admin screen, and that is deliberate

A preview resolves `{customer_first_name}`, `{billing_address}`, `{customer_email}` and
the rest against a real order and renders them on screen. `manage_woocommerce` is
required — the same capability every other screen in this plugin requires
(ADR-0017 §1) — and the data shown is **the same data the merchant can already see on
the order screen itself**, reached with a capability they already hold to get there.

The boundary is therefore deliberate rather than incidental: **preview exposes no
personal data to anybody who could not already read it**, and it adds no new
capability, no new endpoint and no unauthenticated surface. What it must not do is
render for somebody without the capability, and gate 28 asserts that on the screen and
on every handler.

### 3. Preview covers both delivery modes

| Mode | What is rendered |
|---|---|
| **separate** | subject, heading and body exactly as the customer would receive them, inside the store's own WooCommerce email wrapper (`emails/email-header.php` + `emails/email-footer.php`), in **both** formats |
| **insert** | the **native email the rule targets**, rendered in full, with this plugin's content **in position** — so the merchant sees what the placement actually does |

Insert mode is where §1 matters most, because the insert path is the one with the
ledger. The native email is rendered by setting the object, the recipient and the two
order placeholders on the live registered `WC_Email`, marking the render a preview, and
calling **`WC_Email::get_content()` once per format** — **never `trigger()`**, which
sends. Every property touched (`object`, `recipient`, `placeholders`, `email_type`,
`sending`) is captured before and restored in a `finally`, which is more than core's own
preview does to the same shared object.

> ### ⚠ A FIDELITY DEFECT WAS FOUND HERE DURING IMPLEMENTATION, AND FIXED
>
> Both renderers first called `get_content_html()` and `get_content_plain()` **directly**.
> That is not what a send does. `WC_Email::send()` calls `get_content()`, and for a plain
> body `get_content()` does considerably more than fetch it:
>
> ```php
> wordwrap( preg_replace( $this->plain_search, $this->plain_replace,
>           wp_strip_all_tags( $this->get_content_plain() ) ), 70 )
> ```
>
> — the pass that turns `&mdash;` into `--`, `&#036;&nbsp;` into `$ `, deletes every
> other entity outright (ADR-0014 §9a), and wraps at 70 columns. So the plain-text
> preview showed the merchant WooCommerce's own **raw entities and unwrapped lines**,
> none of which a customer ever receives:
>
> ```
> Just to let you know &mdash; we’ve received your order…
> WCEP Preview Insert Product × 1            &#036;&nbsp;10.00
> ```
>
> against what actually sends:
>
> ```
> Just to let you know -- we’ve received your order, and it is now
> being processed.
> WCEP Preview Insert Product × 1 $ 10.00
> ```
>
> Both renderers now call `get_content()`, so the preview inherits that pass — and every
> future change WooCommerce makes to it, including the block-email branch below.
>
> **⚠ NO ASSERTION CAUGHT THIS.** Every test was green; the defect was found by *reading
> the captured sample* while writing this prompt's report. That is why the sample is in
> the report at all, and `PreviewRenderTest` now asserts the absence of `&mdash;`,
> `&#036;` and `&nbsp;` and the presence of the 70-column wrap, so it cannot come back.

#### 3a. A rule outside the vocabulary is REFUSED, not previewed

A rule whose `delivery_mode` or `consolidation` is not in the accepted set is refused
with the **same reason the read boundary gives** (ADR-0016 §1a, ADR-0019 §4 R3): the
rule is not deliverable, so a preview of it would be showing the merchant something that
would never send. `ManualDelivery::rule_refusal()` is reused for the mode and
consolidation halves rather than re-expressed, so the preview and the send cannot come
to different conclusions about whether a rule is usable.

**Insert mode is NOT refused for preview**, although ADR-0019 §4 R2 refuses it for every
sending action. The two are consistent: R2 refuses because insert content has no message
of its own to *send*. It very much has something to *show*, and showing it in position
is the point.

#### 3b. Preview is available while custom emails are globally switched off

ADR-0019 §4 R9 refuses a manual send when the feature is off, because ADR-0012 §5 says
nothing is claimed while it is off. A preview claims nothing, so R9 does not apply — and
previewing is exactly how a merchant checks a rule *before* switching the feature on.
The screen states that the feature is currently off and that nothing would be sent.

### 4. A test email is a real send, and `'test'` is defined here

#### 4a. Typed `test`, and excluded from idempotency

The attempt row is typed **`test`**, which `DeliveryDetailRepository` validates against
`TYPES` at the storage boundary. Per ADR-0005 a test send is **excluded from
idempotency**: it never consumes an automatic identity and never suppresses a real
delivery. §4d is the mechanism.

#### 4b. It sends ONLY to an address the merchant supplied

**The rule's own recipient definitions are not used, at all.** `resolve_recipients()` is
never called on this path. The address is:

- the one the merchant typed into the test form, or
- when they typed nothing, **the current user's own email address** —
  `wp_get_current_user()->user_email`.

It is validated with `is_email()` and passed through `HeaderGuard::strip()`. Exactly one
`to` address; **`cc` and `bcc` are empty strings**, so `Custom_Email::inject_copy_headers()`
contributes nothing.

> **A test that mails a real customer is the one outcome this feature must never
> produce.** Gate 42 enumerates every source an address could come from and shows each
> one excluded.

#### 4c. It renders the same content a real send would

Same `Consolidation::plan()`, same `PlaceholderResolver`, same `Custom_Email`, same
`Orchestrator` containment boundary, resolved against the **chosen real order**. What
the merchant tests is what the customer would get — with two deliberate differences, and
only two: the recipient (§4b) and the subject marker (§4e).

Because the content must match, a test send **refuses when the rule's targeting matches
nothing on the order** (as ADR-0019 does for a manual send). A message about no products
is not "what the customer would get", and the merchant who wants to see the template
against a non-matching order has **preview** for exactly that, with §2a's note attached.

#### 4d. A test creates its OWN tombstone, under `test:<token>`

`test` joins `DeliveryIdentity::TRIGGER_PREFIXES`, and the identity is

```
test:<32 lowercase hex characters>
```

— the confirmation token, exactly as ADR-0019 §2 does for `manual:`. This is an
**addition** to the identity vocabulary and not a weakening of it: the uniqueness key is
still `sha256(order_id|rule_id|mode|trigger_identity)`, the `UNIQUE` index on
`identity_hash` is untouched, and the form still satisfies
`is_valid_trigger_identity()`'s length bound and character class.

**Why its own tombstone rather than an attempt row on an existing one**, which is the
alternative the prompt names:

- A rule that has never fired for this order **has no tombstone to attach to**, and
  testing a rule before it has ever fired is the main reason to test one.
- An attempt row is written by `DeliveryLogger::record_send()`, which **finalises the
  tombstone it is written against**. A test would therefore move a real delivery's
  recorded terminal status — a test rewriting the history of a real customer email is a
  worse outcome than an extra row.
- A separate tombstone is what makes a test **visible as a test** when read back, by the
  history screen and by support, in the same way `manual:` is.

**It cannot block a later real delivery**, by construction: `TriggerEvent` emits only
`status:`, `transition:` and `refund:`; insert mode emits only `native:`; manual sends
emit only `manual:`. The prefixes are disjoint, the prefix is inside the hashed string,
and therefore no test can ever occupy the identity an automatic delivery will want.
Gate 43 asserts it by sending a test and then letting the trigger fire.

**And a replay cannot send twice.** The token is the uniquifier, so a resubmitted form
hashes to the same `identity_hash` and `claim()` answers `SUPPRESSED` off the `UNIQUE`
index — the same single statement that has prevented duplicate sends since ADR-0004,
underneath the single-use confirmation token of §5.

#### 4e. The subject is visibly marked as a test

The resolved subject is prefixed with a translatable marker — `[Test] ` — applied
**after** placeholder resolution and passed through `HeaderGuard::strip()` with the rest
of the line. A test landing in a shared inbox must not be mistaken for a live customer
email.

The marker rides on the claim array as `subject_prefix`, beside `attempt_type` and
`transition_from`, so the one shared composition body applies it without knowing which
caller invoked it — the ADR-0019 §8 pattern, reused rather than re-invented. The
**recorded** subject carries the marker too, because the history must say what was
actually sent.

### 5. Both are capability-checked; the SEND is POST-confirmed and single-execution

**Preview is a render.** It is a normal `GET` on this plugin's own screen, because it
writes nothing and sends nothing — the property that makes a `GET` unacceptable for a
send (gate 36: a link is followed by history, by a prefetcher, by a referrer) simply
does not apply to something with no side effect. It checks `manage_woocommerce` for
itself, on the screen and on the renderer.

**The test send follows ADR-0019 §5 unchanged**: POST only, a fresh **action- and
subject-specific** nonce, and a **single-use confirmation token** consumed by
`delete_option()`'s affected-row count. One click, one email.

It is implemented as a **fifth action on `Admin\DeliveryActions`**, not as a second
confirmation mechanism. That is deliberate: the capability → method → nonce → token
order, the refusal vocabulary, the post/redirect/get shape and the gate-28, gate-36,
gate-37 and gate-38 tables are all derived from `DeliveryActions::write_actions()`, so a
fifth member inherits every one of them and fails those gates if it does not.

The confirmation screen states, before the merchant commits, **the exact address the
test will go to** — resolved, not described — for the same reason ADR-0019 §6 resolves
recipients: a merchant who has not been shown the address has not confirmed anything.

### 6. Reuse, not a second renderer

A preview that told the merchant something the delivery path would not do is the failure
mode this section exists to prevent. Gate 39 applies unchanged and grows by both
features:

| Component | Shared how |
|---|---|
| Targeting / matched items | `ManualDelivery::matched_items()` → `RuleMatcher::match_rule_against_order()` — preview and test both |
| Consolidation | `Consolidation::plan()` with the same cap and the same capped fallback — preview and test both |
| Placeholder resolution | `PlaceholderResolver::for_delivery()` / `render_body()` / `render_sectioned_body()` via `Orchestrator::compose_preview()`, which is `compose()`'s own body |
| The email wrapper | `Custom_Email::render_preview()`, which applies the **same** `apply_runtime_state()` and calls the **same** `WC_Email::get_content()` the send calls, once per format |
| Rule usability | `ManualDelivery::rule_refusal()` — one answer to "is this rule deliverable" |
| Containment boundary | `Orchestrator::send()` for the test; `RulePreview`'s own `try`/`catch` for the preview, which runs the same third-party filters |
| Identity claim | `DeliveryRepository::claim()` for the test |
| Confirmation | `Admin\ConfirmationToken` + `Admin\DeliveryActions` for the test |

**Nothing needed a change to support these paths that weakens an ADR.** Four additive
changes were required and each is recorded here rather than made quietly:

1. `DeliveryIdentity::TRIGGER_PREFIXES` gains `test`, exactly as ADR-0019 added `manual`.
2. `Orchestrator::execute_claimed()` accepts an optional **recipient override** and an
   optional **subject prefix**, both carried on the claim array. The override is the
   only way to send to an address the rule does not name, and it is confined to the one
   caller that is allowed to: `send_test()`.
3. `Orchestrator::compose_preview()` exposes `compose()`'s result to a caller that will
   not send it. It builds no decision of its own and claims nothing.
4. `Custom_Email::render_preview()` renders the wrapper without sending. It applies the
   runtime state, calls the two content builders, and **restores the previous frame in a
   `finally`** — the same `capture_runtime_state()` / `restore_runtime_state()` pair
   `trigger()` uses, for the same nesting reason.

## Consequences

- Two admin surfaces join the gate-28 table (the preview screen and its renderer) and
  one handler joins it with its own nonce action (`wcep_send_test`).
- `DeliveryDetailRepository::TYPES`' last unwritten member is now written. Nothing in
  `TYPES` is unreachable after this prompt except `debug`, which ADR-0005 reserves for
  debug-mode rows.
- The delivery history shows test sends as ordinary deliveries typed `test`, under a
  `test:` identity, which is what makes them tellable from real ones.
- The preview screen renders **merchant-authored HTML on purpose**, which is a different
  escaping contract from every other screen in this plugin — see below.

### Escaping on the preview surface, which differs from everywhere else

Every other admin screen escapes every value at its point of output for its own context
(gate 31). The preview surface deliberately does not escape **one** thing: the rendered
message body, which is merchant-authored HTML and must render as HTML or the preview is
useless.

That is safe for a stated, checkable reason rather than by assertion:

- The body was passed through **`wp_kses_post()` at the storage boundary**
  (ADR-0012 §6) — the same filter `wp_editor()` applies to what the merchant types —
  and again by `Custom_Email::get_content_html()` before wrapping. `<script>`,
  `onerror=` and every other kses-forbidden construct is gone before the preview ever
  sees it.
- Placeholder **values** are escaped at substitution time, per output context, by
  ADR-0014 §3 — `htmlspecialchars()` called directly, in framework-free code, so no
  third party can filter the escaping off. The template is merchant-authored; the values
  are not, and they are never trusted.
- The rendered document is a **complete HTML document** (WooCommerce's wrapper), so it
  cannot be injected into the admin page's DOM at all. It is emitted into a
  **sandboxed `<iframe srcdoc>`**, `esc_attr()`-escaped into the attribute. The sandbox
  is empty (`sandbox=""`), so the document gets no scripts, no forms, no same-origin
  access and no navigation — the browser reconstructs it in an isolated context that
  cannot reach the admin page even if something did survive kses.
- **Everything else on the screen is escaped normally**: the subject with `esc_html()`,
  the plain-text body inside `<pre>` with `esc_html()`, the order id and the address as
  integers and `esc_attr()`.

Gate 12's test writes hostile values **directly past the repository**, so the kses
storage filter is bypassed and the surface has to hold on its own.

### Accepted residual risks (deliberately not fixed)

- **A test email costs an identity row.** Each confirmed test writes a tombstone that is
  never purged (ADR-0004 keeps tombstones forever). A merchant who sends a thousand
  tests has a thousand rows. Bounded by deliberate confirmed clicks, and the alternative
  — reusing an identity — is §4d's rejected design.
- **`woocommerce_email_recipient_{id}` can still redirect a test.** `WC_Email::get_recipient()`
  applies it, and this plugin does not remove third-party filters from WooCommerce's own
  hooks. A site that has hooked it has redirected *every* WooCommerce email, not just
  this one; gate 42 records it as the one recipient source outside this plugin's control
  and names it rather than claiming a guarantee it cannot make.
- **The 20-order scan can miss a matching order** on a store where the rule matches only
  older orders. Recorded rather than fixed: §2a offers an explicit order id, and the
  unbounded alternative is a resource problem.
- **A preview is not a delivery, so it proves nothing about deliverability.** A rule can
  preview perfectly and still fail to reach a customer because of SMTP, spam filtering
  or a `woocommerce_email_enabled_{id}` filter. That is what the test email is for, and
  the screen says so.

## Flagged WooCommerce behaviour

Verified against the **bundled WooCommerce 11.0.1** (the ADRs that flagged these
verified them on 10.9.4; all four still hold):

- ⚠ **`EmailPreview::render_preview_email()` still has no `try`/`finally`**
  (`src/Internal/Admin/EmailPreview/EmailPreview.php:353-373`): `set_up_filters()`,
  then a render that can throw, then `clean_up_filters()`. ADR-0013 §5's demotion is
  still required, and §1a above is still the reason this plugin sets and clears the
  signal itself.
- ⚠ **`WC_Email::send()` still has no `try`/`finally`** around its three `wp_mail`
  filter registrations (`includes/emails/class-wc-email.php:1228-1241`). ADR-0012 §11d's
  wrapper is still required.
- ⚠ **`WC_Email::get_content()` still strips all tags from the plain body**
  (`class-wc-email.php:872`), so ADR-0014 §3's amended "neutralised in both formats"
  reading stands.
- ⚠ **`templates/emails/email-header.php:113` still echoes the heading through
  `esc_html()`**, so ADR-0014 §3's heading dependency stands.

**One further WooCommerce behaviour is flagged here for the first time, because this is
the first feature that catches a throw from inside a template render:**

- ⚠ **`wc_get_template_html()` is `ob_start()` … `ob_get_clean()` with no
  `try`/`finally`** (`includes/wc-core-functions.php:369-373`), and every email template
  a preview touches goes through it. A throw from a template, a theme override or a
  third party's hook therefore leaves **one open output buffer per nested template**,
  permanently. It is this plugin's problem in particular for the same reason ADR-0012
  §11d's `send()` wrapper is: the preview **catches** the throw and lets the request
  continue, so the unbalanced buffer does not die with a fatal — it silently swallows the
  rest of the admin page the merchant is looking at. `RulePreview::as_preview()` records
  `ob_get_level()` on entry and discards anything left above it in its `finally`, never
  closing a buffer below its own entry depth. **Found by the gate-41 test, which PHPUnit
  reported as a risky test rather than a failure — an unbalanced buffer is invisible
  until something notices it.**

**One behaviour is NEW since 10.9.4 and is recorded for Prompt 13 rather than acted on
here:** `WC_Email::get_content()` now begins with a `get_block_email_html_content()`
branch (`class-wc-email.php:865-869`) which, when the block email editor feature is
enabled, returns block-rendered content and **forces `email_type` to `html`** — bypassing
`get_content_html()` entirely. This plugin's `Custom_Email` has no block template, and
the branch is behind `$this->block_email_editor_enabled`, so nothing changes on a default
store. Because §3's correction routes the preview through `get_content()`, a store that
*does* enable the feature previews what that editor produces rather than what this plugin
would otherwise have assembled — so the preview stays faithful by construction. It
remains flagged for the compatibility matrix because the plain format disappears entirely
on that path, which is a behaviour change the matrix should state rather than discover.
