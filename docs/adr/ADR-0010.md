# ADR-0010: Privacy subject resolution and pagination policy

Status: **Accepted** — 2026-07-26 (Prompt 2d)

## Context

Privacy resolution was corrected three times across Prompts 2a, 2b and 2c. Each
correction was sound and each one exposed the next question, because the *policy*
had never been written down — only the current implementation's behaviour had.

The questions arrived in this order:

1. the eraser missed fields that held personal data (`reason`, `failure_message`);
2. a row whose `recipient` was NULL was invisible to a recipient-string lookup, so
   the order linkage was added;
3. the order linkage then returned **every** row on the subject's order, including
   rows addressed to other people — which disclosed a third party's contact data in
   the subject's own access response.

The fix for (3) introduced a three-way ownership matrix, but still classified rows
against a single global notion of "the subject's rows". That is the next question,
and this ADR answers it and every remaining one at once.

Two facts drive the design:

- **CC and BCC recipients are locked v1.0 scope.** One delivery on one order writes
  several detail rows owned by *different people* (ADR-0009: one row per resolved
  recipient). Any resolution that treats "rows on the subject's order" as "the
  subject's rows" is wrong by construction.
- **A subject can hold different relationships to different deliveries.** They may
  own order X and merely be copied on order Y, in the same request. A single global
  classification cannot express that.

## Decision

### Subject classes, per tombstone — never global

Classification happens **per tombstone**, every time. There is no request-level
"this subject is an owner" flag.

- **ORDER_LINKED** — the tombstone's `order_id` belongs to an order associated with
  the subject, resolved through WooCommerce CRUD (`wc_get_orders()`), never by
  touching posts or postmeta.
- **DIRECT_LINKED** — the tombstone was discovered **only** because a detail row
  beneath it carries the subject's normalised address.

A tombstone reachable both ways is **ORDER_LINKED**. The stronger claim wins: being
the order owner subsumes also being a recipient.

### Row expansion

- **ORDER_LINKED tombstone** → expand to **all** sibling detail rows and apply the
  ownership matrix below. The order owner has a claim on the whole delivery record
  for their order, subject to third-party carve-outs.
- **DIRECT_LINKED tombstone** → include **only** rows whose `recipient` matches the
  subject. No siblings. **No NULL-recipient rows.**

  A person merely copied on a message has no claim on the order owner's data. An
  unattributed row under someone else's order is, by default, the order owner's —
  handing it to a CC recipient would be the same disclosure failure this ADR exists
  to prevent, only in the other direction.

### Ownership matrix — ORDER_LINKED tombstones

| Row class | Condition | Export | Erase |
|---|---|---|---|
| **OWN** | `recipient` == subject | all personal fields | all personal fields |
| **UNATTRIBUTED** | `recipient` IS NULL | all personal fields | all personal fields |
| **THIRD_PARTY** | `recipient` != subject | content fields only; contact fields omitted entirely; the row's own recipient address redacted from the content | content fields only; contact fields preserved |

**Contact fields:** `recipient`, `recipient_header`, `recipient_type`.
**Content fields:** `subject`, `snapshot`, `reason`, `failure_message`.

Contact fields on a THIRD_PARTY row are that other person's data. They are *omitted*
from the export rather than blanked, and *preserved* through erasure — one person
cannot erase another's record.

Content fields may describe the subject whoever the row was addressed to, so they are
in scope both ways. On export they additionally have the row's own recipient address
redacted, because a diagnostic routinely quotes it (`550 5.1.1 <manager@…>: rejected`)
and omitting the column alone would leak it through the back door.

### Ownership matrix — DIRECT_LINKED tombstones

Only **OWN** rows are in scope, handled exactly as OWN above, with one addition
below.

UNATTRIBUTED and THIRD_PARTY rows beneath a DIRECT_LINKED tombstone are **out of
scope entirely** — neither exported nor erased, not even partially.

**Foreign-address redaction on export.** A DIRECT_LINKED subject's own row still
quotes other people: a subject line reads `Order update for alice@example.test`,
a snapshot records `{"customer":"alice@example.test"}`. The row is theirs, but
the order owner's identity is not. So on export, every email address in a
DIRECT_LINKED row's content that is **not the subject's own** is redacted.

This is deliberately generic — it does not need to know who the other parties
are, only who the subject is — and it is the export-side counterpart of the
THIRD_PARTY redaction under an ORDER_LINKED tombstone. It applies to export
only: erasure clears those fields outright, so there is nothing left to redact.

It redacts *addresses*, not arbitrary personal names. A name that appears in
free text without an accompanying address is not detected; see the limits
recorded in `docs/p2-backlog.md`.

### Tombstone export

Both classes export the same minimal record: order id, delivery mode, trigger
identity, final status, first-recorded date. Never `identity_hash` — an internal key
of no value to the subject.

A DIRECT_LINKED subject demonstrably received that delivery, so the existence and
outcome of it are their own data and are disclosed.

**Tombstones are never erased, in either class.** Deleting one would silently re-arm
an already-delivered order (ADR-0004): a later status change would re-send an email
the customer already received. The tombstone contains no direct contact or
message-content fields, but remains linked to an order and is retained to prevent
unintended duplicate automatic deliveries.

### Comparison rule

Every address comparison uses the same ASCII-lowercase normalisation as storage
(`Recipient::normalize()`), applied to **both** the stored value and the incoming
request. No `strtolower()`, no `mb_strtolower()` — an address that folds differently
across hosts would be unfindable by the eraser on some of them.

### Pagination contract

**Exporter — offset paging is correct here.** Export mutates nothing, so the resolved
id set is stable across pages. Page over it with a plain offset.

Tombstone records are emitted in **bounded batches alongside** the detail pages, never
all at once on the final page: a subject with many deliveries would otherwise receive
one oversized final response, which is the failure mode pagination exists to prevent.

**Eraser — offset paging over a mutating set is PROHIBITED.** Erasure nulls
`recipient`, which is one of the two columns resolution matches on. The resolved set
therefore shrinks beneath the cursor: page 2 at offset 25 skips rows that moved into
positions 0–24 when page 1's rows stopped matching, and `done` reports true with rows
silently unerased.

Instead, on **every** invocation:

1. Re-resolve the rows currently **eligible** for this subject.
2. Process up to `PAGE_SIZE` from the **front**. Never apply an offset.
3. Return `done => false` while eligible rows remain; `done => true` only when none
   do.

**Eligibility** means the row is in scope for this subject *and* at least one field
this subject's policy would clear is currently non-null. An already-cleared row is
ineligible, which makes erasure **idempotent** (re-running clears nothing further)
and **convergent** (each pass strictly reduces the eligible set, so it terminates).

Note that eligibility is policy-aware: a THIRD_PARTY row is eligible only while one
of its *content* fields is non-null, because its contact fields are never cleared for
this subject. Without that, a third-party row would stay "eligible" forever and the
loop would not terminate.

### Documented bound — stated honestly

Resolution loads **all** matching order ids and **all** in-scope detail ids for the
subject on **every** invocation, then slices. Individual queries are chunked
(`IN (…)` lists in batches, order lookups in pages of 100), but **chunking a query is
not the same as bounding a request**: the invocation still materialises the full id
set in memory before paging over it.

This comfortably serves the realistic case. A subject with a few hundred orders and a
few thousand detail rows resolves to an id list of a few thousand integers — tens of
kilobytes, one pass per page. It is appropriate for a store's ordinary customers.

It is **not** appropriate at the scale of tens of thousands of deliveries for one
subject — a wholesale account with years of history, or a shared operations mailbox
CC'd on every order. There, resolution should become a query-level cursor: keyset
iteration over `(delivery_id, detail_id)` with the ownership predicate pushed into
SQL, so no invocation ever holds more than one page of ids.

That work is recorded in `docs/p2-backlog.md` as pre-release, not foundation. The
current implementation is honest about what it is: correct, chunked, and bounded in
practice rather than by construction.

## Consequences

- A CC-only subject can no longer receive the order owner's unattributed rows, and
  an order owner can no longer erase a CC recipient's contact details. Both
  directions of the disclosure failure are closed by the same rule.
- Resolution must carry tombstone provenance through to row expansion. Returning a
  flat list of detail ids is insufficient — the class is needed to decide expansion,
  so rows are returned already paired with their tombstone class and downstream code
  cannot lose the distinction.
- Erasure is safe to re-run at any point, including after a partial failure, and
  converges. It cannot silently skip rows.
- A subject with both relationships in one request is handled correctly, because
  nothing is decided globally.
- The exporter and the eraser now page by different mechanisms on purpose. That
  asymmetry is deliberate and documented; making them uniform would reintroduce the
  skip bug.
