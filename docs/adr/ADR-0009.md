# ADR-0009: Production storage schema

Status: **Accepted** — 2026-07-26 (Prompt 2)
Amended 2026-07-26 (Prompt 2a) — one detail row per RESOLVED recipient
(`recipient` normalised and indexed, plus `recipient_type` and the
non-searchable `recipient_header`); the retention purge gained a FAILED tier
and the two single-column detail indexes were replaced by one composite
`(is_debug, state, created_at)`; the tombstone's privacy wording corrected.

## Context

The frozen POC architecture (ADR-0004, ADR-0005, ADR-0007) specifies *what* must
be persisted — a durable delivery identity, a purgeable detail store, and rule
definitions — but the concrete schema was deliberately deferred to the production
phase and recorded in `docs/p2-backlog.md`. This ADR fixes that schema.

Three constraints drive it:

1. **ADR-0004 splits identity from detail.** The durable tombstone must survive
   retention purges and privacy erasure, because purging it would silently re-arm
   already-delivered orders. The detail store holds the personal data and is
   purgeable. These are therefore two tables, not one with a flag.
2. **ADR-0004(b) requires a fail-closed atomic claim** discriminated purely by
   affected rows. That needs a real `UNIQUE KEY` in the database — the constraint
   is the race protection, not application logic.
3. **Orders are reached only through WooCommerce CRUD.** No plugin query may touch
   `wp_posts` or `wp_postmeta` for order data; `order_id` is stored as a plain
   integer reference and resolved through `wc_get_order()`.

## Decision

### Three tables

All three use `$wpdb->prefix` (the current site's prefix — this plugin is
per-site-activation only) and `$wpdb->get_charset_collate()`.

#### `{prefix}extonify_wcep_rules` — rule definitions

`id`, `name`, `status` (`active`/`inactive`), `priority`, `revision`,
`trigger_type` (`status`/`transition`/`refund`), `trigger_value`, `delivery_mode`
(`insert`/`separate`), `native_email_id`, `insert_position`, `targeting` (JSON),
`recipients` (JSON), `subject`, `heading`, `content`, `delay_seconds`,
`consolidation`, `stop_processing`, `created_at`, `updated_at`.

Indexes: `(status, priority)` — the matcher's hot path is "active rules in
priority order"; `(trigger_type, trigger_value)` — narrows candidates for a fired
event before any JSON is decoded.

`revision` is incremented whenever any **behaviour-changing** field changes.
Amended 2026-07-26 (Prompt 2a): this is defined as an **exclusion list**, not an
inclusion list. Everything bumps the revision except the purely administrative
`name`, `status`, `priority`, `created_at` and `updated_at`. The original
inclusion list silently exempted `trigger_type`, `trigger_value`,
`delay_seconds`, `consolidation` and `stop_processing` — so changing a delay
from one day to seven left the revision unchanged and the ADR-0007 scheduling
snapshot could not distinguish which behaviour actually produced a delivery.
Inverting it makes every future column revision-bearing by default; exempting
one becomes a deliberate, reviewable edit.

`revision` exists for the ADR-0007 scheduling snapshot and for audit. Per
ADR-0004 it is **never** part of the delivery identity: editing a rule must not
re-arm an order that already received the email.

#### `{prefix}extonify_wcep_deliveries` — the durable tombstone (ADR-0004)

**Contains no direct contact or message-content fields; it retains a minimal
order-linked delivery identity for duplicate prevention.** An `order_id` is
linkable to a customer inside the store, so calling this row "non-personal"
outright was wrong — what is true is that it holds no address, no subject and
no message body, which is what makes retaining it indefinitely proportionate.
Columns: `id`, `identity_hash` (CHAR(64)), `order_id`,
`rule_id`, `mode`, `trigger_identity`, `first_claimed_at`, `last_seen_at`,
`final_status`, `suppressed_count`, `rule_revision_sent`.

`UNIQUE KEY` on `identity_hash`; `KEY` on `order_id`.

**Why a hash and not the raw tuple.** ADR-0004's identity is
`order_id | rule_id | mode | trigger_identity`. A composite `UNIQUE` over those
raw columns depends on `trigger_identity`'s length, and index-length limits vary
by MySQL/MariaDB version, storage engine, row format and collation — under
`utf8mb4` a generous `VARCHAR` can exceed the limit and the index silently fails
to create, which would remove the only race protection the design has. A
fixed-length `CHAR(64)` hash is 64 bytes on every configuration.

**The hash must be deterministic.** It is
`hash( 'sha256', order_id . '|' . rule_id . '|' . mode . '|' . trigger_identity )`,
computed by exactly one method, `DeliveryIdentity::hash()`. Normalisation is
explicit and uses **no locale-dependent or mbstring-dependent transformation**:

- integers are cast and rendered in base 10;
- string components are trimmed, internal whitespace runs collapsed, and
  case-folded **ASCII-range only** via `strtr()` — never `strtolower()`
  (locale-sensitive before PHP 8.2) and never `mb_strtolower()` (absent when the
  mbstring extension is not installed, so the same input hashes differently
  across hosts).

The sibling Extonify Address Book plugin shipped exactly that bug and needed a
recompute migration (its `HASH_VERSION` 2). This plugin starts at version 2-
equivalent rules and a unit test asserts stability across locale-sensitive inputs.
`DeliveryIdentity::HASH_VERSION` is recorded so a future change arrives with a
recompute migration rather than silently splitting identities.

`rule_revision_sent` is **audit only** and never part of the key.

#### `{prefix}extonify_wcep_delivery_details` — purgeable detail (ADR-0004/0005)

`id`, `delivery_id`, `parent_attempt_id`, `attempt`, `type`
(`auto`/`manual`/`resend`/`test`/`debug`), `state`
(`scheduled`/`sent`/`failed`/`cancelled`/`skipped`/`suppressed`), `reason`
(**personal**), `recipient` (**personal**), `recipient_type`
(`to`/`cc`/`bcc`), `recipient_header` (**personal**), `subject` (**personal**),
`snapshot` (**personal**; the ADR-0007 scheduling snapshot), `failure_message`
(**personal**), `is_debug`, `created_at`.

**ONE ROW PER RESOLVED RECIPIENT** (amended 2026-07-26, Prompt 2a). A delivery
to a customer plus one CC and one BCC writes **three** rows sharing
`delivery_id` and `attempt`. This is forced by privacy, not by tidiness: the
exporter and eraser find rows with `WHERE recipient = %s`, which only works if
the column holds exactly one address. A display name (`Alice <a@b.test>`) or a
comma-joined list would make a legally-required personal-data request silently
miss rows.

- `recipient` is `VARCHAR(191)`, holds exactly ONE address, is normalised to
  lowercase with **ASCII-range-only** folding (the same discipline as
  `DeliveryIdentity::hash()` — never `strtolower()`, never `mb_strtolower()`,
  because an address that folds differently across hosts would be unfindable by
  the eraser on some of them), and is **indexed** so a privacy lookup is not a
  full table scan.
- `recipient_type` records the channel.
- `recipient_header` keeps the original display-name form for the log. It is
  **never searched** and is erased like any other personal field. *(This is the
  STORAGE contract: the column holds a display name whenever one is handed to
  the repository. The automatic delivery path never hands it one — literal
  recipients resolve to bare addresses, decided in
  [ADR-0012 §4a](ADR-0012.md) — so `recipient_header` is null on `auto` rows and
  meaningful on manual and imported ones. Noted 2026-07-28, Prompt 4b.)*
- A comma-joined list is **rejected** at the storage boundary rather than
  stored raw. **The delivery engine must resolve recipients to one row each**;
  that engine is out of scope for this ADR, and refusing the input now is what
  prevents it from being written incorrectly later.

Indexes: `delivery_id` (join back to the tombstone), `recipient` (privacy
lookups), and one **composite** `retention (is_debug, state, created_at)`.
Amended 2026-07-26 (Prompt 2a): this replaces the separate `created_at` and
`is_debug` indexes, because the retention purge filters on all three columns
together and single-column indexes cannot serve that predicate.

**Retention has three tiers, not two** (ADR-0005: 90 / 180 / 14 days). The purge
takes `normal_days`, `failed_days` and `debug_days` and applies three distinct
predicates: `is_debug = 1`; `is_debug = 0 AND state = 'failed'`; and
`is_debug = 0 AND state <> 'failed'`. Before this correction every non-debug row
shared one window, so failed deliveries were destroyed at 90 days instead of the
documented 180 — and failure history is exactly what support needs longest.

**All timestamps are UTC.** `created_at` is written with
`current_time( 'mysql', true )` and compared against `gmdate()`. No datetime
column uses a MySQL `DEFAULT CURRENT_TIMESTAMP`: the database server's system
timezone is not necessarily UTC (on the development runtime it is UTC+5), so a
server-side default would skew every retention decision by that offset.

`delivery_id` is a foreign key **by convention, not by constraint**. WordPress
core ships MyISAM-compatible schemas and `dbDelta()` does not manage foreign keys;
declaring one would fail silently on some hosts. Referential integrity is enforced
in `DeliveryRepository::delete_for_order()`, which deletes details first,
**checks the result, and aborts the parent delete on failure** — a partial
cleanup would orphan detail rows permanently, unreachable even by the privacy
eraser. Both deletes run inside a transaction, the id list is chunked, and the
method returns a structured `{success, details_deleted, tombstones_deleted}`
rather than an ambiguous integer (amended 2026-07-26, Prompt 2a).

`parent_attempt_id` links manual resends into an attempt chain. Per ADR-0004 those
rows live **outside** the automatic uniqueness constraint: a human choosing to
resend is an intentional act and must not be blocked by the idempotency key.

### Migration runner

Schema version lives in the `extonify_wcep_db_version` option (non-autoloaded).
`Migrator` applies ordered, numbered steps and records the achieved version only
after verified success, so future changes are additive and testable. Tables are
created with `dbDelta()`, whose input formatting is load-bearing — two spaces
after `PRIMARY KEY`, `KEY` rather than `INDEX`, lowercase column types, one field
per line — because mis-formatted input fails **silently**.

Migration runs under a short-lived, atomically-acquired option lock so concurrent
activation or upgrade requests run it exactly once; a stale lock self-recovers. A
failure degrades the plugin to no-op mode behind an admin notice and is **never**
fatal. The stored error option carries only a stable code; SQL and host detail go
to the WooCommerce logger.

### Repositories

`RuleRepository`, `DeliveryRepository`, `DeliveryDetailRepository` in
`src/Repository/`. Every query uses `$wpdb->prepare()`; table names are built from
`$wpdb->prefix` plus a hardcoded literal and never from user input. JSON columns
are encoded and decoded through dedicated methods that validate on read and return
a safe empty array for malformed data rather than propagating `null`.

`DeliveryRepository::claim()` implements ADR-0004(b) verbatim: one
`INSERT ... ON DUPLICATE KEY UPDATE suppressed_count = suppressed_count + 1,
last_seen_at = VALUES(last_seen_at), id = LAST_INSERT_ID(id)`, discriminated by
affected rows — 1 claimed, 2 duplicate, **anything else a claim failure that
records `failed` and does not send**. Error text is never parsed.

## Consequences

- The unique constraint is a real database constraint, so two concurrent requests
  cannot both claim the same identity regardless of PHP-level races.
- The tombstone contains no direct contact or message-content fields, but
  remains linked to an order and is retained to prevent unintended duplicate
  automatic deliveries. It is small and holds no address, subject or message
  body, which is what makes retaining it indefinitely proportionate — and that
  in turn is what makes "never re-arm an old order" safe. Because it IS
  retained, the privacy eraser reports `items_retained` as true and says so.
- Retention and erasure act only on the detail table; both leave tombstones
  intact. This is asserted by integration tests, not merely documented.
- A permanently deleted order removes both its tombstones and its details, because
  the identity cannot be re-armed once the order is gone (ADR-0004's bound).
- Because `identity_hash` is a stored, indexed column rather than a computed one,
  a change to the hash algorithm requires a recompute migration. `HASH_VERSION`
  makes that explicit rather than discovered.
- `dbDelta()` cannot express foreign keys or `ON DELETE CASCADE`, so orphaned
  detail rows are prevented by repository discipline. A future move to an
  InnoDB-only floor could add real constraints.

### Claim input validation

`claim()` validates before it hashes or writes (amended 2026-07-26, Prompt 2a):
`order_id > 0`, `rule_id > 0`, a recognised mode, a `trigger_identity` that is
non-empty, within `VARCHAR(191)` and matching an ADR-0004 form
(`status:` / `transition:` / `refund:`), and `rule_revision_sent >= 0`. Invalid
input returns the **failed** result and writes nothing.

This is not defensive noise. A tombstone written under a meaningless identity
can never be matched again, so duplicate prevention silently stops working for
that delivery — the worst failure this table can have. `set_final_status()` uses
an allowlist for the same reason.

### The rule write boundary: every column is classified (amended 2026-07-30, Prompt 5B)

`RuleRepository::sanitize()` writes fourteen columns. Fixing their input handling
one column at a time guaranteed a fifteenth defect, so the whole boundary is
classified here and a future column inherits a decision rather than a habit.

**The two kinds, and why the split is not stylistic.**

- **VALIDATED** — enumerations and identifiers. Their meaning is a fixed set of
  values, so a value outside the set has no correct repair. Sanitising one does
  not produce a safe value, it produces a **different valid value**: junk becomes
  a working setting that behaves in a way nobody chose and nothing explains. These
  are checked against their **RAW** input — before any `sanitize_key()` or
  `sanitize_text_field()` runs — and a failure refuses the **entire write**:
  `insert()` returns `0`, `update()` returns `false`, and **any existing row is
  left byte-identical**. Half-writing a refused rule would be worse than either
  outcome.
- **SANITISED** — free text, documents and numbers. Their meaning is their
  content, so transforming them is lossless in the sense that matters: nothing
  downstream selects rows by them, and a stripped tag or a clamped integer changes
  presentation rather than behaviour.

| Column | Class | Contract on the RAW value |
|---|---|---|
| `status` | validated | exactly `active` or `inactive` |
| `delivery_mode` | validated | exactly `insert` or `separate` |
| `trigger_type` | validated | exactly one of `status` / `transition` / `refund` (ADR-0011 §2) |
| `trigger_value` | validated | normalisable by `TriggerEvent` within ADR-0011 §2's permitted transformations; malformed transitions refused |
| `native_email_id` | validated | `/^[a-z0-9_-]+$/`, at most `MAX_NATIVE_EMAIL_ID_LENGTH` (= the `varchar(100)` column width); empty permitted only on a non-insert rule |
| `consolidation` | validated | exactly `none` or `per_product` — `Consolidation::MODES` (ADR-0016 §1); the shape rules `/^[a-z0-9_-]+$/` and `MAX_CONSOLIDATION_LENGTH` (= the `varchar(20)` column width) are kept as the first test |
| `name`, `subject`, `heading` | sanitised | `sanitize_text_field()` |
| `content` | sanitised | `wp_kses_post()` — merchant-authored email HTML |
| `targeting`, `recipients` | sanitised | structured document encoding (`Targeting::encode()`, `RecipientsDocument::encode()`); `{}` not `[]` for an empty document |
| `priority`, `delay_seconds` | sanitised | integer cast, `delay_seconds` clamped at 0 |
| `stop_processing` | sanitised | boolean normalisation to 0/1 |
| `insert_position` | **repairs — the documented exception** | see below |

**Why each validated column is validated, in the words of what it broke.**

- `delivery_mode` was `sanitize_key()`-then-coerce-to-`separate`. `INSERT`,
  `insert!` and `" insert "` all became `insert` — and, far worse, **`unknown`
  silently became a `separate` rule**, so an importer intending to insert a block
  of content into WooCommerce's own email instead created a rule that **sends its
  own email directly to the customer**. The fallback was defended as making a rule
  do *less*; for this column it made it do *more*, to a real recipient.
- `status` had the identical shape, coercing to `inactive`. Safer in direction,
  identical in kind: the merchant's rule silently did not exist.
- `trigger_type` / `trigger_value` were corrected in Prompt 3b and are confirmed
  here unchanged: an unknown type is refused, never coerced to `status`.
- `native_email_id` was validated for shape but not LENGTH. A 300-character
  well-formed id passed and was **truncated by MySQL** into a different, shorter
  string — the same silent coercion arriving from the database instead of from
  PHP. The bound is one shared constant, used by the write and by
  `find_active_for_native_email()`, and a test asserts it against
  `information_schema` so it cannot drift from the column it protects.
- `consolidation` had `sanitize_key()` and no validation at all. Consolidation
  *behaviour* remains out of scope — only `none` does anything — so this is
  validated by **shape, not vocabulary**: the storage contract can say "does not
  repair" without inventing semantics it has not designed. When consolidation
  lands, this becomes an enumeration like the two above.

  > ⚠ **IT LANDED, AND THIS IS NOW AN ENUMERATION** ([ADR-0016](ADR-0016.md) §1,
  > Prompt 8). `daily`, `weekly` and `per_order` are **invalid values**, not merely
  > unimplemented ones. That closes a real hole rather than tidying a label: under
  > shape validation `daily` was storable and the PHASE FILTER was the only thing
  > stopping it from being delivered as `none` under another name, so one missing
  > filter turned a merchant's digest request into an email per order — which is
  > precisely what happened between Prompts 5B and 5C. A value that cannot exist needs
  > no filter to remember it. The shape rules stay as the first test, so the
  > `varchar(20)` width remains impossible to exceed even if the vocabulary is grown
  > carelessly, and the `information_schema` length assertion still has something to
  > compare.

**The documented exception: `insert_position` repairs, deliberately.**

An unrecognised `insert_position` is stored `sanitize_key()`-ed and falls back to
`after_order_table` at render time (`Injector::normalize_position()`). This is the
one repairing column and it is a decision, not an oversight:

- a position is **presentation**, not behaviour or targeting. Every value in the
  set puts the same content in the same email for the same order; only the
  location differs. There is no "different valid target" failure available here,
  which is the property that makes the other five refuse;
- the alternative failures are both worse. Refusing the write loses a rule over a
  cosmetic field, and emitting nothing gives a merchant a rule that is configured,
  active, matching — and invisible, with no way to tell why;
- the fallback is a real position, not a silent no-op, so the content still
  reaches the customer.

This was previously only a backlog note. It is recorded here so it is a decision a
future reader can disagree with explicitly, rather than the one unexamined
survivor of the sweep.

### Attempt allocation is atomic (amended 2026-07-30, Prompt 5B)

`DeliveryDetailRepository::record_attempt()` allocates the attempt number, writes
the attempt row and records the tombstone's resulting `final_status` and
`rule_revision_sent` **inside one transaction holding the parent row `FOR
UPDATE`**. It closes two races that the previous split — read the number, then
open the transaction — left open:

1. **Duplicate attempt numbers.** The number was computed from the tombstone's
   `suppressed_count` **outside** the transaction, so two concurrent recorders
   read the same value and both wrote the same attempt. `suppressed_count` was
   also the wrong source: it counts CLAIMS, not attempt rows, so a claim whose row
   failed to write left the numbering permanently offset. It is now
   `MAX(attempt) + 1` over the attempt rows, read under the lock.
2. **A tombstone contradicting its own highest attempt.** Request A inserted
   attempt 2, request B inserted attempt 3 and set `final_status = sent`, then A
   finished and set `final_status = failed`. Allocating and writing the status
   under one lock makes that ordering impossible: whoever allocates the higher
   number is necessarily the one who writes last.

A failed status write does **not** roll back the attempt row — the row records
something that really happened, and discarding it would destroy the only evidence
of a real send. The shortfall is reported to the caller instead (ADR-0012 §3).

Separate mode is deliberately unchanged: it writes one attempt per send with N
recipient rows sharing it, and tombstones are keyed by mode, so an insert
tombstone and a separate tombstone can never share an attempt sequence.

## Amendment history

- **2026-07-26 (Prompt 2):** Created. Fixes the schema deferred by the frozen POC
  backlog, adopting the fixed-length `identity_hash` unique key and the
  deterministic, locale-independent hash rules.
- **2026-07-26 (Prompt 2a):** Schema v1 amended in place (unreleased, so no
  migration 2).
  - **Recipient storage model.** One detail row per RESOLVED recipient;
    `recipient` normalised ASCII-lowercase, `VARCHAR(191)` and indexed;
    `recipient_type` and the non-searchable `recipient_header` added; header-form
    input parsed and comma-joined lists rejected. Why: the privacy exporter and
    eraser match on `recipient`, so anything else silently misses rows a personal
    -data request is legally required to return.
  - **Retention.** A FAILED tier added (`normal` / `failed` / `debug`), and the
    separate `created_at` and `is_debug` indexes replaced by one composite
    `(is_debug, state, created_at)` matching the purge predicate.
  - **Privacy completeness.** `reason` and `failure_message` recognised as
    personal — they routinely carry the address, customer names, order values and
    raw SMTP responses — so the eraser clears them and the exporter surfaces
    them, alongside `recipient_header`.
  - **Schema verification.** `Migrator::verify_schema()` reads the LIVE database
    (columns, column types, indexes, UNIQUE-ness) and the version option is
    stamped only after it passes. `dbDelta()` fails silently, so "the tables
    exist" was never evidence that the UNIQUE index guarding against duplicate
    sends had actually been created.
  - **Fail-closed order cleanup**, **claim input validation** and the
    **revision exclusion list**, all described in the sections above.
  - **Tombstone privacy wording corrected**: it holds no direct contact or
    message-content fields, rather than "no personal data" — an `order_id` is
    linkable to a customer inside the store.
- **2026-07-30 (Prompt 5B):** Schema v1 amended in place (still unreleased, so
  still no migration 2).
  - **The rule write boundary classified in full** — every column written by
    `RuleRepository::sanitize()` is now VALIDATED or SANITISED, with the
    enumerated and identifier columns validated on their RAW values and a refused
    write leaving any existing row untouched. `status`, `delivery_mode` and
    `consolidation` moved from sanitise-then-coerce to refuse; `native_email_id`
    gained the length bound its `varchar(100)` column always implied.
    `insert_position` is recorded as the single, reasoned repairing exception.
  - **Atomic attempt allocation** — `record_attempt()` allocates from
    `MAX(attempt) + 1` and writes the tombstone status inside the parent row
    lock, closing the duplicate-number and status-ordering races.
  - **`abandoned`** added to `DeliveryDetailRepository::STATES` and
    `DeliveryRepository::FINAL_STATUSES` (ADR-0013 §6a). Both columns are
    PHP-policed varchars, so this is a constant change and not a migration — the
    same reasoning that added `skipped` and `unresolved`.
- **2026-08-06 (Prompt 8):** No schema change.
  - **`consolidation` moved from SHAPE validation to an EXHAUSTIVE ENUMERATION**
    validated on the RAW value ([ADR-0016](ADR-0016.md) §1) — `none` or
    `per_product`, nothing else, with the shape rules kept as the first test. `daily`,
    `weekly` and `per_order` became invalid values rather than unimplemented ones.
    Why: shape validation left them STORABLE, with only a phase filter between a
    stored `daily` rule and delivery as `none` under another name.
  - **An insert rule may not consolidate**, refused at the write boundary on the
    EFFECTIVE mode and consolidation, exactly as a non-zero `delay_seconds` already is
    (ADR-0013 §2, ADR-0016 §2). `sanitize()` additionally forces
    `consolidation = 'none'` on an insert-mode write, for completeness rather than
    repair.
  - **`resolution` joined the matched-item record** (ADR-0011 §4, ADR-0016 §4). The
    item descriptor always carried it and the matched record dropped it, so every
    consumer treated a `partially_resolved` item as fully resolved. Not a storage
    change — the record is in-memory — but it is a contract change and is recorded
    here with the others.
