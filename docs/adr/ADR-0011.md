# ADR-0011: Rule matching semantics

Status: **Accepted** — 2026-07-26 (Prompt 3)

## Context

The matching engine answers one question: *which rules apply to this order for
this trigger, which line items they matched, and why*. Everything downstream —
claiming ([ADR-0004](ADR-0004.md)), logging ([ADR-0005](ADR-0005.md)),
scheduling ([ADR-0007](ADR-0007.md)), deferral ([ADR-0008](ADR-0008.md)) —
consumes its output and can only be as correct as the decisions handed to it.

Privacy resolution ([ADR-0010](ADR-0010.md)) needed four correction passes
because its policy existed only as the current implementation's behaviour. Each
pass was sound and each exposed the next question. Matching has **more**
decidable corners than privacy did: a targeting schema with two polarities and
five kinds, a five-rung specificity ladder that the schema has six kinds to fill,
a halt flag, a deferral rule, and eight reason codes whose loggability is a
policy decision rather than an implementation detail.

So every corner is settled here, before implementation, including the ones the
brief did not name. Where this ADR decides something the brief left open, the
decision is marked **DECIDED HERE** with its reasoning.

Three structural constraints frame the whole design:

1. **The engine writes nothing.** It is a pure function of
   `(order, trigger event, active rules)`. No claim, no log row, no order or
   product mutation. Anything that must be recorded is recorded by the delivery
   phase from the engine's returned result.
2. **A boolean answer is not sufficient.** ADR-0005 forbids logging a rule that
   merely failed targeting, while *requiring* that a rule which matched and was
   then excluded is logged. A boolean engine cannot tell those apart, which
   would make ADR-0005's logging policy unimplementable and leave the
   delivery-history panel with nothing to show. Reason codes carry that
   distinction from the first line of code.
3. **Orders and products are reached only through WooCommerce CRUD**
   ([ADR-0009](ADR-0009.md)). Never `wp_posts`, never `wp_postmeta`.

## Decision

### 1. Trigger matching

| Trigger type | Fires on | Identity ([ADR-0004](ADR-0004.md)) |
|---|---|---|
| `status` | order enters status S | `status:{S}` |
| `transition` | order moves A to B | `transition:{A}>{B}` |
| `refund` | full or partial refund | `refund:{refund_id}` |

A single status change evaluates **both families**: `status:{to}` rules and
`transition:{from}>{to}` rules, fetched with **two** separate
`RuleRepository::find_active_for_trigger()` calls. The two families produce
**two independent evaluations** with **two distinct trigger identities**, and
therefore two independent claims downstream. They are not merged, ordered
against each other, or deduplicated here.

Custom order statuses are discovered from `wc_get_order_statuses()`, so a status
registered by a theme or another plugin is matchable without any change to this
plugin.

**Status slug normalisation happens in exactly one place**,
`Domain\TriggerEvent::normalize_status()`: trim, collapse internal whitespace,
ASCII-range lowercase (via `Domain\DeliveryIdentity::normalize()`, so matching
and identity hashing agree by construction), then strip **one** leading `wc-`
prefix. `wc-Completed`, `WC-completed`, ` completed ` and `completed` all
normalise to `completed`. Every comparison, every fetch and every identity
string uses the normalised form. No other code may strip the prefix.

**`checkout-draft` never triggers anything — and the exclusion is load-bearing,
not incidental.** *(DECIDED HERE, corrected against the runtime.)* It would be
convenient to say "checkout-draft is excluded because `wc_get_order_statuses()`
does not return it". **That is false on any install with WooCommerce Blocks
active.** Verified on WC 10.9.4:
`Automattic\WooCommerce\Blocks\Domain\Services\DraftOrders` registers
`wc-checkout-draft` through the `wc_order_statuses` filter, so
`wc_get_order_statuses()` **does** return it and discovery alone would make it
matchable. The engine therefore carries an **explicit** exclusion constant.

**The destination status governs.** *(DECIDED HERE.)* A trigger is
non-triggering when its **destination** status is `checkout-draft` or is not a
known order status. Consequently:

- `status:checkout-draft` — never fires.
- `transition:{any}>checkout-draft` — never fires.
- `transition:checkout-draft>pending` — **does** fire. The order has *left* the
  draft state, which is a genuine lifecycle event and the exact moment a
  block-checkout order becomes real. Refusing it would remove the only way to
  target that event, and nothing about it is a draft-order notification.

A non-triggering event returns an empty result: no decisions, no deferral, no
identity claimed.

### 2. `rules.trigger_value` storage contract

*(DECIDED HERE. The brief specifies the identity strings; it does not say what
the rule row stores, and the repository fetch is an exact-match query — so this
has to be fixed or the matcher silently finds nothing.)*

`RuleRepository::find_active_for_trigger()` matches `trigger_value` with `= %s`.
The stored value is therefore **the normalised trigger value**, never a
`wc-`-prefixed or mixed-case one:

| Trigger type | Stored `trigger_value` | Example |
|---|---|---|
| `status` | normalised destination slug | `completed` |
| `transition` | `{from}>{to}`, both normalised | `pending>processing` |
| `refund` | **empty string** | `` |

Refund rules have no natural sub-value — ADR-0004 keys refunds by refund id, and
the brief's trigger table describes one refund family covering both full and
partial refunds — so `trigger_value` is empty and every active refund rule is a
candidate for every refund. Distinguishing full from partial refunds is
deferred (`docs/p2-backlog.md`).

**The REPOSITORY normalises on write, not the editor.** *(AMENDED 2026-07-27,
Prompt 3a. Supersedes "the rule editor must normalise on save".)* A rule stored
as `wc-completed`, `WC-COMPLETED` or `wc-pending>wc-processing` is never returned
by the exact-match fetch, so it never fires **and never explains why** — no
decision, no reason code, nothing in the delivery log. Placing that obligation on
the editor was the wrong boundary: the editor is one of several writers, while
`RuleRepository` is the only one **every** path crosses — importers, WP-CLI,
migrations, a future REST endpoint, and the editor itself.

`RuleRepository::insert()` and `::update()` therefore normalise
`trigger_value` before storage:

- **`status`** — strip **one** leading `wc-`, normalise case and whitespace,
  store the bare slug.
- **`transition`** — normalise both sides of `>` identically. A **malformed**
  transition (no `>`, more than one `>`, or an empty side) is **refused**:
  `insert()` returns 0 and `update()` returns false. There is no repair that is
  not a guess, and storing one produces a rule that can never match.
- **`refund`** — the value is forced empty. Changing a rule's `trigger_type` to
  `refund` re-normalises the value even when the caller did not mention it, or
  the row would keep a stale slug no refund fetch can match.
- A **partial update** of `trigger_value` that omits `trigger_type` reads the
  **existing row's** type, because `completed` normalises one way for a status
  rule and is malformed for a transition one.

**A dead or misclassified trigger is REFUSED, never coerced.** *(AMENDED
2026-07-27, Prompt 3b.)* Two gaps remained, and the second was the worse:

- An **empty or whitespace-only status value** stored successfully, and no real
  status event can ever fetch it — permanently dead, silently. Refused.
- A **status value that is not a slug** — `on hold`, `on.hold`, `wc-`, `100%` —
  stored after trimming and lowercasing, and likewise can never match. The value
  must now equal its own sanitised slug form: validated by **shape**, on both
  polarities and on **each side** of a transition.
- An **unknown `trigger_type` was coerced to `status`**, so `statuz` was silently
  stored as a working status rule. That is **worse** than an inert rule: junk
  input became a *different valid trigger* and the rule fired on events its
  author never chose — the identical failure shape as the `(int)` cast removed
  from id parsing, and refused for the identical reason. Falling back is right
  for `status` and `delivery_mode`, whose defaults make a rule do **less**; a
  trigger fallback makes a rule do something **different**.

Slug shape is checked by `TriggerEvent::is_valid_status_slug()` — a validator, not
a second normaliser. It is deliberately **stricter** than
`DeliveryIdentity::is_valid_trigger_identity()`, which permits spaces and dots
because it exists to reject invented identity *formats* rather than to know what
an order status looks like.

The normaliser is `Domain\TriggerEvent`'s and **there is no second one** — the
fetch compares the stored value against `TriggerEvent::value()` with `= %s`, so
the two agreeing by construction is the entire point.

**`find_active_for_trigger()` normalises its own argument too**, so the fetch
cannot miss from the other direction either. This costs no query.

Existing rows written before this amendment are **not** migrated; no released
build has stored any. Recorded in `docs/p2-backlog.md`.

### 3. Targeting schema

`rules.targeting` is JSON of this exact shape:

```
{
  "include": {
    "products":   [int],
    "variations": [int],
    "categories": [int],
    "tags":       [int],
    "types":      ["simple","variable","grouped","external","virtual","downloadable"]
  },
  "exclude": { ...same shape... },
  "match_all": false
}
```

**`match_all` lives at the ROOT and nowhere else.** *(AMENDED 2026-07-27, Prompt
3a.)* The implementation also read `include.match_all` and invented an
`exclude.match_all`. Neither was ever specified, and `exclude.match_all` had no
coherent meaning — a rule that excludes everything is simply an inactive rule.
Three spellings of one flag is three things import, export and future editor
validation each have to agree on. Both extensions are removed: `include.match_all`
and `exclude.match_all` are now ordinary **unknown keys** and are ignored.

- **Unknown keys are ignored** — at the root and inside `include`/`exclude`.
  Forward compatibility: a document written by a newer version degrades to the
  kinds this version understands rather than failing shut.
- **Malformed targeting means the rule matches nothing and reports
  `targeting_invalid`.** Malformed means *structurally* wrong, and validation is
  **strict** *(TIGHTENED 2026-07-27, Prompt 3a)*, because the alternative is
  silent: a malformed document that merely "declares nothing" reports
  `no_targeting_match`, which [ADR-0005](ADR-0005.md) does **not** log — so a
  corrupted, truncated or badly imported rule stopped working with **no entry
  anywhere in the delivery log**, the exact failure the decision log exists to
  eliminate. `[1,2]` and `{"include":[1,2]}` were both accepted as valid empty
  documents before this. A document is invalid when:
  - the JSON text is **syntactically** invalid, or decodes to something that is
    not an array;
  - the **root** is a **list** rather than an object;
  - `include`/`exclude` is present and is not an object — a scalar, or a
    list;
  - a known **kind** is present and is not an array;
  - **`match_all` is present and is not a real boolean.** `"yes"`, `"true"`, `1`
    and `0` are rejected rather than guessed at: guessing decides whether a rule
    targets the entire catalogue.
  - a known **kind** is written as a JSON **object** where a list is required.

  *(DECIDED HERE.)* Junk **entries** inside an otherwise well-formed kind are
  **dropped, not fatal**, and are **never converted** *(TIGHTENED 2026-07-27,
  Prompt 3a)*. `(int)` is not a validator: it turned `"1abc"` into 1, `"12x"`
  into 12, `true` into 1 and `1.9` into 1, so a rule could target a product
  nobody ever selected — worse than not working at all. An id entry is accepted
  only when it is a **real positive integer**, or a **string of nothing but
  decimal digits**. Booleans, floats, `null`, arrays, objects, mixed
  alphanumeric strings, signed strings, decimal strings, zero and negatives are
  all dropped. Non-string `types` entries are dropped likewise. **A digit string
  beyond `PHP_INT_MAX` is dropped too** *(ADDED 2026-07-27, Prompt 3b)*: the cast
  does not fail, it **clamps**, so `"999999999999999999999999999999"` became
  `PHP_INT_MAX` — one supplied id silently becoming a *different* id, which is
  exactly the coercion this parser exists to prevent. `PHP_INT_MAX` itself is a
  usable id; leading zeros still normalise (`"0100"` → `100`), because padding is
  not overflow. An oversized JSON *number* decodes to a float and is dropped by
  the existing type gate, so the hole is closed from both directions. The line is
  drawn at structure because a wrong-shaped container means the author's intent
  is unknowable, whereas one bad id in a list of twenty plainly is not.

  **Detecting syntactic malformation requires the RAW column.** `Json::decode()`
  returns an empty array both for an empty column and for one holding broken
  JSON, which is the right contract for a reader that just wants an array — but
  it collapses the exact distinction this reason code exists to make.
  `RuleRepository::hydrate()` therefore carries each JSON column's original
  string alongside the decoded array under `{$column}_raw`
  (`RuleRepository::RAW_SUFFIX`), and the matcher parses that when present.
  These keys are read-only passengers: `sanitize()` never emits them, so a
  hydrated row handed back to `update()` cannot write one.

**`{}` and `[]` are distinguished — at the RAW STRING boundary only.** *(AMENDED
2026-07-27, Prompt 3b. Supersedes "an empty array is accepted wherever an object
is required".)* The previous amendment accepted `[]`, `{"include":[]}` and
`{"exclude":[]}` as valid inert documents on the grounds that
`json_decode( $raw, true )` renders `{}` and `[]` identically. That is a
limitation of the **associative decode mode**, not of JSON: decoding *without* it
keeps objects as `stdClass` and arrays as arrays, and the distinction survives
exactly. Since the entire purpose of strict validation is that a corrupted or
truncated rule reports the **loggable** `targeting_invalid` rather than the silent
`no_targeting_match`, the distinction is worth making.

The boundary is therefore **split**, deliberately:

| Entry point | Input | `{}` vs `[]` | Empty document |
|---|---|---|---|
| `Targeting::from_value( string )` → `from_json()` | raw column text | **enforced** | `{}` valid, `[]` invalid |
| `Targeting::from_array( array )` | decoded PHP array | not available | `array()` valid |

`from_json()` decodes non-associatively, requires the root and each declared
`include`/`exclude` to be `stdClass`, requires each declared known kind to be a
JSON list, and only then converts to the internal array form. `from_array()`
accepts `array()`, because a **programmatically constructed** empty document is
legitimate and at that point the information genuinely no longer exists. Pretending
otherwise would reject valid callers to no benefit.

**The writer has to be as precise as the reader.** *(DECIDED HERE, forced by the
above.)* PHP renders `array()` as `[]`, so `Json::encode()` stored an empty
targeting document in exactly the shape strict reading now rejects — every
brand-new rule with no targeting yet would have reported itself
`targeting_invalid`, contradicting the "empty `include`" rule below.
`Targeting::encode()`
is the counterpart to `from_json()`: it casts object-shaped nodes in object
positions (the root, `include`, `exclude`) to objects, leaves kind entries as
lists, and leaves a genuinely list-shaped root alone so garbage still reads back
as invalid rather than being quietly repaired on the way in. `RuleRepository`
encodes the `targeting` column through it, on both write and revision comparison,
so the two can never disagree.

- **Both polarities are read.** `include` decides candidacy, `exclude` removes.
- **An empty `include` with `match_all: false` matches nothing** and reports
  `no_targeting_match`. A brand-new rule with no targeting yet is *valid* and
  simply inert — it is not `targeting_invalid`.
- **`match_all: true` matches every item**, at `match_all` specificity.
  *(DECIDED HERE, refinement.)* When `match_all` is true **and** the item also
  satisfies a declared `include` kind, the item records the **higher**
  specificity it actually achieved. In the ordinary case — `match_all` with an
  empty include — this is exactly "every item at global specificity"; the
  refinement only makes a mixed document report the truth rather than
  under-reporting it.

**`types` mixes two different kinds of thing, deliberately.** An entry matches
when **either**:

- the product's **type slug** equals the entry (`simple`, `variable`,
  `grouped`, `external`, and any custom type another plugin registers — the
  listed set is the WooCommerce core set, **not** a closed allowlist); **or**
- the entry names a **boolean flag** that is true on that product: `virtual`
  or `downloadable`.

A type slug and a product flag are not the same kind of thing — a product has
exactly one type but may carry both flags, and `virtual`/`downloadable` are not
values `WC_Product::get_type()` can ever return. Treating them identically in
this one list is a deliberate usability decision: a store owner thinking "send
this for downloads" should not have to know which of the two mechanisms
WooCommerce used. It is stated explicitly here so it is never mistaken for a
conflation.

**A variation item is matched against its parent's type slug as well as its
own.** *(DECIDED HERE.)* `WC_Product_Variation::get_type()` returns `variation`,
never `variable`, so `types: ["variable"]` would otherwise match no line item
that anybody ever actually buys — a variable product is only ever purchased as
one of its variations. The type slugs considered for an item are therefore
`{ the resolved product's own type slug } ∪ { the parent product's type slug, if
the item is a variation }`. Flags are read from the **variation itself**, which
is where WooCommerce stores per-variation `virtual`/`downloadable`.

### 4. Item matching

For each order line item:

- Resolve the product through **WooCommerce CRUD** (`wc_get_product()`).
- **If the product no longer exists, record `product_unavailable` for that item
  and skip it.** Never fatal, and **never** fall back to `wp_posts`. Other items
  on the same order still evaluate normally.
- A variation item carries **both** its variation id and its parent product id.
- Evaluate `include`, then `exclude`.
- **Exclusion always wins, at every specificity level.** An excluded item cannot
  be rescued by a more specific include. A rule that both includes variation V
  and excludes V's category matches nothing on that item.

**Identity comes from the order item; facts come from the product.** *(DECIDED
HERE.)* `product_id` and `variation_id` are read from the **line item**, which
stores them, so id-based targeting keeps working even when a product object no
longer loads. Type slugs, flags, category ids and tag ids can only come from the
product object.

**Resolution has THREE states, not two.** *(AMENDED 2026-07-27, Prompt 3a.)* The
two-state version — resolvable when *at least one* of the variation and parent
loads, facts taken from the most specific object available — was not merely
coarse, it was **affirmatively wrong** for a deleted variation whose parent
survives. Facts fell back to the parent, and a variation may be **virtual or
downloadable when its parent is not**, while `WC_Product_Variation::get_type()`
returns `variation` and never the parent's slug. A `types` rule could therefore
match on facts that **never applied to what the customer actually bought**.
Skipping the item instead is also wrong: the customer *did* buy that product, and
a category or tag rule should still fire after a discontinued variation is
removed.

| State | When | Item evaluated? | Note |
|---|---|---|---|
| `resolved` | everything needed loaded | yes, fully | none |
| `partially_resolved` | the **variation** is gone, the **parent** survives | yes, on identity only | `variation_unavailable` |
| `unresolved` | **neither** loads | no — skipped | `product_unavailable` |

For **`partially_resolved`**:

- **Identity matching proceeds.** Product id, variation id, category ids and tag
  ids come from the order item and the parent. This is safe because variations
  never carry their own category or tag terms anyway — see the flagged
  WooCommerce behaviour below — so the parent was already the source.
- **Variation-specific facts are UNKNOWN and are NEVER inherited.** The type slug
  and the `virtual`/`downloadable` flags are unavailable. A `types` entry
  **cannot match** a partially resolved item, on either polarity: unknown is not
  false, and it is certainly not the parent's value.
- The degradation is recorded with its own **loggable** item-level note,
  `variation_unavailable`, distinct from `product_unavailable`, so the delivery
  log can explain why a type rule stopped firing.

`product_unavailable` behaviour is unchanged: the item is skipped, other items on
the order still evaluate, and the request never fatals.

**Categories and tags always come from the parent product.** *(DECIDED HERE,
forced by WooCommerce.)* Verified against WC 10.9.4:
`WC_Product_Variation` does **not** override `get_category_ids()`/`get_tag_ids()`
and `WC_Product_Variation_Data_Store_CPT::read()` never populates them —
`parent_data` carries title, sku, stock, dimensions and image, and no taxonomy
at all. Reading them off the variation returns an empty array, so **every**
category and tag rule would silently miss **every** variation purchase. The
resolver therefore loads the parent product for a variation item and takes the
term ids from it.

**Variation fallback.** A rule targeting parent product P matches a variation of
P at **`product`** specificity. A rule targeting variation V matches **only** V,
at **`variation`** specificity. A variation id listed under `products` matches
nothing (it is not any item's product id), and a parent id listed under
`variations` matches nothing — the two lists are compared against the two
distinct ids the line item carries.

**Quantity is irrelevant to matching.** An item of quantity 5 matches **once**.
Two separate line items of the same product both appear in `matched_item_ids`,
while `matched_product_ids` is de-duplicated. The engine returns **both** lists;
consolidating them into one message, or one message per item, is a **delivery**
decision and is deliberately not made here.

**`exclude.match_all` no longer exists.** *(AMENDED 2026-07-27, Prompt 3a.
Supersedes "honoured literally".)* It was never in the schema, and a rule that
excludes every item is just an inactive rule — there is nothing for the honoured
reading to express that `status = 'inactive'` does not express better. Together
with `include.match_all` it is now an ordinary ignored unknown key; `match_all`
is read from the **root only** (§3).

### 5. Specificity ladder

```
variation 4  >  product 3  >  category 2  >  tag 1  >  match_all 0
```

**`types` shares rung 1 with `tag`.** *(DECIDED HERE — the ladder as specified
has five rungs and the schema has six include kinds, so `types` has to be
placed.)* The five named rungs and their numbers are fixed and not renumbered.
A type match ranks **above `match_all`**, because selecting "every downloadable
product" is a deliberate targeting act and not the absence of targeting; and it
cannot rank above `tag`, because a type is the broadest possible classification
— every product in the catalogue carries one. Rung 1 is the only placement
consistent with both.

**The LEVEL and the KIND are carried as two separate values, everywhere,
including in the serialised decision.** *(AMENDED 2026-07-27, Prompt 3a.)* The
rung is numeric and its only name is a rung name: `Specificity::label( 1 )` is
`tag`. The kind was recorded internally from the start, but the **serialised**
decision carried the bare rung — so a type-only match came out of the engine
indistinguishable from a tag match the instant it left PHP, in exactly the
payload the delivery log and the future admin panel consume. `to_array()` now
carries `specificity_level`, `specificity_kind` and the matched-item records.
**The numeric rung is never used as a human-readable match type.**

Specificity is recorded **per matched item** (level plus the kind that produced
it). A **rule's** specificity — used **only** for ordering — is the highest
level present in its **declared** `include`, computed from the declaration
rather than from the match, so ordering is stable, cheap, and independent of
which order happens to be under evaluation. A rule that declares nothing and
does not set `match_all`, and a rule whose targeting is invalid, both take
declared specificity `-1` and sort last within their priority.

**One parse, one representation, never supplied from outside.** *(ADDED
2026-07-27, Prompt 3c, closing a live violation of the paragraph above.)*
Ordering and evaluation read the same `targeting` column but from **different
representations of it**: ordering used the decoded array, evaluation used the raw
passenger. A document valid as an array and invalid as text —
`{"include":{"products":{"0":1}}}` — therefore sorted at **product specificity
3** while its own decision was `targeting_invalid` at **-1**, contradicting the
sentence directly above. **And it was not confined to log ordering:** at equal
priority it placed a malformed rule *ahead of* a valid `stop_processing` rule,
so the halt landed elsewhere, later rules received `blocked_by_stop_flag`
instead of their real reasons, and §6's deterministic sequence changed.

Two rules now hold, both enforced in `Domain\PreparedRule` rather than trusted:

1. **Each rule's targeting is parsed exactly once, before ordering**, and that
   single `Targeting` instance serves declared specificity, structural validity
   and item evaluation. The **raw string is authoritative** whenever the
   hydrated passenger is present; the decoded array is used only when no
   passenger exists at all.
2. **Declared specificity is always recomputed from the parsed document, never
   read from the row.** `Specificity::sort_rules()` annotates rows with
   `declared_specificity` for the caller's convenience; that annotation is
   **output only**. Otherwise any caller handing a previously sorted array back
   — or a hand-built row carrying the key — would dictate evaluation order
   directly, bypassing the declaration it is derived from. **Ordering is never
   externally supplied.**

### 6. Evaluation order and conflict resolution

Rules are evaluated in a **total, deterministic order**:

1. **`priority` ascending — lower runs first.**
2. then **declared specificity descending** (most specific first).
3. then **`rules.id` ascending**.

**The priority convention is explicitly "lower runs first", matching WordPress
hook ordering.** A store owner who knows `add_action( ..., 5 )` beats
`add_action( ..., 20 )` already knows this plugin's convention. The comparator is
total, so the result does not depend on the sort implementation's stability or
on the order rows came back from the database.

**Every matching rule produces a decision. Specificity is a tie-breaker for
ordering only — it never suppresses another rule.** Two rules that both match the
same item both fire. Duplicate-content protection is a **delivery** concern
(consolidation, ADR-0005's logging, ADR-0004's identity) and is deliberately not
implemented here.

**`stop_processing`.** When a rule carrying the flag **matches**, evaluation
halts immediately. Every rule not yet evaluated receives a
`blocked_by_stop_flag` decision, so the halt is visible in the log rather than
being an unexplained absence. Decisions already produced are unaffected, and the
halting rule keeps its own `matched` decision. A rule carrying the flag that does
**not** match does not halt anything.

**The halt is scoped to one trigger identity.** *(DECIDED HERE.)* A status change
evaluates two families as two independent evaluations; a stop flag in the
`status:` family does **not** halt the `transition:` family, and vice versa.
Cross-family halting would make the outcome depend on which family the engine
happened to evaluate first, which is exactly the non-determinism this section
exists to remove. Halting across families, if ever wanted, needs a superseding
decision.

### 7. Decision results and reason codes

Every rule returns a **structured decision, never a boolean**:

```
rule_id, matched (bool), reason (code), loggable (bool),
matched_item_ids[], matched_product_ids[], matched_items[],
specificity_level (int), specificity_kind (string), trigger_identity
```

*(`specificity` was a single numeric field until 2026-07-27, Prompt 3a — see §5
for why it had to be split.)*

| Reason | Meaning | Loggable |
|---|---|---|
| `matched` | at least one item matched and was not excluded | yes |
| `no_targeting_match` | no item matched the include set | **no** (debug only) |
| `excluded_by_rule` | matched the include set, then excluded | yes |
| `blocked_by_stop_flag` | a higher-priority rule halted evaluation | yes |
| `rule_disabled` | disabled between fetch and evaluation | yes |
| `targeting_invalid` | malformed targeting JSON | yes |
| `no_items_deferred` | ADR-0008 — trigger fired with zero line items | yes |
| `product_unavailable` | item-level note, product no longer resolvable | yes |
| `variation_unavailable` | item-level note, variation gone but parent alive | yes |

**Why `loggable` is carried and not derived later.** ADR-0005 forbids logging
rules that merely failed targeting — that silence is what keeps the log bounded
— while *requiring* that rules which matched and were then excluded are logged
(`excluded-after-product-match`). Those two outcomes are both "did not send", so
a boolean engine cannot distinguish them; the logging policy would be
unimplementable and the delivery-history panel would have nothing to show. The
reason code carries the distinction from the start, and `loggable` is a fixed
property of the reason rather than a judgement each caller re-derives.

**Reason precedence for one rule**, evaluated top to bottom:

1. `blocked_by_stop_flag` — the rule was never evaluated at all, so nothing else
   about it can be known. A disabled rule after a halt reports the halt.
2. `rule_disabled`.
3. `targeting_invalid`.
4. `matched` — at least one item survived exclusion.
5. `excluded_by_rule` — items matched the include set, and all were excluded.
6. `no_targeting_match`.

**`rule_disabled` needs no extra query.** *(DECIDED HERE.)* The engine re-reads
`status` on the row it was handed, immediately before evaluating it. Rules
fetched by the engine itself are `status = 'active'` by construction, so the code
path exists for a caller that supplies a set the engine did not fetch.
Re-querying each rule to check would violate the per-trigger query bound below.

> **SUPERSEDED IN PART — 2026-07-27, Prompt 3c.** This paragraph previously went
> on to name "the ADR-0008 deferred re-evaluation, where an arbitrary delay sits
> between fetch and evaluation" as the caller this path exists for. **That is
> withdrawn.** It described the matcher's `status` check as if it made a
> stale rule set safe to evaluate, which contradicted §7a below — and the
> delivery phase would have been written by reading both. Handing the matcher a
> set captured before a delay is **not** supported. §7a is the single contract;
> see it for what a deferred caller must do instead, and for the one legitimate
> use of `rule_disabled`.

### 7a. Rule-freshness contract

*(ADDED 2026-07-27, Prompt 3b. Previously assumed rather than written down.
Sole contract as of Prompt 3c — the §7 paragraph above is superseded in part.)*

> `RuleMatcher::evaluate()` is a pure function of the rule rows it is handed. It
> does not re-read rule state and makes no freshness guarantee. **Supplying
> current rules is the caller's responsibility.** The immediate path satisfies
> this by fetching immediately before evaluating. Any deferred path must
> re-validate rule existence and enabled state at execution time, per
> [ADR-0007](ADR-0007.md), before calling the matcher — that re-validation
> belongs to the delivery phase, not to the engine.
>
> The `rule_disabled` reason exists for callers that hand the matcher a row they
> have already determined to be inactive — for instance a deferred job that
> re-reads a rule and wants the outcome recorded in the log rather than silently
> dropped.

In one table, because this is the paragraph the delivery phase will be written
from:

| Path | What the caller does | What the matcher does |
|---|---|---|
| **Immediate** | fetch active rules, then evaluate **immediately** | evaluates the rows given |
| **Deferred** | **reload and revalidate** rules at execution time per [ADR-0007](ADR-0007.md), then hand over the **current** rows | evaluates the rows given |
| **Never** | hand over a set captured before a delay | — this is not supported |

`RuleMatcher` **never queries rule freshness itself**, on any path.

**Why the engine does not solve this itself.** A second staleness mechanism
running beside the ADR-0007 snapshot would be **two sources of truth for one
question** — the exact defect eliminated in [ADR-0002](ADR-0002.md) when per-rule
`WC_Email` registration was rejected. ADR-0007 already froze the mutation policy:
a scheduled delivery carries a snapshot, disabling or deleting a rule cancels its
pending deliveries immediately, and execution re-validates. The deferred path also
does not exist yet, so building its re-validation now would be speculative.

**`rule_disabled` is currently unreachable through the immediate path**, and that
is stated rather than assumed: `find_active_for_trigger()` filters
`status = 'active'` in SQL, so a disabled rule is simply absent from the set the
matcher is given. The reason code is **not dead code** — it is the delivery
phase's contract — but **nothing exercises it end to end yet**. The required
delivery-phase test is recorded in `docs/p2-backlog.md`.

**`product_unavailable` and `variation_unavailable` are item-level notes, never a
rule's reason.** They are carried on the order-level result as
`item_id → note`, because they describe the **order**, not any rule's decision. A
rule whose only candidate items were unresolvable reports `no_targeting_match`,
and a `types` rule that could not match a degraded item reports the same; the
note is what explains why. Both are loggable so support can see that the order,
not the rule, was the problem. They are **two codes, not one**: the log has to be
able to say whether the item was skipped entirely or merely lost its
variation-specific facts.

**`no_items_deferred` is the order-level result's reason**, not a per-rule one —
under §8 no rules are evaluated at all, so there are no decisions to carry it.

**The order-level result carries:** order id, trigger type, trigger value,
trigger identity, the `deferred` flag, an optional result-level reason, all
decisions **in evaluation order**, the per-item notes, and the **actionable
subset** (the decisions with `matched === true`, in the same order).

### 8. ADR-0008 deferral

If the trigger fires on an order with **zero line items**: evaluate nothing,
claim nothing, and return `deferred: true` with the **trigger identity
preserved**, so the later deferred evaluation reuses the identity the immediate
path would have used and the DB unique constraint collapses the two into one
claim ([ADR-0004](ADR-0004.md), [ADR-0008](ADR-0008.md)). Targeting is **not**
attempted against an empty item set — an empty set is not evidence that nothing
matches, it is evidence that the question cannot be answered yet.

The deferral test is applied **uniformly to all three trigger types**. ADR-0008's
motivating case is status-before-items, and a refund on a zero-item order is
pathological rather than expected; but the engine reports the same structural
fact in all three cases and the delivery phase's single-deferral cap bounds the
cost. Making the engine's answer depend on trigger type here would be an
unrequested behavioural difference in the one place ADR-0008 exists to keep
simple.

An order whose items all fail to resolve (`product_unavailable`) is **not**
deferred: it has items, they are simply gone. Deferring would re-run the same
question and get the same answer.

### 9. Purity, performance and determinism

- **No writes of any kind.** No claims, no log rows, no order or product
  mutation. This is asserted by an integration test that captures every write
  statement issued during an evaluation, not merely by row counts.
- **Reads only through WooCommerce CRUD.** Never `wp_posts` or `wp_postmeta` for
  order or product data.
- **Rules are fetched once per trigger family** — one query each, using the
  `(trigger_type, trigger_value)` index ([ADR-0009](ADR-0009.md)).
- **Each line item's product is resolved once**, and its category and tag term
  ids once, cached for the request. A second line item of the same product costs
  no further query, and both trigger families of one status change share one
  resolution pass.
- **Never query per rule per item.** The query count is a function of the number
  of **distinct products** on the order plus a constant, and is **independent of
  the number of rules**. The engine's own query cost does not grow at all with
  rule count beyond the one fetch per family.
- **Determinism.** The same inputs always produce the same decisions, with the
  same reasons, in the same order. The ordering comparator is total, and item
  and product id lists are emitted in line-item order with duplicates removed
  from `matched_product_ids` only.

### 10. Invalid trigger identity

*(DECIDED HERE.)* A trigger event whose identity does not satisfy
`DeliveryIdentity::is_valid_trigger_identity()` — an empty status, a status
containing characters the identity grammar forbids — returns an **empty result**:
no decisions, no deferral. No new reason code is introduced for it. Downstream,
`DeliveryRepository::claim()` already refuses such an identity (ADR-0009 §Claim
input validation), so the engine and the storage layer agree: an identity that
cannot be reproduced by a later call must never reach the tombstone, because a
tombstone nobody can match again silently disables duplicate prevention for that
delivery.

## Consequences

- The delivery phase receives, for every trigger, an ordered and complete
  account of what happened — including the rules that did *not* fire and why —
  and can implement ADR-0005's logging policy by reading `loggable` rather than
  re-deriving it from a boolean and a guess.
- One status change producing two identities means a store owner can have a
  status rule and a transition rule both fire for the same change, each with its
  own claim. That is intended: they express different intents.
- Because the halt is per-identity, adding a transition rule can never silently
  suppress a status rule, and the two families can be reasoned about
  independently.
- Because a rule's ordering specificity is computed from its **declaration**, the
  evaluation order for a set of rules is the same on every order. Support can
  reproduce an ordering complaint without needing the customer's cart.
- Because exclusion always wins, "everything in this category except that one
  product" is expressible and cannot be defeated by a more specific include
  elsewhere in the same rule.
- Because quantity is ignored and both item and product id lists are returned,
  the delivery phase can choose per-order or per-item consolidation later
  without the engine having pre-judged it.
- A deleted product degrades one item, never the request, and the order-level
  note says so — instead of the rule appearing to have simply not matched.
- Zero-item orders are handled structurally rather than by accident: the engine
  refuses to answer, ADR-0008's deferral asks again later, and the shared
  identity guarantees the two paths cannot both send.
- The engine is testable without WordPress for every decision that does not need
  a product: targeting, specificity, ordering and identity construction are pure
  value objects, and only the item resolver touches WooCommerce.
- **`checkout-draft` is excluded by an explicit constant**, so a future
  WooCommerce change to what `wc_get_order_statuses()` returns cannot
  accidentally make draft orders start sending customer email.

## Flagged WooCommerce behaviour

Recorded here and in `docs/p2-backlog.md`; **re-check on version bumps.**

- **⚠ A DELETED VARIATION ERASES ITS ID FROM THE ORDER LINE ITEM'S CRUD
  ACCESSOR — this CONTRADICTS §4's premise that identity survives.** *(Found
  2026-07-27, Prompt 3a; verified WC 10.9.4.)*
  `WC_Order_Item_Product::set_variation_id()` rejects any value whose
  `get_post_type()` is not `product_variation`, and the data store sets it
  through `WC_Data::set_props()`, which **swallows the resulting
  `WC_Data_Exception` per property**. Once the variation post is deleted,
  `get_variation_id()` therefore returns **0** while `_variation_id` still holds
  the real id in `woocommerce_order_itemmeta`. §4 states that `product_id` and
  `variation_id` "are read from the line item, which stores them, so id-based
  targeting keeps working even when a product object no longer loads." **That is
  false for `variation_id` on this runtime.** The consequences, left unhandled,
  are exactly what the three-state amendment exists to prevent:
  - a `variations` rule silently stops matching a purchase that plainly was of
    that variation; and
  - the line item disguises itself as an ordinary **parent-product** purchase, so
    the resolver loads the parent as the primary object and hands targeting the
    **parent's** type slug and flags — with nothing anywhere marked degraded,
    because nothing looks degraded.

  `Matching\ItemResolver::variation_id()` therefore falls back to
  `wc_get_order_item_meta( $item_id, '_variation_id', true )` — WooCommerce's own
  public order-item meta API, and the **same source**
  `WC_Order_Item_Product_Data_Store::read()` reads this property from, so this
  stays inside CRUD (ADR-0009): no `wp_posts`, no `wp_postmeta`, no direct SQL.
  It costs no query, because the data store's own `get_metadata()` calls during
  `read()` have already primed the `order_item` meta cache. Pinned by
  `MatchingTargetingTest::test_deleted_variation_with_surviving_parent_is_partially_resolved()`,
  which asserts **both** halves — the accessor reporting 0 and the meta still
  holding the id — so an upstream fix shows up as a failing test rather than as
  silently dead code.

- **`wc_get_order_statuses()` includes `wc-checkout-draft`** whenever WooCommerce
  Blocks is active (verified WC 10.9.4, via
  `Blocks\Domain\Services\DraftOrders::register_draft_order_status()` on the
  `wc_order_statuses` filter). Discovery alone therefore does **not** exclude
  draft orders; the explicit exclusion above is what does.
- **A variation carries no category or tag term ids** (verified WC 10.9.4).
  `WC_Product_Variation` inherits `get_category_ids()`/`get_tag_ids()` unchanged
  and its data store never populates them, so both return empty. Category and tag
  targeting must resolve through the parent product or it misses every variation
  purchase.
- **`WC_Product_Variation::get_type()` returns `variation`, not `variable`.**
  Type targeting must consider the parent's type slug for variation items.
- **`wc_get_product()` returning an object is NOT evidence the product exists**
  (verified WC 10.9.4). The two data stores disagree about a missing post:
  `WC_Product_Data_Store_CPT::read()` **throws**, the factory catches it and
  `wc_get_product()` returns `false`; but
  `WC_Product_Variation_Data_Store_CPT::read()` **returns silently**, so a
  deleted VARIATION yields a fully constructed, entirely hollow
  `WC_Product_Variation` — type `variation`, both flags false, no term ids, and
  a real-looking id. Believing it would report a deleted variation as an
  ordinary variation that simply matched nothing, instead of
  `product_unavailable` — precisely the silent miss §4 exists to prevent.
  Resolution therefore also requires `WC_Data::get_object_read()`, checked for
  **every** product type rather than only variations, so the plugin does not
  depend on which store throws today.
