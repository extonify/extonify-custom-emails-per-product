# ADR-0017: The rules admin — placement, the editor–validator contract, and the shape of a refusal

Status: **Accepted** — 2026-08-08

## Context

Every delivery feature in the locked v1.0 scope is built. This ADR covers the
surface a merchant actually touches: the menu, the rules list, the rule editor,
and the handlers behind them.

**The risk profile is different in kind from every prompt before it.** The
delivery machinery had a small number of deep invariants — identity,
correlation, phase isolation, state machines — and its defects were subtle,
singular and reachable only by reasoning. An admin surface has **breadth**
instead: every form field is an input boundary, every rendered value is an
escaping decision, every handler is a capability decision and a nonce decision.
The failure mode is not one clever bug. It is **one field out of forty**.

That changes what an argument is worth here. "All handlers check the
capability" is not evidence; a table naming each handler, its capability check,
its nonce action and the test that asserts both is. This ADR is therefore
written as **enumerations** rather than as principles, and the gates that
enforce it (28, 31) fail on *absence from a table* rather than on a
demonstrated defect.

It also changes what counts as severe. In the delivery machinery a Tier 1
finding was a wrong or duplicate email. Here a missing `current_user_can()` is
privilege escalation and an unescaped echo is stored XSS, so **both are Tier 1**
under the existing bar, for a consequence the delivery bar never had to name.

---

## Decision

### 1. Placement, and one capability everywhere

**The screens live under the WooCommerce menu**, as a submenu of `woocommerce`:

| Screen | URL | Menu |
|---|---|---|
| Rules list | `admin.php?page=extonify-wcep-rules` | WooCommerce → Custom Product Emails |
| Rule editor | `admin.php?page=extonify-wcep-rules&action=new` / `&action=edit&rule={id}` | — (reached from the list) |

**Why the WooCommerce submenu and not a top-level menu.** This plugin is
meaningless without WooCommerce — `Requirements::check()` refuses to wire
anything without it, and `Requires Plugins: woocommerce` is declared in the
header. A rule targets WooCommerce products, fires on WooCommerce order events
and either sends through or inserts into a WooCommerce email. A merchant looking
for it will look where the rest of their store's email settings are. A top-level
menu would also claim a slot in a sidebar that ordinary stores already overflow,
which is precisely the kind of self-importance a free plugin has no licence for
(ADR-0001).

**The editor is the same page slug with an `action` parameter, not a second
submenu entry.** A hidden submenu page (`add_submenu_page` with a `null` parent)
is the other conventional option; it costs an extra registered page, an extra
entry in the gate-28 table and a second capability surface, and buys nothing the
`action` parameter does not already give. One page slug, one registration, one
capability check at the top of one dispatcher.

**The capability is `manage_woocommerce`, everywhere, with no exceptions.** It
is the capability the original technical requirements name, it is what
WooCommerce itself gates its settings and its email configuration with, and a
rule editor is a mail-sending configuration surface.

> **⚠ EVERY ENTRY POINT CHECKS IT FOR ITSELF. No handler trusts a prior check
> made by another.** The menu registration's own capability argument is what
> WordPress uses to decide whether to *draw the link*, and a drawn link is not
> an authorisation — `admin.php?page=…` is reachable by URL whether or not the
> menu rendered it, and `admin-ajax.php` never consults the menu at all. The
> gate-28 table exists because the alternative is a handler that is safe today
> because of where it happens to be called from.

### 2. THE EDITOR–VALIDATOR CONTRACT (the load-bearing decision)

`Domain\Targeting` and `Domain\RecipientsDocument` validate their raw stored
strings **strictly**, and deliberately so (ADR-0011 §3, ADR-0012 §4): the root
must be object-shaped, `include`/`exclude` must be object-shaped, each known
kind must be a JSON list, ids must be positive integers or digit-strings within
`PHP_INT_MAX`, `match_all` must be a real boolean, and `{}` is a different
document from `[]`.

A document that fails any of that is `targeting_invalid`. That is a **loggable**
outcome — which is the whole point of the strictness — but it is **invisible to
a merchant who has just clicked Save**. The rule saves, reports success, and
never fires; the only trace is a WooCommerce log line the merchant will never
read.

> **THE EDITOR MUST THEREFORE BE STRUCTURALLY INCAPABLE OF PRODUCING A DOCUMENT
> EITHER VALIDATOR REJECTS.** Not "validated so it does not". Incapable.

**How that is guaranteed, not merely intended:**

1. **The browser never sends a document.** It sends *field values*: checkbox
   sets of ids, checkbox sets of type slugs, and one `match_all` checkbox. There
   is no request shape in which a JSON string reaches the storage layer.
2. **The document is assembled server-side by one function**,
   `Admin\RuleDocuments::targeting()`, from already-parsed values. It is a pure
   function of `(array $input) → array`, free of WordPress and free of `$_POST`,
   so the space of documents it can emit is a property of its code rather than
   of a request.
3. **Every id is produced by `Admin\RuleDocuments::id_list()`**, whose output
   type is `int[]`, strictly positive, unique, and — this is the part that
   matters — **never a repair**. It reads the same "a cast is not a validator"
   contract `Targeting::positive_int()` holds: `1abc`, `1.9`, `true`, `-3`,
   `0`, an oversized digit string and a nested array are **dropped**, never
   coerced into a different id.
4. **Every type slug is produced by `RuleDocuments::type_list()`**, whose output
   is non-empty lowercase `[a-z0-9_-]` strings, unique.
5. **An empty kind is omitted, an empty side is omitted, and `match_all` is
   always written as a real PHP `bool`.** So the emitted structure is exactly:
   a root object; optionally `include` and/or `exclude`, each an object with at
   least one kind; each kind a non-empty list; `match_all` a boolean.
6. **`Targeting::encode()` is the only writer**, as it already was. It casts the
   root and each object-shaped side to `stdClass` so an empty document stores as
   `{}` and never as `[]`.

The same six points hold for `RuleDocuments::recipients()` against
`RecipientsDocument`: three channels, each omitted when empty and otherwise a
list of non-empty strings, root always object-shaped.

**What "prove, not sample" means here (gate 29).** The emitted structure has a
finite shape-space that is *exhaustively enumerable*, and the test enumerates
all of it rather than picking documents:

- **targeting** — each of 2 sides is any of the 2⁵ = 32 subsets of
  `Targeting::KINDS`, and `match_all` is either boolean: **32 × 32 × 2 = 2048
  documents**, every one encoded and read back through the *raw string* path,
  asserting `is_valid()`.
- **recipients** — each of 3 channels present or absent: **2³ = 8 documents**,
  every one encoded and read back, asserting a non-`null` decode.
- **the value space** is infinite and is therefore handled by *type* rather than
  by enumeration: `id_list()` and `type_list()` are driven over a hostile corpus
  and asserted to emit only values of the constrained output type, so the
  structural enumeration over representative values is a complete proof.

**No raw JSON editing in v1.0.** A textarea accepting arbitrary JSON hands the
merchant a loaded footgun — every failure mode above, back in one control — for
a benefit the field UI already provides in full. **A future power-user view
would need its own ADR**, and that ADR would have to answer how a merchant sees
`targeting_invalid` before saving, which is the question this section exists to
close.

### 3. A refused write must never look like success

The repository refuses `status`, `delivery_mode`, `trigger_type`,
`trigger_value`, `native_email_id` and `consolidation` on the **effective**
value, returning `0` from `insert()` and `false` from `update()` (ADR-0009,
ADR-0013 §2, ADR-0016 §1a). The Prompt 7A backlog already records that a generic
"could not save" would discard a specific meaning the storage layer had and the
merchant needed.

**Decision, in four parts:**

1. **The repository's return value is the sole source of truth for the
   outcome.** Not the admin layer's own opinion of the input, not the absence of
   a thrown exception. `0`/`false` is a failure and nothing overrides it.
2. **A refusal re-renders the editor with the merchant's input intact**, in the
   same request. There is no redirect. A silent redirect-on-failure — the shape
   that loses the input and shows a generic notice — is **prohibited**.
3. **The error names the specific field and why it was refused**, and the field
   is marked in the form.
4. **No success notice is emitted**, and the stored row is left byte-identical.

**Where the field name comes from, without duplicating the rules.** The
repository is the only thing that knows why it refused, so it is what says so:
`RuleRepository::explain_refusal()` is now **public**, and
`write_is_valid()` is implemented *in terms of it*:

```php
private static function write_is_valid( array $data, array $existing ): bool {
    return array() === self::invalid_column( $data, $existing );
}
```

> **⚠ ONE IMPLEMENTATION, SO DRIFT IS IMPOSSIBLE BY CONSTRUCTION.** The
> alternative — an admin-side diagnosis that mirrors the repository's checks —
> is a second copy of a five-column refusal contract, free to disagree with the
> first the next time either is edited, and disagreeing in the direction that
> names the wrong field to a merchant who then edits the wrong thing. The
> checks did not move and their order did not change; the boolean is now
> derived from the explanation rather than computed beside it.

`explain_refusal()` returns `array()` or `array( 'field' => …, 'code' => … )`,
covering the six validated columns **and** the trigger resolution that
`insert()`/`update()` refuse separately. Gate 30's test asserts the two agree
over a corpus: `explain_refusal() === array()` **iff** the write is actually
stored.

**A refusal the repository cannot explain is still a refusal.** A genuine
database failure returns `0` with no invalid column; the handler shows a generic
message, keeps the input, and shows no success notice. The outcome is never
softened — only the explanation degrades.

### 4. Field contracts mirror the repository; they do not duplicate it

Client-side and server-side field validation exist for the merchant's benefit.
The repository remains the authority. **Nothing in `src/Admin/` hard-codes a
vocabulary.** `Admin\FieldOptions` reads:

| UI control | Reads |
|---|---|
| status | `RuleRepository::STATUSES` |
| delivery mode | `RuleRepository::DELIVERY_MODES` |
| trigger type | `RuleRepository::TRIGGER_TYPES` |
| consolidation | `Delivery\Consolidation::MODES` |
| insert position | `Render\Injector::POSITIONS` |
| targeting kinds | `Domain\Targeting::KINDS`, `Targeting::ID_KINDS`, `Targeting::FLAG_TYPES` |
| recipient channels | `Domain\RecipientsDocument::CHANNELS` |
| status slugs | `Matching\OrderStatuses` / `wc_get_order_statuses()`, shape-checked by `TriggerEvent::is_valid_status_slug()` |
| native email ids | `WC()->mailer()->get_emails()` |

A hard-coded duplicate list in the UI is a defect waiting for the next enum
change: it renders a control for a value the repository refuses, or hides one it
accepts. Labels are the admin layer's own — a vocabulary is data, its human name
is presentation — but **every value comes from the frozen constant**, and a test
asserts the rendered option set equals the constant.

### 5. Merchant-facing warnings — surfaced, never enforced

The backlog has accumulated facts a merchant cannot otherwise discover. They are
**warnings on the editor, not refusals**, because every one of them describes a
legitimate configuration that merely surprises:

| # | Condition | What the merchant is told |
|---|---|---|
| W1 | `{product_name}` (or another singular product placeholder) in subject/heading/content **and** the targeting can match more than one product | the singular forms bind to the **first** matched item (ADR-0014 §5); suggest `{product_names}` or `{matched_product_list}` |
| W2 | `consolidation = per_product` | beyond the cap the fallback renders the body for the first `cap` products and only **names** the rest (ADR-0016 §7a), and **the cap is per rule, not per order** — several `per_product` rules multiply |
| W3 | subject, heading or content is empty | an empty field renders as **nothing**, indistinguishable from an absent one — which is also what a placeholder resolving empty looks like |
| W4 | `delivery_mode = insert` | delay and consolidation **cannot** apply (ADR-0013 §2, ADR-0016 §2); their controls are **disabled with the explanation**, rather than accepted and then refused by the repository |

**W4 is a disabled control, not a warning after the fact**, and that is the
point of listing it here: ADR-0013 §2 and ADR-0016 §2 make the combination
unstorable, so letting a merchant fill it in and then refusing them is a worse
experience than not offering it. The **forged** case still exists and is still
refused by the repository with the field named (§3) — the disabled control is
the courtesy, not the boundary.

> **⚠ "can match more than one product" IS A PROPERTY OF THE DOCUMENT, NOT OF AN
> ORDER.** W1 fires when `match_all` is set, or when any include kind is a
> non-identity kind (`categories`, `tags`, `types`), or when `products` /
> `variations` together name more than one id. A single-product rule never sees
> it. Computed from the submitted document, so it reflects what is on screen.

### 6. Assets: no build step

**Vanilla JS and plain CSS, hand-written, no bundler, no npm.**

- Enqueued **only** on this plugin's own screen, by `$hook_suffix === Menu::hook()`
  — strict equality against the value `add_submenu_page()` returned, and `false`
  when no menu was registered so an empty hook cannot match an empty hook. Never a
  `strpos()` on the page name, which matches other plugins' screens.
- Versioned by `EXTONIFY_WCEP_VERSION`, so a plugin update busts the cache.
- Data passed through `wp_localize_script()`. No inline `<script>` writing
  globals, no data in `data-` attributes that needs `JSON.parse`.
- **No dependency on WooCommerce's admin bundle.** Adding this screen to
  `wc_get_screen_ids()` would load WooCommerce's whole admin JS/CSS here and let
  this plugin's pickers depend on `wc-enhanced-select`'s class names, AJAX
  actions and nonce names — WooCommerce internals, on a screen WooCommerce has
  never heard of, none of it reachable by PHPUnit. **This plugin owns its own
  picker and its own search endpoint instead**, which costs more JavaScript and
  buys an entry point that is inside our own capability, nonce and sanitisation
  contracts and is covered by gate 28 like every other one.
- **Nothing loads on the front end and nothing outputs during plugin load.** All
  wiring is inside `Plugin::init()`'s existing `is_admin()` branch and registers
  hooks only.

> **An un-reproducible build artefact in the release is worse than more
> hand-written JS.** `.distignore` excludes development files by enumeration; a
> build step would put a generated file in the archive that no reviewer can
> regenerate from the tag, and the archive gate would be asserting the checksum
> of something nobody can rebuild.

### 7. `WP_List_Table`, and the `@access private` it carries

The rules list uses **`WP_List_Table`**. It gives pagination, column headers,
sortable columns, row actions, the search box, the "no items" state and native
admin styling, and every merchant already knows how it behaves.

**WordPress marks it `@access private` and this ADR accepts that**, explicitly
rather than by not noticing:

- it has been effectively public API for fifteen years, and core has never
  broken its subclass contract;
- every plugin of this kind uses it, so a break would be a core-wide event, not
  a surprise landing on this plugin alone;
- the surface used here is the documented-by-convention one —
  `prepare_items()`, `get_columns()`, `get_sortable_columns()`,
  `column_default()`, `column_{name}()`, `set_pagination_args()`,
  `display()`. No private method is called and no property is written;
- the alternative — a hand-rolled table — is *more* risk, not less: pagination,
  sortable-column URL state, nonce-carrying row actions and screen options all
  re-implemented, with none of it exercised by anybody else's install.

`class-wp-list-table.php` is not loaded on every admin request, so it is
required explicitly before the subclass is defined.

**No bulk actions in v1.0.** `get_bulk_actions()` returns `array()`, so no bulk
UI renders and there is no bulk entry point to secure or to enumerate. Deferred
deliberately: bulk delete over a filtered, paginated set is a fourth destructive
handler with its own selection semantics, and the row actions cover the need.

### 8. Pagination, filtering and ordering happen in SQL

`RuleRepository::all()` was written for tests and takes a limit and an offset
only. The list needs status, trigger-type and mode filters, three sort columns
and a total count.

**Decision: two new repository methods, `query()` and `count()`, and no PHP-side
slicing.** Loading every rule to filter and page in PHP is unbounded in the one
dimension a merchant grows over time.

> **⚠ THE ORDER-BY COLUMN AND DIRECTION ARE ALLOWLISTED, NOT INTERPOLATED.**
> `ORDER BY` cannot be bound by `$wpdb->prepare()`, so a request-supplied column
> name reaching it is SQL injection with a capability check in front of it.
> `query()` matches `orderby` against a fixed map of column names and `order`
> against exactly `ASC`/`DESC`, and anything else takes the default. Every
> *value* is bound with `prepare()` as everywhere else in this repository.

### 9. What the list shows for "targets", and what it costs

A rules list whose targeting column reads "3 products" is honest but not useful;
one that names every targeted product issues an unbounded number of queries per
page.

**Decision: up to three names per kind, resolved for the whole page in two
batched queries** — one `get_posts( post__in )` for products and variations, one
`get_terms( include )` for categories and tags — with the remainder shown as
"+N more". The batch is bounded by *page size × kinds × 3*, so the cost is two
queries per page render regardless of how many ids the rules name.

A targeted id whose product or term no longer exists renders as `#123` with a
"no longer available" note rather than vanishing — in the list **and** in the
editor, where it stays removable. Silently dropping it would make the editor
lie about the stored document.

### 10. Delete unschedules first

Deleting a rule removes its pending deliveries' queued jobs **before** the row
goes, per the Prompt 7A rule that no action may outlive the row it points at.
`Delivery\ScheduledCancellation` already subscribes to
`RuleRepository::delete()`'s `extonify_wcep_rule_deleted` action, so the admin
handler calls `delete()` and the existing mechanism does it — the admin layer
adds no second cancellation path.

**Tombstones are deliberately left alone** (ADR-0004): they are keyed by order
and rule id and must survive, or deleting a rule would re-arm every order it had
already served.

### 11. Duplicate creates an INACTIVE copy

A duplicated rule is stored `inactive`, whatever the original's status, with
`(copy)` appended to its name. It gets a new id, a fresh `revision` of 1, and no
delivery history — history is keyed by rule id and the copy's id has never been
delivered for.

> **⚠ INACTIVE IS NOT A COURTESY.** An active duplicate of an active rule
> immediately doubles that rule's mail for every order the original matches,
> before the merchant has seen the copy, let alone edited the one field they
> duplicated it to change.

## Consequences

- Every admin entry point is enumerated in gate 28 with its capability check,
  its nonce action and the test that asserts both. **A new entry point that is
  not added to that table fails the gate** — which is the mechanism, not the
  documentation.
- Every rendered value is enumerated in gate 31 with its escaping function and
  its output context, and hostile input is asserted inert in each.
- The editor cannot emit a document its own validator rejects, proven over the
  full 2048-document structural space rather than a sample.
- No refused write reports success, for each of the six validated columns, with
  the field named and the stored row byte-identical.
- The repository grows one public method (`explain_refusal()`) and two query
  methods. `write_is_valid()`'s behaviour is unchanged and is now derived from
  the explanation rather than computed beside it.
- **PHPUnit cannot test the browser.** Keyboard operation of the picker and the
  placeholder reference, the disabled-control JS, TinyMCE insertion and visual
  layout are outside the suite. What *is* tested is the server side of every one
  of them: the markup that carries the ARIA relationships, the no-JS fallback
  each control degrades to, and the fact that a forged POST bypassing the JS is
  refused.

### Accepted residual risks (deliberately not fixed)

- **A disabled control does not submit.** With JavaScript off, switching a
  stored `separate` rule with a delay to `insert` mode submits the delay
  unchanged and the repository refuses it, naming `delay_seconds`. With
  JavaScript on, the hidden mirror inputs submit the forced `0`/`none` so the
  save succeeds. The no-JS path is a correct refusal with a specific message,
  not a silent failure, so it is recorded rather than engineered around.
- **The targeting summary names at most three ids per kind.** A rule targeting
  forty categories reads "Cat A, Cat B, Cat C +37 more". The editor shows all of
  them; the list is a summary by design (§9).
- **`WP_List_Table` is `@access private`** (§7).
- **No raw JSON view** (§2), **no bulk actions** (§7), **no cross-rule merging
  and no order-level cap** (ADR-0016 §1, out of scope) in v1.0.
