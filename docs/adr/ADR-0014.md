# ADR-0014: Placeholder resolution

Status: **Accepted** — 2026-07-31 (Prompt 6)

## Context

Rule content is stored once and sent many times. Until now it was sent
**literally**: a rule whose body said `Hi {customer_first_name}` delivered those
twenty-four characters to the customer. Every earlier ADR that touched content
said so explicitly and deferred the question here — [ADR-0012](ADR-0012.md) §6
("sent literally: placeholder substitution does not exist yet") and
[ADR-0013](ADR-0013.md)'s injector comment being the two load-bearing ones. **Both
of those statements are now superseded by this ADR and are marked as such where
they stand** (ADR-0012 §6, and `docs/p2-backlog.md`); the quotation above is a
citation of what was true before, not a live claim.

This ADR settles the syntax, the value set, the escaping rules, the security
boundary around parameterised meta access, and where in the delivery lifecycle
resolution happens.

Three earlier decisions frame it and are not reopened:

1. **[ADR-0007](ADR-0007.md)** — a scheduled delivery sends the CONTENT captured
   in its snapshot, and resolves placeholders **fresh at execution time**. That
   fixes the timing question before Prompt 7 asks it (§8).
2. **[ADR-0011](ADR-0011.md)** — `PARTIALLY_RESOLVED` means *unknown*, and
   unknown is never silently replaced by the parent's value (§5).
3. **[ADR-0012](ADR-0012.md) §4** — every value that reaches a mail header
   passes `Delivery\HeaderGuard`, at resolution rather than at send.

**Scope.** The syntax and resolver, the v1.0 placeholder set, context-correct
escaping, the parameterised meta placeholders and their security boundary, and
resolution in **both** delivery modes. `delay_seconds` scheduling (Prompt 7),
consolidation behaviour (Prompt 8), preview as a feature, test emails, the admin
UI and the rule editor's placeholder picker are out of scope and — per the
Prompt 4 lesson, restated as ADR-0013 §8a — are **filtered out**, never handled
by whatever path happens to exist.

## Decision

### 1. Syntax, and what an unrecognised placeholder does

Two forms, and no others:

```
{placeholder_name}
{namespace:key}
```

The grammar is deliberately narrow, and every part of it was chosen against a
case:

| Input | Result | Why |
|---|---|---|
| `{customer_first_name}` | resolved | the ordinary case |
| `{order_custom_field:total_paid_note}` | resolved | the parameterised case |
| `{CUSTOMER_EMAIL}` | resolved | names are folded ASCII-lowercase — the same locale-independent fold `Recipient`, `Targeting` and `RecipientResolver` already use, and for the same reason: `strtolower()` maps `I` to a dotless `ı` under a Turkish locale, so a template would stop resolving on one host |
| `{customer_frist_name}` | **empty**, recorded | §1a below |
| `{ customer_email }` | left LITERAL | not a token: whitespace is not part of the grammar, and treating it as one would mean guessing what the merchant meant |
| `{`, `{}`, `{123}` | left literal | not tokens |
| `{customer_\nemail}` | left literal | ⚠ a token may not span a line break — the grammar excludes CR and LF from both the name and the parameter, so a placeholder broken across two lines is inert rather than accidentally matching across content |
| `{{customer_email}}` | inner token resolves; the outer braces stay | the output is `{alice@example.test}`, which is literal and harmless. The alternative — treating the result as a token — is exactly the recursion §2 forbids |

**Meta keys are case-SENSITIVE and are not folded.** WordPress meta keys are
case-sensitive in the database, so folding one would look up a key that was never
stored. Only the placeholder NAME is folded.

#### 1a. An unrecognised placeholder resolves to EMPTY and is recorded

A token whose name is not in the §4 set resolves to the empty string, and the
occurrence is recorded **once per delivery, per distinct token** — not once per
occurrence.

**Why empty rather than literal.** Leaving `{customer_frist_name}` in place sends
the merchant's typo to the customer, in a message the merchant believes is
finished. Empty is the lesser failure: the sentence reads oddly, nothing leaks,
and nothing looks like a broken template to the recipient.

**Why recorded rather than silently dropped.** A merchant looking at a blank in
their email has no way to tell a typo from an order that genuinely has no phone
number. The delivery log answers that question — it names the exact token that
failed, so "why is this blank" has an answer that does not require reading the
plugin's source.

**Once per delivery, deliberately.** A template with the same typo in twenty
places is one authoring mistake, not twenty events. The reason column would
otherwise be filled with one repeated sentence and the useful notes beside it
pushed out.

#### 1b. The grammar RECOGNISES; the validator DECIDES

*(ADDED 2026-08-01, Prompt 6A, fixing a defect that reached the customer.)*

**No length limit belongs in `TOKEN_PATTERN`.** The parameter was capped at
`{0,255}` so that the grammar would agree with `META_KEY_PATTERN`. The effect was
the opposite of the intent:

| Parameter length | Recognised as a token? | `is_valid_meta_key()` runs? | What the customer received |
|---|---|---|---|
| ≤ 255 | yes | yes | resolved, or empty + recorded |
| **256+** | **no** | **never** | **the entire raw `{order_custom_field:…}`, verbatim** |

The validator sat behind a gate that only opened for keys it was going to accept
anyway, so the one case it existed for — a key too long to name anything — was the
one case it never saw. A merchant's template leaked into a customer's inbox as
template text.

**The grammar therefore excludes only braces, CR and LF, at any length**, and the
255-character cap lives in `META_KEY_PATTERN` alone. WordPress's `meta_key` column
is `varchar(255)`, so an overlength key cannot name anything that exists: it is
**refused, recorded as `refused a malformed meta key`, and resolves empty** — the
same treatment `{order_custom_field:bad key}` gets, and for the same reason.

**Tested end to end through a real send**, not against the validator. The direct
unit test passed throughout the whole time the delivered email was wrong, which is
what a test that stops at the gate is worth.

#### 1c. Partial notes survive a throw

*(ADDED 2026-08-01, Prompt 6B.)*

§1a's notes are accumulated **as resolution proceeds**, and they used to be read
off `PlaceholderValues` only once every resolution had finished — after subject,
heading and both body formats, in separate mode; and in insert mode the catch
passed `null` for the value set entirely. So an unknown token noticed *before* a
throw vanished from the record.

That is the wrong way round. The merchant is left with an exception and no sight of
the earlier problem — and the earlier problem is the one they can actually fix,
whereas the exception belongs to somebody else's callback.

**Decision: the containment state holds the LIVE value set (§10a), and the failure
row merges whatever it had accumulated.** In insert mode the failure note and the
partial notes are both kept, joined, rather than the failure note replacing them;
in separate mode the merge happens at the point the row is written rather than
being copied into the state at one instant, so the success path and the failure
path cannot disagree and cannot double-count.

#### 1d. Per-rule notes are an exact-keyed, capped SET, flattened only at storage

*(ADDED 2026-08-01, Prompt 6B.)*

`PlaceholderValues` caps its notes at 20 **per value set**. At the per-item
injection position a rule gets a **fresh value set per line item**, and
`RenderLedger` concatenated those per-item strings into one rule-level string with
**no cap at all** — so a fifty-line order with a per-item failure on each grew it
linearly. That is the same memory-leak-wearing-a-useful-name shape Prompt 5B capped
in `RenderContext` and in the ledger's own diagnostics; it was missed here only
because the collection was new.

De-duplication was wrong in a second, quieter way: the test was
`false === strpos( $existing, $note )`, which asks "does the accumulated string
*contain* this note". A **distinct** note that happened to be a substring of an
earlier one was silently discarded — `unknown placeholder {a}` swallowed by
`unknown placeholder {ab}`.

**Decision: a set keyed by the exact note, capped at 20 per rule, with the dropped
count stated rather than truncated silently.** A `; `-joined run is split so each
part is keyed and capped on its own. The set becomes a string in exactly one place,
`RenderLedger::notes_line()`, at storage.

**The general rule this is an instance of: every new collection declares its cap
and its key at the moment it is created**, because a diagnostic that grows without
limit is a memory leak and an inexact key is a silent data loss.

#### 1e. An empty parameter is NOT "no parameter"

*(ADDED 2026-08-01, Prompt 6B.)*

The grammar has always matched `{name:}` — §1's table says so, because the
alternative is delivering those characters to a customer. But the extraction read

```php
$param = isset( $matches[2] ) && '' !== $matches[2] ? (string) $matches[2] : null;
```

so `{customer_email:}` was **coerced into `{customer_email}`** and resolved to the
customer's address. §7's recipient safe set authorises the exact **name** and
refuses anything parameterised — so the coercion handed the safe set a token it had
never authorised, assembled out of a spelling the merchant did not write.

This is the same **"junk repaired into a different valid target"** shape removed
from the trigger boundary (ADR-0011 §2), the `native_email_id` boundary
(ADR-0013 §2) and the meta-key boundary (§6.2). Recognition must not repair.

**Decision: `''` and `null` are different answers, carried apart**, and each
consumer refuses `''` on its own terms:

| Where | `{name:}` |
|---|---|
| meta namespace | refused as a meta placeholder with an **empty key**, recorded |
| any non-parameterised name | **unknown placeholder**, recorded — a parameter on a placeholder that takes none is not that placeholder |
| recipient field | a **disallowed placeholder**; §7a drops the whole entry |

`isset()` alone is the correct discriminator, and that is a property of the pattern
rather than a convention: the parameter is the **last** group, and PCRE omits
trailing groups that did not participate. Verified against the shipped pattern.

**The unit case asserting "an empty parameter is no parameter" is replaced**, since
it encoded the coercion.

### 2. SINGLE-PASS RESOLUTION IS A SECURITY BOUNDARY

**Resolution is strictly single-pass. A resolved value is never re-scanned for
placeholders.** This is not a performance choice, and it must never be
"optimised" into a loop.

Placeholder values come from **customer-controlled fields**. A billing first name
is whatever the customer typed at checkout. If resolution were recursive, or ran
a second pass over the output, then a customer who set their billing first name
to

```
{order_custom_field:_stripe_source_id}
```

would receive an email in which that token had been **resolved and mailed back to
them** — a payment-token disclosure caused by nothing more than a text field the
customer controls. The same trick reaches `_customer_ip_address`,
`_billing_address_index`, and any other private meta the store happens to hold.

Single-pass makes that string appear in the output **literally**, which is
harmless: a customer who names themselves `{order_custom_field:_stripe_source_id}`
receives an email addressed to that name.

**The implementation makes this structural rather than careful.** Substitution is
one `preg_replace_callback()` over the template; PCRE does not re-scan replacement
text, so there is no pass in which a resolved value could be examined. Any future
change that resolves in a loop, or resolves a value and then calls the renderer on
it, reintroduces this vulnerability.

**Tested as a security property, not as behaviour** (gate 16): a billing name
containing `{customer_email}` renders literally; a billing name containing
`{order_custom_field:_stripe_source_id}` renders literally and resolves nothing;
a value containing the placeholder that produced it does not loop.

### 3. Escaping is per output context, applied to the VALUE

The **template** is merchant-authored and passed through `wp_kses_post` at the
storage boundary (ADR-0012 §6). The **values** are not: they come from the order,
from products, and from customer input. So escaping happens **at substitution
time**, to the value, chosen by destination:

| Destination | Treatment of the resolved value |
|---|---|
| HTML body | `htmlspecialchars( …, ENT_QUOTES \| ENT_SUBSTITUTE, 'UTF-8' )`, then `\n` → `<br />` |
| Plain-text body | **no HTML escaping** — text must read as text |
| Subject | `HeaderGuard::strip()` — CR and LF, raw and encoded, plus every other control character |
| Heading | `HeaderGuard::strip()`; see the ⚠ note below |
| Recipient fields | §7 — a restricted safe set, then the existing `is_email()` + `HeaderGuard` path |

**The same placeholder therefore renders differently per format, by design.** A
billing name of `A & B` is `A &amp; B` in the HTML body and `A & B` in the plain
one. Both are correct; neither is a bug to be "made consistent".

**⚠ `esc_html()` is deliberately NOT used.** WordPress's `esc_html()` ends with
`apply_filters( 'esc_html', $safe_text, $text )` — a third-party callback can
return the *unescaped* input, and several plugins do filter it. An escaping step
that a third party can switch off is not a security boundary. `htmlspecialchars()`
is called directly, in framework-free code, so nothing can hook it.

**⚠ Newline-to-`<br />` happens AFTER escaping, never before.** The `<br />` is
markup this plugin emits; the value can never contribute markup of its own. This
is what lets `{billing_address}` render as a readable multi-line address in HTML
while remaining a plain `\n`-separated string in text.

**⚠ NO PLACEHOLDER EVER YIELDS MARKUP, including the ones whose WooCommerce
helper returns HTML.** `wc_price()` returns a `<span class="…">` wrapper and
`get_formatted_billing_address()` returns `<br/>`-joined, `esc_html`-escaped
parts. Both are flattened to text before substitution — tags stripped, entities
decoded — so `£12.34` and a `\n`-separated address are what the substitution sees.
Without this there would be two classes of value with two escaping rules, and the
first value that changed class would be the vulnerability.

**⚠ THE ORIGINAL "SAFE IN BOTH FORMATS" REQUIREMENT IS SUPERSEDED HERE, FOR PLAIN
TEXT.** *(AMENDED 2026-08-01, Prompt 6A.)* Prompt 6 required that a hostile value
appear **safely in both formats**, the implied reading being that it appears,
neutralised, in each. That is true of HTML — `<script>alert(1)</script>` arrives as
`&lt;script&gt;alert(1)&lt;/script&gt;` and is inert. **It is not true of plain
text, and cannot be made true from this side.** `WC_Email::get_content()` runs
`wp_strip_all_tags()` over the *whole* plain body (WC 10.9.4,
`class-wc-email.php:872`), so the sequence is **deleted outright** — by
WooCommerce, after this plugin has finished, and to the merchant's own text
equally. This plugin deliberately does not escape a `text/plain` body (§3 above,
ADR-0013 §4b); escaping it could only corrupt a message nothing parses as HTML.

**The requirement therefore reads, as amended:** a hostile value is
**neutralised** in both formats — escaped and visible in HTML, removed by
WooCommerce in plain text — and in neither format can it execute or leak. The
integration test asserts the plain-text outcome as *WooCommerce's* behaviour, so a
future version that stops stripping tags fails the suite rather than surprising a
customer.

**⚠ THE HEADING'S HTML SAFETY IS WOOCOMMERCE'S, AND THAT IS A DEPENDENCY, NOT AN
ASSUMPTION.** The heading is not a mail header — it is rendered into the HTML
body by `templates/emails/email-header.php`, which echoes it through `esc_html()`
(verified, WC 10.9.4, line 113). This plugin therefore applies `HeaderGuard` only:
escaping here as well would double-escape, and a customer named `A & B` would
appear as `A &amp;amp; B`. **An integration test asserts that a `<script>` in the
heading arrives escaped**, so if WooCommerce ever stops escaping it, the suite
says so rather than the customer finding out.

### 4. The v1.0 placeholder set

These, and no others. An unrecognised name is §1a's case.

**Customer** — `{customer_first_name}`, `{customer_last_name}`,
`{customer_full_name}`, `{customer_email}`, `{customer_phone}`.

**Order** — `{order_number}`, `{order_date}`, `{order_status}`, `{order_total}`,
`{payment_method}`, `{shipping_method}`, `{billing_address}`,
`{shipping_address}`, `{view_order_url}`.

**Store** — `{store_name}`, `{store_email}`, `{store_url}`, `{my_account_url}`.

**Matched products** — `{product_name}`, `{product_names}`, `{product_sku}`,
`{product_quantity}`, `{product_url}`, `{variation_name}`,
`{variation_attributes}`, `{matched_product_list}`.

**Parameterised** — `{order_custom_field:key}`, `{item_custom_field:key}`.

**Formatting is WooCommerce's own**, so a store's currency, date and address
conventions are what the customer sees:

| Placeholder | Source |
|---|---|
| `{order_total}` | `wc_price( $order->get_total(), [ 'currency' => $order->get_currency() ] )`, flattened to text |
| `{order_date}` | `wc_format_datetime( $order->get_date_created() )` |
| `{order_status}` | `wc_get_order_status_name()` — the human-readable name, not the slug: a customer reading "wc-processing" learns nothing |
| `{billing_address}` / `{shipping_address}` | `get_formatted_billing_address()` / `get_formatted_shipping_address()`, flattened to `\n`-separated text |
| `{store_name}` | `get_bloginfo( 'name' )`, entity-decoded as WooCommerce's own `get_blogname()` does |
| `{store_email}` | the `woocommerce_email_from_address` setting, falling back to `admin_email` — the store's *email identity*, which is what a merchant writing `{store_email}` means, and what the From address already uses |
| `{my_account_url}` | `wc_get_page_permalink( 'myaccount' )` |
| `{product_name}` | the **line item's** name, which is what the customer bought — for a variation that includes the variation's own naming, exactly as it appears in the order table |
| `{product_names}` | every matched item's name, comma-joined |
| `{matched_product_list}` | one matched item per line, `quantity × name` |
| `{variation_attributes}` | `wc_get_formatted_variation( …, true, true, false )` — "Colour: Blue, Size: L" |

A placeholder whose underlying field is empty resolves to the empty string and is
**not** recorded: an order with no phone number is not an authoring error, and
recording it would bury §1a's real signal.

### 5. Singular placeholders in a multi-match context

A rule can match several line items, so `{product_name}` is ambiguous by nature.

**Decision: the singular product placeholders resolve against the FIRST matched
item in line-item order**, and `{product_names}` / `{matched_product_list}`
render all of them.

> **⚠ WITH ONE EXCEPTION, ADDED IN PROMPT 6A — READ §5a BELOW BEFORE RELYING ON
> THIS PARAGRAPH.** At the `item_meta` injection position the item-scoped
> placeholders resolve against the **line item being rendered**, because that
> position exists to put content beside each matched item. Everywhere else — every
> other position, and all of separate mode — this paragraph is unchanged.

"First in line-item order" is the order `WC_Order::get_items()` returns and the
order `RuleMatcher` preserves — the same order the customer sees in the order
table. It is not "the best match" or "the most specific": those would make the
value depend on targeting internals that the merchant cannot see.

**`{product_name}` on a multi-match rule is an authoring choice, not a defect.**
The merchant asked for one product's name and got one. **Prompt 9 note:** the
rule editor's placeholder picker should surface the plural forms alongside the
singular ones and say which is which, because the editor is the only place this
distinction can be made visible before the email is sent.

#### 5a. ⚠ At the PER-ITEM position, item-scoped placeholders take the item being rendered

*(ADDED 2026-08-01, Prompt 6A, fixing content attributed to the wrong product
line.)*

§5's "first matched item" rule was applied **everywhere**, including at the
`item_meta` injection position — the one position Prompt 5 built specifically so a
rule's content sits **beside each matched line item**. A rule matching items A and
B therefore emitted a block next to B that read **A's** meta: a gift message, an
engraving, a serial number or a download key printed against the wrong product.

**Decision:**

| Position | Item-scoped placeholders resolve against |
|---|---|
| `item_meta` (per-item) | **the line item currently being rendered** |
| every other position, and all of separate mode | the **first** matched item in line-item order (§5, unchanged) |

**"Item-scoped" is `{item_custom_field:key}` and the singular product
placeholders** — `{product_name}`, `{product_sku}`, `{product_quantity}`,
`{product_url}`, `{variation_name}`, `{variation_attributes}`.

> **⚠ THE SINGULAR PRODUCT PLACEHOLDERS ARE AN EXTENSION OF THE SPECIFIED FIX, AND
> IT IS FLAGGED RATHER THAN SLIPPED IN.** Prompt 6A named
> `{item_custom_field:key}` alone. Binding that to the current item while leaving
> `{product_name}` on the first matched item would print *"Engraved: Happy
> birthday"* beside item B under the heading *"Your WCEP Widget A"* — the same
> wrong-product-line defect, one placeholder to the left, and a strictly stranger
> result than either rule applied consistently. One binding, one meaning.

The plural forms are unaffected: `{product_names}` and `{matched_product_list}`
render every matched item at every position, which is what makes them the plural
forms.

**The binding is validated, not trusted.** The current item must be one of *this
rule's* matched items; anything else falls back to the first matched item, so a
block can never advertise a product the rule did not match.

**⚠ ONE VALUE SET PER LINE ITEM, AND THAT IS A REQUIREMENT OF THE MEMO.**
`PlaceholderValues` memoises by `name:parameter` (§8). Reusing one set across two
line items would answer the second with the first's memoised value — reintroducing
this exact defect through the cache. The injector therefore opens a fresh set per
emission at the per-item position. **What a fresh set loses is the MEMO, not the
underlying cache**, and the underlying cache is what §8's costs are made of: the
`WC_Order` (order fields, order meta, line items, item meta) and the shared
`ItemResolver` (products) are the same objects for every block, so every 0-cost
class stays 0-cost. `{shipping_method}` is the one class with a cost, and it is
**order**-scoped: `WC_Order::get_shipping_method()` loads the shipping items onto
the order object, which WooCommerce then caches there, so a per-item block writing
it pays the +2 once for the order rather than once per block.

**`{variation_name}` and `{variation_attributes}` resolve EMPTY for a
non-variation item** — there is nothing to name.

**And they resolve EMPTY for a `PARTIALLY_RESOLVED` item** (ADR-0011 §4: the
variation was deleted, the parent survives). They do **not** fall back to the
parent's name or attributes. Unknown is not the parent's value — exactly the rule
`types` targeting already holds, where a partially resolved item refuses every
type test rather than answering with the parent's slug. Falling back here would
tell the customer they bought a variation nobody can identify.

### 6. Parameterised meta placeholders — the data-leak boundary

`{order_custom_field:key}` and `{item_custom_field:key}` read arbitrary post
meta, which is a customer-facing window onto everything the store has ever
stored against an order. Four constraints, and each closes a specific hole:

1. **Keys beginning with `_` are REFUSED.** WordPress's own convention makes
   `_`-prefixed meta *protected* — hidden from the editor UI — and WooCommerce
   stores exactly the things that convention exists for: `_stripe_source_id`,
   `_customer_ip_address`, `_customer_user_agent`, `_billing_address_index`,
   `_edit_lock`. Putting any of them in a customer-facing email is a data breach,
   and it takes one plausible-looking template to do it. A refused key resolves
   empty and the refusal is **recorded** (§1a's mechanism), so the merchant
   learns that the plugin declined rather than that the field was empty.
2. **The key's shape is validated on the RAW value, and a bad key is refused
   rather than repaired.** This is the plugin's **seventh input boundary** and it
   follows the same rule as the other six (ADR-0009's classification; ADR-0011 §2
   and ADR-0013 §2 for the two most recent): `sanitize_key()`-then-accept would
   turn `total paid note` into the *different, valid* key `totalpaidnote` and read
   whatever that holds. Junk becoming a different valid target is worse than junk
   being inert. The accepted alphabet is `[A-Za-z0-9_][A-Za-z0-9_.-]{0,254}`,
   applied as a **test**.
3. **String, integer or float. Nothing else.** *(CORRECTED 2026-08-01, Prompt 6A:
   this said "scalars only", and PHP counts `bool` as a scalar while the code
   refuses it — the ADR and the code disagreed.)*

   An array or an object resolves empty and is never serialised:
   `a:2:{i:0;s:5:"…"}` in a customer email is meaningless at best, and `print_r` of
   an object graph can carry anything the object happens to reference.

   **A boolean also resolves empty, and that is a decision.** `(string) true` is
   `"1"` and `(string) false` is `""`, so `{order_custom_field:is_gift}` would
   render as `1` for yes and as *nothing at all* for no — two spellings, one of
   which is indistinguishable from "the key does not exist". There is no wording
   this plugin could pick that would be right for every store's flag, so it
   declines to guess. `null` is the same case with one fewer spelling. Every
   refusal is **recorded**, and a boolean is recorded as a boolean rather than
   lumped in with arrays, because the merchant's fix differs: store the words you
   want printed.
4. **A filter can permit a specific key deliberately:**

   ```php
   apply_filters( 'extonify_wcep_meta_placeholder_allowed', $allowed, $key, $scope, $order )
   ```

   `$allowed` arrives `false` for a protected key and `true` for a public one, so
   the default is refusal for exactly the class §6.1 describes. A site owner who
   genuinely needs `_wc_shipment_tracking_number` in an email opts in, per key,
   in their own code — which is a decision with an author, rather than a plugin
   setting a merchant can flip without understanding it. The filter can also
   refuse a public key, which costs nothing and lets a site tighten as well as
   loosen.

   **⚠ THE TWO REFUSALS ARE RECORDED SEPARATELY.** *(CORRECTED 2026-08-01, Prompt
   6A: a filter vetoing a **public** key was logged as `refused a protected meta
   key`, sending the merchant looking for an underscore that was not there.)*

   | What happened | Recorded as |
   |---|---|
   | `_`-prefixed key, default-deny (filter absent or agreeing) | `refused a protected meta key {…}` |
   | **public** key, refused by a site filter | `a site filter (extonify_wcep_meta_placeholder_allowed) refused the public meta key {…}` |

   Two different facts with two different remedies: the first is answered by
   writing the filter, the second by reading the one already there.

   **⚠ AND THE FILTER IS TREATED AS HOSTILE — see §10.** It is a plugin-owned
   extension point invoked in the middle of a claimed delivery, so a callback on it
   that throws is this plugin's problem to contain, not the site owner's to avoid.
5. **A protected key is opened by `true` and by NOTHING ELSE.** See §6.5.

#### 6.5. Only a literal boolean decides, and a non-boolean return is itself a refusal

*(ADDED 2026-08-01, Prompt 6B. A security fail-open on the boundary this prompt
series exists to harden.)*

The filter result was read as `(bool) apply_filters( … )`. For a protected key the
default is `false`, so **any truthy return opened it**:

| Return | Under the cast | Now |
|---|---|---|
| `true` | opens | **opens** — the only return that may |
| `false` | refuses | refuses, `refused a protected meta key {…}` |
| `"true"`, `"false"`, `"no"` | **OPENS** | refused, `refused an invalid non-boolean meta permission result (string) …` |
| `1` | **OPENS** | refused (`integer`) |
| `0` | refuses (for the wrong reason) | refused (`integer`) |
| `array()` | refuses (for the wrong reason) | refused (`array`) |
| `array('error')` | **OPENS** | refused (`array`) |
| `new stdClass` | **OPENS** | refused (`stdClass`) |
| **`WP_Error`** | **OPENS** | refused (`WP_Error`) |
| `null` | refuses (for the wrong reason) | refused (`NULL`) |

**`WP_Error` is the case that matters most.** It is what a callback conventionally
returns when it *failed to decide* — a lookup that errored, a permission service
that was unreachable. Under the cast, "I could not work out whether this key is
safe" was read as "yes, mail `_stripe_source_id` to the customer".

**Decision: only `is_bool()` decides. Anything else is a refusal in its own right,
with its own recorded reason** — `refused an invalid non-boolean meta permission
result (<type>) from extonify_wcep_meta_placeholder_allowed for {…}`.

**Why the reason is separate from the two in §6.4.** They are three different
facts with three different remedies: write a filter; read the filter you have; fix
the filter you have. A non-boolean return is a **bug in the callback**, and saying
so is the only diagnostic that leads anywhere.

**Why refuse rather than fall back to `$allowed`.** A filter that answered
incoherently for a *public* key has still answered incoherently. Falling back would
silently serve the value and leave the bug undiscovered; the merchant is told
instead. And the type name is reported without ever printing the value — a filter
that returned an object could otherwise put order meta it had just been asked about
into the delivery log, which is the exposure the refusal exists to prevent.

**The principle, stated generally, because this is the third time it has come up
(claim results, database errors, and now here): an extension point that cannot
decide must never be read as consent.**

### 7. Recipients take a restricted safe set only

**Only `{customer_email}` and `{store_email}` may appear in a recipient field.**
Every other placeholder resolves to the empty string there and the refusal is
recorded.

This is narrower than the body deliberately. A recipient field becomes part of a
mail header, and a free-text value in one is a header-injection vector even after
CR/LF stripping — stripping is a defence in depth, not a licence to put arbitrary
customer input there. And there is **no legitimate use**: a merchant wanting to
mail the customer writes `{customer_email}` (or the existing `customer` token),
and nobody wants to mail an address assembled from a billing first name.

Everything a recipient placeholder resolves to still goes through the whole
existing path: `HeaderGuard::strip()`, then `Recipient::normalize()`'s
`is_email()` validation, then de-duplication (ADR-0012 §4). A placeholder is a
source of an address, never a bypass around the checks an address faces.

**A recipient entry that resolves empty is dropped with a note**, exactly as an
unresolvable `customer` token already is. If that leaves the rule with no `to`
recipient, the existing path records a skip with the reason — the rule sends
nothing, and the delivery log says why.

#### 7a. A disallowed placeholder refuses the WHOLE entry

*(ADDED 2026-08-01, Prompt 6A, closing a hole in §7 itself.)*

§7 was implemented as *"resolve the disallowed placeholder to empty, then validate
what is left"*. What is left is frequently a valid address:

```
{customer_first_name}alice@example.test   ->  alice@example.test   ->  DELIVERED
alice+{order_number}@example.test         ->  alice+@example.test  ->  DELIVERED
```

The refused placeholder vanished and the remainder passed `is_email()`, so the
entry delivered — to an address §7 never authorised, **assembled out of exactly the
customer-controlled field §7 exists to keep out of a mail header**. The existing
test covered only an entry consisting *solely* of a disallowed placeholder, which
is the one shape where empty-and-revalidate happens to fail closed.

**Decision: if a recipient entry contains ANY placeholder outside the §7 safe set,
the ENTIRE entry is refused, whatever survives substitution, and the refusal is
recorded.** §7 says a recipient field takes two placeholders and nothing else; the
only implementation that means that is one which discards the entry the moment a
third appears. Empty-and-revalidate meant "takes two placeholders, plus anything
you can build out of the wreckage of the others".

Refused whole, and recorded:

| Entry | Outcome |
|---|---|
| `{customer_first_name}alice@example.test` | refused, recorded, **not sent** |
| `alice+{order_number}@example.test` | refused, recorded, **not sent** |
| `{order_custom_field:email}` | refused, recorded, **not sent** (parameterised forms were never in the safe set) |
| `{customer_email}` / `{store_email}` | resolved (§7) |

### 8. Timing: at send time, against the live order

**The resolver runs at send time, never at rule-save time**, and reads the live
order.

ADR-0007 already requires this of scheduled deliveries: a delayed email sends the
**content** captured in its snapshot, with **placeholders resolved fresh** at
execution — so a customer who changes their name between the trigger and the send
gets the name they have now, while the merchant's edits to the rule body do not
retroactively change a queued message. Resolving at save time would have to be
undone in Prompt 7; resolving at send time is Prompt 7's requirement already met.

**Cost is a gate, and this is the gate.** *(AMENDED 2026-08-01, Prompt 6A. The
gate as originally specified — "a rule with 25 placeholders performs the same
query count as the same rule with one" — is **superseded**: the measurement was 24
versus 26, because `{shipping_method}` loads a line-item type nothing else reads.
Amending it explicitly, rather than rewriting the test to match the result and
reporting the gate as passed, is the point. A gate that gets quietly amended to fit
its own result is not a gate.)*

> **No per-placeholder and no per-occurrence query growth. One bounded, named cost
> per distinct data class a body reads. Every such class is enumerated with its
> measured cost.**

**The enumeration.** Measured per whole delivery, WARM, as the delta against a body
carrying no placeholders at all (WC 10.9.4, WP 7.0.2, PHP 8.3.6):

| Data class | Placeholders that read it | Warm cost | Why |
|---|---|---|---|
| *(baseline: no placeholders)* | — | **21 queries** | the delivery itself: fetch, match, claim, send, record |
| Order fields | `{customer_*}`, `{order_number}`, `{order_date}`, `{order_status}`, `{payment_method}`, `{view_order_url}` | **0** | already on the `WC_Order` the delivery holds |
| Order total | `{order_total}` | **0** | `wc_price()`; its tax-rate classes are request-cached |
| Addresses | `{billing_address}`, `{shipping_address}` | **0** | formatted from fields already loaded |
| Order meta | `{order_custom_field:key}` | **0** | the order object carries its own meta |
| Line items | `{product_name}`, `{product_quantity}` | **0** | `WC_Order::get_items()`, cached by WooCommerce, indexed **once** per delivery |
| Item meta | `{item_custom_field:key}` | **0** | read off the same indexed line items |
| Products | `{product_sku}`, `{product_url}`, `{variation_name}`, `{variation_attributes}` | **0** | the shared `ItemResolver` cache the matcher already filled (ADR-0012 §11b) |
| Product lists | `{product_names}`, `{matched_product_list}` | **0** | same line items |
| Store / request-level | `{store_name}`, `{store_email}`, `{store_url}`, `{my_account_url}` | **0 warm** | the my-account page permalink and the from-address option are request-cached; the **cold** cost is reported beside the warm one, never hidden by a warm-up |
| ⚠ **Shipping line items** | **`{shipping_method}`** | **+2, once per delivery** | `WC_Order::get_shipping_method()` loads a line-item **type** nothing else in the delivery path reads, so WooCommerce fetches them and primes their meta |

**No class beyond `{shipping_method}` carries a cost.** The costs above are
**declared in the test, above the measurement**, and the test fails if the
measurement disagrees — so a class that starts costing a query has to be written
down by somebody who noticed it, rather than described accurately and passed
silently.

And the two growth properties, measured separately from the classes because *"25
versus 1"* conflates how many placeholders a body carries with what class of data
they read:

- **No growth per placeholder.** Each distinct placeholder resolves once per
  delivery; the per-delivery value object memoises by `name:parameter`.
  **Measured: 1 placeholder and 24 placeholders of already-loaded classes cost an
  identical 24 queries.**
- **No growth per occurrence.** **Measured: the same 25 placeholders and those 25
  written three times over (75 occurrences) cost an identical 26 queries.**

⚠ **`WC_Order::get_item( $id )` DEFAULTS TO A DATABASE READ**, and this gate is how
that was found. `$load_from_db = true` makes it call
`WC_Order_Factory::get_order_item()` every time (WC 10.9.4,
`abstract-wc-order.php:1091`), so resolving product placeholders one item lookup at
a time cost **one query per product placeholder** — 24 extra queries on a
25-placeholder body. The per-delivery value object now indexes
`WC_Order::get_items()` once instead.

**Per-delivery state lives on a per-delivery object, not on the shared resolver**
(ADR-0012 §11). `Delivery\PlaceholderResolver` is a per-request collaborator
holding the shared `ItemResolver`; `Delivery\PlaceholderValues` is created per
delivery, carries that delivery's order, matched items, memo and notes, and is
discarded with it. A nested delivery gets its own object and cannot disturb the
outer one — the re-entrancy rule of ADR-0012 §11a, satisfied by construction
rather than by capture-and-restore.

### 9. Where resolution happens in each mode

| Mode | Resolved | Contexts |
|---|---|---|
| separate | `Delivery\Orchestrator::attempt()`, inside `send()`'s containment boundary (§10), before `Custom_Email::trigger()` | subject and heading as headers; body rendered **twice**, once HTML and once plain |
| insert | `Render\Injector::emit()`, per render — and **per LINE ITEM** at the per-item position (§5a) | HTML or plain, from the render's own `$plain_text` argument |

**Both formats are rendered for a separate-mode delivery, and that is required
rather than wasteful.** WooCommerce's `multipart` email type builds the plain
alternative from `get_content_plain()` at `phpmailer_init`, long after the
orchestrator has returned — so a single pre-rendered body would either lose the
plain alternative or send HTML-escaped values inside it. The second format adds no
query cost, because both draw on the same memoised values — the §8 no-growth
property applied across formats.

**⚠ THE PLAIN BODY IS BUILT BY FLATTENING THE TEMPLATE FIRST, THEN SUBSTITUTING.**
Order matters and the other order is wrong: substituting into HTML and flattening
afterwards would run `wp_strip_all_tags()` over the *values*, so a customer named
`<script>x</script>` would lose their name entirely, and any `&` in a value would
be mangled by the entity handling. Flatten, then substitute, and the value reaches
the text body as text.

#### 9a. ⚠ Separate mode's plain body did not decode entities

*(FOUND while implementing this ADR, verified, and fixed here.)*

ADR-0013 §4b fixed exactly one half of this: the **insert-mode** plain branch
decodes entities, because `WC_Email::get_content()` runs every plain body through
`$plain_search`/`$plain_replace`, whose last-but-one pattern is `/&[^&\s;]+;/i` →
`''` — **every entity WooCommerce does not explicitly handle is deleted
outright**.

`Custom_Email::get_content_plain()` was doing
`wp_strip_all_tags( wp_kses_post( $content ) )` with **no decode step**, so the
identical defect was live in separate mode: a rule body containing `caf&eacute;`
reached the customer as `caf`. The two modes now share one flattening function
(`Domain\Text::to_plain_text()`), so the fix cannot come apart again.

### 10. Resolution is CONTAINED, and every filter it invokes is HOSTILE

*(ADDED 2026-08-01, Prompt 6A. The most serious defect found in any phase, and
this ADR created it.)*

**Any plugin-owned filter invoked during resolution must be treated as hostile: it
can throw, and containing that throw is this plugin's responsibility.** §6.4
introduced `extonify_wcep_meta_placeholder_allowed` — a *new third-party extension
point*, shipped by this plugin, invoked in the middle of a claimed delivery in
separate mode and inside WooCommerce's own rendering hooks in insert mode. The same
applies to every WooCommerce formatter resolution calls
(`woocommerce_order_formatted_billing_address`, `wc_price`,
`formatted_woocommerce_price`, …), each of which ends in filters somebody else
owns.

#### Separate mode: the boundary was around `trigger()` alone

The claim happened, then recipient resolution, then placeholder resolution, then
content assembly — and only *then* did the `try` begin. Everything between was
unprotected:

```
claim identity                                  <- consumed here
resolve recipients                                 UNPROTECTED
resolve subject / heading / body                   UNPROTECTED
apply extonify_wcep_meta_placeholder_allowed       UNPROTECTED   <- new in Prompt 6
try { $email->trigger() } catch                 <- the boundary began here
```

A `Throwable` from any of those escaped into `woocommerce_order_status_changed`,
**breaking the merchant's status change**, while the tombstone stayed `claimed`
with no detail row and the consumed identity blocked every retry — the exact
"claimed forever" failure Prompt 4a built containment to prevent.

**Decision: every post-claim step is inside the boundary** — recipient resolution,
placeholder resolution, content assembly and the send. Any `Throwable`:

1. does not escape the WooCommerce event;
2. finalises the delivery **`failed`**;
3. records the **exception class and sanitised message** on a detail row;
4. leaves **no claimed-only tombstone**.

**⚠ AND (3) NEEDED MORE THAN A WIDER `try`.** Failure rows are written **one per
resolved recipient** (ADR-0012 §4), so a throw *before* recipient resolution
returned had no address to write against and would have written **no row at all** —
finalising the tombstone with no evidence anywhere. A recipient-less failure row is
written for that case, and it is asserted.

**⚠ WHAT "RETRIED" CAN AND CANNOT MEAN HERE.** ADR-0004 makes `status:processing`
fire **once per order per rule, ever**, so the same identity is never re-deliverable
— failed or not. What containment restores is everything else: the tombstone is
`failed` rather than `claimed`, so support can see it and ADR-0004's linked
attempt rows support a manual resend; the **other trigger family on the same status
change still delivers**, where an escaping throw took it down too; and the rule
delivers normally on the next identity once the offending filter is gone. All three
are asserted.

#### Insert mode: there was no `try` at all

`Render\Injector` contained none, and it runs inside WooCommerce's own rendering
hooks. A throw there **aborted the merchant's native processing, completed or admin
email** — this plugin breaking WooCommerce's own mail, which is strictly worse than
this plugin's content going missing.

**Decision: containment is PER RULE.** A throwing rule emits nothing, the native
email **continues normally**, every other matched rule still emits, and the failure
is recorded against that rule. The render happens into a variable and is echoed
only once it has succeeded, so a half-substituted body can never reach a customer.

The rule's own failure is recorded as **`not_rendered`** — see §10c, which is
where the relationship between that and the message's outcome is settled.

**⚠ AND IT IS PER RULE, NOT PER EMISSION.** At the per-item position one rule emits
once per matched line item. A rule that threw on one item and rendered on the next
**did** reach the customer: it keeps `emitted = true` and the throw is recorded in
its notes. Only a rule that emitted nothing at all is `not_rendered`.

#### 10a. The containment state holds LIVE objects, not snapshots of them

*(ADDED 2026-08-01, Prompt 6B.)*

Whatever a catch reports has to be established **before** the thing that throws.
§10's boundary declared `recipients`, `subject` and `notes` up front for exactly
that reason — and then read the placeholder notes out of `PlaceholderValues` only
once every resolution had finished, and passed `null` for the value set entirely in
insert mode's catch. See §1c: a partial diagnostic that is discarded on failure is
the diagnostic the merchant most needed.

**Decision: the boundary holds the live value set, and every note it accumulates is
merged at the point the row is written** — never copied into the state at one
instant. Both the success path and the failure path then read the same object and
cannot disagree.

#### 10b. `emitted` is true only when output was actually written

*(ADDED 2026-08-01, Prompt 6B.)*

`Injector` registered the rule against the ledger and *then* evaluated
`echo wp_kses_post( wpautop( $html ) )`, under a docblock claiming "the echo is
last, deliberately: everything that can throw has finished by then". **That claim
was false.** `wp_kses_post()` fires `wp_kses_allowed_html`, so the escaping call is
itself third-party-reachable. When it threw:

1. the ledger already held `emitted = true`;
2. the catch registered `emitted = false`;
3. `register()` OR-ed them and the result stayed `true`.

Nothing was printed and the history said content was inserted — a claim that
travels all the way to a merchant reading `sent` for a block their customer never
saw.

**Decision: every transformation that can throw completes into a variable BEFORE
the registration, and the echo is the last statement that runs.** The same ordering
is applied to the plain-text branch, which has no escaping step today and must not
acquire one silently.

**The OR is right ACROSS emissions and was wrong WITHIN one.** A rule emitting
beside two line items and throwing on only one of them did reach the customer, so a
later `false` must not erase an earlier genuine `true`. What must not happen is a
`false` being OR-ed into a `true` that *the same emission* had already recorded
without earning it. The ordering fix is what makes that distinction structural
rather than argued: an emission either registers and echoes, or never registers.
The catch passes **that emission's own** flag rather than a blanket `false`, so a
throw after the echo returned is reported truthfully too.

#### 10c. The MESSAGE outcome and the RULE RENDER outcome are two facts

*(ADDED 2026-08-01, Prompt 6B, correcting §10 as written in 6A.)*

§10 introduced `not_rendered` as a **fifth insert outcome**, and the code
implemented that literally: it **replaced** the message's outcome. So a rule whose
resolution threw during an `abandoned` render — a message that was never sent at
all — was recorded `not_rendered`, and `not_rendered` stores as `state = 'failed'`,
which `DeliveryDetailRepository::GENUINE_ATTEMPT_STATES` counts as a real delivery
attempt. The merchant's next, **first**, genuine send was then typed `resend`:
precisely the ADR-0013 §6b defect Prompt 5C fixed, reintroduced through a different
column. The stored sentence was untrue as well — it always ended *"and the native
email was sent without it"*, for messages nobody had sent.

**Decision: they are two orthogonal axes, recorded side by side, and neither is
ever derived from or collapsed into the other.**

| Axis | Values | What it describes |
|---|---|---|
| **message outcome** | `sent` / `failed` / `unresolved` / `abandoned` | what became of the WooCommerce email |
| **rule render outcome** | `rendered` / `not_rendered` | whether THIS rule's content got into it |

`not_rendered` is therefore **not** a member of `INSERT_OUTCOMES`, and passing it
as a message outcome is refused by the same allowlist that refuses any other
unrecognised code.

**The stored `state`** is a four-value storage allowlist that retention tiering,
the privacy exporter, `GENUINE_ATTEMPT_STATES` and every support query read, so the
two axes project onto it:

| Message | Rendered? | Stored `state` | Snapshot |
|---|---|---|---|
| `sent` | yes | `sent` | `outcome: sent`, `render: rendered` |
| `sent` | **no** | **`failed`** | `outcome: sent`, `render: not_rendered` |
| `failed` | no | `failed` | both preserved |
| `unresolved` | no | `unresolved` | both preserved |
| **`abandoned`** | no | **`abandoned`** | both preserved |

**Only the `sent` row is affected by the render outcome**, and that is the whole
correction. A message that went out *without* this rule's content is a failed
delivery **of this rule** and must be found by `state = 'failed'`. A message that
was **abandoned** was no delivery at all, so it keeps `abandoned` whether or not
this rule rendered — and is therefore **not a genuine attempt**, so a later first
send is `auto` and not `resend`. `unresolved` keeps its own state for the same
reason one step weaker: a send that began and never reported is not a send that
failed.

Nothing is inferred back out of the shared state: `snapshot.insert.outcome` and
`snapshot.insert.render` keep both codes exactly.

**And the reason sentence is assembled from both facts**, so no stored reason
claims the native email was sent when it was not:

| Message | Rendered? | Reason |
|---|---|---|
| `sent` | yes | `inserted into {email} at {position}` |
| `failed` | yes | `inserted into … — WooCommerce reported the message as not sent` |
| `unresolved` | yes | `content was rendered into … but the send outcome was never reported` |
| `abandoned` | yes | `content was rendered into … but that render was never sent — no delivery was attempted` |
| `sent` | no | `NOTHING was inserted into … — resolving this rule threw, so its content was withheld and **the native email was sent without it**` |
| `failed` | no | `… and **WooCommerce reported the native email itself as not sent**` |
| `unresolved` | no | `… and **the native email's send outcome was never reported**` |
| `abandoned` | no | `… and **that render never reached a send at all — no delivery was attempted**` |

### 11. The twin audit: one-mode fixes are a defect CLASS, not an accident

*(ADDED 2026-08-01, Prompt 6A.)*

§9a was found by accident. ADR-0013 §4b fixed the entity-deletion defect for
**insert** mode in Prompt 5A; the identical defect stayed live in **separate** mode
for six prompts and surfaced only because Prompt 6 happened to unify
`to_plain_text()`. `caf&eacute;` reached customers as `caf` the whole time.

**That is a class: a decision applied to one delivery mode whose twin was never
applied to the other.** Every ADR-0012 and ADR-0013 decision touching rendering,
escaping or content assembly is therefore audited, and the audit is recorded rather
than performed once and forgotten.

| Decision | Applies to | Implemented in both? |
|---|---|---|
| ADR-0012 §3 — **a throw during delivery is caught** | **both** | ⚠ **NO → FIXED HERE.** Separate mode caught only around `trigger()`; insert mode had no `try` at all. §10 |
| ADR-0012 §3 — every write is verified and shortfalls logged | both | yes — `write_attempt_rows()` and `record_insert()` both end in `verify()` |
| ADR-0012 §4 / §4a — recipient resolution, `HeaderGuard`, bare addresses | **separate only** | n/a — insert mode contributes to a message whose recipients are WooCommerce's |
| ADR-0012 §5a — global switch vs per-delivery filter | **separate only** | n/a — the switch is the enable box for *this plugin's own* `WC_Email`, which insert mode never sends. See the backlog: whether it *should* also silence insert mode is a product question, not a twin |
| ADR-0012 §5b — headers are WooCommerce's plus this plugin's Cc/Bcc | separate only | n/a — insert mode composes no headers |
| ADR-0012 §6 — content stored through `wp_kses_post` | both | yes — one repository boundary |
| ADR-0012 §6 — rendered inside WooCommerce's own wrapper | both | yes — separate mode wraps in `email-header`/`email-footer`; insert mode is *already* inside a native email |
| ADR-0012 §6 — plain-text output when `email_type` calls for it | both | yes |
| ADR-0012 §10 — one rule snapshot per delivery | both | yes — separate mode's per-run local; insert mode captures the row at frame-push evaluation |
| ADR-0012 §11–§11d — no per-run state on shared objects | both | yes, by different mechanisms: capture/restore on the email object, stacks in the render context |
| ADR-0013 §1a — the recorded outcome is the one WooCommerce **reported** | both | yes — `Custom_Email::trigger()` returns a string outcome; insert mode records the `woocommerce_email_sent` boolean |
| ADR-0013 §4b — plain text emitted **verbatim**, entities **decoded**, never HTML-escaped | **both** | yes — **this is the twin §9a fixed**; one `Domain\Text::to_plain_text()` serves both, so it cannot come apart again |
| ADR-0013 §4a / §4c / §5* — frames, slots, tokens, send-observation frames | insert only | n/a — separate mode is triggered by an order event, not by a render |
| ADR-0013 §6 / §6a — `unresolved` and `abandoned` | insert only | n/a — separate mode owns its own send and always learns the outcome |
| ADR-0013 §6b / §6c — attempt typing and numbering from delivery history | insert only | **live-correct, flagged.** Separate mode writes at most one attempt set per identity (ADR-0004), so `auto` is always right today. A manual-resend feature must give separate mode the same history-derived typing — recorded in the backlog |
| ADR-0013 §7 — ordering and audience | both | yes — one `Specificity` / `PreparedRule` |
| ADR-0014 §1a — a note recorded once per delivery per token | both | yes — one `PlaceholderValues` |
| ADR-0014 §2 — single-pass resolution | both | yes — one `PlaceholderSyntax::render()` |
| ADR-0014 §3 — per-context escaping applied to the value | both | yes |
| ADR-0014 §5a — per-item binding | insert only | n/a — separate mode has no per-item position |
| ADR-0014 §7 / §7a — the recipient safe set | separate only | n/a |

**The one live twin the audit found is the containment one, and §10 fixes it.**
It ran in the opposite direction to §9a: a *separate*-mode protection with no
insert-mode counterpart, which is why unifying one shared helper would never have
surfaced it.

## Consequences

- A merchant writes one rule and every customer receives their own name, their
  own order number and their own products.
- **A customer cannot make the plugin resolve anything.** Values are inert text;
  the only thing that decides what gets resolved is the merchant's template.
- The delivery log distinguishes *"this field was empty"* from *"this token was
  not recognised"* from *"this key was refused"* — three different facts a
  merchant would otherwise have to guess between.
- Because escaping is per context and applied to the value, the same rule is safe
  in HTML and readable in plain text, with no second template to maintain.
- Because meta access is default-deny with a per-key opt-in, a store can expose
  the one field it needs without exposing everything WooCommerce stores.
- Because resolution reuses the matcher's product cache, **every data class except
  shipping line items costs nothing** (§8) — and because the expected cost of each
  class is declared in the test above the measurement, a future placeholder that
  *would* cost a query fails gate 6 rather than being described accurately and
  passing silently.
- **Nothing a third party does during resolution can break a merchant's order
  update or a merchant's native WooCommerce email** (§10). A filter this plugin
  ships is treated as hostile, containment is the plugin's, and a rule that could
  not be resolved is recorded as one — never as delivered.
- **One-mode fixes are audited as a class** (§11), because the six prompts it took
  to find §9a were not bad luck.
- Placeholders are **not** available in the recipients document beyond two
  addresses, which is a deliberate limitation and will read as one to anybody
  who tries it; the log says why.

Recorded here and in `docs/p2-backlog.md`; **re-check on version bumps.**

- **⚠ `esc_html()` is filterable** (`wp-includes/formatting.php`, the `esc_html`
  filter). This plugin's escaping is `htmlspecialchars()` directly, so a
  third-party filter cannot switch it off. Applies to WordPress generally, not
  just this version.
- **⚠ The email heading is escaped by WooCommerce, not by this plugin**
  (`templates/emails/email-header.php:113`, WC 10.9.4). Asserted by test; if a
  future WooCommerce stops escaping it, the assertion fails.
- **⚠ `WC_Countries::get_formatted_address()` returns `<br/>`-joined HTML with
  each part already `esc_html`-escaped** (WC 10.9.4,
  `includes/class-wc-countries.php:684`). Address placeholders are flattened and
  decoded before substitution, so the value is text and is escaped once, by us,
  for the destination it is going to.
- **⚠ `wc_price()` returns a `<span>` wrapper**, so `{order_total}` is flattened
  to text before substitution.
- **⚠ `WC_Email::get_content()` DELETES unrecognised HTML entities from
  plain-text bodies** (WC 10.9.4, `$plain_search` pattern `/&[^&\s;]+;/i` → `''`)
  — first recorded as ADR-0013 §4b for insert mode, and the reason §9a exists.
- **⚠ `WC_Email::get_content()` ALSO RUNS `wp_strip_all_tags()` OVER THE WHOLE
  PLAIN BODY** (WC 10.9.4, `class-wc-email.php:872`), before the entity
  replacements above. So a value containing `<script>x</script>` is **removed
  entirely** from a plain-text email — not by this plugin, which deliberately does
  not escape a `text/plain` body, but by WooCommerce. The consequence for §3 is
  worth stating: a plain-text body cannot carry angle brackets at all, whoever put
  them there, and a merchant writing `a < b` in a rule will not see it in the
  plain alternative. Asserted by test so a change in WooCommerce is visible.
- **⚠ `WC_Order::get_item( $item_id )` DEFAULTS TO `$load_from_db = true`**
  (WC 10.9.4, `abstract-wc-order.php:1091`) and issues a query per call, even when
  the order has already loaded its items. Found by this ADR's own cost gate; see
  §8.
- **⚠ `WC_Order::get_shipping_method()` LOADS THE SHIPPING LINE-ITEM TYPE**, which
  the delivery path does not otherwise read — two queries, once per delivery, for
  bodies using `{shipping_method}`. Measured and reported rather than hidden; see
  §8.

## Amendment history

- **2026-07-31 (Prompt 6):** Created, before any placeholder code was written.
  Settles the two-form syntax with ASCII-folded names and case-sensitive meta
  keys; unrecognised placeholders resolving empty and recorded once per delivery;
  **single-pass resolution as a security invariant** with the customer-controlled
  billing-name example; per-context escaping applied to the value with
  `htmlspecialchars()` rather than the filterable `esc_html()`; the v1.0 set with
  WooCommerce's own formatters and the no-markup-ever rule; first-matched-item
  semantics for singular product placeholders with `PARTIALLY_RESOLVED` resolving
  empty rather than falling back to the parent; the four-part meta boundary with
  a default-deny filter; the two-address recipient safe set; send-time resolution
  with per-delivery state on a per-delivery object; and §9a, the separate-mode
  plain-body entity defect found while writing this ADR.
  **Corrected during implementation, by the ADR's own gates:** §8's cost claim was
  written as "no placeholder issues a query" and the measurement disproved it
  twice — first because `WC_Order::get_item()` defaults to a database read (one
  query per product placeholder, now one indexed `get_items()` per delivery), and
  then because `{shipping_method}` loads a line-item type nothing else reads. The
  section now states what was measured: cost scales with the number of distinct
  DATA CLASSES a body reads, never with the number of placeholders or
  occurrences.
- **2026-08-01 (Prompt 6A):** the failure boundary and the contract freeze.
  - **§10 (NEW) — resolution is CONTAINED, and every filter it invokes is
    hostile.** The most serious defect found in any phase, and this ADR created
    it: §6.4's filter is a plugin-owned extension point invoked between the claim
    and the send, where separate mode's `try` did not yet reach and where insert
    mode had no `try` at all. A throwing callback could strand a consumed identity
    or abort a merchant's native WooCommerce email. Adds the fifth insert outcome,
    `not_rendered`, and a recipient-less failure row for a throw that happens
    before any address exists.
  - **§11 (NEW) — the twin audit.** §9a was found by accident; one-mode fixes are
    a defect CLASS. Every ADR-0012 and ADR-0013 decision touching rendering,
    escaping or content assembly is tabled with the mode it applies to and whether
    both are implemented. Exactly one live twin was found — the containment one —
    running in the opposite direction to §9a.
  - **§1b (NEW) — the grammar recognises, the validator decides.**
    `TOKEN_PATTERN` capped the parameter at 255, so a 256-character meta key was
    not a token at all, the validator never ran, and **the whole raw placeholder
    was delivered to the customer verbatim**. The cap now lives only in
    `META_KEY_PATTERN`, and the case is tested end to end through a real send —
    the direct unit test passed throughout.
  - **§5a (NEW) — the per-item position binds to the item being rendered.** Item
    meta always resolved against `matched_items[0]`, so a block emitted beside item
    B printed item A's gift note or engraving. Extended — flagged, not slipped in —
    to the singular product placeholders, because binding one and not the other is
    stranger than either rule applied consistently.
  - **§7a (NEW) — a recipient entry is refused WHOLE.**
    `{customer_first_name}alice@example.test` resolved the disallowed placeholder
    to empty and **delivered to the remainder**. §7's safe set only means what it
    says if the entry is discarded the moment a placeholder outside it appears.
  - **§8 — the gate is amended EXPLICITLY**, with every data class enumerated and
    its measured cost DECLARED IN THE TEST above the measurement, so a new cost
    has to be written down by somebody who noticed it.
  - **§6.3 corrected** — "scalars only" disagreed with code that refuses booleans;
    the contract is string, integer or float, and a boolean's refusal is recorded
    as a boolean.
  - **§6.4 corrected** — a site filter vetoing a **public** key was logged as
    "refused a protected meta key"; the two refusals are now named apart.
  - **§3 amended** — the original "a hostile value appears safely in both formats"
    requirement is superseded for plain text, where WooCommerce deletes the
    sequence outright rather than neutralising it.
- **2026-08-01 (Prompt 6B):** the permission and outcome freeze. Four defects, and
  the first is a **security fail-open on the boundary this prompt series exists to
  harden**.
  - **§6.5 (NEW) — only a literal boolean opens a protected meta key.** The filter
    result was cast with `(bool)`, and the default for a protected key is `false` —
    so **any truthy return opened it**: `"no"`, `"false"`, `1`, a non-empty array,
    an `stdClass`, and worst of all **`WP_Error`**, which is what a callback
    conventionally returns when it *failed to decide*. Failing to decide was being
    read as permission to mail `_stripe_source_id` to a customer. A non-boolean
    return is now a refusal in its own right, with its own recorded reason. Stated
    generally, and for the third time in this codebase: **an extension point that
    cannot decide must never be read as consent.**
  - **§10b (NEW) — `emitted` is true only when output was actually written.**
    `Injector` registered against the ledger and *then* ran
    `wp_kses_post( wpautop( … ) )`, under a docblock claiming everything that could
    throw had already finished. It had not: `wp_kses_post()` fires
    `wp_kses_allowed_html`. A throw there left `emitted = true` OR-ed over the
    catch's `false`, so nothing was printed and the history said content was
    inserted. Every throwing transformation now completes before the registration,
    and the catch records that emission's own fact rather than a blanket `false`.
  - **§10c (NEW) — the message outcome and the rule render outcome are two
    facts.** §10 introduced `not_rendered` as a *fifth insert outcome* and the code
    implemented that literally, **replacing** the message outcome. An `abandoned`
    render whose resolution threw was therefore stored `state = 'failed'`, which
    `GENUINE_ATTEMPT_STATES` counts as a real delivery attempt — so the merchant's
    **first** genuine send was typed `resend`, the ADR-0013 §6b defect Prompt 5C
    fixed, reintroduced through a different column. The reason text was untrue as
    well, always ending "and the native email was sent without it" for messages
    nobody sent. The two axes are now recorded side by side and neither is ever
    collapsed into the other.
  - **§1e (NEW) — an empty parameter is not "no parameter".** `{customer_email:}`
    was coerced into `{customer_email}` and resolved to the customer's address —
    handing §7's recipient safe set a token it had never authorised. The same
    "junk repaired into a different valid target" shape ADR-0011 §2, ADR-0013 §2
    and §6.2 each removed from their own boundaries.
  - **§1c (NEW) — partial notes survive a throw**, and **§10a (NEW) — the
    containment state holds live objects rather than snapshots of them.** A note
    taken before a throw was discarded, leaving the merchant with somebody else's
    exception and no sight of the problem they could fix.
  - **§1d (NEW) — per-rule notes are an exact-keyed, capped set.** Unbounded at the
    rule level despite a per-value-set cap one layer down, and de-duplicated with
    `strpos()`, so a distinct note that was a substring of another was silently
    dropped. Generalised: **every new collection declares its cap and its key at
    the moment it is created.**
