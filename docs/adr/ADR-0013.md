# ADR-0013: Insert mode and the render context

Status: **Accepted** — 2026-07-28 (Prompt 5)

## Context

[ADR-0012](ADR-0012.md) froze the delivery spine for **separate** mode: a
WooCommerce event produces a trigger identity, the identity is claimed, an email
is sent, the outcome is recorded. Every step is ours, and the claim happens
*before* anything leaves the building.

Insert mode is a different shape end to end. WooCommerce is sending **its own**
email — processing, completed, refunded, admin new order — and this plugin adds
content **inside** it. Nothing about that send is ours to decide, schedule or
suppress. What is ours is deciding *which* content goes in, putting it in the
right place, and recording what went.

The machinery this needs is not new. `poc/_render-context.php` is the one POC
module always destined to become production code, and it took four correction
passes (1a–1d) against real WooCommerce behaviour to make correct. **This ADR
ports it; it re-derives nothing.** Every invariant in §5 is already proven
against WC 10.9.4 and is restated here so the production classes can be read
against a specification rather than against procedural harness code.

Three earlier decisions frame this one and are not reopened:

1. **[ADR-0003](ADR-0003.md)** — the two hook classes, the render-token frame
   stack, and render-scoped teardown.
2. **[ADR-0004](ADR-0004.md)** — insert identity is
   `order_id | rule_id | native_email_id`, an aggregate row with an attempt
   count, and intentional resends **do** re-insert.
3. **[ADR-0005](ADR-0005.md)** — the render-slot state machine, preview
   suppression and exact send correlation.

**Scope.** The render context, the five injection positions, insert-rule
fetching and evaluation, insert claiming and logging, preview safety and
front-end leakage prevention. Placeholders, `delay_seconds` scheduling,
consolidation, previews *as a feature*, test emails and the admin UI are out of
scope and — per the Prompt 4 lesson — are **filtered out**, never processed by
whatever path happens to exist.

## Decision

### 1. Insert mode inverts the claim

**This is the load-bearing decision of this ADR, and reversing it breaks the
mode in one of two ways.**

Separate mode claims **before** sending, because the claim *is* the decision:
if the identity is already consumed, nothing is sent. Insert mode has no such
decision to make. WooCommerce is sending its email regardless of what this
plugin thinks, and by the time the outcome is known the content is **already
inside the message**.

Therefore, for insert mode:

| | Separate mode | Insert mode |
|---|---|---|
| Identity | `order_id \| rule_id \| separate \| trigger_identity` | `order_id \| rule_id \| insert \| native_email_id` |
| When the record is written | **before** sending | at **finalization**, after the send |
| What the record is | a **gate** — it decides whether to send | a **log** — it records what was inserted |
| A repeat | suppressed, nothing sent | content **is** inserted again, count increments |

**Why claiming first would be wrong.** The claim would have to happen at render
time, before WooCommerce's send is known to succeed. Then:

- a render that never sends (a preview, a thrown send, a `get_content()` call by
  a customizer) would have **consumed the identity**, so the real send that
  followed would find it claimed and record nothing — the content would go out
  with no record of it;
- a merchant's deliberate resend of the completed-order email would find the
  identity claimed and be recorded as suppressed, while the content **did** go
  out again — a phantom record describing the opposite of what happened.

Both failures are invisible at the moment they occur, which is the family of
failure ADR-0005's decision log exists to eliminate.

**Consequences that follow, and are intended:**

- **An intentional native-email resend inserts the content again** and
  increments the attempt/send count. That is ADR-0004's stated behaviour, not a
  duplicate bug: if a merchant re-sends the completed-order email, the inserted
  block re-appears, because the merchant asked for that email to be sent again.
- **Within a single render, each rule inserts at most once.** The slot's matched
  rule set is a **set keyed by rule id**, not a list, so a rule matching two line
  items still contributes one block at a non-per-item position.
- The insert record can never suppress a native WooCommerce email. There is no
  code path in which this plugin's log state changes what WooCommerce sends.

### 1a. The recorded outcome is the one WooCommerce reported

*(ADDED 2026-07-29, Prompt 5A. Corrects an implementation that ignored it.)*

`woocommerce_email_sent` carries **the mail callback's own return value**. The
first implementation dropped it and wrote every finalized render `sent`, so a
`false` — a failure WooCommerce had *explicitly reported* — became a delivery
history stating the content had been delivered. **That is worse than an
unresolved slot**: unresolved is honest about not knowing, this was confidently
wrong about the one question the delivery log exists to answer.

**Four MESSAGE outcomes, and no two of them are synonyms:**

| Outcome | Means | Attempt row `state` |
|---|---|---|
| `sent` | the mail callback returned true | `sent` |
| `failed` | the mail callback returned false — a **reported** failure | `failed` |
| `unresolved` | a send **began** and no report ever arrived (§6) | `unresolved` |
| `abandoned` | **no send happened at all** — the render was thrown away (§6a) | `abandoned` |

⚠ **WHETHER ONE RULE'S CONTENT GOT INTO THAT MESSAGE IS A SECOND, INDEPENDENT
FACT** — `rendered` / `not_rendered`, recorded alongside rather than instead of the
outcome above. See [ADR-0014](ADR-0014.md) §10c for the full matrix.

*(CORRECTED 2026-08-01, Prompt 6B. Prompt 6A introduced `not_rendered` as a FIFTH
member of this table and the code implemented that literally: it **replaced** the
message outcome. An `abandoned` render whose resolution threw was therefore stored
`state = 'failed'`, which `GENUINE_ATTEMPT_STATES` counts as a real attempt — so
the merchant's **first** genuine send was typed `resend`, which is the §6b defect
Prompt 5C fixed, reintroduced through a different column. `not_rendered` is not a
message outcome and never was; only the `sent` row of §10c's matrix is affected by
it, where a message that went out without this rule's content is stored `failed`.)*

**The attempt row always records its own true outcome. That is not optional and
has no policy attached to it.**

**`final_status` on the aggregate tombstone reflects the LATEST DELIVERY
ATTEMPT**, never "any success". A merchant looking at an identity they have just
re-sent is asking *did the message I just sent go out*, and a `sent` left over
from three days ago answers a different question. Nothing is lost by the aggregate
tracking the newest fact, because the per-attempt rows keep the whole history —
and this is applied **uniformly across the three outcomes that describe a
delivery**, including `unresolved`: a tombstone that had finalised `sent` and
whose next *send* never reported an outcome becomes `unresolved`, because that is
the newest true thing about it. (Before Prompt 5A the unresolved path alone kept
an "any success" rule, which was both inconsistent and one extra read per repeat.)

**⚠ AMENDED 2026-07-30, Prompt 5B: "latest attempt" means latest *delivery
attempt*, and an abandoned render is not one.** See §6a — the literal reading of
this clause reported a message that demonstrably reached the customer as
`unresolved`, because a third party rendered the same email again afterwards and
threw the render away.

**Every attempt row also carries a per-attempt audit** in its structured
`snapshot`: `rule_revision`, `native_email_id`, `position` and `outcome`. The
tombstone can only hold one `rule_revision_sent` — necessarily the newest — so
without this a send at revision 1 followed by a resend at revision 2 exposed a
single revision for two materially different bodies, defeating the
single-snapshot audit trail Prompt 4a exists to protect. `set_final_status()`
now carries the revision alongside the status, so the aggregate's audit column
describes the attempt its `final_status` describes.

*(Amended 2026-07-30, Prompt 5B: `attempt` was REMOVED from the snapshot. The
number is allocated inside the write transaction (ADR-0009), and the `attempt`
COLUMN is its single source — a JSON copy could only ever disagree with the
column it duplicates, and the number it used to copy was precisely the one that
could be wrong.)*

**A repeat is a `resend` whatever its outcome.** The unresolved path computed
"is this a repeat" and then wrote `type = 'auto'` regardless, making the second
attempt of a resent email indistinguishable from the first.

### 2. Which rules are insert rules, and what triggers them

**`native_email_id` is the single source of truth.** For a rule with
`delivery_mode = 'insert'`, `trigger_type` and `trigger_value` are **not
consulted** — not at fetch time, not at evaluation time, not anywhere. The
question "does this rule apply?" is answered by *which WooCommerce email is
currently rendering*, and by the ADR-0011 product targeting.

**This follows the refund precedent already in `RuleRepository`.** ADR-0011 §2
already has a trigger type whose `trigger_value` is meaningless and is therefore
forced empty on write: `refund`. An insert rule is the same situation one step
further — *both* trigger fields are meaningless, so both are stored **empty**
and trigger validation is **skipped** rather than satisfied with a placeholder.
Storing a plausible-looking `status:completed` on an insert rule would be worse
than storing nothing: it would read as a promise the engine does not keep.

`native_email_id` is validated in its place:

- **non-empty** — a rule that targets no email can never fire and cannot say why;
- **well-formed, judged on the RAW value and REFUSED rather than repaired**
  *(amended 2026-07-29, Prompt 5A)*. `sanitize_key()` used to run first, so
  `customer_processing_order!` was **repaired into a valid, registered id and
  stored** — and the rule then targeted an email nobody chose. That is the
  identical silent-coercion shape ADR-0011 §2 removed from trigger types and
  Prompt 3B removed from trigger values, surviving on a new column: junk input
  becoming a *different valid target* is worse than an inert rule. The accepted
  alphabet is `sanitize_key()`'s own — `[a-z0-9_-]` — but it is **applied as a
  test, not as a transformation**, so `CUSTOMER_PROCESSING_ORDER`,
  `" customer_processing_order "`, `<b>customer_processing_order</b>` and
  `customer_processing_order%20` are all refused with no row written or modified.
  The check runs on **every write that supplies the column**, not only
  insert-mode ones, because otherwise a repaired id could be stored on a
  `separate` rule and become an insert rule's target via one later
  `update( $id, [ 'delivery_mode' => 'insert' ] )`;
- **matching a registered email** where that is verifiable, i.e. when
  `WC()->mailer()->get_emails()` is available. It frequently is not — a CLI
  importer or a migration can write rules long before the mailer initialises —
  so verification is **capability-detected, and its absence is not a rejection**.
  Refusing a valid rule because the mailer had not booted would be a worse
  failure than accepting an id that is checked again at render time, where the
  id is compared to the actually-rendering email anyway (§4).

**The read side refuses exactly what the write side refuses**, from the same
predicate — the discipline `normalize_trigger()` already shares between the two
trigger paths. `find_active_for_native_email()` repairing its argument would let
a lookup for `Customer Processing Order` match rows stored as
`customer_processing_order`, which is the same coercion arriving from the other
side.

**An insert-mode write FORCES its own columns, whatever the caller supplied**
*(added 2026-07-29, Prompt 5A)*. `sanitize()` writes only the keys a partial
update names, so the resolved-empty trigger was computed and then dropped:
converting a stored rule with
`update( $id, [ 'delivery_mode' => 'insert', 'native_email_id' => … ] )` left
`trigger_type = 'status'` and `trigger_value = 'completed'` behind, and the row
advertised a trigger the engine does not consult — the single-source violation
this section exists to prevent. `trigger_type`, `trigger_value` and
`delay_seconds` are therefore written on **every** insert-mode write, bypassing
the partial-update key filter. The mode that governs this is the **resulting**
mode: read from the write when it says, and from the stored row otherwise, by one
shared helper rather than three separate re-derivations — `sanitize()` used to
have its own, and it defaulted to `separate` whenever a partial update had not
mentioned the mode.

**`delay_seconds` must be `0`, and a non-zero value is REFUSED, not ignored.**
Content cannot be delayed inside an email that is already sending; there is no
sensible interpretation of "insert this in seven days". Silently coercing it to
zero would leave the merchant with a rule whose editor said seven days and whose
behaviour said none. The repository refuses the write, exactly as it refuses a
malformed transition trigger.

**Fetching.** `RuleRepository::find_active_for_native_email()` returns active
insert rules for one email id, ordered `priority ASC, id ASC` — the same
contract as `find_active_for_trigger()`. A supporting index
`insert_lookup (delivery_mode, native_email_id, status)` is added. **Schema v1 is
still unreleased, so this is an in-place amendment of v1 and NOT migration 2**,
the same reasoning ADR-0012 §2 used for adding `skipped` to the final-status
allowlist.

### 3. Evaluate once per render, at frame push

Matched rules are resolved **once**, when the render frame is pushed at
`woocommerce_email_order_details` priority 5, and stored **on the frame**. The
five injection callbacks read that list; **they never evaluate**.

Evaluating per position would run the matcher five times per render for one
answer, multiplying its cost by five for no benefit — and would make the five
positions capable of disagreeing with each other if a rule were edited
mid-render. One evaluation, one answer, five readers.

**The per-render query cost is a gate**: it must not scale with the number of
injection positions, and must not scale with rules × items.

### 4. Hook classes — ADR-0003, unchanged and binding

**SHARED hooks.** `woocommerce_order_item_meta_end`, and anything else that also
fires on front-end order templates. Permanently registered, and a **hard no-op
unless an email-render frame is active** — they carry no `$email` argument and
cannot otherwise tell an email render from a storefront view. The fourth
parameter is **optional with default `false`**, because stale theme and plugin
template overrides in the wild still call it with three arguments and a required
fourth parameter would throw `ArgumentCountError` on those installs.

**EMAIL-ONLY hooks.** `woocommerce_email_before_order_table`,
`woocommerce_email_after_order_table`, `woocommerce_email_order_meta`,
`woocommerce_email_customer_details`. They self-identify from their own `$email`
and `$plain_text` arguments and **MUST validate before emitting anything**:

1. the **email id** matches the rule's `native_email_id`;
2. the **order** matches the current render — taken from the frame recorded at
   push, never from `$email->object` (§5);
3. the **audience** matches `$sent_to_admin`.

**Unconditional emission is prohibited.** A rule targeting
`customer_processing_order` must never appear in `admin_new_order`,
`customer_completed_order`, or any unrelated email.

**HARD GUARANTEE: zero injected output and zero PHP notices** on My Account
view-order, the thank-you page, and order-pay. This is asserted directly, not
argued.

#### 4a. ⚠ Only three of the five positions fire inside the ADR-0003 frame

*(FOUND while implementing, verified in the WC 10.9.4 templates. Flagged rather
than adapted to silently.)*

`woocommerce_email_order_details` is a single action that **renders the order
table**. The ADR-0003 frame opens at its priority 5 and closes at priority 15.
But `customer-processing-order.php` fires two of the injection positions
**after** that action returns:

| Position | Fired from | Inside the frame? |
|---|---|---|
| `before_order_table` | `email-order-details.php`, itself run at `woocommerce_email_order_details` priority 10 | yes |
| `item_meta` | per item, same template | yes |
| `after_order_table` | same template | yes |
| `order_meta` | `customer-processing-order.php`, after the order-details action | **no** |
| `customer_details` | same, after that | **no** |

Keeping the frame open until `woocommerce_email_footer` instead is **not**
available: ⚠ plain-text templates never fire the footer, and they fire both of
those positions too.

**This does not weaken ADR-0003 — it clarifies what the frame is for.** ADR-0003
and the POC both call the frame stack *the item-hook context window*, and that is
exactly the job it keeps: the SHARED `woocommerce_order_item_meta_end` hook is
gated on a live frame, so the storefront guarantee above is untouched.

Alongside it, `RenderContext` keeps a **render record** per render — the same
identity (email id, order, audience) plus the matched rules — which lives from
push until the render can no longer emit. The EMAIL-ONLY positions read that and
perform the identical three-way validation §4 requires. Three structures, one job
each, mirroring the POC's own division:

| Structure | Lifetime | Read by |
|---|---|---|
| frame stack | order-details priority 5 → 15 | the SHARED position |
| render record | push → retirement (below) | the four EMAIL-ONLY positions |
| slot (§5) | push → send finalization | recording |

**THE RENDER RECORD'S LIFETIME AND RETIREMENT POINT, STATED EXPLICITLY**
*(added 2026-07-29, Prompt 5A)*. It is a **second validation path** with its own
lifetime, so leaving that lifetime implicit would be leaving a hole open.

A record is created at push and retired at the **first** of:

1. **send finalization** — `woocommerce_email_sent` resolves the bound token and
   retires that token's record. This is the normal path, and it is the reason a
   completed email's record can never serve a later one;
2. **preview reconciliation** — a stale preview frame's record goes with the
   frame, before the next push;
3. **shutdown** — every remaining record is dropped.

While a record is live it can only be selected by a caller matching **all four**
of `spl_object_id`, email id, order id and audience. A *different* email or a
*different* order matches nothing of it at all.

⚠ **CORRECTED 2026-07-29 (Prompt 5A) and again 2026-07-30 (Prompt 5B).** This
paragraph used to end "*and the scan runs newest first — so even a render that
never sends cannot outrank a later render of the same email for the same order*".
That was the defect, stated as the defence: newest-first is exactly how an inner
render captured an outer render's emission (§5a). **There is no scan.** The only
candidate is the innermost open record, validated against all four fields plus the
enclosing-depth invariant, and the answer is 0 or 1 — two matching records emit
**nothing** and log the ambiguity. And per §4c the in-frame positions do not
consult records at all.

#### 4b. Plain text is emitted verbatim, never HTML-escaped

*(ADDED 2026-07-29, Prompt 5A. Corrects an implementation that escaped it.)*

> **⚠ THIS SECTION APPLIES TO BOTH DELIVERY MODES, AND FOR SIX PROMPTS IT WAS
> IMPLEMENTED IN ONLY ONE.** Separate mode's `get_content_plain()` had no decode
> step, so `caf&eacute;` reached customers as `caf` the whole time — found by
> accident in Prompt 6 and fixed as [ADR-0014](ADR-0014.md) §9a. Both modes now
> share one `Domain\Text::to_plain_text()`. ADR-0014 §11 is the standing audit that
> exists because of this: **a fix applied to one mode and not the other is a defect
> class, not an accident.**

The plain-text branch ran `esc_html( to_plain_text( $content ) )`. After
`wp_strip_all_tags()` there is **no markup left for HTML escaping to protect**,
and the result goes into a `text/plain` body that is **never parsed as HTML** —
so escaping there could only corrupt.

The plain branch therefore: strips block-ish tags to newlines, removes every
remaining tag, **decodes entities**, normalises line endings to `\n`, and emits
the result **unescaped**. Decoding happens *after* stripping, deliberately:
decoding first could reveal sequences the strip would then eat, so a merchant's
`&lt;3` would silently vanish. **The HTML branch keeps its escaping unchanged.**

⚠ **This is more than cosmetic, because of what WooCommerce does next.**
`WC_Email::get_content()` runs the whole plain body through `$plain_search` /
`$plain_replace`, whose last-but-one pattern is `/&[^&\s;]+;/i` → `''`: **every
entity WooCommerce does not explicitly handle is deleted outright**. An
un-decoded `caf&eacute;` reached the customer as `caf`, and `40&#176;C` as
`40C`. The handled entities fared better but were still not what the merchant
wrote.

#### 4c. In-frame positions resolve through the FRAME; only post-frame positions use records

*(ADDED 2026-07-30, Prompt 5B.)*

§4a splits the five positions by *when* they fire. This clause makes that split
decide *what they ask*:

| Position | Fires | Authoritative source |
|---|---|---|
| `before_order_table` | inside the frame window | the **live frame** |
| `item_meta` (shared) | inside the frame window | the **live frame** |
| `after_order_table` | inside the frame window | the **live frame** |
| `order_meta` | after the priority-15 pop | the **render record** |
| `customer_details` | after the priority-15 pop | the **render record** |

**Why the in-frame positions must not ask the record stack.** A render record
outlives its frame by design (§4a), and it is retired at `customer_details`, at
the HTML footer, at finalization or at shutdown. A third party that fires
`woocommerce_email_order_details` **on its own** — which is how a plugin borrows
WooCommerce's order table for its own email — fires none of the first three, so
its record survives. That leaked inner record then sat on top of the stack while
the **enclosing** render reached its own `after_order_table`, and the enclosing
render either emitted nothing or emitted into the inner record's slot.

Measured before the fix, with 15 nested renders: the outer send finalised with
**no rules**, and content that was physically inside the outer message was
recorded against a slot then reported as never sent. Wrong in both directions at
once — the §5a defect shape in a third place.

The frame cannot be shadowed: exactly one frame is topmost, the same action
brackets it and these three positions, and a refused frame (§5c) answers null
rather than deferring to anything. The frame being live does **not** excuse the
callback from validating the email object, email id, order and audience it was
handed; ADR-0003 requires that of every position regardless of source.

*(This also makes the shared `item_meta` position's long-standing rule — gate on
the frame, never on a record — the general rule for its whole class, rather than
an exception it happened to follow.)*

### 5. Frame and slot invariants — ported from the POC, not re-derived

Every item below is already proven against WC 10.9.4 by POC-C and POC-D. The
production classes implement exactly these; a change to any of them is a change
to ADR-0003 or ADR-0005, not a refactor.

- **Frames are a stack.** A nested render pushes and pops its own. A boolean
  would be cleared by the inner render while the outer one was still going.
- **Cleanup is render-scoped.** `cleanup_matching( $email, $order, $token )`
  removes **exactly one** frame — the one bearing that token — and is
  tuple-validated against the email object and order. A valid token from a
  *different* render removes **nothing** and records a mismatch. Matching on the
  email object alone is insufficient, because one shared object serves every
  delivery of an email type.
- **The order comes from the slot recorded at push, never from
  `$email->object`.** Verified on WC 10.9.4: after a nested same-object render,
  WooCommerce does **not** restore `$email->object`, so it points at the inner
  order for the rest of the outer render.
- **Slot states:** `rendering` → `awaiting_send` → `reserved` → `in_flight` →
  resolved.
- **The `awaiting_send` transition happens at `woocommerce_email_order_details`
  priority 15, NOT at `woocommerce_email_footer`** — plain-text templates never
  fire the footer, so a footer-based transition leaks one slot per plain-text
  render. The footer remains a **backstop** for HTML renders only.
- **A send RESERVES its slot at `woocommerce_mail_content`, and binds the
  reserved token at `woocommerce_mail_callback_params`.** The params are returned
  **unmodified** — no render token is ever embedded in outgoing mail —
  and `woocommerce_email_sent` resolves **exactly the bound token**. No
  reservation means bind nothing; no binding means finalize nothing.

#### 5a. Selection is by identity at every stage — "most recent" is prohibited

*(ADDED 2026-07-29, Prompt 5A.)*

Prompt 1D moved the binding **point** to `woocommerce_mail_callback_params` and
removed the "most recent `awaiting_send`" heuristic from the resolution. **The
same heuristic survived one layer down, in the binding's own selection**, and
reproduced the original defect exactly:

1. an outer native render completes; its slot is `awaiting_send`;
2. `WC_Email::send()` fires `woocommerce_mail_content`;
3. a third party calls `get_content()` on the **same** email object for another
   order **and does not send it** — that inner render becomes the newest
   `awaiting_send` slot;
4. the outer send reaches `woocommerce_mail_callback_params` and binds the
   **inner** slot;
5. the outer mail's result finalises the inner order's rules, and the real outer
   render is reported `unresolved` at shutdown.

Wrong order attributed, wrong rules recorded, real delivery lost. A nested
**full send** does not expose this — it resolves immediately — which is why the
existing nested test stayed green throughout.

**The sequence, and what each stage selects on:**

> ⚠ **SUPERSEDED IN PART BY §5d (2026-07-30, Prompt 5B).** The stage *order* below
> is unchanged and still binding. What changed is the RESERVE stage: it no longer
> selects at all. The scope observation now **takes the exact published token** and
> `reserve()` consumes it, because selection-by-uniqueness fails outright when two
> renders share an identity — see §5d. The bullets below are kept because the
> reasoning behind each still governs the code; the two marked ✗ describe rules
> the code no longer has.

```
woocommerce_email_headers / _attachments  (PHP_INT_MAX)
    -> TAKE the exact completed token for the send about to begin  (§5d)
woocommerce_mail_content                  (PHP_INT_MIN)
    -> RESERVE that token; verify it still exists and is awaiting_send
third-party callbacks on the same filter
    -> may render or send; their slots cannot displace an outer reservation
woocommerce_mail_callback_params          (9999)
    -> BIND the innermost reservation, verified against the email object
woocommerce_email_sent                    (10)
    -> FINALIZE exactly the bound token
```

- **The scope is authoritative when known.** Only a token published by that object
  can be taken, and "none" is an answer — falling back to another object's slot is
  precisely how a separate-mode send nested inside a native render would consume
  the native render's slot, since `Email\Custom_Email` renders no order details
  and has no slot of its own.
- **State does the nesting.** A slot already `reserved` belongs to an enclosing
  send and cannot be reserved again, so an inner send cannot take an outer one's
  slot and needs no ordering rule to say so.
- ✗ ~~**Ambiguity is refused, never resolved.** Two eligible candidates reserve
  nothing; both renders are reported `unresolved`.~~ **This rule is gone (§5d).**
  It was fail-closed but total: two renders of the same email for the same order
  are a legitimate, third-party-producible state, and refusing both meant the
  outer send — whose content demonstrably went out — recorded no delivery at all.
  There is now no candidate set to be ambiguous about.
- **Reservations nest LIFO** and are popped by the bind that belongs to the same
  `WC_Email::send()` invocation, so they stay one-to-one with sends however
  deeply those nest. A blank reservation is still pushed when no token was taken,
  exactly so that alignment holds.

**"The most recent `awaiting_send` slot" is prohibited at every stage** — as a
reservation rule, as a binding rule and as a finalization rule. The
counterfactual diagnostic that used to record what such a rule *would* have
chosen has been removed too, so no recency scan exists in `RenderLedger` at all.
*(Still true, and stronger since §5d: `reserve()` no longer reads the slot list to
choose anything — only to verify the token it was handed.)*

⚠ **Two hooks are needed because one cannot supply both halves.**
`woocommerce_mail_content` is the last moment before a third party can create a
competing slot, but WooCommerce passes it **only the message** (WC 10.9.4,
`class-wc-email.php:1233`) so it cannot say which email is sending. The object
comes from `woocommerce_email_headers` and `woocommerce_email_attachments`,
which `send_notification()` and `send_if_recipient()` evaluate as the last two
arguments to `send()` — immediately before it is entered, with nothing in
between. Every native WooCommerce email in WC 10.9.4 sends through one of those
two methods.
- **`$email->object` is type-guarded** (`instanceof WC_Order`) before any use.
- **Preview state is render-scoped**, consumed at push and cleared by that
  render. WooCommerce's own `woocommerce_is_email_preview` signal is **preferred**
  but **demoted** the moment reconciliation proves it leaked: verified on
  WC 10.9.4, `EmailPreview::render_preview_email()` calls `clean_up_filters()`
  with **no `try`/`finally`**, so an interrupted preview leaves the signal
  returning `true` for the rest of the request and a later **real** send would
  report itself as a preview and silently write nothing.
- **A preview render creates a frame and NO slot.** Injection callbacks still
  need a context to read, so the frame exists; but with no slot, a preview can
  never register a rule, never reach `awaiting_send`, never bind, and therefore
  **can never produce a record**. Preview safety is structural, not conditional.
- **Reconciliation runs at the start of every push** and again at shutdown: a
  surviving *preview* frame is proof that a preview was interrupted between push
  and pop, because a completed preview always removes its own frame. Such frames
  and their open tokens are dropped **before** the new frame is pushed, so no
  render inherits a previous render's residue. *(Amended 2026-07-30, Prompt 5B: a
  **refused** push (§5c) skips reconciliation, because it creates no record and no
  slot for residue to contaminate and must do the least work possible. The next
  accepted push reconciles as always.)*

#### 5c. Render depth is bounded, and the bound is a denial-of-service fix

*(ADDED 2026-07-30, Prompt 5B.)*

`RenderContext::push()` had no bound. Every frame accepted costs a frame record, a
render record, a ledger slot, two open-token entries and — the expensive one —
**one rule evaluation, which is a database query**. Measured: 41 nested renders
were accepted and produced 41 render records, 41 ledger slots and 41 evaluations.

This plugin never originates a recursion. But a third-party callback that
re-enters a render hook does not merely recurse: it makes **this plugin amplify**
its recursion by a query and three structures per level. On a live store that is a
denial-of-service amplifier driven by somebody else's bug, and it must be closed.

**`MAX_RENDER_DEPTH = 16`.** WooCommerce's own order emails nest zero deep. Every
legitimate nesting comes from a third party rendering another email from inside a
render hook, and one or two levels covers every such pattern. 16 is an order of
magnitude of headroom over that while capping this plugin's contribution at 16
evaluations per request-path, and is far below the point at which PHP's own stack
or `xdebug.max_nesting_level` (256 by default) would intervene — so the refusal is
ours, taken deliberately, rather than a crash.

**Beyond the bound a render is REFUSED:** no render record, no ledger slot, **no
rule evaluation and therefore no query**. It is logged **once per request**, not
once per level. The render itself proceeds **uninjected** — WooCommerce composes
and sends its own email, simply without this plugin's content. Losing an insertion
at depth 17 is a vastly better outcome than a store that stops responding.

**A refused frame pushes a marker, and that is not decoration.** If nothing were
pushed, the **outer** frame would stay topmost: `in_email()` would still report an
active render, `current()` would hand the shared item-meta hook the outer frame,
and in the same-order/same-email case the outer render's content would be emitted
**into the refused inner render** — content in the wrong message, recorded against
the wrong slot. The marker makes every guard see *inside a render, and not one of
ours*: no record bears its token, and the enclosing-depth invariant disqualifies
every open record while it is topmost. Both fail closed, which is emit nothing.

**Not an exception, deliberately.** A throw would propagate out through the third
party's callback, through WooCommerce's rendering, and into whatever triggered it
— potentially a checkout or an admin order save — converting a memory problem into
a broken order flow on a merchant's live site. And it would stop nothing: see the
limitation below.

**The diagnostic arrays are capped** at `MAX_DIAGNOSTIC_ENTRIES = 100` —
`unresolved_emissions`, `mismatches`, `reconciled`, and `RenderLedger`'s
`reservation_log` and `finalizations` for the same reason one layer down (a third
party that *sends* in a loop drives one entry per iteration). Entries past the cap
are **dropped and counted**: a diagnostic that truncates without saying so is
worse than one that is missing.

⚠ **STATED LIMITATION — what this cannot do.** It cannot stop the recursion. A
directly self-recursive third-party hook loops through that party's own closure
and WordPress's dispatcher and **never re-enters this class**, so neither refusing
nor throwing ends it. In-flight refused markers therefore still scale with the
third party's own recursion depth — at roughly a six-key array and two strings per
level, against that party's own stack frame, output buffer and order object. What
the bound does is **starve the recursion of this plugin's amplification**: the
query per level, which is the part that reaches the database, is gone. That is the
honest limit of what this plugin controls.

#### 5d. The exact token is CARRIED from render to send, never inferred

*(ADDED 2026-07-30, Prompt 5B. Replaces the scan §5a left in place.)*

§5a removed recency from the *selection*, leaving `reserve()` scanning the
`awaiting_send` slots and reserving only when exactly one was eligible. That is
fail-closed but wrong, and the failure is total: two renders of the **same email
for the same order** — which a third party produces by calling `get_content()`
from inside a render hook — are two eligible slots, so **nothing** was reserved,
**nothing** bound, **nothing** finalized, and the outer send recorded **no
delivery at all** even though its content demonstrably went out. Uniqueness cannot
resolve what identity cannot distinguish; only structure can.

The token is therefore carried:

```
order_details:15                       -> ARM the slot
render reaches its TERMINAL position   -> PROMOTE the exact token          (§5e)
send scope observed (headers/attachments, PHP_INT_MAX)
                                       -> TAKE the exact token for this send
woocommerce_mail_content               -> RESERVE that token
woocommerce_mail_callback_params       -> BIND that token
woocommerce_email_sent                 -> FINALIZE that token
```

*(The first two lines were one line — "render complete (order_details:15) ->
PUBLISH the exact token" — until §5e split them. Arming and candidacy are not the
same event, and treating them as one is what let a render nested from a post-frame
position displace the render enclosing it.)*

- **`reserve()` consumes the token the scope observation already took, and never
  scans.** It reads the slot list only to VERIFY that token — that its slot still
  exists and is still `awaiting_send` — never to choose. No token means no
  reservation, no binding and no finalization. A blank reservation is still pushed
  so reserve/bind stay one-to-one with `send()` invocations however deeply they
  nest.
- ⚠ **SUPERSEDED BY §5e (2026-07-30, Prompt 5C):** ~~Published at the
  render-complete signal, priority 15~~ and ~~the publish stack is LIFO and that is
  structural because an enclosing render cannot finish before the render nested
  inside it~~. **That reasoning was false for the two positions this plugin ships.**
  `order_meta` and `customer_details` fire AFTER priority 15, so a render nested
  from either one published *after* the render enclosing it and was taken by the
  enclosing send. §5e replaces publication-then-ordering with promotion at each
  render's own terminal position. The slot is still ARMED at priority 15 — that part
  stands, and is why the post-frame positions can still register onto it.
- ⚠ **One send takes exactly one token, though BOTH observation filters fire.**
  `get_headers()` and `get_attachments()` are two arguments to one `send()` call.
  The second observation recognises its own send by descriptor and keeps the token
  already taken.
- ⚠ **The order is deliberately NOT validated at the handoff.**
  `woocommerce_email_headers` hands over `$email->object`, and WooCommerce does not
  restore that property after a nested render (§5), so at the send it can name a
  different order entirely. Validating against it would reject the correct token
  and accept a wrong one. The email id comes from `$email->id`, which no render
  mutates.

**Residual, recorded rather than hidden.** A third party that *completes* a render
on the same email object **between** the enclosing render's completion and the
enclosing send's header evaluation would have its token taken instead. Both renders
are complete, both belong to the same object and the same email id, and the only
remaining discriminator — the order — comes from `$email->object`, which
WooCommerce has already corrupted. The window is one PHP statement wide
(`send( $to, $subject, $content, $headers, $attachments )`), and the failure is a
mis-attribution between two renders of the same email rather than a lost delivery.

#### 5e. Candidacy is PROMOTED at each render's own terminal position

*(ADDED 2026-07-30, Prompt 5C. Replaces §5d's publication-and-stack-ordering.)*

§5d carried the exact token instead of inferring it, and that stands. What it got
wrong was **when a render becomes a send candidate**: it published at
`order_details:15` and took the tail, assuming that an enclosing render always
finishes last. That is true only of nesting sites INSIDE the frame window — and
this plugin injects at two positions that fire after it:

```
outer publishes token 1               (order_details:15)
outer reaches order_meta
    third party calls get_content() on the same object
    inner publishes token 2           <- now the tail
    inner returns without sending
outer finishes; get_headers() takes the tail -> token 2, the INNER render
```

The outer message finalised the inner slot; the genuine outer slot was swept as
never sent. **This was the same defect in its fourth location** — after
`current_render()`, `bind()` and `reserve()` — and it was recorded in Prompt 5B's
gate-12 table as "top entry only, structural". It was not structural: the ordering
was assumed, not produced.

**The rule.** Arming and candidacy are separated:

| Point | Effect |
|---|---|
| `woocommerce_email_order_details` : 15 | ARM the slot — reservable, and still registrable by the post-frame positions |
| `woocommerce_email_customer_details` : `PHP_INT_MAX` | **PROMOTE** — append this exact token to its object's candidate queue |
| `woocommerce_email_footer` : `PHP_INT_MAX` | **RE-PROMOTE** — move this exact token back to the tail (HTML only) |
| `woocommerce_pos_email_footer` : `PHP_INT_MAX` | the same, for the two POS receipt templates |

⚠ **CORRECTED 2026-07-31 (Prompt 5D): the priority was 999 and the claim attached
to it was false.** The docblock said 999 "runs after any third party".
**WordPress runs LOWER priority numbers FIRST**, so every callback registered at
1000 or above ran *after* this plugin's promotion — and priority 1000 is an
entirely ordinary choice for a plugin that wants to run late. A third party
nesting a render there promoted last, and the enclosing send took the nested
render's token: the fifth appearance of the §5a defect, reachable without any
exotic behaviour at all.

**The real guarantee, stated exactly:**

> Extonify promotes at the highest numeric priority available. A callback
> registered later at the same `PHP_INT_MAX` priority still runs after ours,
> because same-priority callbacks execute in registration order. That residual is
> accepted and recorded.

**The invariant that guarantees the order, and it is produced rather than
assumed:** a render promotes itself at the last position it can reach, and our
callbacks sit at `PHP_INT_MAX` on those positions. PHP unwinds a nested render
completely before the enclosing render's next statement runs, so the enclosing
render necessarily promotes *after* every render nested within it. The queue order
is therefore the true completion order.

**Re-promotion at the footer is required, not tidy.** ⚠ For HTML the footer fires
*after* `customer_details`, so a third party rendering from the footer would
otherwise promote after the enclosing render already had. Re-promotion restores the
enclosing render to the tail, because our footer callback also runs at
`PHP_INT_MAX` — after that nested render has finished and promoted itself.

**The terminal position, verified against the WC 10.9.4 templates rather than
assumed.** All thirteen order-email templates that fire
`woocommerce_email_order_details` also fire `woocommerce_email_order_meta` and then
`woocommerce_email_customer_details`, in that order, in **both** formats:

| Format | Terminal position | Footer? |
|---|---|---|
| HTML | `woocommerce_email_customer_details` | yes — eleven templates fire `woocommerce_email_footer`; ⚠ `customer-pos-completed-order.php` (line 122) and `customer-pos-refunded-order.php` (line 133) fire **`woocommerce_pos_email_footer`** instead |
| Plain | `woocommerce_email_customer_details` | ⚠ **no** — only `plain/customer-cancelled-order.php` fires one in the whole tree |

⚠ **CORRECTED 2026-07-31 (Prompt 5D): the POS row previously read "fire no footer
at all".** That was true only of the hook this plugin was listening to. They fire
a POS-specific footer hook, which is now registered — and, more importantly, §5h
removes the dependence on knowing that at all.

So `customer_details` is the mechanism for both formats and the footer is only a
later HTML backstop. A promotion rule built on the footer would never promote a
plain-text render at all.

**When neither fires — the explicit last resort.** A custom template override that
fires neither position leaves the render **unpromoted**. Nothing is guessed: the
send finds no candidate, `RenderLedger::take_candidate()` counts an unidentified
send, nothing is reserved, bound or finalised, and the slot is swept at shutdown as
**`unresolved`** — not `abandoned`. The distinction matters: the render was never
offered to a send, so we cannot claim no send took it; its message may well have
gone out carrying our content. `unresolved` says exactly that (§6a).

**A mismatched tail takes nothing.** If the tail candidate's email id is not the
sending email's, nothing is taken and the refusal is logged. Nothing searches
deeper — a search would be selection by position under another name.

#### 5f. A leaked render record is collected when the enclosing frame closes

*(ADDED 2026-07-30, Prompt 5C. Amends §4a's record lifetime.)*

§4c fixed the in-frame positions by resolving them through the live frame. The
post-frame positions have no frame to resolve through — that is why records exist —
so a **leaked** record still shadowed them, and Prompt 5B recorded that as a known
cost. §5e makes it blocking: promotion happens at a post-frame position, so a render
that cannot identify itself there can never become a candidate.

A third party firing `woocommerce_email_order_details` **on its own** — how a plugin
borrows WooCommerce's order table — fires neither post-frame position nor the
footer, so its record was never retired.

**The retirement rule, and it is provable rather than heuristic:** when a frame is
removed at `order_details:15`, every render record pushed *after* that render's is
retired. WooCommerce's templates fire `order_details`, then `order_meta`, then
`customer_details`, with nothing of ours in between — so a render nested inside this
one has already had its own post-frame positions, which fire immediately after its
own `order_details` returns and therefore still inside this render's window. By the
time this frame closes, anything pushed after it is either already retired or
provably dead.

Measured on a 19-deep third-party render storm: 15 leaked records before, **0**
after, and the enclosing render's own `after_order_table`, `order_meta` and
`customer_details` all emit and promote normally again.

#### 5g. The send handoff is a STACK of observation frames, one per `send()`

*(ADDED 2026-07-31, Prompt 5D. The fifth and last location of the §5a defect.)*

§5d carried the exact token from the render to the send, and §5e produced the
promotion order rather than assuming it. What remained was **where the carried
token was held between the two**: one scalar token plus one `{spl, email_id}`
descriptor, with the descriptor deciding whether an observation belonged to the
send already in progress.

```php
if ( null !== $this->send_scope && $this->send_scope === $scope ) {
    return $this->send_token;   // "the SECOND filter of one send"
}
```

**For a send nested inside another send through the same singleton with the same
email id, that equality is TRUE.** The inner send was therefore treated as the
outer send's second observation:

```
outer headers      -> takes outer token
inner headers      -> descriptor matches -> returns the OUTER token
inner attachments  -> same
inner mail_content -> reserves the OUTER token
inner send         -> FINALIZES the OUTER token with the INNER result, clearing
                      the scalars
outer attachments  -> descriptor now clear -> takes the remaining candidate,
                      which is the INNER token
outer send         -> FINALIZES the INNER token
```

Reversed in both directions. The code even carried a comment anticipating *"a
third party sent from inside the observation filters"* — but the equality above it
meant that branch could never be reached in the same-id case, which is the case
that matters.

**The rule. One frame per `WC_Email::send()` invocation, each carrying its own
token, popped by that same call's own reservation:**

```
outer headers      -> push outer frame (outer token)
inner headers      -> push inner frame (inner token)
inner attachments  -> top frame = inner
inner mail_content -> consume inner frame, reserve inner token
inner send done    -> inner frame gone
outer attachments  -> top frame = outer
outer mail_content -> consume outer frame, reserve outer token
```

**No equality test on `{spl, email_id}` can distinguish nested calls through one
singleton — that is the whole lesson of this defect class, and it is now gate 12's
standing requirement. Depth is structural.**

**What pairs the two observations of one send, since identity cannot.** The FILTER
is the discriminator. `WC_Email` evaluates `get_headers()` and then
`get_attachments()` as the last two arguments of one `send()` call (WC 10.9.4,
`class-wc-email.php:1173-1178` and `1209-1214`), so one send fires
`woocommerce_email_headers` exactly once and then `woocommerce_email_attachments`
exactly once. A **headers** observation therefore always opens a frame; an
**attachments** observation completes the frame on top when that frame is still
waiting for its own. Any send nested between the two opens and closes its own
frame in full, so the frame on top at that moment is this send's — and the
identity is then re-checked as a **verification of a frame chosen by depth**,
never as the thing that chose it.

**The released-token accounting is unchanged in meaning.** A frame still open at
the shutdown sweep belongs to a send that took a token and never reached
`woocommerce_mail_content` — a throw between the two, or `get_headers()` evaluated
outside a send. The frame is dropped and counted; its slot is still
`awaiting_send`, so it is reported as an **abandoned render** (§6a), which is the
honest answer. Passing the token on would attribute one render's content to
another's message.

#### 5h. A finalized token is purged from every open-token ledger, token-exactly

*(ADDED 2026-07-31, Prompt 5D.)*

`RenderContext` keeps two open-token ledgers so an interrupted render can be
reconciled: `open_details`, retired at `order_details:15`, and `open_footer`,
retired at the footer. Every accepted render appends to both at push.

⚠ **Two WC 10.9.4 HTML templates fire no footer hook this plugin was listening
to** — the POS receipts of §5e — so each POS receipt left one `open_footer` entry
behind **permanently**. A request sending 100 receipts left 100 stale tokens on
the request-shared singleton. Not a wrong-email event; exactly the unbounded
per-request residue gate 10 exists to forbid.

**The rule, in two parts, and the second is the one that matters:**

1. `woocommerce_pos_email_footer` is registered alongside `woocommerce_email_footer`
   — verified to exist in the bundled WooCommerce before being relied on;
2. **on `woocommerce_email_sent`, after the slot is finalized, that exact token is
   purged from both ledgers and its render record retired.** This makes correctness
   independent of *which* footer hook a template fires, or whether it fires one at
   all — a custom template is as safe as a bundled one, and a future WooCommerce
   footer hook needs no code change.

The purge is **token-exact, never positional**: the token names one render, and a
positional pop here would take an enclosing render's entry.

**And `shutdown()` clears every per-request collection it reconciles** —
`frames`, `renders`, `open_details`, `open_footer`, `preview_pending` — not only
the records. Reconciliation alone removes stale *preview* frames; an interrupted
**real** render left its frame behind, so `in_email()` kept reporting an active
render, and the shared item-meta hook stayed armed, for the rest of the request.
The capped diagnostic arrays are deliberately not cleared: they exist to explain
the request afterwards and `shutdown` is when something reads them.

**The general rule this instance follows:** *every per-request collection on a
request-shared object must name where it is populated and where it is cleared, and
a collection whose clearing path depends on a third party's template firing a
particular hook does not have one.*

### 6. Unresolved slots are recorded, not dropped

*(DECIDED HERE.)*

Per [ADR-0012 §11e](ADR-0012.md), a send that throws never reaches
`woocommerce_email_sent`, so its slot is never finalized. The same is true of a
render that never sends at all.

**Stated precisely** *(corrected 2026-07-29, Prompt 5A)*:

> A throwing native send **can escape its caller**; PHP shutdown reconciliation
> records the inserted slot as `unresolved`.

The earlier wording implied this plugin contained the throw. It does not, and it
should not: `WC_Email::trigger()` is WooCommerce's, the throw comes from a third
party inside the mail transport, and reimplementing native sending to catch it
would be a far larger risk than the one it removed. What is **proven** is the
second half — the slot is reported `unresolved`, whoever catches the exception.

**At shutdown, every remaining slot that carried matched rules is written as a
detail row** — in the distinct state `unresolved` when the slot had reached the
send path, and in the distinct state `abandoned` when it had not. *(Amended
2026-07-30, Prompt 5B: this clause originally wrote `unresolved` for **every**
remaining slot and finalised the tombstone `unresolved` unconditionally. §6a
gives the reason that was wrong and the state test that separates the two. A slot
that reached the send path still behaves exactly as described below.)*

A slot carrying **no** matched rules is dropped silently: nothing of ours was
inserted, so there is nothing to report — the same noise-floor reasoning as
ADR-0005's `no_targeting_match`.

**Why record rather than drop.** The content **was rendered into the message**.
Whether the message left the building is unknown. Dropping the slot leaves the
merchant with an email whose content this plugin supplied and whose delivery log
has no entry at all — a silent gap, which is precisely the failure the decision
log exists to prevent. `unresolved` says exactly the true thing: *we inserted
this, and we never learned the outcome*.

`unresolved` is added to `DeliveryDetailRepository::STATES` and to
`DeliveryRepository::FINAL_STATUSES`. Both are PHP-enforced varchar allowlists
and schema v1 is unreleased, so this is a constant change and **not** a
migration — the same reasoning ADR-0012 §2 applied to `skipped`.

### 6a. An abandoned render is not a delivery attempt

*(ADDED 2026-07-30, Prompt 5B. Settles the policy question §5d exposed.)*

§6 swept **every** remaining slot as `unresolved`, and §1a says `final_status`
follows the latest attempt. Those two rules together produce a false statement:

> A merchant's completed-order email is sent successfully — attempt 1, `sent`. A
> third party later calls `get_content()` on the same email for the same order and
> throws the render away, as analytics, preview and PDF plugins routinely do. That
> render's slot is swept as a **later** `unresolved` attempt, and the tombstone —
> **the row the merchant actually looks at** — now reports a message that reached
> the customer as being of unknown fate.

**Decision: a render that never reached the send path is not a delivery attempt.**
It is recorded **distinctly**, as an *abandoned render*, and it never downgrades a
tombstone whose latest genuine send attempt succeeded. The merchant sees the truth
in both places: the attempt row shows the abandoned render happened, and the
aggregate keeps the outcome of the last real delivery.

**The dividing line is the slot state, so nothing has to guess it:**

| Slot state at the sweep | Meaning | Recorded as |
|---|---|---|
| `reserved`, `in_flight` | a send **began**; no outcome was ever reported | `unresolved` |
| `awaiting_send`, **promoted** | the render was offered to a send and none took it | `abandoned` |
| `awaiting_send`, **never promoted** | the render never reached a terminal position, so it was never offered — its message may still have gone out | `unresolved` |
| `rendering` | the render never even completed | `abandoned` |

*(The promotion column was added 2026-07-30, Prompt 5C, with §5e. Without it, a
render under a custom template that fires no terminal position would be labelled
`abandoned` — asserting that no send happened, when in truth we were never in a
position to know.)*

`reserved` and `in_flight` are reachable only through `woocommerce_mail_content`,
which is the first statement inside `WC_Email::send()`. A slot in either state
therefore *did* reach the send path — and its message may well have gone out,
which is exactly what `unresolved` means (§6, ADR-0012 §11e). A slot still
`awaiting_send` never got there.

**How the status is protected, and it is not a read-then-write.** The write path
passes `defer_to_genuine_attempt` to `DeliveryDetailRepository::record_attempt()`,
which checks for an existing `sent` / `failed` / `unresolved` attempt row **inside
the same transaction that allocates the attempt number and holds the parent row
lock** (ADR-0009). Checking outside it would be a third race. When such an attempt
exists the tombstone keeps its status; when none does — an identity whose only
event has ever been an abandoned render — the tombstone is finalised `abandoned`,
because `claimed` would say nothing and any delivery status would say something
untrue.

**Why not simply drop the abandoned slot.** Content **was** rendered. The rule
matched, the block was produced, and a merchant asking "did this rule do anything
for this order" deserves a truthful answer. Dropping it re-creates the silent gap
§6 exists to remove; recording it as a delivery re-creates the false statement
above. A distinct state is the only answer that is true in both directions.

**The alternative was considered and rejected.** Keeping the literal
latest-attempt rule is defensible in isolation — it is simpler, and it has one
consistent sentence behind it. It was rejected because the resulting statement is
not merely imprecise but *wrong in the direction that matters*: it reports a
successful delivery as unresolved, on the strength of an event that had nothing to
do with delivery and that a **third party** caused. A log that can be made to lie
about a delivery by an unrelated plugin's render is not a log a merchant can use.

`abandoned` joins `DeliveryDetailRepository::STATES` and
`DeliveryRepository::FINAL_STATUSES` under the same reasoning as `unresolved`
above: PHP-enforced varchar allowlists, schema v1 unreleased, constant change and
not a migration.

### 6b. Attempt typing follows genuine delivery history, never claim suppression

*(ADDED 2026-07-30, Prompt 5C. §6a was applied to `final_status` and not to
`type`; this finishes it.)*

An abandoned render **claims the identity and creates the tombstone** (§1 — the
claim is inverted, so it happens at recording time). The attempt `type` was derived
from the claim result, so:

```
third party renders, never sends   -> attempt 1  auto/abandoned      (claim CLAIMED)
WooCommerce performs the FIRST send -> claim SUPPRESSED
                                    -> attempt 2  resend/sent
```

The merchant's **first genuine delivery** was recorded as a *resend* of a message
that had never gone out — which contradicts §6a's own rule in the place a merchant
is most likely to read it.

**The rule.** `auto` versus `resend` is derived from **prior genuine attempts**:
no earlier `sent` / `failed` / `unresolved` row on this tombstone → `auto`; one or
more → `resend`. It is evaluated inside the transaction that already holds the
parent row lock and already computes that fact for §6a (ADR-0009), so it is neither
a second query nor a second race.

Abandoned rows keep their sequential attempt numbers and stay fully visible — they
are simply not what decides whether a later delivery is a repeat.

**The two columns answer different questions**, which is what makes
`resend/abandoned` a truthful pair rather than a contradiction:

| | Question | Example |
|---|---|---|
| `type` | has this identity delivered before? | `resend` — attempt 2 already sent |
| `state` | what happened to THIS attempt? | `abandoned` — this render was thrown away |

**The stored `reason` no longer says "re-inserted".** It was chosen from the same
wrong source, so it offered a second, weaker answer to the question `type` now
answers correctly. Whether an attempt is a repeat is recorded in exactly one place.

### 6c. Attempt numbers are PERSISTENCE order, not occurrence order

*(ADDED 2026-07-31, Prompt 5D. No code change — this is a property of §6/§6a that
support tooling and the future admin UI must not be built against wrongly.)*

Abandoned renders are recorded at the **shutdown sweep** (§6), and a real send is
recorded at **finalization**. So a render that happened *first* can be persisted
*after* a later real send, and the numbered history then reads:

```
attempt 1  auto/sent        (the later real send)
attempt 2  resend/abandoned (the EARLIER abandoned render)
```

**`final_status` is still correct** — §6a keeps an abandoned render from
downgrading a tombstone whose latest genuine attempt succeeded, and §6b types the
first genuine delivery `auto` whatever claimed the identity first. What is *not*
correct is reading the attempt sequence as a timeline: **the numbers record the
order rows were written, which for abandoned renders is the end of the request.**

Stated here plainly because the alternative is a support tool, or a merchant-facing
history, that silently asserts an ordering the data does not carry. Adding
`rendered_at` / `finalized_at` to the per-attempt snapshot would make the true
occurrence order recoverable and is a reasonable future improvement; it is recorded
in `docs/p2-backlog.md` and deliberately **not** built now, because the fix is a
schema-adjacent addition and this prompt is a correction pass.

### 7. Ordering and audience

Multiple insert rules matching one render inject in the **frozen ADR-0011
order**: `priority` ascending, then declared specificity descending, then rule
id. The ordering code is `Domain\Specificity` and `Domain\PreparedRule`,
unchanged — insert mode gets no ordering of its own.

`stop_processing` halts **within this phase only**, exactly as ADR-0012 §9
requires in the other direction: a separate rule's stop flag has never halted
insert rules and an insert rule's stop flag must never halt separate ones,
because they are different phases evaluated from different events.

Audience isolation is §4's validation, restated as a requirement because it is
the customer-visible one: a rule targeting `customer_processing_order` appears in
that email, for that order, for that audience — and **nowhere else**.

### 8. Mode constants and the phase filter

`DeliveryLogger::MODE` was hardcoded to `'separate'` and Prompt 4a's phase filter
(ADR-0012 §9) relies on it. Insert mode gets `MODE_INSERT = 'insert'` alongside
`MODE_SEPARATE = 'separate'`; `MODE` remains as an alias of `MODE_SEPARATE` so
every existing separate-mode call site keeps its meaning.

**The phase filter's guarantee is unchanged and still absolute**: a rule
belonging to another phase is left **entirely untouched** — no claim under a mode
it never had, no send, no row. Prompt 5 removes only its own condition:
`deliverable_in_this_phase()` continues to admit `separate` + `delay_seconds = 0`,
and the insert path independently admits `insert` + `delay_seconds = 0`. **A
delayed rule of either mode still belongs to Prompt 6 and is still filtered out
of both.**

### 8a. Phase filtering is a TEMPORARY boundary, and it covers every unimplemented column

*(ADDED 2026-07-30, Prompt 5C.)*

⚠ **`consolidation` was shipping deliverable.** Prompt 5B gave the column validated
storage, so a merchant could store `daily`, `weekly` or `per_order` — and **neither
phase filtered it**. Those rules were delivered immediately, once per trigger, which
is `none`'s behaviour under another name: the merchant asked for a digest and got an
email per order. A non-default rule carrying `stop_processing` could also halt
supported rules.

This is the **Prompt 4 defect repeating**: out-of-scope behaviour reachable through
**data** rather than through code, with "out of scope" silently meaning "handled by
whatever path exists". Adding validated storage for a column is what makes its
values reachable, so **storage and phase filtering must land together**.

**The rule, and it is now an enumeration rather than a habit.**
`Orchestrator::UNIMPLEMENTED_BEHAVIOUR_DEFAULTS` names every rule column whose
behaviour no phase implements, with the only value that column may hold to be
deliverable:

| Column | Deliverable value | Owner |
|---|---|---|
| `delay_seconds` | `0` | Prompt 6 — ADR-0007 scheduling |
| `consolidation` | `none` | a later prompt — ADR-0005 consolidation |

Both phases apply it, from that one constant: separate mode through
`deliverable_in_this_phase()`, insert mode inside the indexed repository fetch. A
rule holding anything else is left **entirely** untouched — **no claim, no send, no
record, and no halt**, because the filtering happens **before evaluation** and a
filter applied afterwards could not undo a halt that had already changed every later
decision.

**A future column carrying unimplemented behaviour is added to that constant**, and
both phases inherit the filtering. Growing the list one incident at a time is
exactly what let `consolidation` ship deliverable.

## Consequences

- The delivery log answers *"what did this plugin put inside order #123's
  processing email, and did it go?"* for every render, including the ones that
  never sent.
- Preview safety is **structural**: no slot, no record. It cannot be defeated by
  a conditional being evaluated in the wrong order, and it survives WooCommerce
  leaking its own preview signal.
- Because the five positions read one pre-computed list, adding a sixth position
  later costs no additional evaluation and no additional query.
- Because insert records are written at finalization, a merchant's deliberate
  resend is recorded truthfully as a second occurrence rather than as a
  suppressed duplicate.
- Because `native_email_id` is the only trigger source for insert rules, there is
  no second place for the question "which email does this belong to" to be
  answered differently.
- The delivery log distinguishes *"it went"*, *"WooCommerce said it did not go"*
  and *"nobody ever said"* — three different facts, three different states, and
  never the first standing in for the other two.
- Because every attempt row carries its own revision and outcome, "which body
  actually went out on the resend" is answerable from the history rather than
  inferred from the aggregate.
- Because the send's slot is fixed at the top of `WC_Email::send()`, a third
  party rendering from inside the send window can no longer change which render
  the send is attributed to — whatever it renders, and however many times.
- Because the handoff is a stack rather than a scalar, a third party that *sends*
  from inside another send's argument evaluation gets its own token, its own
  reservation and its own record — and neither message can finalize the other's
  slot however deeply the two nest (§5g).
- Because a finalized token is purged token-exactly, the open-token ledgers are
  bounded by the number of renders **in flight**, not by the number of renders a
  request has performed, whatever footer hook any template fires (§5h).
- The front-end guarantee is a property of hook *class*, not of runtime checks
  scattered through five callbacks: the one shared hook no-ops without a frame,
  and no frame exists outside an email render.

## Flagged WooCommerce behaviour

Recorded here and in `docs/p2-backlog.md`; **re-check on version bumps.**

- **⚠ `EmailPreview::render_preview_email()` has no `try`/`finally`** (WC 10.9.4),
  so an interrupted preview leaks `woocommerce_is_email_preview = true` for the
  rest of the request. Detection demotes the core signal to the render-scoped
  marker whenever reconciliation proves the leak, and promotes it again when the
  signal reads healthy.
- **⚠ `$email->object` is NOT restored after a nested render** (WC 10.9.4). Both
  `woocommerce_email_sent` events of a nested pair report the **inner** order.
  Every order used by this phase comes from the slot recorded at push.
- **⚠ Plain-text email templates never fire `woocommerce_email_footer`**, which
  is why the render-complete signal is `woocommerce_email_order_details`
  priority 15 and the footer is only an HTML backstop.
- **⚠ The two POS receipt templates fire `woocommerce_pos_email_footer`, not
  `woocommerce_email_footer`** (WC 10.9.4,
  `templates/emails/customer-pos-completed-order.php:122` and
  `customer-pos-refunded-order.php:133`; the hook is also added and removed around
  the render by the email classes themselves,
  `class-wc-email-customer-pos-completed-order.php:126`). Prompt 5C recorded these
  templates as firing "no footer at all", which was true only of the hook this
  plugin was listening to. Both footer hooks are now registered — and §5h removes
  the dependence on enumerating them correctly.
- **`woocommerce_order_item_meta_end` is called with three arguments by stale
  template overrides** still in the wild, so the fourth parameter is optional
  with a default.
- **⚠ `woocommerce_email_order_meta` and `woocommerce_email_customer_details`
  fire AFTER `woocommerce_email_order_details` returns**, so two of the five
  injection positions are outside the ADR-0003 frame window entirely — see §4a.
  Found while implementing this prompt. The frame keeps its ADR-0003 lifetime
  and a separate render record serves the email-only positions; the storefront
  guarantee, which depends on the frame, is unchanged.
- **⚠ `woocommerce_mail_content` carries no `$email` argument** (WC 10.9.4,
  `class-wc-email.php:1233` — `apply_filters( 'woocommerce_mail_content', … )`
  with one parameter), even though it is the first thing `WC_Email::send()` does
  and its sibling filters two lines later both receive `$this`. The send scope is
  therefore taken from `woocommerce_email_headers` /
  `woocommerce_email_attachments` instead — see §5a.
- **⚠ `WC_Email::get_content()` DELETES unrecognised HTML entities from
  plain-text bodies** (WC 10.9.4, `$plain_search` pattern `/&[^&\s;]+;/i` →
  `''`). Content inserted into a plain-text email must therefore be delivered
  already decoded — see §4b.
- **⚠ `wc_get_template_html()` leaves an output buffer open on an exception.**
  An interrupted render therefore leaks an `ob_start()` level as well as the
  preview signal above. This plugin cannot close a buffer it did not open, at a
  call site it does not own; it is cosmetic for delivery correctness and is
  already recorded in `docs/p2-backlog.md`.
