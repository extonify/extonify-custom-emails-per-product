# ADR-0005: Bounded decision logging

Status: **Accepted** — 2026-07-25
Amended 2026-07-25 (Prompt 1a) — retention scoped explicitly to the purgeable
detail store (ADR-0004a); finalization hardened with a WC_Order type-guard, a
per-request generation counter against spl_object_id reuse, and positive
preview detection.
Amended 2026-07-25 (Prompt 1b) — WITHDREW the generation counter (unsafe:
mutable global read at finalization ≠ value written at registration) and
replaced it with a render-token pending-render ledger + LIFO finalization; made
preview state object-scoped and lifecycle-cleared with a shutdown fallback.
Amended 2026-07-25 (Prompt 1c) — replaced the lazy-on-match ledger with a render-
SLOT state machine (rendering → awaiting_send → resolved; a slot per applicable
render, matched or not) and made preview state render-scoped (marker consumed at
push into the render frame). HARD RULE restated in Decision: order is never read
from `$email->object` at finalization.
Amended 2026-07-25 (Prompt 1d) — a preview render creates a context frame but
**no delivery slot at all**, so preview tokens never enter the ledger, never
reach `awaiting_send` and never appear in `unresolved`; finalization resolves the
**exact token bound at `woocommerce_mail_callback_params`**, replacing
most-recent-`awaiting_send` selection.
Amended 2026-07-30 (Prompt 5B) — two Decision clauses below are marked where
[ADR-0013](ADR-0013.md) supersedes them for production code: **§5a/§5d** replace
the bind-time slot selection with a token carried from the render, and **§6a**
splits the shutdown sweep into `unresolved` (a send began) and `abandoned` (none
did). The POC state machine itself is unchanged and stays as frozen history.

## Context

Support and store owners need to answer "why did (or didn't) this customer get
this email?" without the log itself becoming an unbounded, privacy-hostile
data sink. A log that records every rule that *failed to match a product* on
every order would grow without bound and leak order contents; a log that
records too little is useless for support. We need a **bounded** decision log:
enough to explain every *actioned* decision, nothing for the vast majority of
non-matches, with retention and privacy tooling built in.

Insert-mode finalization also needs care: during a native email render we do
not yet know whether the mail actually went out — only `woocommerce_email_sent`
tells us the boolean result, and it fires once per email with `($return, $id,
$email)` but **no order id**.

## Decision

### Always log (actioned decisions)

`claimed`, `scheduled`, `sent`, `failed`, `cancelled`,
`duplicate-suppressed` (with an **atomic `suppressed_count` increment** on
retry storms rather than a new row per duplicate), `empty/invalid recipient
after placeholder resolution`, `excluded-after-product-match`,
`priority/stop-flag block`, `disabled-before-scheduled-execution`,
`invalidated-by-order-state`, `manual send`, `manual resend`, and `test sends`
(flagged `test`, and **excluded from idempotency** so testing never consumes a
real delivery identity).

### Never log (the noise floor)

Rules that **fail initial product targeting are never logged**, except as
**debug-flagged rows when debug mode is on**. This is what keeps the log
bounded: the common case (a rule simply does not apply to this order) produces
no row in normal operation.

### Retention

- Retention applies to the **purgeable detail store only**
  ([ADR-0004](ADR-0004.md) §Durable identity vs purgeable detail). The durable
  tombstone is **never** purged; purging it would silently re-arm old orders.
- **90 days** normal, **180 days** failed, **14 days** debug — of detail rows.
- Purged by a **daily Action Scheduler recurring action.**
- A **keep-indefinitely** option is available for stores that need it.
- Detail rows are covered by the **privacy exporter/eraser** (personal data in
  rows is exportable and erasable); erasure nulls personal fields and leaves the
  tombstone intact.

### Insert-mode finalization — render-SLOT state machine

Insert-mode records are **finalized only via `woocommerce_email_sent`**. That
hook carries no order id and fires **after** the render, so finalization uses a
**render slot** with explicit state, created for **every applicable native-email
render** — including one that matches no rule. A slot is **never** created lazily
on match: creating slots only on match lets an unmatched inner send pop a matched
outer render's entry and finalize the outer against the wrong result.

Each slot is:

```
slot = [ 'token' => render token, 'order_id' => order id recorded at push,
         'spl' => spl_object_id($email), 'rules' => set (may stay empty),
         'state' => 'rendering' | 'awaiting_send' | 'in_flight' ]
```

A slot carries **no `is_preview` field**, because a preview render never creates
one (see *Preview renders create no delivery state*, below).

**State machine:**

1. **push (render begins)** → slot created `state = 'rendering'` — **only for a
   non-preview render**.
2. **matched rule registers** → `rules[rule_id] = true` on the slot bearing the
   **current render token** (never "the last slot").
3. **render completes** → `state = 'awaiting_send'`. (This transition is taken at
   the order-details close, which fires for **both** HTML and plain templates —
   plain templates do **not** fire `woocommerce_email_footer`.)
4. **`woocommerce_mail_callback_params`** → the **send is bound**: ~~the
   most-recent `awaiting_send` slot for that email object~~ **the token RESERVED
   for this send** becomes `in_flight` and is pushed onto the object's **bind
   stack**. The filter returns its params **unmodified**.

   > ⚠ **SUPERSEDED by [ADR-0013](ADR-0013.md) §5a and §5d.** "Most-recent
   > `awaiting_send`" is prohibited in production: a render that never sends can
   > complete *after* a send has begun, and would then be the newest slot when the
   > real send reached the mail callback. Prompt 5A replaced it with a reservation
   > taken at `woocommerce_mail_content`; Prompt 5B replaced the reservation's
   > remaining selection with an **exact token carried from the render**. This
   > clause is kept as written because the state machine it belongs to is frozen
   > POC history — the production rule is ADR-0013's.
5. **`woocommerce_email_sent`** → **type-guard** `$email->object instanceof
   WC_Order`, then pop the object's bind stack and finalize **exactly that token**;
   finalize its rules against **its own recorded `order_id`**; remove the slot.
   **If its rule set is empty, finalize nothing but still consume the slot.**
6. **no binding** (or the bound slot is not `in_flight`) → **bail, finalize
   nothing, never guess.**
7. **shutdown** → any slot still present is recorded **`unresolved`**, never
   finalized as sent.

   > ⚠ **REFINED by [ADR-0013](ADR-0013.md) §6a.** In production the sweep splits
   > by slot state: `reserved` / `in_flight` (a send began, no outcome reported)
   > is `unresolved`; `rendering` / `awaiting_send` (no send ever began) is
   > `abandoned`, which is **not a delivery attempt** and never downgrades a
   > tombstone whose latest real attempt succeeded. "Never finalized as sent"
   > holds unchanged for both.

**Finalization binds at the mail callback, not by recency.** `woocommerce_email_sent`
fires *after* the mail callback, so between a render and its send result any number
of further renders of the same object can complete. Selecting the *most recent*
`awaiting_send` slot at that point attributes the real send to the wrong render.
`woocommerce_mail_callback_params` fires **inside `WC_Email::send()`**, receives the
email object, and runs **before** the mail callback — it is the last point that is
still unambiguously part of *this* send, and therefore the correlation point. A
render that never reaches the mail callback stays `awaiting_send` forever, is
reported `unresolved` at shutdown, and **can never be consumed by another send**.

**Rejected: embedding a render token in the email body.** Round-tripping a token
through the message and stripping it before delivery was rejected outright. It
mutates outgoing customer email, needs separate stripping paths for HTML and plain
text, and fails *visibly, in the customer's inbox* if stripping ever misses.
Binding at the mail callback achieves exact correlation while leaving the message
bytes untouched.

**State gating is required, not optional.** At the instant an inner send fires,
the outer slot is still `rendering` and is therefore **structurally ineligible**,
not merely lower in a stack. This also stops a render that never sends (an email
customizer calling `get_content()` directly) from consuming a later send's slot —
that render's slot is orphaned and reported `unresolved` at shutdown.

**HARD RULE — the order is NEVER read from `$email->object` at finalization.**
Verified against WC 10.9.4: when the same singleton email object renders
**nested** (an injection triggers another email of the same type mid-render),
WooCommerce **does not restore `$email->object`** afterward — empirically
**both** `woocommerce_email_sent` events then report the **inner** order. The
order is therefore always taken from the slot's `order_id` recorded at push. (The
type-guard still reads `$email->object` only to confirm the email carries *some*
`WC_Order`.)

**Why not a generation counter (withdrawn from Prompt 1a):** keying on a
monotonically increasing per-request counter is unsafe — both registration and
finalization read the *same mutable global*, so a nested render increments it
between the two and the outer render can never be finalized. The value read at
finalization would not be the value written at registration whenever renders
interleave. The render token is bound to its render and cannot drift.

### Preview renders create no delivery state

A preview render creates a **context frame only** — injection callbacks still need
a context to read so preview content renders correctly — and **no delivery slot**.
Recording `is_preview` on a slot (Prompt 1c) was not enough: the slot still
transitioned to `awaiting_send`, was never consumed (a preview never fires
`woocommerce_email_sent`), and was filed as `unresolved` at shutdown. That directly
contradicted this ADR's own promise that preview writes no record.

- **No slot for a preview.** Preview tokens therefore cannot enter the ledger,
  cannot reach `awaiting_send`, and cannot appear in `unresolved` — not as a matter
  of correct bookkeeping, but structurally.
- Registration reads `is_preview` from the **current render frame**, never from
  object-level state. On a preview there is no slot to register against, so
  registration is a no-op by construction.
- The **absence of a send result is NOT** acceptable evidence that a path was a
  preview — detection is positive only.

**Detection: prefer WooCommerce's own render-time signal.** Where the runtime
exposes `woocommerce_is_email_preview` (WooCommerce ≥ 9.6), that filter is the
primary signal: it is true for the whole preview render and false for a real send.
The `woocommerce_prepare_email_for_preview` **next-render marker** — set at
`set_email_type()`, consumed into the render frame at push, object-level marker
cleared immediately — remains as the fallback for runtimes without the core signal.

**The core signal must not be trusted blindly.** Verified against WC 10.9.4:
`EmailPreview::render_preview_email()` calls `clean_up_filters()` **without a
`try`/`finally`**, so an exception thrown mid-render leaves
`woocommerce_is_email_preview` attached and returning `true` **for the rest of the
request** — and the next *real* send then reports itself as a preview, suppressing a
genuine delivery record. Detection therefore treats the core signal as **leaked**
whenever reconciliation removes a stale preview frame while the signal still reads
true; the render-scoped marker becomes authoritative until the signal is observed
healthy (false) again. This is what makes a real send after an interrupted preview
register and finalize normally.

### Guaranteed preview frame teardown

A preview render that is interrupted between push and pop must not leave a context
frame, an open order-details token, or an open footer token behind — a surviving
frame makes `in_email()` report an active email context while nothing is rendering,
which is precisely the invariant [ADR-0003](ADR-0003.md) exists to guarantee.

Teardown is **reconciliation at the start of every push, plus the shutdown
fallback**: a preview frame that still exists when the next render begins is proof
that a preview was interrupted, because a completed preview always removes its own
frame at the order-details close. Reconciliation drops such frames together with
their open tokens. Delivery-side residue is **zero at the instant of interruption**
(there was never a slot); frame-side residue is cleared at the next push or at
shutdown, whichever comes first, and is never observable by another render.

## Consequences

- The log explains every actioned decision and every suppression, but stays
  bounded because the dominant "rule didn't apply" case is silent in normal
  mode.
- Retry storms increment one row's `suppressed_count` atomically instead of
  inserting thousands of duplicate-suppressed rows.
- Retention is automatic and tiered; failures are kept longer for
  investigation; debug rows are ephemeral; stores that must keep everything can
  opt in.
- Privacy requests are honoured because rows participate in the exporter/eraser.
- Insert-mode success is recorded truthfully (only after the send result is
  known) and the singleton email object cannot cause one order's record to be
  finalized against another order.
- Preview and customizer are safe to use freely — they never consume a delivery
  identity ([ADR-0004](ADR-0004.md)) and never write a log row, because preview
  is detected positively and suppresses registry creation entirely.
- A non-order email (customer/product notifications carrying non-`WC_Order`
  objects) can never be mis-finalized, and interleaved/nested renders can never
  cross-finalize, because of the type-guard and the render-token LIFO ledger
  (which binds each finalization to the render that created it).
- An interrupted preview cannot silently disable real sends for the rest of the
  request: the marker is render-scoped and consumed by the next render, and a
  leaked core preview signal is detected and demoted rather than believed.
- An unmatched inner send, a failed inner send, and a render that never sends can
  none of them corrupt another render's delivery record — each render owns a slot
  whose state and recorded order are independent of every other render.
- A second render of the same email object completing between the real render and
  `woocommerce_email_sent` can no longer steal the attribution: the send is bound
  before the mail callback runs and finalization resolves that exact token.

### Accepted residual risks (Prompt 1d — deliberately not fixed)

- **A third party rendering the same email object from *inside* the mail callback**
  (`pre_wp_mail`, `phpmailer_init`, or a `woocommerce_mail_callback` replacement)
  creates a newer `awaiting_send` slot *after* binding. Binding at
  `woocommerce_mail_callback_params` narrows the exposure to that case alone: the
  real send still finalizes against its own bound token and its own recorded order,
  and the intruding render creates **no** delivery record — but it does leave an
  extra slot that is reported `unresolved` at shutdown. Proven, not merely argued,
  by POC-C's exact-send-correlation test. A *nested full send* from that same
  position is handled by the per-object bind **stack** but is not covered by a test.
- **Frame-side residue between an interrupted preview and the next push.** PHP
  offers no unwind hook at a call site we do not own, and WooCommerce's preview
  renderer has no `finally`, so instantaneous teardown at the moment of interruption
  is not achievable. The window is bounded by the next push or shutdown, and no
  delivery state exists in it.
- **Reconciliation is global to preview frames.** A real send triggered by third-
  party code from *within* a live preview render would have the enclosing preview
  frame reconciled early. WooCommerce never nests renders this way.

Each of these requires third-party code to actively call WooCommerce or plugin
internals mid-send; all are recorded in `docs/p2-backlog.md`.

## Amendment history

- **2026-07-25 (Prompt 1a):**
  - **(a) Retention scope.** Stated explicitly that retention (and privacy
    erasure) act on the **purgeable detail store only**, cross-referencing
    [ADR-0004](ADR-0004.md); the durable tombstone is never purged.
  - **(b) Finalization safety.** The `woocommerce_email_sent` handler now
    **type-guards** `$email->object` (bail unless `WC_Order`), the registry key
    gained a **per-request generation counter** to defeat `spl_object_id` reuse
    after GC, and an entry is never finalized against a mismatched order id.
    **Preview detection is positive** — a flag set on
    `woocommerce_prepare_email_for_preview` suppresses all registry creation;
    absence of a send result is not treated as evidence of a preview.
- **2026-07-25 (Prompt 1b):**
  - **Render-token ledger replaces the generation counter (BLOCKER fix).** The
    generation counter is withdrawn as unsafe — registration and finalization
    both read the same mutable global, so a nested render decouples them and the
    outer render can never be finalized. Finalization is now render-bound: a
    token minted at context push, carried in a pending-render ledger
    `pending[spl][oid][] = {token, rules}`, resolved **LIFO** on
    `woocommerce_email_sent`, **bailing** if nothing matches, with still-pending
    entries recorded **unresolved** at shutdown (never sent).
  - **Object-scoped preview (BLOCKER fix).** Preview state is keyed by
    `spl_object_id($email)`, cleared by that email's own render lifecycle (footer)
    with a shutdown fallback, and **never** cleared by external code — so a stuck
    flag on one object cannot suppress a different email's registration.
- **2026-07-25 (Prompt 1c):**
  - **Render-SLOT state machine (BLOCKER 1 fix).** The lazy-on-match ledger let an
    unmatched inner send pop a matched outer render's entry. A slot is now created
    for **every applicable render** (matched or not) and gated by state
    (`rendering` → `awaiting_send` → resolved). Finalization consumes the most-
    recent `awaiting_send` slot for the email object and finalizes against its own
    recorded order; an empty rule set finalizes nothing but still consumes the
    slot; a `rendering` slot is structurally ineligible, so an inner send (or a
    render that never sends) cannot consume an outer/ later slot. Proven by POC-C
    unmatched-nested, inner-fails-outer-succeeds, and render-without-send tests.
  - **Render-scoped preview (BLOCKER 2 fix).** The prepare filter now marks the
    **next render**; the marker is consumed into the render frame at push and the
    object-level marker cleared immediately, so a same-object interrupted preview
    cannot suppress the next real send (proven with no manual clearing).
  - The order-details close (not the footer) is the render-complete signal, since
    plain-text templates do not fire `woocommerce_email_footer`.
- **2026-07-25 (Prompt 1d):**
  - **Preview slot suppression (BLOCKER 1 fix).** Recording `is_preview` on a slot
    was not enough — the slot still reached `awaiting_send`, was never consumed, and
    was filed `unresolved` at shutdown, contradicting this ADR. A preview render now
    creates a **context frame only and no slot at all**, so preview tokens cannot
    enter the ledger by construction. Detection **prefers WooCommerce's own
    `woocommerce_is_email_preview`** signal, with the `prepare_email_for_preview`
    next-render marker retained as the fallback — and as the authority whenever the
    core signal is detected **leaked** (WC 10.9.4 `render_preview_email()` omits a
    `finally` around `clean_up_filters()`, so an interrupted preview leaves preview
    mode on for the rest of the request). **Guaranteed teardown** of an interrupted
    preview's frame and open tokens by reconciliation at the start of every push
    plus the shutdown fallback.
  - **Exact send correlation (BLOCKER 2 fix).** Most-recent-`awaiting_send`
    selection at `woocommerce_email_sent` mis-attributed a real send whenever a
    second render of the same object completed in between. The send is now **bound
    at `woocommerce_mail_callback_params`** (slot → `in_flight`, token pushed onto a
    per-object bind stack, params returned unmodified) and finalization resolves
    **exactly that token**; no binding means finalize nothing. Embedding a render
    token in the email body and stripping it before delivery was **explicitly
    rejected** — it mutates outgoing customer mail.
  - Consequences gained an explicit **Accepted residual risks** section.
